# 项目文件放置规范

本文档用于规定 NeuroGRA 项目的文件放置方式。以后新增文件时，先判断文件属于哪一类，再放入对应目录，避免项目再次变乱。

## 顶层目录

```text
NeuroGRA/
├─ code/
├─ data/
├─ docs/
├─ output/
├─ paper/
├─ study/
├─ README.md
├─ pyproject.toml
├─ .gitignore
└─ .env.example
```

## code

`code/` 只放项目代码。

适合放入：

- Python 源码
- 项目脚本
- 测试代码
- 和系统运行直接相关的代码文件

不放入：

- 论文 PDF
- 课题方案文档
- 个人学习笔记
- 程序运行结果
- 临时输出文件

## data

`data/` 只放项目数据。

适合放入：

- 原始数据
- 清洗后的数据
- 示例病例数据
- 知识库数据
- 图谱节点、边、索引等数据文件

不放入：

- Python 代码
- 论文正文草稿
- 运行日志
- AI 生成的报告正文

如果数据较大，默认不要提交到 git。必要时只提交小型示例数据或数据说明。

## docs

`docs/` 放项目方案、设计文档和说明文档。

适合放入：

- 课题总体方案
- 系统架构设计
- 数据结构设计
- 需求说明
- 接口说明
- 项目规范文档

`docs/assets/` 专门放 `docs` 文档中使用的图片。

注意：

- 文档中的图片统一放 `docs/assets/`。
- 论文 PDF 不放 `docs/`，放 `paper/`。

## output

`output/` 放程序运行产生的本地输出。

适合放入：

- 调试日志
- 中间运行结果
- 临时图表
- 程序导出的表格
- 本地实验输出

不放入：

- 项目运行时 AI 输出的正文内容
- AI 生成的诊断报告正文
- AI 生成的论文精读 Markdown
- 需要长期维护的方案文档

说明：

项目运行时 AI 生成的内容要根据用途归类：

- 属于方案或设计，放 `docs/`。
- 属于论文精读笔记，放 `paper/精读总结/`。
- 属于正式论文材料，放 `paper/` 或 `docs/` 中合适位置。
- 只是临时调试文本，确认无价值后删除，不长期堆在 `output/`。

## paper

`paper/` 放论文相关材料。

适合放入：

- 论文 PDF
- 指南 PDF
- 文献阅读笔记
- 引用资料
- 和论文阅读直接相关的文件

`paper/精读总结/` 用于放置通过 skill `paper-note-standard` 生成的 Markdown 文档。

`paper/精读总结/assets/` 用于放置这些精读总结 Markdown 使用的图片。

注意：

- `paper/精读总结/` 只放整理后的精读笔记。
- 原始 PDF 仍放在 `paper/` 下。
- 不把项目代码放进 `paper/`。

## study

`study/` 是个人学习文件夹，和本项目无关。

适合放入：

- 数据库学习笔记
- 算法练习
- LeetCode 代码
- 面试八股文
- 其他个人学习材料

要求：

- 项目代码不要依赖 `study/`。
- 论文和系统文档不要引用 `study/` 作为正式材料。
- `study/` 中的内容不参与项目运行。

## 根目录文件

根目录只放少量项目级文件。

`README.md`：项目说明、目录结构、快速开始。

`pyproject.toml`：Python 项目配置、依赖、测试和工具配置。

`.gitignore`：规定哪些文件不提交。

`.env.example`：环境变量模板，不包含真实密钥。

不要在根目录随手放：

- 临时代码
- 临时输出
- PDF
- Word 文档
- 图片
- 学习笔记

## 新增文件判断规则

新增文件前，按下面顺序判断：

1. 是项目代码吗？放 `code/`。
2. 是项目数据吗？放 `data/`。
3. 是方案、设计、说明吗？放 `docs/`。
4. 是 `docs` 使用的图片吗？放 `docs/assets/`。
5. 是程序运行产生的普通输出吗？放 `output/`。
6. 是论文、指南、文献笔记吗？放 `paper/`。
7. 是 paper-note-standard 生成的精读总结吗？放 `paper/精读总结/`。
8. 是精读总结使用的图片吗？放 `paper/精读总结/assert/`。
9. 是个人学习材料吗？放 `study/`。

如果仍然判断不出来，先不要随手放到根目录，优先在 `docs/` 中记录用途，或单独确认位置。

## 命名规范

建议：

- 文件名尽量表达内容，不使用 `新建文档1`、`最终版2`、`temp`。
- 日期使用 `YYYY-MM-DD`。
- 同一类文件命名风格保持一致。
- 中文文档可以使用中文名。
- 代码文件使用英文小写和下划线。

示例：

```text
docs/硕士课题总体方案_多智能体与图谱增强RAG辅助诊疗_2026-09-17.md
docs/assets/system_architecture_2026-09-17.png
paper/精读总结/ADAgent_论文精读.md
code/run_demo.py
```

## 清理原则

每次阶段性完成后，检查一次：

- 根目录是否出现了不该出现的文件。
- `output/` 中是否堆积了无用临时结果。
- `docs/assets/` 是否只放文档使用图片。
- `paper/精读总结/assert/` 是否只放精读总结使用图片。
- `study/` 是否被项目代码或文档错误依赖。

如果文件已经不再使用，优先删除；如果仍有参考价值，移动到对应目录并改成清楚的文件名。
