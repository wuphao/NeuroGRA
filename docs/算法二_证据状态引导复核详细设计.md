# 算法二：证据状态引导复核详细设计

返回：[研究现状、目标与系统架构](<D:/Python Project/NeuroGRA/docs/NeuroGRA_RAG与知识图谱架构及关键算法设计_2026-09-21.md>)  
前置算法：[算法一：鉴别证据检索详细设计](<D:/Python Project/NeuroGRA/docs/算法一_鉴别证据检索详细设计.md>)

本文只讨论第二项关键算法：在第一轮检索后，如何识别未决证据、决定复核动作，并控制最终结论。公式使用纯文本记法，不依赖 LaTeX；当前是设计方案，尚无效果验证。

## 1. 算法要解决的问题

证据不足有不同原因：医学知识没找到、条款前提没解释清楚、患者资料没记录、可比证据冲突，或者引用根本不支持结论。这些情况不能统一通过“再检索一次”处理。

本算法的目标是建立一条明确链路：**什么证据状态触发了什么请求，请求执行后解决了什么问题，哪些结论因此需要保留、改写或撤回。**

知识检索只能补知识。患者检查未做或资料不存在时，检索更多文献不能把对应患者事实补成已知。

## 2. 输入、输出与总体流程

### 2.1 输入输出

| 类型 | 内容 |
|---|---|
| 输入：患者观测 | 已记录事实、极性、时间、方法、出处及缺失状态 |
| 输入：算法一结果 | 完整证据包、适用状态、允许用途、未覆盖需求和知识版本 |
| 输入：候选结论 | 分层结论草案，以及各结论依赖的患者观测和条款 ID |
| 输入：执行约束 | 现有资料访问范围、最大请求数、剩余 token 与调用预算 |
| 输出 | 更新后的证据状态、请求执行轨迹、仍未解决问题、每条结论允许的表述 |

```text
第一轮证据 + 患者观测 + 候选结论
                    |
                    v
建立证据状态，判断缺口与冲突类型
                    |
                    v
生成、合并并排序具体复核请求
                    |
          至多一个复核批次
                    |
     +--------------+---------------+
     |              |               |
  重检索知识    读取已有患者资料    无资料：保留未决
     |              |               |
     +--------------+---------------+
                    |
                    v
根据真实返回更新状态，检查成功判据
                    |
                    v
限制或改写受影响结论，交给报告模块
```

### 2.2 全程保留的两个区分

**条件状态与证据用途分开。** 条款前提为 T（满足）、F（不满足）、U（未知）；冲突另外标记。U/F 条款可以用于解释限制，但不能被当作已经成立的正向支持。

**知识缺口与患者事实缺口分开。** 前者可以通过检索填补；后者只可通过已有真实记录补取，否则保持缺失。详细字段与条件求值规则见算法一第 2 节。

## 3. 详细算法步骤

### 3.1 EvidenceState 的结构

对每个候选结论维护：

```text
E_t = (P_t, N_t, K_t, M_t, C_t, V_t, U_t)
```

其中 `P_t` 为可用支持证据；`N_t` 为削弱/限制证据；`K_t` 为知识条款缺口；`M_t` 为患者资料缺口；`C_t` 为可比证据冲突；`V_t` 为引用/层级/版本问题；`U_t` 为未覆盖需求。

这些是集合或结构化记录，不是未经校准的概率向量。条款对候选的方向可以为支持、削弱、限制、不确定；“没有支持”不等于“已有反证”。

### 3.2 步骤 1：先判断两条证据是否真的冲突

依次核对主体、字段、判断层级、采集时间、检测方法、单位、人群条件与命题方向。

- 同字段、同一可比条件下的相反事实，登记观测冲突。
- 条件不同的指南建议，先登记适用范围差异。
- 不同时间的结果，先登记时间变化，不自动互相抵消。
- 临床表型与生物学维度不同，先检查是否允许共存。
- 两个病因都有支持，不能仅因此登记逻辑矛盾；可能是并存，也可能不足以确定归属。

无法确认可比性时记录“待核对”，不自动消解冲突。两条证据语义相反也不意味着其中必有一条错误。

### 3.3 步骤 2：确定缺口类型及允许动作

| 状态类型 | 具体触发条件 | 允许动作 | 解决判据 |
|---|---|---|---|
| 知识缺口 | Need 没有完整条款覆盖 | 对指定候选对/需求重检索 | 新条款完整覆盖该需求 |
| 条件定义缺口 | 找到条款但其平台、人群或例外说明不全 | 定位同来源上下文及限制条款 | 条件语义完整且可定位 |
| 患者条件缺口 | 知识前提清楚，但患者对应字段未知 | 查已有真实资料；无资料则登记待补项 | 有原始患者记录支持；不能以文献替代 |
| 可比证据冲突 | 同层且可比的信息相互牵制 | 查原始记录、方法差异、例外及替代解释 | 有来源的解释消除冲突，或明确保留冲突 |
| 引用支持失败 | 引用存在，但不支持该具体断言 | 核对原文、缩小表述或撤回断言 | 新表述与原文支持范围一致 |
| 版本或层级不合 | 使用旧版本失效条款，或跨层推断 | 对照版本与层级，替换依据/改写结论 | 有效版本及正确层级得到确认 |

“保留冲突”是合法终止状态，但不计为冲突已解决。文献检索永远不能把 `not_measured` 自动改成患者结果。

### 3.4 步骤 3：生成可执行 ReviewRequest

每条请求包含：

| 字段 | 内容 |
|---|---|
| request_id / dedup_key | 唯一 ID；目标结论、缺口、动作、来源版本组合键 |
| trigger_ids | 哪条观测、条款或检查结果触发 |
| target_pair / claim_ids | 涉及哪个候选对、哪些结论 |
| gap_type / question | 缺口类型与一句可检索问题 |
| allowed_action | retrieve_knowledge / read_existing_record / verify_source / keep_unresolved |
| forbidden_inference | 例如“不允许把未检记录写成阴性” |
| success_condition | 哪个可检查的条件满足才算解决 |
| budget / status | 剩余调用限额、待执行/完成/未解决/预算停止 |

典型请求：“结论 C3 使用条款 K7，但 K7 要求检测方法 M；观测 O5 未提供方法。先读取 O5 的原始报告对应字段；若资料不存在，保留方法未知，并禁止 C3 使用 K7 作直接支持。”

这比“请重新检查诊断”多了可验证的目标、动作和终止条件。

### 3.5 步骤 4：排序请求与分配预算

首期采用固定的字典序，避免设计一个无法标定的“信息增益概率”：

1. 影响关键结论的患者事实错误、明确条件误用、来源不支持。
2. 影响关键结论的可比冲突与适用性未知。
3. 缺少候选间鉴别证据。
4. 一般背景补充。

同一级内，优先处理有可执行资料源、影响多个结论、预估成本较小的请求。没有患者资料可读取的请求立即变成待补项，不耗费循环搜索文献的预算。

复核批次最多处理开发阶段冻结的请求数，例如 3 条；共同指向同一来源或同一条件的请求合并执行。一次“复核”指一个有界批次，不是无限多次查询藏在一个 Agent 调用中。

### 3.6 步骤 5：让复核改变 算法一，而非只增加材料

复核请求至少改变下面一项：查询内容、目标需求优先级、允许证据用途、来源范围、受影响结论的状态。

对于知识重检索，在剩余预算内收集新候选，与原候选合并去重，**重新运行证据集合选择**；不能把新结果直接追加在旧上下文后，导致“3,000 tokens”实际变为 6,000。

已经识别的重大冲突两侧应形成同一个冲突包，或保留双方 ID 与可核查摘录，防止集合重选只留下有利一侧。如果预算不足以完整呈现，标记冲突未解决，并限制依赖该冲突的结论。

### 3.7 步骤 6：更新状态和停止

满足以下任一条件即停止：没有可执行请求、所有目标已解决、一个复核批次完成、累计预算耗尽、没有新增有效证据或新的可执行动作。

更新时每一项必须有变化依据：

```text
原状态：患者检测方法未知
动作：读取既有原始报告
返回：报告仍无方法字段
新状态：仍未知
结论变化：依赖该方法的判断保持条件性，不计为复核成功
```

重复得到同一文献或相同模型答案不算新增证据。不以 Agent 数量、循环次数或检索命中频率累加“置信度”。

## 4. 复核结果如何约束结论

结论检查是本算法的最后一步：复核只有真正改变证据状态或允许输出的内容，才形成完整闭环。

### 4.1 先形成结构化结论，再生成自然语言

每条结论绑定患者依据、知识条款、推断层级、未决前提和允许强度。检查器依次验证：

1. 患者依据是否存在、主体和时间是否一致。
2. 知识条款原文能否定位，版本是否允许使用。
3. 条件是否满足；冲突或未知是否阻止当前表述。
4. 条款方向和证据内容是否支持该结论，是否遗漏重要限制。
5. 是否从综合征跳到了病理、从“支持”跳到了“确诊”、从“未记录”跳到了“排除”。

形式上，对结论 `y` 定义五类检查结果 `g_1 ...  g_5 in {T,F,U}`。任一关键检查 F 则当前表述不允许输出；有关键 U 则只能条件性表达或保留未决；全部 T 也只允许达到原条款规定的强度，不能自动确诊。

### 4.2 报告状态

| 状态 | 报告应表达什么 |
|---|---|
| 有依据的倾向 | 哪些具体观测与适用条款支持哪个候选，仍有哪些限制 |
| 条件性结论 | 缺少哪些条件，满足后才能使用哪条知识 |
| 多候选/可能并存 | 各候选分别由什么支持；区分证据不足与共同贡献证据 |
| 仅可描述事实 | 目前可以确认的观察，不扩展为病因判断 |
| 证据不足 | 缺口和原因，现有资料不足以回答什么 |

疾病倾向不输出由检索分数换算的百分比。若以后需要概率，须有独立标签、明确预测头和校准实验。

### 4.3 双重追踪

每条结论必须同时支持：

```text
结论 → 患者观测或工具结果 → 病历/报告原始位置
结论 → 条款与条件 → 指南/论文原文位置与版本
```

只有指南引用，没有患者事实，不能证明患者满足该指南；只有患者事实，没有可适用知识，也不足以证明病因推断。追踪链用于复核依据，不等价于因果解释。

## 5. 完整执行示例

以下为抽象教学例，A/B 为候选病因，K1 为示意条款，不是真实医学规则或引用。

### 5.1 初始状态

患者观测 O2 记录一项检验结果，但没有检测方法；条款 K1 明确要求特定检测方法。算法一已找到完整 K1，因此**知识并不缺失，缺少的是患者的方法字段**。

草案 C1 却直接利用 O2 与 K1 给出确定判断。建立状态时，将 K1 对该病例的适用性记为 U，并将 C1 标为需要限制的结论。

### 5.2 生成请求

| 请求字段 | 本例内容 |
|---|---|
| 触发 | O2 的方法字段未知，C1 使用了要求该字段的 K1 |
| 缺口类型 | 患者条件缺口 |
| 目标 | 核对 O2 原始报告的检测方法 |
| 允许动作 | 读取已有报告 |
| 成功判据 | 原始患者资料中找到明确方法信息 |
| 未解决时的结论限制 | C1 不得把 K1 当作已适用的直接支持 |

### 5.3 执行后的三个分支

| 实际返回 | 状态变化 | 结论处理 |
|---|---|---|
| 找到方法，符合 K1 要求 | 该前提 U → T，再检查其他前提与事实支持 | 只允许达到 K1 原文支持的强度；不自动确诊 |
| 找到方法，不符合 K1 要求 | 该前提 U → F | 撤回使用 K1 支持 C1 的推断，可解释不适用原因 |
| 原报告仍无方法字段 | U 保持 U，请求未解决 | 保留待补项和条件性表达，不再次以文献补写患者事实 |

如果缺失的是“K1 的方法要求是什么”，才属于知识缺口，应该交给算法一检索。这一动作差异是本算法需要验证的核心。

## 6. 与已有工作相比，差异具体在哪里

| 对照工作 | 已有机制 | 本算法拟增加并需要验证的内容 |
|---|---|---|
| SEMA-RAG | 临床约束、充分性/缺口反馈、下一轮查询、证据裁决 | 状态绑定具体患者观测与条款，区分动作类型，使用明确成功判据并限制特定结论。[L3] |
| i-MedRAG | 依据既有信息生成后续检索问题 | 对能通过检索解决和不能通过检索解决的问题显式分流。[W7] |
| 王梦涵 Self-VEQA | 问答与验证 Agent 多轮交互、修正推理路径 | 验证目标从一般答案/路径合理性转为适用条件、患者事实和结论强度。[L7] |
| 姚行志后验图矫正 / 高福财事实核查 | 利用图知识矫正答案，或检查原子声明的支持情况 | 核查结果不仅作为一个真假标签，还生成下一步动作并更新结论依赖。[L5][L6] |
| MedCoRAG | 指南、图路径和多专科定向再检索 | 重点验证条款状态、患者缺失分流与结论约束的增量，而非仅声称首次闭环。[W8] |

SEMA-RAG 已有临床条件、冲突处理和两轮检索配置，因此“加入条件”“允许两轮”“增加裁决角色”不能单独作为本算法的差异。

## 7. 如何验证算法有效

### 7.1 对照设置

在相同第一轮证据、模型、资料访问权限、最多两轮检索和累计预算上限下，比较：不复核、固定查询复核、自由文本缺口反馈、本文显式状态与动作复核。

不复核用于判断是否有复核收益；后面三者用于判断收益是否来自复核策略本身。另优先加入 SEMA-RAG-style 的任务适配，并披露适配差异。

### 7.2 主要指标

| 指标 | 评价对象与判据 |
|---|---|
| 错误强结论病例率 | 全部病例中，必要条件未决仍输出确定性关键判断的比例 |
| 请求解决率 | 可执行请求中，返回证据真正满足预设成功判据的比例；保留未决不计为解决 |
| 患者缺失误补率 | 缺失场景中，把文献或模型推断误写成真实患者结果的比例 |
| 回答覆盖率 | 全部任务要求中，有依据且达到要求的回答所占比例 |
| 关键事实遗漏率 | 应保留的患者事实在最终报告中被遗漏的比例 |
| 兼容例误报冲突率 | 本可兼容的证据对被误识别为冲突的比例 |
| 引用支持率 | 引用真正支持断言内容与强度的比例，而非链接存在率 |

必须联合报告错误与回答覆盖：不能通过删除大部分结论获得表面的低错误。所有请求还需记录触发、动作、成本、前后状态和受影响结论，便于解释改善来自哪里。

### 7.3 场景、消融与停止要求

首批可设计 30–50 个开发性场景，分别覆盖知识缺口、未测、未记录、显式阴性、同层冲突、跨层兼容和来源不支持；正式留出样本按患者或条款组隔离，策略冻结后评价。

关键消融为：不区分知识/患者缺口、固定查询替代状态请求、取消结论级约束。一次只改变一个因素。

一次反馈批次结束、无可执行请求、没有新增有效证据或预算耗尽时，系统必须退出并说明未解决项。各 Agent 不得在内部另起循环绕过统一预算。

## 8. 与系统及算法一的交接

发给算法一的请求要携带目标候选对、需求类型、已知/未知条件、允许证据用途和剩余预算。算法一返回新旧候选去重并重新选择后的证据集合，最终上下文仍满足原定证据预算。

发给报告模块的是**检查后的结论对象**及其证据，包含允许强度、未决项和来源。报告模块只负责表达，不得把“倾向”润色成“确定”，或隐藏影响结论的限制。
