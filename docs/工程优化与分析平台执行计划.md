# NeuroGRA 工程优化与分析平台执行计划

编制日期：2026-10-23  
本次整理日期：2026-10-26  
状态：执行中，已完成首批基础改造与核心工作台局部验收，完整平台尚未完成。  
目标：将现有脚本驱动的分析系统整理为可安装、可配置、可恢复、可追溯的本地病例分析平台。

## 1. 实施范围与交付目标

本轮工程建设优先服务于单机、单用户的研究分析工作。保留既有主 Agent、专科分析、KB/KG 检索、来源核验和报告生成逻辑，补齐应用入口、后台任务、数据管理和用户界面。

首个可用版本应支持：

1. 使用统一命令安装并启动，运行病例时无需修改 Python 源码。
2. 在浏览器导入患者 JSON、预览资料、选择配置并提交分析。
3. 启动前检查模型、知识版本、输入文件、目录和预算是否满足要求。
4. 查看任务阶段、已完成批次、失败原因，执行取消、重试或符合条件的恢复。
5. 查看报告正文、患者资料、证据出处、未解决问题和历史版本，并下载报告。
6. 明确区分持久数据、正式产物、缓存和日志，提供备份、完整性检查和清理预览。

本计划不新增研究创新、对比实验或诊断性能评价；不重新训练影像模型；第一版不建设多人协作、分布式调度和复杂图谱可视化。技术验收通过不等同于医学有效性验证。

实施时继续维护本计划的任务状态和验收结果，不为每个小任务重复生成方案、实施记录和验收文档。

| 现状 | 证据/位置 | 工程影响 |
| --- | --- | --- |

| 清理后主入口默认病例与默认 Neo4j 凭据文件缺失 | `main.py` 中引用的 `output/` 路径 | 应由配置和启动预检处理，不应依赖旧产物 |

| 当前有 173 个未跟踪 Python 文件 | Git 工作树检查 | 当前磁盘状态尚未形成完整可恢复版本基线 |
| `output/` 当前仅保留 `kb/` | 用户已批准的清理结果 | 新平台须重新定义目录职责，不能假定旧运行产物还在 |

清理是用户已授权的操作。本计划不恢复已删除的旧文档和批次产物，也不将旧记录中的缺失文件伪装为完整报告。

## 3. 总体实现方式

采用模块化单体应用，加一个独立后台执行进程。先保证本机可用，再根据真实使用量扩展。

```text
浏览器工作台
    ↓
应用接口：病例 / 任务 / 报告 / 知识 / 设置
    ↓
应用服务层：校验输入、解析配置、创建任务、登记产物
    ↓
持久任务表 ← 后台执行进程 → 现有临床分析与 KB/KG 服务
    ↓
运行状态数据库 + 输入快照 + 知识资源 + 报告与日志
```

### 3.1 必须保持的边界

- CLI 和 Web 调用同一应用服务；不各自复制一套分析流程。
- 页面服务提交任务并查询状态，不直接承载耗时推理。
- 后台执行进程复用已有分析函数，预算、证据和身份校验继续生效。
- 单机阶段继续使用 SQLite；先实现事务领取任务、租约和迁移，再考虑更换数据库。
- 模型调用并发由后台执行层统一限制。现有进程内模型锁不能视为跨进程资源锁。
- 启动预检默认不执行生成推理；真实模型试运行必须明确触发。
- 第一版仅监听本机。账户、权限和远程访问能力完成前不改为对外监听。

### 3.2 数据目录职责

下表先定义职责，不要求第一阶段立即搬迁已有文件。

| 类别 | 目标位置/职责 | 清理原则 |
| --- | --- | --- |
| 病例输入与版本 | `data/clinical/` 下的病例原件、输入快照和索引 | 持久保存，删除需检查引用 |
| 应用状态 | 明确命名的应用 SQLite 及迁移版本 | 备份后迁移，不当作缓存 |
| 知识来源与发布 | 现有 `data/kb/`、`data/kg/`、`output/kb/` 等注册路径 | 通过资源登记定位，第一阶段保持路径与内容不变 |
| 正式运行产物 | 单独的受管理产物根目录，按运行/尝试归档 | 与运行记录关联，不能混入普通缓存清理 |
| 缓存 | 独立缓存目录 | 可清理，但显示重建成本及运行依赖 |
| 日志 | 独立日志目录，按运行和尝试关联 | 设置滚动、容量上限与保留期 |
| 临时文件 | `tmp/` | 仅放可丢弃的中间物，完成或失败后回收 |

知识发布位置变更必须作为单独迁移任务：验证 manifest、资源校验和、向量绑定和回退路径，不能直接移动文件夹后修改一个字符串就宣布迁移完成。

目标：从当前本地状态收敛出一套可重复运行的工程基础。

| 编号 | 任务 | 主要范围 | 验收标准 |

| P0-03 | 统一配置解析和覆盖规则 | `clinical/config.py`、CLI、主入口、建库入口 | 同一输入及配置从不同入口得到相同的有效配置摘要 |

| P0-06 | 合并环境检查能力 | `diagnostics.py`、KG/KB 探测、CLI | 返回结构化检查结果，区分必须项、可选项、未验证项；可选模块关闭时不阻止启动 |
| P0-07 | 核对历史记录和缺失产物 | `RunStore`、报告读取 | 缺失报告显示“文件已清理/不可用”，保留原始运行结论，不返回笼统 500 |

配置覆盖规则固定为：代码内置默认值 → 配置方案 → 配置文件 → 显式命令行参数；秘密由专用环境变量或本地凭据加载。配置来源和生效值可追踪，敏感值不回显。设置页面后续写入同一配置体系。

P0-07 先提供只读检查与预览。状态修正使用可回退的迁移，不直接删除历史运行，不因旧记录状态为 analyzing 就认定仍有活跃进程。

阶段出口：使用合成病例执行离线检查；在模型环境就绪后完成一次真实本地分析，留下输入、配置、知识版本及产物索引。

## 6. 阶段三：持久后台任务和恢复

目标：让分析任务与页面进程解耦，能够管理排队、取消、失败和恢复。

### 6.1 任务状态

调度状态建议为：`queued → running → succeeded / failed / cancelled / interrupted`。

另设业务执行结果：`completed / partial / unresolved` 等；诊断判断继续保留自身状态。调度成功只表示任务按协议结束，不代表发布有效诊断，也不等于资料完整。

每次重试使用独立 attempt，保存父任务、尝试序号、触发原因、开始结束时间和日志位置。相同提交的防重规则由病例版本、配置摘要、任务类型及用户请求标识确定，不以患者编号单独判重。

### 6.2 执行任务

| 编号 | 任务 | 实现要求 | 验收标准 |
| --- | --- | --- | --- |
| P2-01 | 持久队列与独立 worker | 使用事务领取、worker 标识、租约与心跳 | 两个 worker 不能重复领取同一尝试；失联任务不永久占用运行位 |
| P2-02 | 统一资源调度 | 设模型/嵌入/影像的并发上限和等待预算 | 并发提交不会绕过模型限额；等待时间有记录 |
| P2-03 | 阶段事件和进度 | 导入、准备、专科、补查、综合、核对、报告分别记录 | 页面能看到当前阶段、批次数和最近活动；无可靠分母时不显示伪精确百分比 |
| P2-04 | 协作取消 | 调用之间检查取消标记；在途调用按超时结束 | 取消后不继续派发新调用，已保存结果不冒充完整报告 |
| P2-05 | 恢复与重试分离 | 复用现有 `execution_binding`、预算和来源校验 | 兼容的未完成步骤可恢复；代码/配置/知识变化时给出新建尝试路径 |
| P2-06 | 统一单例与批量执行 | 批量只负责创建病例任务和汇总，不再拥有另一套执行内核 | 单例和批量任务使用相同状态、产物和错误结构 |

恢复不得重置原运行预算或截止时间。原截止时间已过时，不做隐式延长；由用户显式新建尝试，重新分配预算并保留原运行关系。进程失联、租约过期和预算到期是不同事件，不能混用。

服务启动时进行中断核对，页面重启不直接终止 worker。只有明确用户动作或可验证故障才能触发重试，避免重启导致重复模型调用。

阶段出口：排队任务、正常任务、模型超时、worker 异常退出、取消和重复提交均有可验证结果；预算不重置，不能产生双重执行。

## 7. 阶段四：交付单病例 Web 工作台

目标：用户在浏览器完成一次完整分析，无需操作终端和内部文件。

| 页面 | 第一版功能 | 对应验收 |
| --- | --- | --- |
| 系统状态 | 模型、嵌入、KB、KG、RWE、磁盘和 worker 状态；显示检查时间 | 缺失必要依赖时能解释原因，并阻止不满足要求的提交 |
| 病例列表/详情 | JSON 上传、RWE 编号导入、输入版本、字段预览、质量提示 | 导入错误不丢失原始资料；选择某版本后固定该版本 |
| 创建分析 | 配置方案、专科和知识开关、预算与知识版本摘要 | 设置和后端有效配置一致；开始前可复核 |
| 任务列表/详情 | 排队、阶段、最近事件、停止原因、取消/重试/恢复 | 刷新页面不丢任务；按状态只显示可执行操作 |
| 报告详情 | 正文、诊断状态、引用跳转、原始资料位置、未解决问题 | 来源与报告关联正确；partial 明确可见，缺失文件有专门提示 |
| 历史与下载 | 按病例查看尝试和报告版本，下载 Markdown/JSON 及来源包 | 不覆盖原报告；下载资源通过产物 ID 和授权边界校验 |

技术落点：将现有 `clinical/web.py` 中页面、传输接口和应用逻辑分离；前端资源纳入包发布，不再依赖项目根目录下缺失的 `frontend/`。具体前后端框架在本阶段开始时确定，不以更换框架代替任务与数据契约建设。

Web 输入须限制大小，上传文件使用程序生成的存储名；报告和患者文本按数据渲染并转义，不能当作页面脚本执行。用户错误信息不包含账号密码、Token、数据库连接串或完整患者资料。

阶段出口：完成浏览器端全流程验收，覆盖成功、部分完成、输入错误、环境不可用、任务取消、失败重试、历史报告缺失和服务重启。保存必要截图及紧凑结果，不保留大量重复候选稿。

## 8. 阶段五：知识管理、空间管理和持续交付

| 编号 | 任务 | 交付与验收要求 |
| --- | --- | --- |
| P4-01 | 知识构建任务化 | 文献上传/导入、解析预览、失败原因、构建状态和发布状态分开；失败文献不标作成功 |
| P4-02 | 知识版本管理 | 查看版本、内容清单和覆盖范围；显式切换/回退；运行中的任务继续使用原固定版本 |
| P4-03 | 数据生命周期管理 | 按病例、运行、知识、缓存和日志统计空间；清理先预览影响；被活动任务引用的资源不可清理 |
| P4-04 | 缩减重复快照和日志 | 共享知识资源按 ID/哈希引用，不为每个病例复制完整图；日志设容量与保留策略，完整调试日志按需启用 |
| P4-05 | 备份与恢复 | 数据库、输入、知识发布、正式报告形成一致备份；从备份恢复到新目录验证，不覆盖当前工作数据 |
| P4-06 | 自动化与发布验收 | 提交检查、单元/集成/浏览器测试、安装包资源检查、合成病例端到端验收纳入发布流程 |

空间清理只能删除已登记、满足策略且没有有效依赖的资源。目录链接先检查真实边界，只删除本项目内的链接，不跟随链接删除共享运行时。备份中的凭据使用独立保护策略，不进入公开导出包。

多人使用作为后续版本：账户认证、病例级访问权限、操作审计、备份访问控制和服务部署必须先完成，之后才开放远程访问。

## 9. 测试与验收策略

| 层次 | 范围 | 运行条件 |
| --- | --- | --- |
| 单元测试 | 配置覆盖、输入版本、状态迁移、错误分类、引用校验、预算、取消逻辑 | 不依赖真实患者或外部服务 |
| 集成测试 | 队列事务领取、进程崩溃、迁移、产物登记、HTTP 接口、包内资源 | 独立临时目录与测试数据库 |
| 浏览器测试 | 病例导入到报告查看的实际交互、错误提示和重启后的状态 | 可访问的测试工作台 |
| 真实环境功能验收 | 本地生成/嵌入、真实知识资源、可选 RWE/影像服务 | 明确触发，不进入普通快速测试 |
| 备份恢复演练 | 数据库和受管理文件在新目录恢复，校验引用和哈希 | 不破坏当前数据 |

既有三套 unittest 是回归基础，继续复用。2026-10-20 的检查曾出现 Windows 沙箱临时目录权限和 asyncio 初始化阻塞；复验时记录环境并定位，不能直接把环境失败算业务失败，也不能跳过后宣称全套通过。

历史测试结果不作为新版本验收结果。对失败必须记录用例、错误、影响和处理结论；验证成功后不无依据重复扩大测试。

## 10. 顺序、依赖和里程碑

按阶段门槛推进，不给尚未估算的工作承诺固定完成日期。每个阶段开始前结合本机模型耗时和实际任务量细化工作量。

| 里程碑 | 依赖 | 完成定义 |
