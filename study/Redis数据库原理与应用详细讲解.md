## 一、先建立整体地图

你之前学 MySQL 时，主线是：数据如何存进页和 B+ 树，SQL 如何执行，事务和日志如何保证并发与故障下的正确性。

Redis 可以沿着类似的问题学习：

```text
Redis
├── 对外提供的能力
│   ├── 键值读写：SET、GET、DEL……
│   ├── 数据类型：String、Hash、List、Set、ZSet、Stream……
│   ├── 过期时间：EXPIRE、TTL……
│   └── 事务与脚本：MULTI/EXEC、WATCH、Lua
├── 内部执行与存储
│   ├── 网络连接、事件循环、命令处理
│   ├── 数据库键空间：通过键找到值
│   ├── SDS、哈希表、跳表、listpack、quicklist……
│   └── 过期清理、内存淘汰
├── 重启恢复
│   ├── RDB：数据快照
│   └── AOF：写操作日志
└── 多节点协作
    ├── 复制：保存数据副本
    ├── Sentinel：自动故障转移
    └── Cluster：数据分片与故障转移
```

例如一个商品系统：

```text
MySQL：保存商品、订单等业务记录
Redis：缓存商品详情、记录排行榜、保存部分临时状态
应用程序：决定何时读缓存、查数据库、删除缓存
```

这三个角色要分清。普通 Redis 缓存不会自己执行 SQL，也不会自动感知 MySQL 中的商品价格变了。

一次价格变更后是否删除缓存，需要应用或数据同步组件负责。

你可以先记住四个问题：

1. 数据用什么结构存，才方便操作？
2. 一个请求怎样被快速处理？
3. 内存不足、进程重启、机器故障时怎么办？
4. Redis 和 MySQL 同时保存相关信息时，怎样控制不一致？

## 二、Redis 与 MySQL、进程内字典有什么区别

### 1. Redis 的键值模型

执行：

```redis
SET user:1001:name "Tom"
```

可以理解为保存了：

```text
key   = user:1001:name
value = Tom
```

`user:1001:name` 是一个完整的字符串键。冒号只是命名约定，Redis 没有因此建立 user 表、1001 行和 name 列。

执行：

```redis
GET user:1001:name
```

Redis 根据完整键名查找值。

如果你想查询“所有年龄大于 18 的用户”，仅靠这些基础键值命令，不会自动获得 MySQL 那样的 SQL 查询和索引优化能力。需要另外设计数据组织方式或使用相应查询能力；这份教材主要讲基础键值结构。

### 2. 与 MySQL 的关系

| 问题 | MySQL/InnoDB | 本文讨论的 Redis 基础能力 |
|---|---|---|
| 数据组织 | 表、行、索引、约束 | 键与多种值类型 |
| 查询入口 | SQL，可表达连接和复杂条件 | 按键和数据结构执行命令 |
| 运行中访问 | Buffer Pool 缓存数据页，必要时读磁盘 | 主要访问内存中的数据结构 |
| 事务 | 支持回滚、隔离级别、MVCC 等 | MULTI/EXEC、WATCH、脚本，语义不同 |
| 重启恢复 | 数据文件与日志协作 | 依赖启用的 RDB/AOF 等配置 |
| 常见搭配 | 保存业务事实 | 缓存、计数、排行榜、协调等 |

**MySQL 也大量使用内存。** 不能把两者性能差异解释成“MySQL 每次都读硬盘，Redis 每次都读内存”。

Redis 常见按键访问的路径较短，数据结构操作直接，通常不涉及 SQL 解析优化、复杂连接和完整的关系型事务处理。比较性能时还要看数据量、命令复杂度、网络和持久化策略。

### 3. 为什么不用 Python 的 dict

假设你启动三个应用进程，每个进程有自己的字典：

```text
应用 A：自己的 dict
应用 B：自己的 dict
应用 C：自己的 dict
```

A 把访问次数从 10 加到 11，B 的字典不会自动变化。进程重启后，字典也消失了。

Redis 作为独立服务，允许这些进程访问同一个计数器，并提供原子命令、过期时间和持久化等机制。

代价是增加网络通信与服务依赖。因此，进程内缓存和 Redis 可以同时使用，分别解决不同层次的问题。

## 三、一条 GET 命令是怎样执行的

对应原文第 36—42、148—151 页。

假设客户端执行：

```redis
GET product:1001
```

可以把过程拆成下面几步：

```text
客户端将命令编码为协议数据
-> 通过连接发送给 Redis
-> Redis 收到可读事件，读取并解析请求
-> 检查命令、参数、权限等
-> 在数据库键空间中查找 product:1001
-> 检查键是否已过期、值类型是否适用于 GET
-> 取得结果或返回空值/错误
-> 编码响应并发送给客户端
```

### 1. 为什么按键查找通常很快

经典 Redis 数据库使用字典组织键空间。逻辑上是：

```text
完整键名 -> 哈希计算 -> 桶位置 -> 查找对应条目 -> 值对象
```

这使键查找在通常情况下具有平均 O(1) 的复杂度。发生冲突、扩容或返回很大数据时，实际耗时仍然可能增加。

### 2. 找到键，不代表已经完成所有工作

如果执行的是：

```redis
LRANGE mylist 0 -1
```

找到 mylist 只是第一步，之后还要遍历元素并返回结果。

即使查找键是平均 O(1)，返回一百万个元素也不可能只花固定时间。

### 3. type 和 encoding 的区别

值对象可以从两个层面理解：

```text
type：对外是什么数据类型，例如 Hash
encoding：内部用什么方式保存，例如 listpack 或 hashtable
```

例如一个小 Hash 与一个很大的 Hash，对外都使用 `HGET`，内部却可能采用不同结构。

可以在学习实例中观察：

```redis
TYPE user:1001
OBJECT ENCODING user:1001
```

前者帮助你判断如何使用这个键，后者帮助你理解它当前的实现方式。

原文将数据库键、值对象和底层指针画在一起，适合建立概念。阅读源码时应再区分：键名字符串与值的 `redisObject` 包装，并不意味着所有字典的每个键都经过完全相同的对象包装。

## 四、单线程为什么快，多线程又做什么

### 1. 单线程说的是哪一部分

原文重点讨论的模型中，普通命令执行主要由主线程完成。

Redis 还可以有后台线程处理文件关闭、AOF 刷盘、异步内存释放等工作；Redis 6 引入了可配置的网络 I/O 多线程。

因此要区分：

```text
命令执行是否并行
网络收发是否并行
后台任务是否并行
```

这三个问题的答案可以不同。

### 2. I/O 多路复用解决什么问题

假设有一万个客户端连接，大部分时间都没发请求。如果每个连接都占用一个线程等待，管理成本很高。

I/O 多路复用让操作系统通知 Redis：哪些连接现在可以读、哪些连接可以写。Redis 再处理这些就绪连接。

它提高的是管理大量连接的效率，不会自动把一条耗时命令变成并行计算。

### 3. 为什么顺序执行也能高吞吐

常见小数据命令执行很短，内存访问和数据结构操作开销较低。顺序执行还减少了核心数据结构的并发加锁与线程切换成本。

但“Redis 一定能达到某个 QPS”没有脱离条件的答案。一次 GET 100 字节与一次 GET 100 MB，无法用同一个吞吐量数字描述。

### 4. 单线程意味着哪些风险

如果一个请求执行很久，后续请求会等待，例如大范围集合操作、长脚本、超大结果生成。

这与 MySQL 中某条 SQL 很慢影响系统的现象相似，但阻塞机制不完全一样：Redis 常见风险是长任务占住主要命令执行线程。

> 要掌握：Redis 的高性能来自短执行路径、内存访问、高效结构和事件驱动；维持短命令、控制结果规模同样重要。

## 五、String：字符串、缓存对象与原子计数

对应原文第 96 页起。

### 1. String 能保存什么

String 保存字节序列，可以是普通文本、JSON、图片的二进制内容等。Redis 不会自动理解 JSON 中的业务字段。

```redis
SET product:1001 '{"name":"keyboard","price":199}' EX 600
GET product:1001
```

此时得到的是整段 JSON。应用通常要解析它，才能取出 price。

`EX 600` 是 600 秒过期；`PX 600000` 是以毫秒设置有效期。

### 2. 数字为什么也属于 String

```redis
SET article:88:views 0
INCR article:88:views
INCRBY article:88:views 10
GET article:88:views
```

在干净的示例数据中，最终值为 11。Redis 会按照命令要求解析整数并执行计算。

如果值是 `hello`，`INCR` 会报错；它并不是任意字符串都能加一。

### 3. INCR 为什么比 GET 后 SET 安全

两个请求自己读取再加一：

```text
初始 views = 10
A：GET，得到 10
B：GET，得到 10
A：SET 11
B：SET 11
最终为 11，丢了一次增加
```

改成两个 `INCR`：

```text
Redis 执行 A 的 INCR：10 -> 11
Redis 执行 B 的 INCR：11 -> 12
```

读、计算、写被封装进单条命令，因此其他客户端无法插入到这条命令的中间。

这与 MySQL 中 `UPDATE counter SET value = value + 1` 比应用先查询再写回更合适，是类似的思考方向。

### 4. NX、XX 与过期时间

```redis
SET task:123 "running" NX EX 30
```

含义是：仅当键不存在时创建，并同时设置 30 秒有效期。

`NX` 表示不存在才设置，`XX` 表示存在才设置。把条件和写入合并，避免“先检查、再写入”的竞争窗口。

另一个容易忽略的细节：普通 `SET` 覆盖已有键时，默认会清除旧 TTL；需要保留时使用相应的 `KEEPTTL` 选项，或明确重新设置有效期。

> 要掌握：String 可保存整块数据；计数优先使用原子计数命令；多条命令拼起来不自动具有原子性。

### 5. 共享 Session 为什么常用 Redis

用户登录后，应用可以把会话信息写入 `session:随机会话标识`，浏览器只携带相应标识。

下一次请求即使落到另一台应用服务器，也能根据标识查询同一份会话，不必依赖最初登录的那个进程。

过期时间可以限制会话寿命；退出登录可以删除相应记录。是否滑动续期、允许多少设备在线、如何撤销会话，仍属于应用规则。

### 6. 限流计数的一个入门思路

补充：以“用户 + 时间窗口”作为键，每次请求用 INCR 增加计数，超过阈值则拒绝后续处理。

这里又出现一个组合操作：第一次增加计数时需要设过期。如果 INCR 后程序崩溃，EXPIRE 没执行，就可能遗留无过期计数器。可以用短脚本把计数和首次设置 TTL 合在一起。

固定窗口还可能在两个相邻窗口的边界允许短时间内通过接近两倍阈值的请求；更平滑的限流需要滑动窗口或令牌桶等设计。原子计数解决并发计数，不自动决定限流算法是否适合业务。

## 六、Hash：怎样保存对象的多个字段

对应原文第 109 页起。

### 1. Hash 的两层键

```redis
HSET user:1001 name "Tom" age 20 city "Shanghai"
HGET user:1001 name
HMGET user:1001 name age
HINCRBY user:1001 age 1
```

逻辑结构是：

```text
数据库中的 key：user:1001
它的 value 是 Hash：
    name -> Tom
    age  -> 21
    city -> Shanghai
```

`user:1001` 是数据库级的键；`name`、`age` 是该 Hash 内部的 field。

### 2. Hash 与 JSON String 怎么选

如果业务每次都整体读写商品详情，序列化成 String 简单直接。

如果经常单独改一个字段，例如年龄或购物车数量，Hash 提供字段级操作，不必每次读出整个 JSON。

但 Hash 也不等同于一张 MySQL 表：没有自动获得外键、关系连接、列类型约束和 SQL 条件查询。

### 3. 购物车例子

```redis
HSET cart:1001 product:88 2 product:99 1
HINCRBY cart:1001 product:88 1
HGETALL cart:1001
```

用户 1001 对商品 88 的购买数量变成 3。

真实系统还要校验购买数量是否合法、商品是否下架等。Redis 完成字段存取，不替你定义业务约束。

### 4. 为什么大 Hash 不适合频繁 HGETALL

`HGETALL` 返回全部字段和值，成本随结果规模增加。一个用户购物车只有少量商品时通常很直接；把全站用户塞进一个 Hash 后频繁全量读取，成本就不同了。

原文的主要过期模型是整个 key 的过期。Redis 7.4 起提供 Hash 字段过期能力，例如 HEXPIRE，学习与部署时要按实际版本确认，不能把“字段永远不能单独过期”背成绝对结论。[官方 HEXPIRE 说明](https://redis.io/docs/latest/commands/hexpire/)

## 七、List：顺序、队列与阻塞读取

对应原文第 105 页起。

### 1. List 的基本性质

List 保留元素顺序，允许重复，可以从两端插入和弹出。

```redis
RPUSH jobs "job1" "job2" "job3"
LPOP jobs
```

先从右侧依次加入，左侧弹出得到 job1，形成先进先出。

如果同一端入、同一端出，则可以形成后进先出。因此 List 本身并非只能用于 FIFO。

### 2. 阻塞读取到底阻塞谁

```redis
BLPOP jobs 5
```

如果队列没有元素，这个客户端最多等待 5 秒；有元素到来时可以提前得到结果。

**等待的是这个客户端的请求，不是让整个 Redis 主线程停下来睡 5 秒。** Redis 仍可以处理其他客户端。

### 3. 直接弹出后，任务可能怎样丢失

```text
消费者 LPOP 取到 job1
-> job1 已从队列移除
-> 消费者在真正处理前崩溃
-> 队列里没有 job1，任务也没完成
```

可以将任务原子地从待处理队列移动到处理中队列，成功后再从处理中队列删除。原文使用 `BRPOPLPUSH` 说明这种模式；学习较新版本时也可以了解 `BLMOVE`。

但“移到处理中队列”只是可靠消费的一部分：还要有超时回收、重试、重复处理防护和故障恢复。

### 4. List 与 Stream 的区别

List 的简单弹出模式没有原生的完整消费组和待确认消息管理。业务越需要确认、重试和多个独立订阅方，越需要了解 Stream 或专业消息系统。

## 八、Set：去重和集合运算

对应原文 Set 章节。

```redis
SADD article:88:likes user:1 user:2 user:1
SCARD article:88:likes
SISMEMBER article:88:likes user:1
SREM article:88:likes user:1
```

第一次加入后成员数量为 2，因为重复的 user:1 只保留一份。

### 1. 为什么点赞适合 Set

点赞业务同时需要：记录谁点了赞、避免同一用户重复计入、查询人数。Set 对应地提供添加、成员判断和数量统计。

如果只保存一个总数，你无法仅靠这个数知道某个用户是否已点赞。

### 2. 共同关注如何计算

```redis
SADD follows:alice bob carol dave
SADD follows:tom carol dave eric
SINTER follows:alice follows:tom
```

结果集合包含 carol 和 dave。

`SINTER` 是交集，`SUNION` 是并集，`SDIFF` 是差集。

### 3. Set 无序是什么意思

它不保证按照插入顺序、名称或分数排序。显示时偶然出现某个顺序，不等于它承诺该顺序。

集合操作也不是无成本的：对特别大的集合求交集、返回大量成员，可能占用较长执行时间。

## 九、ZSet：为什么适合排行榜

对应原文 ZSet 章节。

### 1. 成员与分数

```redis
ZADD ranking 100 alice 200 bob 150 carol
ZINCRBY ranking 60 alice
ZREVRANGE ranking 0 2 WITHSCORES
```

最终从高到低为 bob 200、alice 160、carol 150。

ZSet 中 member 唯一，score 可以重复。再次为同一 member 设置分数，是更新其分数。

### 2. 排名查询和分数查询不同

```redis
ZSCORE ranking alice
ZREVRANK ranking alice
ZRANGEBYSCORE ranking 100 180
```

分别回答：alice 几分、alice 的倒序排名是多少、哪些成员分数在指定区间。

排名从 0 开始，所以界面展示“第几名”时通常需要加 1。

### 3. 分数相同怎么办

同分成员按成员的字节字典序进一步排序。它不会自动根据“谁先达到这个分数”排先后。

如果业务需要同分时按达到时间排序，就要额外设计排序规则，且注意浮点分数的精度范围。

### 4. 延迟任务的思路

可以把执行时间戳当 score、任务 ID 当 member。工作进程取出已经到期的任务再执行。

补充：查询到期任务与移除任务若分两步执行，多消费者可能取到同一任务。因此还需要原子领取、处理中状态和失败重试。ZSet 只提供有序存储，不自动变成完整可靠的调度器。

## 十、Bitmap、HyperLogLog、GEO 分别解决什么问题

对应原文第 126—134 页附近。

### 1. Bitmap：一个状态只用一个 bit

一个用户每月是否签到，可以用一个键保存一串位：

```text
第 1 天 第 2 天 第 3 天 第 4 天
   1       0       1       1
```

```redis
SETBIT sign:1001:202609 0 1
SETBIT sign:1001:202609 2 1
BITCOUNT sign:1001:202609
```

在这个示例中签到两天。offset 从 0 开始。

如果按连续用户编号记录一天内的活跃状态，一百万个位约占 125000 字节，不含对象和键的额外开销。

但空间由最大偏移量决定：只有两个用户，编号却分别是 1 和 10 亿，直接用用户编号作为位偏移仍然可能分配很大的字符串。适合稠密编号或经过映射的编号。

### 2. HyperLogLog：估算有多少不同元素

```redis
PFADD uv:20260921 user:1 user:2 user:1
PFCOUNT uv:20260921
```

它用于估计去重后的数量，例如网页 UV。

原文给出的典型误差指标约为 0.81%，是统计意义上的标准误差，不是“每次结果最多偏差 0.81%”。稠密表示的主要数据空间约 12 KB，小基数时可以使用稀疏表示。

它不保存一份可供列举的完整用户名单，也不能像 Set 一样准确回答“user:1 是否在集合里”。

适用场景是允许估算的统计；精确结算和必须准确去重的业务需要其他结构。

### 3. GEO：按地理位置查询

```redis
GEOADD shops 121.4737 31.2304 shop:1
GEOADD shops 121.4800 31.2400 shop:2
GEODIST shops shop:1 shop:2 km
```

前两条保存两个位置，第三条计算两者距离，单位为千米。参数顺序是经度、纬度，不能颠倒。

GEO 的经典实现利用有序集合及地理编码，把二维位置映射成便于检索的表示，再完成候选筛选和距离计算。

需要区分直线/球面距离与实际道路行驶距离。附近门店可以使用前者，开车路线和交通时间还需要地图路网服务。

## 十一、Stream：一条消息如何被可靠处理

对应原文第 135—143 页。这里将发送、消费、确认、重试分开解释。

### 1. 写入消息

```redis
XADD orders * order_id 1001 status created
```

`*` 让 Redis 自动生成消息 ID，形式通常类似 `毫秒时间-序号`。该 ID 在相应 Stream 中用于标识条目和排序；不同 Stream 可能出现相同 ID，不能直接当成跨系统全局业务唯一号。

### 2. 消费组有什么作用

```redis
XGROUP CREATE orders inventory 0 MKSTREAM
XREADGROUP GROUP inventory worker1 COUNT 1 STREAMS orders >
```

创建 inventory 消费组，worker1 从组里领取尚未交付的新消息。

```text
orders Stream
├── inventory 组：worker1、worker2 分担库存处理
└── analytics 组：worker3、worker4 分担统计处理
```

同一组内通常分担新消息；不同组独立维护消费进度。需要同一条消息触发两种业务时，建立两个组。

这与“同一个组的每个消费者都收到同一份新消息”不同。

### 3. PEL 与 XACK

消息交付给组内消费者后，进入该组的待确认记录 PEL。业务处理成功后，再执行：

```redis
XACK orders inventory 具体消息ID
```

这里的“具体消息ID”需要替换为前面读取到的真实 ID。

**XACK 移除的是该消费组的待确认记录，不会自动删除 Stream 里的消息正文。** 消息保留、删除或裁剪需要单独管理。原文第 140 页的“消息就会被删除”应按这一层含义修正理解。[官方 XACK 说明](https://redis.io/docs/latest/commands/xack/)

### 4. 消费者宕机后怎样恢复

```text
领取消息 -> PEL 有记录 -> 消费者崩溃 -> 没有 ACK
```

系统可以检查 `XPENDING`，再通过领取待处理消息的机制恢复，例如 `XCLAIM` 或 `XAUTOCLAIM`。

它不会仅凭客户端一直读取 `>` 就把所有旧待处理消息自动重新执行。应用需要设计恢复流程，并确保消息没有提前被裁剪。

### 5. 为什么有 ACK 仍可能重复处理

```text
业务已经成功写入数据库
-> 消费者在发送 ACK 前崩溃
-> 消息被再次领取
-> 同一笔业务再次执行
```

因此要做幂等：同一消息或业务请求重复执行，结果不应重复扣款、重复发货。

例如在数据库中用订单 ID 和事件类型建立唯一约束，并把去重记录与业务修改放在同一个事务内。仅仅“先记已处理，再执行业务”也会产生新的失败窗口。

### 6. Redis 自身故障怎么办

消费确认解决消费者侧的进度问题；Redis 节点故障下的数据保留，还受持久化、复制、切换以及消息裁剪策略影响。

消息 ID、ACK、持久化、幂等分别解决不同问题，不能用一个机制替代其他机制。

## 十二、Pub/Sub 与消息队列有什么区别

对应原文第 143 页。

```redis
SUBSCRIBE news
PUBLISH news "hello"
```

这是一种在线广播模式：订阅者在线时接收推送，离线期间的历史消息不会按可靠队列的方式等它回来再补发。

适合允许错过的实时通知、可以重新查询完整状态的变化提醒等。要求断线补偿、业务确认和重试时，应采用提供相应机制的消息方案。

还要区分：Redis 自己配置了 AOF，并不意味着 Pub/Sub 广播会变成可重放的持久化消息队列。

## 十三、SDS：为什么 Redis 不直接用普通 C 字符串

对应原文第 152—162 页。

### 1. 普通 C 字符串的问题

普通 C 字符串依赖末尾的 `\0` 标记结束。要计算长度，通常需要从头遍历到终止符。

如果数据中间本来就有零字节，使用这种结束规则的字符串函数会提前停止，不适合直接表达任意二进制内容。

追加内容时，调用方还必须保证空间足够，否则可能越界。

### 2. SDS 保存哪些信息

可以用下面的概念结构理解，实际结构随长度类别而变化：

```text
len   ：已经使用多少字节
alloc ：分配了多少容量
flags ：采用哪种头部布局
buf   ：真正的数据
```

于是：

```text
取长度：直接读 len
追加数据：检查 alloc - len 是否足够
读取内容：按照 len 处理，不靠中间的零字节判断结束
```

这带来长度查询方便、二进制安全、容量检查和扩容管理等好处。

“二进制安全”指能正确保存包含任意字节的内容，不代表加密或自动识别内容格式。

### 3. 为什么要预留空间

如果每追加一个字符都重新分配一次空间，一段字符串增长一千次就可能触发许多次分配和复制。

预留一部分容量，可以减少短时间内反复扩容的次数。代价是暂时占用一些尚未使用的空间。

> SDS 的设计主线：多保存少量元数据，让字符串读写更安全、更方便，并减少反复分配的成本。

## 十四、String 的 int、embstr、raw 编码

对应原文第 97—99 页。

### 1. int 编码

如果值能表示为合适范围内的整数，Redis 可以使用整数编码节省空间。对外仍是 String。

### 2. embstr 编码

对较短字符串，可以把对象头和 SDS 放在一次连续分配中：

```text
[对象头 | SDS 头 | 字节内容]
```

好处是减少分配和释放次数，内存布局更紧凑。

### 3. raw 编码

较长或需要独立管理的字符串可以分别分配对象头与 SDS：

```text
[对象头] -> [SDS 头 | 字节内容]
```

这使字符串的容量调整更灵活。

### 4. embstr 是否不能修改

可以修改。经典实现会在需要修改内容时转换为 raw，再执行修改。

原文的“只读”是在解释这种内部表示的修改策略，不能理解成用户对短字符串执行 APPEND 一定失败。

不同版本的边界值有变化。学习时重点理解编码选择的原因，并用 `OBJECT ENCODING` 观察自己的实例。

## 十五、哈希表与渐进式 rehash

对应原文第 170—177 页。

### 1. 哈希冲突怎样处理

假设哈希表有 8 个桶，两个不同键都计算到桶 3：

```text
桶 0 -> 空
桶 1 -> ...
桶 2 -> ...
桶 3 -> keyA -> keyB
```

经典 Redis 字典用链式结构处理冲突。找到桶之后，再比较真正的键。

落到同一个桶不会让两个键自动互相覆盖；只有键本身相同才属于更新同一项。

### 2. 为什么要扩容

桶数量不变，条目越来越多，同一个桶里的链可能变长，查询就变慢。

负载因子可以理解为：

```text
负载因子 = 已存条目数 / 桶数量
```

扩容后，桶数变化，需要重新计算条目的归属，这个重新分布过程称为 rehash。

### 3. 一次搬完有什么问题

若有一千万个键，一次性搬迁会长时间占用执行资源，客户端感受到明显停顿。

渐进式 rehash 将搬迁分散到多个步骤：

```text
旧表与新表暂时共存
-> 每次推进一部分搬迁
-> 所有条目搬完
-> 释放旧表，使用新表
```

### 4. 搬迁过程中怎样查询和写入

旧数据可能在旧表，也可能已经到新表，所以查找需要考虑两张表。

新增条目写入新表，让旧表逐渐清空。搬迁可以在相关操作及后台周期性工作中逐步推进。

代价是短期额外空间和更复杂的查找逻辑，换来更平滑的延迟。

### 5. 它与 Cluster 分片的区别

rehash 是一个节点内部字典的桶调整；Cluster 分片是数据在不同 Redis 节点之间的分布。两者都涉及哈希，但层级不同。

## 十六、ziplist、listpack、quicklist 为什么不断演变

对应原文第 162—170、188—192 页。

### 1. 普通双向链表的空间代价

一个链表节点除了数据，还要保存前后指针。元素只有几个字节时，指针和分配器元数据可能比内容还大；节点分散也不利于缓存局部性。

因此，小集合适合考虑连续紧凑存储。

### 2. ziplist 怎样省空间

ziplist 把多个条目放在一块连续内存里，根据数据大小采用较短的编码。

代价是查找中间元素通常需要遍历，插入和删除可能移动后面的内容。

### 3. 连锁更新的原因

ziplist 的条目保存前一个条目的长度。该长度字段自身可能需要 1 字节，也可能需要 5 字节。

```text
A 变大
-> B 用来记录 A 长度的字段从 1 字节变成 5 字节
-> B 自身也变大
-> C 用来记录 B 长度的字段可能也要扩展
-> 继续向后传播
```

这是长度元数据依赖相邻条目造成的连锁更新，不是哈希冲突，也不是线程死锁。

### 4. listpack 怎样改进

listpack 仍使用紧凑的连续布局，但条目尾部记录自身编码长度，支持反向遍历，不再依赖前一个条目的长度字段。

因此一个条目的长度变化不会以 ziplist 那种方式迫使后续条目的长度元数据连锁扩展。

不过，连续数组里的插入仍可能引发内存移动或重新分配，所以 listpack 并不意味着所有修改都变成 O(1)。

### 5. quicklist 怎样折中

可以把 quicklist 理解成“装着一段段紧凑数组的双向链表”：

```text
节点 A <-> 节点 B <-> 节点 C
  |          |          |
[a,b,c]    [d,e,f]    [g,h,i]
```

这样不用给每个小元素都分配一套链表指针，也不必把所有元素塞进一个超大的连续数组。

早期 quicklist 的节点装 ziplist，后续常见版本使用 listpack。quicklist 将长列表分块，listpack 修复紧凑条目的依赖设计，作用不同。

## 十七、整数集合与跳表

对应原文第 178—188 页。

### 1. intset：小整数集合怎样节省空间

如果 Set 中都是较小整数，可以用有序的紧凑数组保存，而不必每个整数都创建一套较重的哈希节点。

原文展示的整数宽度包括 16、32、64 位。假设集合目前保存 1、2、3，都能放进较窄表示；加入一个超出范围的整数时，需要升级编码并调整已有元素。

它按需使用更宽的整数空间，以减少小数据的内存开销。经典 intset 升级后不会因为删除大数就自动降回窄编码。

### 2. 跳表如何加速有序查找

普通有序链表查找 90 可能要一个一个走：

```text
10 -> 20 -> 30 -> 40 -> 50 -> 60 -> 70 -> 80 -> 90
```

跳表增加稀疏的上层指针：

```text
高层：10 -----------------> 50 -----------------> 90
中层：10 ------> 30 ------> 50 ------> 70 ------> 90
底层：10 -> 20 -> 30 -> 40 -> 50 -> 60 -> 70 -> 80 -> 90
```

查找时先在高层跳过一大片，快越过目标时下到更细一层，直到找到位置。

这是示意图，真实节点层数通过概率方式生成，不要求每隔固定几个节点建立一层索引。合理的随机分层让平均查找复杂度达到 O(log N)。

### 3. ZSet 为什么同时需要跳表和字典

在使用跳表编码时：

```text
字典：member -> score，方便按成员查分数
跳表：按 score 和 member 排序，方便范围与排名操作
```

跳表找到区间起点后，可以沿底层继续读取后续元素。节点上的跨度信息帮助累计排名，后向指针支持反向遍历。

查询一个范围通常要同时考虑定位成本和输出数量，不能只写 O(log N) 而忽略返回 M 个元素的成本。

### 4. 为什么不像 InnoDB 那样用 B+ 树

InnoDB 重点考虑按页组织数据、降低磁盘访问次数；Redis 的有序集合位于内存，跳表容易实现范围遍历、插入删除和排名扩展。

两者都是有序索引设计，不同存储环境和操作需求影响选择。不能由此得出“跳表在任何场景都比 B+ 树快”。

## 十八、为什么同一种类型会有多种编码

小对象和大对象的成本结构不同。

只有三个字段的 Hash，紧凑数组即使逐项扫描也很短，而且省掉很多指针。字段增长到几万个后，哈希查找的收益更明显。

因此 Redis 会根据元素数量、元素大小、内容与版本，在不同编码之间选择。

| 类型 | 需要理解的经典编码思路 |
|---|---|
| String | 整数直接表示，短字符串紧凑分配，较长字符串独立分配 |
| Hash | 小对象紧凑存储，较大对象采用哈希表 |
| List | 分块紧凑存储与链式组织结合 |
| Set | 小整数集合可用 intset，也可能使用紧凑结构或哈希表 |
| ZSet | 小对象紧凑存储，较大对象用字典加跳表 |

版本核对：Redis 7 的 Hash、ZSet 使用 listpack 取代相应的 ziplist 编码；Redis 7.2 起，小 Set 也可使用 listpack。因此“Set 只有 intset 和 hashtable”并非跨版本结论。[官方内存优化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

> 学习重点是理解时间与空间的取舍。具体阈值应查看运行版本的配置，编码结果应查看实例，不能把教材某页的数字当成永久规则。

## 十九、Pipeline：命令很快，为什么应用仍然觉得慢

这一节是对线程模型和网络开销的补充。

### 1. 网络往返可能比执行时间更长

假设一次命令执行只需很短时间，但客户端与 Redis 之间一次往返需要 1 毫秒。如果连续发送 1000 条命令，而且每次都等前一条返回再发下一条，仅网络等待就可能累计到约 1 秒。

普通模式：

```text
发命令 1 -> 等结果 1 -> 发命令 2 -> 等结果 2 -> ...
```

Pipeline：

```text
连续发送一批命令 -> 集中读取这一批结果
```

Redis 仍要执行每条命令，主要节省的是逐条等待网络往返的成本。

### 2. Pipeline 不保证这一批业务不可被插入

它是批量传输方式，不提供整批命令的事务隔离保证。其他客户端的命令可能在处理过程中交错。

部分客户端库的 pipeline 默认会额外包装事务，这属于客户端行为；分析时要看它究竟发送了什么。

### 3. 一批也不应该无限大

太大的一批会积累请求与响应，占用缓冲区，增加内存和尾延迟。合理批量需要结合单条响应大小和延迟目标。

## 二十、Redis 事务与 MySQL 事务差在哪里

这一节用于连接你已学过的 MySQL 事务知识。

### 1. MULTI、EXEC、DISCARD

```redis
MULTI
SET account:alice 100
SET account:bob 200
EXEC
```

`MULTI` 后，命令通常先入队并返回 QUEUED；`EXEC` 时按顺序执行。

执行这一组命令期间，不会插入其他客户端的普通命令。`DISCARD` 则放弃还没执行的队列。

### 2. 两种错误的后果不同

**入队阶段错误**，例如命令参数数量错误，现代 Redis 会标记事务失败，EXEC 时拒绝执行整组。

**执行阶段错误**，例如数据类型不符合命令要求，不会回滚已经执行成功的命令，也不会让所有后续命令自动取消。

```redis
SET demo:n "abc"
MULTI
SET demo:a "done"
INCR demo:n
SET demo:b "done"
EXEC
```

预期：demo:a 和 demo:b 被设置成功，INCR demo:n 因非整数失败。不能把整个过程当成失败后自动恢复原状的 MySQL 事务。

### 3. 为什么“事务原子性”容易说混

有时资料用“原子执行”强调不被其他命令穿插；MySQL ACID 中的原子性则包含事务失败时整体回滚的含义。

面试中应直接说清具体保证：Redis 事务在 EXEC 时顺序、隔离地执行队列，但不提供执行错误后的自动回滚；持久性还依赖持久化配置。

### 4. WATCH 怎样防止丢失更新

客户端需要根据读到的值作决定，可以使用乐观并发控制：

```text
WATCH stock
读取 stock，检查是否大于 0
MULTI
写入计算后的 stock
EXEC
```

如果 WATCH 后、EXEC 前该键被其他操作修改，EXEC 会放弃执行并返回空结果。客户端需要重新读取、检查并决定是否重试。

WATCH 不会把键锁住，也不会让其他客户端不能修改。它表达的是“如果我依据的值被改过，就拒绝提交这次结果”。

以上事务与 WATCH 边界参见 [Redis 官方事务说明](https://redis.io/docs/latest/develop/using-commands/transactions/)。

## 二十一、Lua：把读、判断、修改放在服务端完成

原文在分布式锁章节使用 Lua。先理解它的作用，再理解锁会更容易。

### 1. 为什么需要服务端判断

如果库存检查和扣减是两条独立命令：

```text
库存为 1
A 读取，发现可以购买
B 读取，也发现可以购买
A 扣减
B 扣减
```

单条命令顺序执行，并不能保护客户端的整个“检查再行动”。

### 2. 一个库存脚本示例

下面是学习脚本，假设该键专门用于保存非负整数库存：

```lua
local raw = redis.call('GET', KEYS[1])
if not raw then
    return -1
end

local stock = tonumber(raw)
if not stock then
    return redis.error_reply('stock must be numeric')
end

if stock <= 0 then
    return 0
end

redis.call('DECR', KEYS[1])
return 1
```

返回 -1 表示库存键不存在，0 表示售罄，1 表示成功扣减一次。进入写操作前检查数据，可以减少执行中出错留下部分修改的风险。

脚本运行时，这些步骤不会被其他客户端的命令穿插。它同时减少了客户端与服务器之间的多次往返。[官方脚本说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

### 3. 脚本的三个边界

第一，脚本执行太久仍会阻塞其他命令，因此不能把长循环或复杂计算随意搬进去。

第二，运行时错误不会自动回滚脚本已经完成的写操作。应尽量先验证输入与类型，再修改数据。

第三，脚本只能保护它在 Redis 内执行的部分。Redis 扣库存成功后，应用写 MySQL 订单失败，不会因为 Redis 用了 Lua 就自动恢复两边状态。

> Pipeline 侧重减少网络等待；MULTI/EXEC 侧重队列隔离执行；WATCH 检查读写间的并发变化；Lua 将相关判断与写操作放到服务端一起执行。

## 二十二、AOF：一条写命令怎样变成可恢复的数据

对应原文第 193—209 页。

### 1. 为什么只放在内存不够

内存中的值在进程或机器故障后可能丢失。持久化要把恢复所需的信息保存到磁盘。

例如：

```redis
SET counter 10
INCR counter
```

如果有足够的写操作记录，重新执行这些操作就能恢复 counter 的状态。这就是理解 AOF 的入口。

### 2. 写入经过哪几层

```text
执行写操作，修改内存
-> 追加对应的 AOF 数据到 Redis 缓冲区
-> write() 写入操作系统页缓存
-> 按策略执行 fsync 等同步工作
-> 存储设备完成持久化
```

要区分 Redis 自己的缓冲区、操作系统页缓存和最终持久化存储。

`write()` 成功，不代表突然断电时数据一定还在；数据可能仍处于操作系统管理的内存里。

### 3. 三种 appendfsync 策略

| 策略 | 主要含义 | 取舍 |
|---|---|---|
| always | 每批写操作的 AOF 同步落盘要求更严格 | 通常延迟更高，持久性更强 |
| everysec | 通常约每秒安排同步 | 性能与风险折中，常按约一秒数据窗口理解 |
| no | 不由 Redis 主动按上述频率同步，交由操作系统 | 持久化时机更不可控 |

“everysec 只会丢一秒”适合作为正常工作条件下的简化理解，不能当作任意磁盘异常、阻塞和故障下的严格上限。

### 4. 与 MySQL redo log 对照

你学过 InnoDB 的 WAL：相关 redo 要先于脏数据页的持久化，以便数据页尚未刷盘时也能恢复。

AOF 主要记录 Redis 的逻辑写操作效果；redo 服务于 InnoDB 的页恢复体系。AOF 通常在内存命令执行后形成日志记录，不能直接套用“先写 redo 再刷脏页”的全过程。

两者都涉及“写入操作系统缓存”和“同步到稳定存储”的区别，但日志格式、记录对象和恢复机制不同。

### 5. AOF 是否不影响当前请求

原文强调先执行命令再记 AOF，有助于理解顺序。但客户端感受到的是端到端延迟，日志写入、磁盘阻塞、always 同步等仍可影响响应。

不能由“先执行命令”推导出“AOF 对本次请求延迟没有影响”。

## 二十三、AOF 重写：压缩的是历史，不只是文件字节

对应原文第 202—207 页。

### 1. 为什么日志会越来越大

假设 counter 被改了一百万次，但最终只等于 1000000。恢复当前状态时，不一定需要保留整个增长历史。

如果采用命令形式重建状态，可以用类似：

```redis
SET counter 1000000
```

表达当前结果。

所以 AOF 重写的核心是读取当前内存数据，生成足以恢复当前状态的新表示，而非必须从头读取旧日志、逐条删除重复命令。

复杂集合可能需要多条命令或分批序列化，因此也不能把“每个键一定只写一条命令”理解成硬性规则。

### 2. 为什么用后台子进程

遍历整个数据集、生成新文件比较耗时。如果全部在主线程完成，会影响正常请求。

经典实现使用 fork 创建子进程，使子进程处理重写，而父进程继续服务。

### 3. 重写期间的新写入怎么办

子进程看到的是 fork 时刻附近的数据视图，父进程仍会不断修改数据。必须保存这期间的增量，否则重写完成后会丢掉新变化。

原文详细介绍的是旧版“重写缓冲区 + 新 AOF 文件”流程：后台生成基础内容，主进程保留增量，最后合并并切换。

版本补充：Redis 7 起采用多部分 AOF，用基础文件、增量文件和 manifest 管理恢复集合。基础文件可为 RDB 或 AOF 格式。不要把旧版单文件切换细节套到所有新版实现上。[官方持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 4. 重写与清空历史不是业务审计

AOF 目标是恢复数据状态，重写会压缩历史，不能把它当成永久保留所有业务事件的审计系统。

## 二十四、RDB、fork 与写时复制

对应原文第 210—216 页。

### 1. RDB 保存什么

RDB 保存某个时点的数据快照，可以理解为把那一刻的数据集序列化到文件。

AOF 以操作效果日志为主要理解入口；RDB 直接表达数据状态。

### 2. SAVE 与 BGSAVE

```text
SAVE：主线程生成快照，期间阻塞常规服务
BGSAVE：创建子进程生成快照，父进程继续处理请求
```

这是理解执行方式的例子，不建议为了学习就在业务实例随意执行 SAVE。

### 3. fork 是否立即复制全部数据

不是立即把所有数据内容拷贝一遍。经典写时复制机制让父子进程起初共享物理内存页，并维护各自的地址映射。

```text
fork 之后：
父进程虚拟地址 ─┐
                ├─> 同一物理页，内容是 price=100
子进程虚拟地址 ─┘
```

当父进程要把价格改成 120：

```text
子进程仍然看到旧页：price=100
父进程使用复制后的可写页：price=120
```

子进程因此可以生成旧时点的一致数据视图，父进程继续接受新写入。

### 4. 为什么 BGSAVE 仍有开销

fork 本身需要操作系统工作和页表处理，可能造成停顿。后续写时复制会增加内存使用与复制成本；后台保存也会争用 CPU、磁盘和内存带宽。

复制通常以操作系统内存页为单位，不是“改一个字段就一定复制整个 Redis 键”，也不是“只复制这个字段的几个字节”。

### 5. RDB 的丢失窗口怎么理解

如果最后一次成功快照对应 12:00，12:03 故障，且没有其他恢复记录，那么此后的修改无法仅靠这份快照恢复。

设置每五分钟尝试快照，不意味着无论保存失败还是延迟都最多丢五分钟。需要看最后一次成功保存的状态以及故障发生时间。

## 二十五、RDB、AOF、混合持久化怎样选择

| 方式 | 优势 | 成本与边界 |
|---|---|---|
| RDB | 状态紧凑，适合快照与备份，加载通常直接 | 快照间的更新可能丢失，生成有资源开销 |
| AOF | 可更频繁保存写操作效果 | 同步、重放和文件管理有开销 |
| 混合方式 | 基础状态用 RDB 表示，后续变化用增量日志表示 | 恢复与文件管理要符合对应版本格式 |

混合方式可以这样理解：

```text
恢复基础数据状态
-> 再应用之后的增量修改
-> 得到更接近故障前的状态
```

不要把“开启 RDB 和 AOF”与“混合格式的文件组织方式”简单当成同一个概念。

选择时先问业务：Redis 数据是否可从其他地方重建？允许丢多少？多久必须恢复？数据量与写入量多大？

例如商品详情缓存可以从 MySQL 重建，但大规模冷启动可能压垮数据库；即使缓存允许丢失，保留快照也可能有利于快速预热。

登录状态、队列任务、去重记录丢失后的影响不同，不能统一套用“Redis 只是缓存，丢了没事”。

## 二十六、大 Key、热 Key 与延迟排查

对应原文第 82 页附近、第 217—224 页。

### 1. 大 Key 与热 Key 的区别

```text
大 Key：内容很大，或集合元素很多
热 Key：访问特别频繁
```

一个 100 字节的活动状态可以极热；一个没人访问的 100 MB 对象可以很大但不热。

### 2. 大 Key 影响哪些环节

读写需要搬运更多字节；结果编码与网络传输耗时；大集合遍历和释放可能占据执行线程；复制和持久化也需要处理更大的数据量。

例如每秒读 1000 次、每次返回 1 MB，单响应正文就约 1 GB/s，尚未计算协议和其他流量。

即使 AOF 的 fsync 在后台，主线程的数据处理、write 调用和磁盘资源竞争也未消失。原文第 220 页“不会影响主线程”应理解为特定同步工作被转移，不能泛化为整体无影响。

### 3. DEL 与 UNLINK

`DEL` 通常同步释放对象；复杂集合包含很多分配时，释放成本可能较高。

`UNLINK` 先把键从键空间摘除，再允许将较重的释放工作交给后台机制。

```redis
UNLINK large:temporary:data
```

这可以改善删除造成的停顿，但不会消除原先大对象的传输与遍历成本。

### 4. 怎样发现问题

```redis
MEMORY USAGE product:1001
STRLEN product:1001
HLEN user:1001
LLEN jobs
SLOWLOG GET 10
INFO memory
INFO stats
```

`STRLEN` 只反映 String 内容长度，不等于对象全部内存；集合元素数量也不等于准确内存。`MEMORY USAGE` 更接近对象及相关开销的估算。

慢日志侧重命令执行耗时，客户端慢还可能来自网络、连接池等待、排队等因素。

### 5. KEYS 与 SCAN

`KEYS *` 一次遍历整个键空间，在大实例上可能造成长时间停顿。

`SCAN` 用游标分批推进，更容易控制单次工作量，但不是一致性快照：遍历期间数据变化可能影响结果，返回也可能重复。

循环必须以返回游标回到 0 判断结束；一次返回空列表并不表示遍历结束；COUNT 是工作量提示，不保证每批精确返回指定数量。[官方 SCAN 说明](https://redis.io/docs/latest/commands/scan/)

### 6. 热 Key 怎样思考

对热点读可以考虑进程内缓存、多层缓存、请求合并等，代价是引入额外失效与一致性管理。

Cluster 不会自动把同一个键的请求均匀摊到所有分片。一个键仍属于一个槽，热点写入常常需要从业务结构上拆分或减少竞争。

### 7. 删除数据后，进程占用为什么没立即下降

原文面试篇还讨论内存碎片。分配器按一定尺寸管理内存块，释放一些对象后，空闲空间可能散布在许多仍被使用的页里，不能立即把整页归还操作系统。

```text
一页中原本：[对象 A][对象 B][对象 C]
删除 B 后：[对象 A][空闲块][对象 C]
```

空闲块可能供将来的 Redis 分配复用，但这一页仍有 A、C，进程 RSS 不必立即下降。

要结合 used_memory、RSS、分配器指标、峰值和后台任务看内存，不能只凭一个碎片比例就下结论。数据集很小时，固定开销也可能使比例看起来很高。

碎片整理会移动或重组对象以改善布局，但同样有 CPU 成本。它也不能代替对大对象、无界集合和缓存容量的设计。

## 二十七、过期删除：TTL 到了，Redis 做什么

对应原文第 225—236 页。

### 1. 设置与查询有效期

```redis
SET code:login:1001 123456 EX 60
TTL code:login:1001
```

TTL 表示剩余秒数；常见特殊返回值为 -1（键存在但无过期时间）和 -2（键不存在）。

有效期是数据生命周期信息。验证码到期后，即使底层内存还没回收，也不应被作为有效验证码使用。

### 2. 为什么不每个键配一个精确定时器

数量巨大时，维护和触发海量定时任务有成本；大量键同时到期也可能集中占用执行资源。

Redis 使用惰性检查与主动周期性清理配合，在 CPU 开销与内存回收之间折中。

### 3. 惰性删除

访问键时检查过期状态，发现已过期则按过期逻辑处理，不把旧值作为正常结果返回。

好处是把检查分散到访问过程；问题是一个过期后永远没人再访问的键，不能只靠这种方式及时回收。

### 4. 主动清理

周期性从设置了过期时间的键中做检查，清除过期项，并限制清理工作占用的时间。

原文给出“抽 20 个、比例超过 25% 继续”等经典源码说明。这些数字对应特定实现，核心是采样、继续清理条件与时间预算；不要当成所有版本永远固定的执行公式。

### 5. 过期与淘汰为什么要区分

过期是时间条件满足了。淘汰是容量压力下选择移除数据，可能移除尚未过期的数据。

因此，即使给某个键设置一小时 TTL，也不代表它一定能在缓存中保留一小时：淘汰、主动删除、覆盖等都可能使其更早消失。

## 二十八、内存淘汰：LRU、LFU 与 Buffer Pool 的联系

对应原文第 237—243 页。

### 1. maxmemory 是什么

Redis 可设置用于控制数据内存的阈值，达到限制后按照策略尝试淘汰。

进程真实内存还可能包含缓冲区、分配器碎片、写时复制等成本，所以不能把 maxmemory 直接等同于机器全部物理内存。

### 2. 原文的八类策略

| 策略 | 候选范围与选择方式 |
|---|---|
| noeviction | 不主动淘汰，内存不足时拒绝相应写入 |
| allkeys-lru | 所有键中，近似淘汰最久未访问的 |
| allkeys-lfu | 所有键中，近似淘汰低频访问的 |
| allkeys-random | 所有键中随机选择 |
| volatile-lru | 有过期时间的键中按近似 LRU |
| volatile-lfu | 有过期时间的键中按近似 LFU |
| volatile-random | 有过期时间的键中随机选择 |
| volatile-ttl | 有过期时间的键中优先选择剩余寿命较短的 |

volatile 的候选对象可以还没过期，只是设置了过期时间。如果找不到适合淘汰的对象，写入仍可能失败。

### 3. LRU 关注最近访问

LRU 倾向于淘汰最久没被访问的数据。

如果 A 一小时前频繁访问，B 刚刚只访问一次，单纯按最近时间，A 可能先被淘汰。

Redis 采用采样与候选管理近似实现 LRU，减少精确维护全局访问顺序的开销。

### 4. LFU 关注访问频率

LFU 希望保留经常访问的数据，降低一次性大扫描对缓存的污染。

经典 Redis LFU 使用紧凑的概率计数与随时间衰减机制，不是无限精确地累计从系统启动到现在的每次访问。

为什么需要衰减？昨天的热门商品今天可能已经无人问津，不能因为历史总次数高就永久占据内存。

### 5. 与 InnoDB Buffer Pool 的关键区别

你学过 Buffer Pool 中的 LRU、冷热页等管理。共同目标是把有限内存留给更有价值的数据。

区别在于：InnoDB 淘汰的是磁盘数据页的内存副本，脏页要按相应规则处理；Redis 淘汰的是键空间里的键，不会把它临时搬进 AOF，等下次 GET 再自动按键加载回来。

如果 Redis 是缓存，下次未命中后由应用回源；如果它保存唯一业务数据，允许淘汰就意味着业务数据可能被移除。

## 二十九、主从复制：全量、增量与两个缓冲概念

对应原文第 260—277 页。

### 1. 为什么需要副本

单机即使有 RDB，也可能因机器宕机而暂时无法服务。复制让其他节点保存数据副本，为读扩展和故障恢复提供基础。

```text
主节点：接受写入
├── 从节点 A：接收复制
└── 从节点 B：接收复制
```

### 2. 首次全量同步

经典流程可以理解为：

```text
从节点请求复制
-> 主节点与从节点协商复制身份和进度
-> 提供一份基础 RDB 数据
-> 从节点加载基础数据
-> 补上生成和传输期间的新写入
-> 转入持续的增量传播
```

基础 RDB 可以通过落盘或无盘传输等路径交付；理解重点是“基础状态 + 后续增量”。

为什么一定需要增量？假设开始复制时库存为 100，传输期间主节点卖出 5 件。如果只加载旧快照，从节点仍是 100，需要应用后续变更才能追到 95。

### 3. 复制 offset 是什么

offset 表示复制流中的进度，以字节偏移理解更准确，不是“已经执行了多少条命令”，也不是数据库记录数。

主节点到了 10000，从节点到了 9500，说明从节点还缺一段复制流；是否能补这段还要看复制历史身份和日志保留范围。

### 4. backlog 与待发送缓冲的区别

```text
replication backlog：保留最近复制历史，以便断线后补增量
复制连接的待发送缓冲：处理当前还没发给/没被从节点接收的数据
```

它们的用途不同。具体版本可能共享底层缓冲资源，不应把教材示意图理解成永远两套完全独立的物理存储。

### 5. 重连一定全量复制吗

如果复制身份匹配，而且从节点缺失的部分仍被 backlog 保存，可以部分重同步。

如果断线太久，旧内容已被覆盖，或者历史不匹配，就可能需要全量同步。

估算 backlog 时可以先考虑：

```text
需要保留的字节量 ≈ 每秒复制流字节数 × 希望覆盖的断线秒数
```

再给流量波动留余量。例如每秒 2 MB、希望覆盖 30 秒断线，基本量约 60 MB；不是所有实例都统一设成这个数。

### 6. 为什么副本可能读到旧值

默认复制是异步的，主节点完成写入后，从节点可能尚未应用对应更新。

```text
主节点库存已经是 95
从节点尚未追上，仍为 100
```

主从复制提高可用性和读扩展能力，但不会自动提供所有节点随时强一致的读取。[官方复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

## 三十、Sentinel：怎样发现故障并选出新主节点

对应原文第 277—298 页。

### 1. 哨兵负责什么

它监测主从节点、判断故障、组织主从切换，并向客户端提供当前主节点信息。

哨兵通常不处于每次 GET/SET 的转发路径上。客户端发现主节点后直接连接数据节点。

### 2. 主观下线与客观下线

主观下线是一个哨兵认为目标在规定时间内没有正常响应。

单个哨兵可能只是自己网络有问题，因此还会向其他哨兵询问。对主节点达到配置 quorum 的故障判断条件后，才形成客观下线判断。

这提高判断可靠性，但“客观下线”仍是协议根据观察得出的判断，不是物理上百分之百证明机器断电。

### 3. 判故障与选领导者是两件事

quorum 用于客观下线判断；真正发起故障转移还要获得所需授权，包括已知哨兵中的多数派支持，并满足相应 quorum 要求。

例如 5 个哨兵、quorum=2，只剩 2 个能通信：可能达到判故障门槛，却拿不到 5 个哨兵中的多数派授权。

因此不能把“quorum 配小一点”理解为可以绕过多数派完成安全切换。

### 4. 为什么常部署三个哨兵

两个哨兵要多数派需要两票，失去一个就不足。三个哨兵失去一个，还可能用剩余两票完成选举。

这是容错部署考虑，并非程序在少于三个哨兵时绝对无法运行。还要分散故障域，避免都放在同一台机器上。

### 5. 哪个副本会被选中

先过滤不适合提升的节点，再按优先级、复制进度、标识等规则选择。

一般理解为：优先级数值越小越优先；相同优先级下比较复制进度；再相同则按标识打破平局。优先级为 0 的副本不参加提升。

原文第 287 页把某个断连时长门槛解释成“断连次数超过 10 次”，这里应修正为时间条件。官方规则考虑与主节点断连的持续时间，包括 `10 × down-after-milliseconds` 和主节点不可用时长。[官方 Sentinel 说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

### 6. 切换流程

```text
选出负责切换的哨兵
-> 挑选适合提升的副本
-> 将它提升为新主节点
-> 让其余副本跟随新主节点
-> 客户端发现并连接新主节点
-> 旧主恢复后，重新配置为副本
```

注意两种“领导者”不同：一个是组织切换的哨兵，一个是接收业务写入的新 Redis 主节点。

## 三十一、Cluster：槽、分片、重定向与多键限制

对应原文第 298—310 页。

### 1. 为什么有哨兵还要集群

哨兵管理的一主多从主要保存同一份数据。多加副本不会把单个主节点的数据容量简单合并成更大的键空间。

Cluster 将不同数据分配给不同主节点：

```text
主节点 A：一部分键，配自己的副本
主节点 B：另一部分键，配自己的副本
主节点 C：其余键，配自己的副本
```

复制增加副本；分片拆分数据规模。

### 2. 哈希槽如何定位

Redis Cluster 有 16384 个槽，普通键通过以下规则得到槽号：

```text
slot = CRC16(key) mod 16384
```

再根据槽与节点的映射找到负责节点。

```text
key -> slot -> 主节点
```

槽不是一块预先划定大小的内存，也不是只能放一个键的格子。多个键映射到同一槽是正常情况，仍按完整键区分，不会因为槽相同而覆盖或未命中。

### 3. 为什么增加一个节点可以扩容

把一部分槽及其中的键迁移到新节点，并更新槽归属，客户端就能根据新映射访问。

这与直接 `hash(key) % 节点数` 相比，引入了稳定的槽层，使数据迁移可以按槽管理。

### 4. MOVED 与 ASK

MOVED 通常表示该槽应由另一节点负责，客户端应调整相应路由信息并重试。

ASK 用于迁移过程中的临时重定向：本次去目标节点，在相应连接发送 ASKING 后执行请求，不把这种临时指引直接当成永久槽归属。

客户端通常缓存槽映射；收到重定向并不意味着 Redis 自动代替客户端转发了所有请求。[官方 Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

### 5. 多个键能一起操作吗

经典 Cluster 对需要在一个节点上共同执行的多键命令、事务或脚本，通常要求这些键位于同一个槽。两个键恰好在同一台服务器，也不等于已经满足同槽要求。

可以使用 hash tag：

```text
order:{1001}:info
order:{1001}:items
```

有效花括号内的共同部分决定哈希输入，使相关键进入同一槽。

但如果给全站所有键都加相同 tag，就把压力集中回一个槽，失去分片意义。

### 6. 16384 的意义

它是路由粒度、节点规模、槽状态表示与通信开销之间的工程取舍，不是 Redis 只能保存 16384 条记录。

原文第 309—310 页把槽碰撞与请求“命中失效”联系起来的解释不成立。同槽多键是设计常态，不应由碰撞概率推导缓存失效。

## 三十二、高可用为什么不等于零丢失、零停顿

### 1. 异步复制下的丢失窗口

```text
主节点接收写入并向客户端返回成功
-> 更新尚未复制到副本
-> 主节点故障
-> 副本被提升
-> 新主节点缺少这次更新
```

哨兵或 Cluster 解决“怎样恢复服务”，并不会自动补回从未到达新主节点的数据。

### 2. 脑裂是什么

网络分区时，旧主节点可能仍与一部分客户端通信，而其他节点在另一侧完成了新主选举。

一段时间里两侧都可能认为自己能接受某些写入，重新汇合后旧侧的写入不一定保留。

限制主节点在缺少健康副本时继续写入，可以降低风险，但会牺牲可用性，也不能消除所有判断和复制窗口。

### 3. WAIT 能解决一切吗

WAIT 可让客户端等待此前写入被一定数量副本确认接收，提高某些故障场景下的保留概率。

但它本身不等价于所有节点同步落盘，也不会把整个 Redis 主从系统变成具备任意故障下强一致保证的共识数据库。需要同时分析持久化、故障提升规则及故障组合。

### 4. 三个目标分别衡量

```text
可用性：还能不能继续接请求
持久性：已确认的数据故障后能否保留
一致性：不同读写观察到的状态是否符合约定
```

方案可以改善其中一个目标，却仍在另一个目标上有边界。学完高可用部分，应能分别回答这三个问题。

## 三十三、分布式锁：从最简单写法一步步修正

对应原文第 244—259、311—324 页。

### 1. 为什么应用里的本地锁不够

两个应用实例同时处理同一资源：

```text
服务器 A：线程 A1，持有自己的本地锁
服务器 B：线程 B1，持有自己的本地锁
```

两把本地锁互相不知道对方，无法协调跨进程竞争。

Redis 锁让多个参与者约定通过同一个键竞争临时使用权。前提是所有相关操作都遵守协议；它不会像数据库行锁那样自动拦住任何 SQL。

### 2. 第一种错误：先 GET 再 SET

```text
A：GET lock，没有
B：GET lock，也没有
A：SET lock A
B：SET lock B
两者都以为自己拿到了锁
```

检查与创建必须原子完成，所以使用 NX。

### 3. 第二种错误：SETNX 后单独 EXPIRE

```text
SETNX 成功
-> 应用进程崩溃
-> EXPIRE 没执行
-> 锁可能一直存在
```

应合并为一条命令：

```redis
SET lock:product:1001 request-unique-token NX PX 30000
```

成功时键不存在检查、写入标识、设置 30 秒有效期一起完成。返回未成功时，业务不能继续进入受保护的处理过程。

### 4. 第三种错误：释放时直接 DEL

```text
A 拿到锁，有效期 30 秒
A 暂停了 35 秒
第 30 秒锁过期
B 拿到新锁
A 恢复，执行 DEL
结果：A 删除了 B 的锁
```

因此每次加锁要生成不同的持有者标识，释放时检查是否仍属于自己。

标识应按每次加锁请求生成，不能只用固定服务器名称。同一服务器上的不同请求也可能重叠或延迟。

### 5. 第四种错误：检查与删除分两条命令

```text
A GET，发现标识还是 A
-> 锁恰好过期，B 加锁成功
A DEL
-> 仍然误删 B
```

检查和删除也必须原子执行。跨版本常用的 Lua 写法：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

### 6. 唯一标识究竟保护什么

它保护的是“只释放自己那一次加锁留下的键”。

它不能阻止锁已过期的 A 恢复后继续修改数据库。因此“安全解锁”与“业务始终只有一个执行者”是两个层次。

## 三十四、锁续约、超时与 fencing token

对应原文第 316—324 页；fencing 为补充说明。

### 1. 固定有效期的困难

设得太短，正常业务可能没做完就过期；设得太长，持有者崩溃后其他请求要等待很久。

平均耗时 5 秒，不代表每次一定小于 10 秒。网络停顿、GC、调度延迟都会影响尾部耗时。

### 2. 看门狗怎样续期

客户端在任务尚未结束时，周期性续约锁，给长任务更多时间。

续期也要原子校验持有者，不能不加判断地 EXPIRE：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ARGV[2])
end
return 0
```

否则旧请求可能替新请求的锁续期，造成所有权混乱。

### 3. 看门狗会怎样失败

```text
持有者 A 与 Redis 网络中断
-> 续约请求到不了
-> 锁过期
-> B 获得锁
-> A 仍可能访问数据库，并继续执行旧业务
```

客户端进程整体暂停时，看门狗通常也无法按时运行。它缓解长任务时间不确定的问题，不保证任意停顿下锁一直有效。

### 4. 续约失败能自动回滚业务吗

不能。应用需要根据失去锁或无法确认所有权的状态，主动停止后续操作。

已经发送给外部系统的请求，可能无法撤回；已经提交的数据库事务，也不会因 Redis 锁失效自动回滚。原文提到的“中断并回滚”是一项业务设计责任，不能当成锁框架自带的普遍保证。

### 5. fencing token 如何保护资源端

补充：每次成功取得使用权时获得递增令牌，例如 41、42。受保护的存储系统记录已接受的最大令牌，拒绝过时令牌的写入。

```text
A 拿到 token=41 后长时间暂停
B 拿到 token=42，资源端接受并记录 42
A 恢复，带着 41 写入
资源端发现 41 < 42，拒绝旧请求
```

随机 UUID 用于标识所有者；递增 fencing token 用于比较权限的新旧，两者功能不同。

这一机制需要资源端实际校验、令牌来源具有所需的单调性。不能仅在一个可能故障回退的 Redis 计数器上 INCR，就假定所有故障模型下都已解决。

> 分布式锁的核心问题：锁到期后，旧持有者可能仍活着。安全设计必须考虑它继续操作资源的后果。

## 三十五、Redlock、锁性能与替代方案

对应原文第 251—258、324—331 页。

### 1. 为什么主从自动切换可能破坏互斥

```text
A 在主节点加锁成功
-> 锁尚未复制到从节点
-> 主节点故障
-> 从节点提升，里面没有锁
-> B 加锁也成功
```

A 和 B 都可能继续处理业务。服务重新可用，不代表旧锁语义没有受损。

### 2. Redlock 的主要步骤

Redlock 在多个独立 Redis 实例上竞争同一资源的锁，不是把一个主节点和它的多个异步副本当成独立投票者。

以 5 个独立实例为例：

1. 记录开始时间。
2. 使用同一唯一标识、有限的单节点超时尝试加锁。
3. 成功数至少为 3，并且考虑加锁耗时和时钟漂移后的剩余租期仍为正，才视为取得有效租约。
4. 失败或释放时，对所有相关实例尝试安全解锁，清理可能已经成功但响应丢失的记录。

理解剩余时间的公式：

```text
可用剩余租期 ≈ 初始 TTL - 已经过的加锁时间 - 漂移余量
```

若 TTL 为 10 秒，加锁已经花了 9 秒，就不能假定还有完整 10 秒处理业务。

### 3. 多数派不等于无条件正确

Redlock 仍有时间、进程暂停、网络和节点重启等方面的假设，需要结合被保护资源与容错目标评估。不能由“部署 5 个节点”直接推导“支付业务绝对安全”。[官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

原文第 257 页把核心业务直接推荐为 Redlock，而后续又讨论限制。学习时应保留这些条件：业务正确性还需要数据库约束、幂等、资源端校验等机制共同保障。

### 4. Singleflight 减少重复工作

假设一个应用实例内 100 个请求同时发现相同商品缓存缺失，可以只让一个请求去重建，其余等待同一结果。

这样减少进程内重复回源；多个应用实例之间仍可能同时重建，需要按业务判断是否进一步跨实例协调。

它适合合并相同查询，不能把 100 个用户不同的下单请求合并成一次下单。

### 5. 本地锁交接为什么复杂

原文还介绍把已取得的锁使用权在同一实例的等待者之间交接，减少重复网络加解锁。

这种做法必须管理剩余租期、持有者生命周期、续期职责、公平性和崩溃恢复。它不会自然继承所有普通锁语义，不适合在没有明确收益和验证时自行拼装。

### 6. 有些问题可直接交给数据库

如果真正目标只是防止库存变负，可以在 MySQL 中使用条件更新：

```sql
UPDATE inventory
SET stock = stock - 1
WHERE sku_id = 1001 AND stock > 0;
```

影响行数为 1 表示成功，为 0 表示没有满足条件的记录。配合订单事务和唯一约束，可能比跨系统加锁更直接。

版本号乐观锁也是一种方式，但底层数据库执行 UPDATE 仍有自己的并发控制与行锁。原文第 330 页“全程无锁”不能理解为数据库内部没有锁。

按业务 ID 固定路由到同一实例也有价值，但扩缩容、重试和故障切换时必须避免旧实例与新实例同时处理。单纯一致性哈希并不自动消除分布式并发问题。

## 三十六、缓存雪崩、击穿、穿透：按请求路径理解

对应原文第 331—343 页。

### 1. 先看正常的读路径

```text
请求到达应用
-> 查 Redis
   -> 命中：返回
   -> 未命中：查数据库
              -> 找到：回填缓存，再返回
              -> 没找到：返回不存在
```

这些缓存问题的共同背景是：原本期望由缓存承担的请求，大量到达数据库。

### 2. 雪崩：很多缓存同时失效

假设预热时给十万个商品都设置恰好 30 分钟过期。30 分钟后，大量商品一起失效，数据库突然接到很多回源请求。

解决这一原因，可以让 TTL 带一些随机差异，或分批刷新，避免同一时刻集中失效。

另一类雪崩是 Redis 整体不可用。这时随机 TTL 没用，需要高可用、限流、降级、本地可用数据等方案。

不能把“Redis 出错就全部直接查数据库”当作万能兜底。如果平时 99% 流量由缓存承接，全部回源会把数据库负载放大许多倍。

### 3. 击穿：一个热点键失效

一个爆款商品每秒有大量查询，键一过期，许多请求同时发现缓存缺失，随后都去查同一条数据。

最典型做法是控制缓存重建：

```text
请求发现缓存缺失
-> 尝试取得该键的重建权限
-> 成功者再查一次缓存
   -> 别人已填好：直接返回
   -> 仍为空：查数据库并回填
-> 其他请求有限等待、返回允许的旧值或降级
```

为什么拿到锁后再查一次？因为等待或抢锁的时间里，另一个请求可能已经填好缓存；不复查就仍然可能做无用回源。

另一种做法是逻辑过期：值中记录新鲜度期限，过期后先返回允许使用的旧值，由后台刷新。它交换的是更高可用性与一定陈旧时间，不能用于要求严格实时的数据而不作额外设计。

### 4. 穿透：数据库也没有这条数据

攻击者或错误程序不断请求不存在的商品编号。Redis 没有，MySQL 也没有，如果从不缓存这种结果，每次都要查询数据库。

可使用短时间的“空结果缓存”，但必须区分：缓存未命中，与缓存明确记录“查过，数据不存在”。

例如使用专门的空结果标记，并设置较短 TTL。代价是商品后来被创建时，需要删除对应空缓存或等待其过期。

### 5. 布隆过滤器如何减少无效查询

布隆过滤器用位数组和多个哈希位置做标记。

```text
插入商品 A -> 把位置 2、7、11 标为 1
查询商品 B -> 检查它对应的多个位置
             有一个是 0：可以判断未被加入
             全部为 1：可能存在，还需进一步确认
```

在所有应存在的数据都已正确加入、过滤器未损坏的前提下，它不会把已加入项判成不存在，但可能误判不存在的项为存在。

业务系统中如果新商品没及时加入过滤器，也可能被错误挡住；这是维护遗漏造成的，不是过滤器算法本身的概率误判。

基础布隆过滤器也不能直接把某几个共享位清零来删除一个元素，因为其他元素可能依赖同一组位。

### 6. 三类问题对照

| 问题 | 数据库中有没有目标数据 | 主要触发点 | 处理重点 |
|---|---|---|---|
| 雪崩 | 通常有 | 大片缓存失效或 Redis 不可用 | 错开失效、保护回源、提高可用性 |
| 击穿 | 有 | 单个热点失效 | 合并重建、互斥回源、提前刷新 |
| 穿透 | 没有 | 反复请求不存在对象 | 校验、空结果缓存、过滤器 |

区分它们的意义在于对症处理：随机 TTL 无法解决所有非法 ID 请求，布隆过滤器也挡不住合法热点过期造成的重建洪峰。

## 三十七、数据库与缓存一致性：逐个推演方案

对应原文第 344—360 页。这是本书最需要画时序、最不适合只背结论的一章。

### 1. 一致性问题从哪里来

数据库和缓存保存同一业务对象的不同副本，但更新它们是两个独立操作。

只要存在并发、执行延迟或部分失败，就可能出现一边是新值、一边是旧值。

设商品原价为 100 元，下文所有例子都围绕这个值变化。

### 2. 先更新数据库，再更新缓存

两个写请求交错：

```text
时间       请求 A：改为 120          请求 B：改为 150
t1         数据库写 120
t2                                  数据库写 150
t3                                  缓存写 150
t4         缓存写 120

最终：数据库 150，缓存 120
```

数据库内部正确处理了两个 UPDATE，不代表缓存写入顺序与数据库提交顺序自动一致。

只在最后“写缓存”时加锁，也不一定能解决问题：A 仍可能更晚拿到锁，然后把更旧的结果写进去。需要控制整个相关流程或引入可靠版本比较等机制。

### 3. 先删除缓存，再更新数据库

一个写请求与一个读请求交错：

```text
A：删除缓存
B：读缓存，未命中
B：查数据库，得到旧价格 100
B：把 100 回填缓存
A：数据库更新为 120

最终：数据库 120，缓存 100
```

问题窗口很直观：删缓存后到数据库提交前，旧数据库值仍可能被重新缓存。

### 4. 先更新数据库，再删除缓存

这是文档重点介绍的 Cache Aside 写路径。日常读路径是先查缓存、未命中再查数据库并回填。

写路径：

```text
数据库事务成功提交
-> 删除相关缓存
-> 后续请求从数据库重建缓存
```

为什么强调“提交后”？如果在数据库事务尚未提交时就删除缓存，其他请求可能读到旧的已提交数据并回填。

删除相较于更新，也避免必须在每次写入时重新计算一份复杂聚合缓存。某些缓存暂时无人访问，删除后按需加载还能减少无用工作。

### 5. 这种顺序仍有哪些竞争

```text
初始缓存不存在
A：从数据库读出旧价格 100，然后被暂停
B：将数据库提交为 120
B：删除缓存
A：恢复，把旧价格 100 回填缓存

最终：数据库 120，缓存 100
```

“Redis 写通常比 MySQL 快”不能证明这个时序不发生，因为 A 可能在网络、线程调度或客户端处理中暂停。

原文第 351 页已展示类似反例，因此第 352 页“可以保证一致性”应理解为工程上常用的降低风险方案，不是无条件强一致性证明。

### 6. 数据库成功，删缓存失败

```text
数据库提交为 120
-> Redis 网络错误，删除失败
-> 缓存仍是 100
-> 后续命中缓存的请求继续读 100
```

TTL 能限制某些旧值存活时间，但它是一种兜底，不代表立即一致。还需要失败补偿与监测。

### 7. 消息重试需要解决“消息本身怎么可靠产生”

原文提出把删除任务送入消息队列，再由消费者重试。

完整分析还要看：

```text
数据库提交成功
-> 应用在发消息前崩溃
-> 队列里没有删除事件
```

补充：可以把业务更新与待发送事件写入同一个数据库事务，即 outbox 思路，随后由后台投递和重试。

```text
一个 MySQL 事务：
    更新商品价格
    插入“失效商品缓存”的事件记录
提交
-> 后台可靠发送
-> 消费者删除缓存
-> 确认处理成功
```

数据库事务把“改了数据却没有事件记录”的窗口收窄到可管理的投递流程。仍要处理重复投递、消费失败与事件积压。

### 8. binlog 订阅怎样连接你学过的 MySQL

你已知道 binlog 记录数据库变更。通过 CDC 工具消费已提交的变更事件，可以触发相关缓存删除。

```text
MySQL 提交变更
-> binlog
-> CDC 解析
-> 消息队列或处理程序
-> 删除缓存
-> 记录消费进度或确认
```

这减少了业务代码主动发送失效事件的负担，但增加链路维护工作，例如事件顺序、断点续传、重试和延迟监控。

删除成功后再确认消息，避免删除失败却已经失去重试机会。重复删除通常容易做到幂等。

### 9. 为什么重试删除仍不是强一致

即使每次删除最终都会成功，旧的读请求仍可能在删除后回填旧值。消息延迟期间，也可能读到尚未删除的缓存。

因此可靠失效、旧值回填控制、数据新鲜度要求需要分别设计。对严格读写一致的关键读取，可以让数据库事务与约束承担权威判断；对允许短暂陈旧的展示数据，才采用相应缓存策略。

### 10. 延迟双删为什么没有万能睡眠时间

常见思路是：先删除、更新数据库、等待一段时间、再删除。

第二次删除希望清掉并发读请求回填的旧值，但系统没有一个永远成立的“所有读请求最多 N 毫秒完成”。应用暂停或网络异常可能比预估更长，第二次删除本身也可能失败。

因此它是一种工程上的概率缓解措施，不是强一致性证明。

### 11. 学这一章要养成的分析习惯

面对任意方案，画两类图：

```text
并发图：请求 A 和 B 的步骤能怎样交错？
故障图：每一步成功后进程立刻崩溃，会留下什么状态？
```

只要这两类问题没回答，就不能仅凭“用了锁”“用了消息队列”认定一致性已经解决。

## 三十八、把全部知识放进一个商品系统

这一节用一个例子把前文串起来，是学习综合，不是可直接上线的完整设计。

### 1. 数据如何分工

```text
MySQL：商品、订单、库存等权威业务记录
Redis String：商品详情缓存
Redis Set：部分点赞/收藏成员
Redis ZSet：热门商品榜
Redis Stream：适合该系统可靠性要求的异步任务
```

不同数据的丢失后果不同，需要分别确定是否可重建、持久化与淘汰策略。

### 2. 用户打开商品详情

```text
查本地或 Redis 缓存
-> 命中：返回展示信息
-> 未命中：合并同键并发回源
-> 查询 MySQL
-> 结果存在：缓存并设置合理 TTL
-> 结果不存在：短暂记录空结果
```

热点键可做预热或提前刷新；TTL 可以带随机差异，减少大量同时失效。

### 3. 管理员修改价格

```text
MySQL 事务提交新价格与必要事件
-> 失效相关缓存
-> 失败时通过可靠事件重试
-> 监控失效延迟
```

如果展示允许几秒陈旧，可以按此目标设计。结算时则应按业务规则从权威数据源重新校验，不能仅信任可能过期的页面缓存价格。

### 4. 用户下单

库存扣减可以由 MySQL 条件更新和事务保护；若采用 Redis 预扣库存，则还要设计订单落库失败补偿、重复请求、恢复和对账。

Lua 只能保证 Redis 内部那段扣减没有被穿插，不能自动完成 Redis 与 MySQL 的跨系统事务。

### 5. Redis 发生故障

主从、哨兵或 Cluster 帮助恢复服务，但客户端可能遇到超时与重连。业务应限制回源并发，避免缓存故障扩大为数据库故障。

恢复后可以从持久化记录加载，再逐步预热需要的数据。不要瞬间对所有键发起无限并行重建。

### 6. 请求超时是否代表写入失败

这是补充但很重要：

```text
Redis 已完成 INCR
-> 返回响应时网络中断
-> 客户端看到超时
```

客户端不知道命令是否已执行，直接重试可能重复计数。需要按操作的幂等性设计重试，而不是统一“超时就再来一次”。

同样适用于数据库写入、消息发送与分布式锁：超时是一种结果不确定状态。

## 四十、面试复述版：先讲机制，再讲边界

### 1. Redis 为什么快

Redis 主要在内存中执行数据结构操作，常见按键命令路径短，结合事件驱动与 I/O 多路复用管理大量连接。普通命令的顺序执行减少了核心数据的并发协调开销，但复杂命令、大对象和长脚本仍会导致高延迟。

### 2. Redis 是单线程吗

应明确所指版本和工作阶段。经典模型中普通命令主要由主线程执行，后台线程处理部分耗时工作，Redis 6 还引入网络 I/O 多线程，所以整个进程并不是只有一个线程。

### 3. 五种常见类型怎么选

整体值和计数选 String，字段级对象操作选 Hash，有序两端操作选 List，去重和集合运算选 Set，按分数排序与范围查询选 ZSet。数据规模与操作复杂度决定是否合适。

### 4. ZSet 为什么使用跳表

在跳表编码下，字典负责按成员快速查分数，跳表负责排序、范围与排名。跳表通过多层指针加速定位，沿底层遍历结果，跨度信息帮助计算排名。

### 5. AOF 与 RDB 有什么区别

RDB 保存时点状态，AOF 记录写操作效果。前者通常便于紧凑保存与加载，后者可缩短正常情况下的持久化间隔。实际恢复风险取决于保存是否成功、刷盘策略和故障类型，混合方式用基础状态加增量记录结合两者。

### 6. 为什么 AOF 要重写

历史写入不断增长，而恢复当前状态不一定需要全部历史。重写从当前数据生成新的恢复表示，并保留期间增量。旧版缓冲区方案与 Redis 7 起多部分文件机制需要区分。

### 7. 过期删除与内存淘汰的区别

过期删除处理已到期的键，结合访问时检查和主动清理；内存淘汰处理容量压力，按策略移除候选键，其中可能包括尚未过期的数据。

### 8. LRU 与 LFU 的区别

LRU 侧重最近访问时间，LFU 侧重访问频率。Redis 使用近似实现控制维护成本；LFU 的衰减帮助适应热点变化，不能只累积历史次数。

### 9. 主从、哨兵、Cluster 有什么区别

主从复制保存副本；哨兵监测故障并组织自动切换；Cluster 把数据按槽分片并提供相应故障转移。复制、故障管理、容量扩展是相关但不同的能力。

### 10. 为什么 Redis 锁要唯一标识和 Lua

唯一标识区分每次锁持有者；原子检查标识再删除，避免锁到期后旧持有者误删新锁。加锁要把 NX 和有效期合在一起，续期也应校验持有者；业务安全还要考虑租约失效后的旧客户端。

### 11. 缓存三大问题怎么区分

雪崩是大片缓存失效或缓存服务不可用，击穿是单个热点失效引起并发回源，穿透是反复查询缓存和数据库都不存在的数据。分别针对失效集中、重复重建和不存在请求设计防护。

### 12. 缓存一致性为什么常用先更新数据库再删缓存

它按数据库权威状态推进，再让缓存按需重建，减少并发更新缓存的覆盖问题。但删除失败和旧读延迟回填仍可能导致陈旧值，需要可靠失效、重试、TTL 和适合业务的一致性策略，不能声称天然强一致。

### 13. Redis 事务是否支持回滚

MULTI/EXEC 在执行时不被其他普通命令穿插，但执行阶段错误不会自动回滚已成功命令。WATCH 提供提交前的乐观检查，Lua 可合并读判断写；这些能力都不同于完整的 MySQL 事务体系。

### 14. Stream 如何处理消费者故障

消费组通过 PEL 记录已交付未确认消息，业务成功后 XACK，故障后检查并重新领取待处理消息。重复投递仍需业务幂等，消息本体保留与 Redis 持久化也必须单独考虑。

|---|---|
| Redis 已返回写成功，主节点马上宕机，副本一定有吗？ | 异步复制窗口；本地持久化与副本保留分开分析 |
| 有 5 个哨兵、quorum=2，只剩 2 个活着就能切换吗？ | 判故障门槛不等于获得多数派授权 |
| Pipeline 发 GET、SET，能防止别人插入吗？ | 批量传输本身不提供事务隔离 |
| 锁有 UUID 且用 Lua 解锁，业务就一定互斥吗？ | 只能防误删；锁过期后的旧客户端仍可能写资源 |
| 先更新数据库再删缓存，为什么仍会出现旧值？ | 旧读暂停，更新与删除完成后再回填 |
| 用消息队列重试删除，为什么还要可靠事件产生机制？ | 数据库提交后、消息发送前崩溃的窗口 |
| XACK 之后其他消费组还能读取消息吗？ | ACK 只作用于相应组的 PEL；正文保留另行管理 |
| 一次 SCAN 没返回键，是否已经结束？ | 看游标是否为 0，不能只看返回列表 |
| maxmemory 淘汰键后，下次 GET 会自动读 AOF 吗？ | 不会按键回读；缓存回源由应用处理 |
| INCR 超时后重试，计数一定只加一次吗？ | 首次可能已执行；超时意味着结果不确定 |

### 与 MySQL 知识的最终对应

| 你已学过的 MySQL 内容 | 学 Redis 时可以联系的内容 | 需要保留的区别 |
|---|---|---|
| B+ 树与索引 | 哈希表、跳表、紧凑结构 | 按页与磁盘访问目标不同于内存结构目标 |
| Buffer Pool | Redis 缓存与内存淘汰 | 淘汰数据页副本不等于删除 Redis 键 |
| redo、binlog | AOF、复制流、CDC | 各自的日志层次、格式与职责不同 |
| 事务与回滚 | MULTI/EXEC、WATCH、Lua | 隔离执行不等于失败自动回滚 |
| 行锁与乐观锁 | 分布式锁、条件更新 | Redis 锁依赖参与者协议和租约边界 |
| 主从与复制延迟 | Redis 主从与故障切换 | 复制历史、日志保留与选举机制不同 |
| 并发事务时序 | 缓存读写交错 | 两个系统的更新不天然属于同一事务 |

读完后，你应该能用“数据如何组织、命令如何执行、故障怎样恢复、跨系统如何协调”四条线解释 Redis，再用具体时序指出方案成立的条件。
