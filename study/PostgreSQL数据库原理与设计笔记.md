## 1. 差异总览与统一案例

### 1.1 两套设计的主线

两库都通过索引减少访问工作，通过多版本和锁协调并发，通过预写日志保护延迟写回的数据页。差异主要在于这些职责如何组织，以及某些相同术语实际承诺了什么。

```text
MySQL / InnoDB
聚簇索引承载表数据
  → 二级索引携带聚簇键
  → 旧版本通过 undo 重建
  → RR 快照读与当前读具有不同访问语义
  → redo 与 Server binlog 需要提交协调

PostgreSQL / heap
表记录与索引分别存储
  → 索引通过 TID 定位堆记录
  → UPDATE 通常生成新的堆元组版本
  → VACUUM 管理旧版本、可见性与事务年龄
  → WAL 支撑崩溃恢复和物理复制，并可用于逻辑解码
```

这里的箭头表示机制联系，不表示所有差异都能由单一原因完全推导。具体实现还受优化器、锁协议和版本演进影响。

### 1.2 核心对照表

| 维度 | MySQL / InnoDB | PostgreSQL | 工程影响 |
|---|---|---|---|
| 普通表组织 | 聚簇索引叶子记录承载行 | heap 与索引分开 | 主键是否参与其他索引定位不同 |
| 普通索引定位 | 二级键定位聚簇键，再访问聚簇记录 | 索引键定位堆 TID | PostgreSQL 主键查全行通常也需访问 heap |
| 更新版本 | 聚簇记录与 undo 历史信息协作 | 通常产生新堆元组，旧版本暂留 | 更新、索引维护和清理成本不同 |
| 列覆盖读取 | 二级索引覆盖列，但存在可见性边界 | Index Only Scan 还依赖 visibility map | 列覆盖不等于绝无表数据访问 |
| 默认隔离 | RR | RC | 相同默认事务代码可能观察到不同状态 |
| RR 并发更新 | 可基于当前可更新版本继续更新 | 对快照后被其他事务更新的目标可能报 40001 | 迁移必须设计完整事务重试 |
| 范围保护 | RR 锁定扫描常用 gap / next-key | 普通行锁不采用 InnoDB 式间隙保护 | 查无记录后插入不能照搬锁假设 |
| Serializable | 主要通过更严格的锁定读取协调 | SSI 检测危险读写依赖，可能中止事务 | 阻塞与重试的代价不同 |
| 旧版本维护 | purge、undo 保留 | VACUUM、autovacuum、freeze | 运维指标与清理对象不同 |
| 日志 | undo、redo、Server binlog 分工 | WAL、事务状态、heap 版本协作 | 不能一一对应三类日志 |
| 页写完整性 | doublewrite 等机制 | WAL 中的 full-page image 等机制 | 同样保护不完整页写，实现路径不同 |
| DDL | 多种 DDL 隐式提交 | 多数普通 DDL 可事务回滚 | 发布脚本事务边界不同 |
| 并发建索引 | Online DDL 按算法和锁要求执行 | CREATE INDEX CONCURRENTLY 有专属协议 | 都不是零锁、零扫描操作 |
| SQL 错误后 | 部分错误只回滚失败语句 | 显式事务通常进入失败状态 | 捕获异常后继续执行的逻辑不同 |
| 类型与约束 | 自增、字符集 / collation、JSON 等 | identity、丰富类型、JSONB、可延迟约束等 | 迁移要核对值域和语义 |
| 内存配置 | Buffer Pool 是主要页缓存 | shared_buffers 与 OS 缓存协作，work_mem 按操作使用 | 参数不能按名字直接替换 |

本表是后文索引，不是脱离条件的所有行为清单，也不表示某一数据库在所有负载下更快。

### 1.3 同一订单模型

```sql
CREATE TABLE orders (
    id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id    bigint NOT NULL,
    status     smallint NOT NULL,
    amount     numeric(12,2) NOT NULL,
    created_at timestamp(6) without time zone NOT NULL,
    remark     text,
    CHECK (user_id >= 0),
    CHECK (status BETWEEN 0 AND 255)
);

CREATE INDEX idx_user ON orders(user_id);
```

`created_at` 在这个对照案例中对应 MySQL 笔记的 DATETIME 本地时间字段。若业务要求跨时区的绝对时刻，应评估 `timestamptz`，而不是将所有 DATETIME 一律机械替换。

PostgreSQL 没有直接对应 MySQL BIGINT UNSIGNED 的内置 unsigned bigint。上面的 bigint 加 CHECK 只能覆盖非负的有符号 bigint 范围，不能表达 MySQL unsigned bigint 的完整上界。真实迁移必须检查数据值域。

统一列表查询为：

```sql
SELECT id, amount, created_at
FROM orders
WHERE user_id=42 AND status=1
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

正文中的 `:qty`、`:cursor_time` 等表示应用绑定参数。A、B 表示独立会话；各候选索引用于比较，不表示同时创建全部候选。并发模型中的 accounts、on_call 等表是独立的最小示意模型。

## 2. 架构与对象边界

### 2.1 会话进程与共享状态

PostgreSQL 使用客户端 / 服务器架构，常规客户端连接由独立 backend 进程服务，多个 backend 通过共享内存、锁系统和持久文件访问同一份数据库状态。系统还包含 WAL writer、checkpointer、background writer 和 autovacuum 等后台角色。[官方架构说明](https://www.postgresql.org/docs/18/tutorial-arch.html)

MySQL 常规连接通常由服务器进程中的线程处理。进程与线程模型会影响连接资源和调度，但不能据此直接判定查询性能优劣。两库都需要限制无效并发，连接数也不等于能够同时高效执行的查询数。

```text
应用 / 驱动 / 连接池
         │
         ▼
会话 backend：解析 → 重写 → 优化 → 执行
         │
         ├─ shared_buffers / 锁与事务状态
         ├─ heap / index / TOAST
         └─ WAL 与后台维护
```

PostgreSQL 存在表和索引访问方法及扩展接口，但本文不将其描述为与 MySQL Server / InnoDB 完全相同的分层。普通 PostgreSQL 事务恢复也不存在必须与一份独立 Server binlog 协调的同构路径。

### 2.2 cluster、database 与 schema

PostgreSQL 中 database cluster 通常指一套数据目录和实例管理的数据库集合，并不必然表示多机器高可用集群。一个 database 内还可以包含多个 schema；schema 再包含表、函数、类型等对象。

```text
实例 / database cluster
  ├─ database A
  │    ├─ schema app：orders、accounts
  │    └─ schema archive：orders_history
  └─ database B
       └─ schema public：其他对象
```

MySQL 中 DATABASE 和 SCHEMA 通常是同义词，同实例中常用 `database.table` 引用；PostgreSQL 的普通连接绑定一个 database，`schema.table` 指的是其内部命名空间，不是另一个 database。[官方 schema](https://www.postgresql.org/docs/18/ddl-schemas.html)

跨 PostgreSQL database 访问通常需要独立连接或 FDW 等机制。`search_path` 决定未限定名称如何解析，连接池复用和多租户场景应明确它的会话状态；长期维护的 SQL 可使用适当限定名减少对象歧义。

### 2.3 扩展能力与边界

扩展可以增加数据类型、函数、操作符和索引能力。扩展是否已安装、版本是否兼容、迁移环境是否允许使用，会影响备份与部署。支持扩展不等于任何新类型天然拥有合适索引，仍需要访问方法与操作符类配合。[官方 CREATE EXTENSION](https://www.postgresql.org/docs/18/sql-createextension.html)

## 3. 堆存储与主键索引

### 3.1 heap 不按主键持续组织行

PostgreSQL 默认 heap 表将元组放到具备可用空间的页中。默认页大小通常为 8KB，编译时可选择不同大小；不能把它当作可像普通会话参数一样任意调整的配置。[官方页布局](https://www.postgresql.org/docs/18/storage-page-layout.html)

这里的 heap 指存储组织，不是优先队列数据结构。主键保证唯一和非空，通常通过唯一 B-tree 索引实现，但不把 heap 转化为主键聚簇树。

```text
PostgreSQL
主键索引：id → TID ───────────┐
用户索引：user_id → TID ──────┤
                             ▼
                        heap 页中的元组

InnoDB
用户二级索引：user_id → id
                         │
                         ▼
                主键聚簇树中的行记录
```

因此 PostgreSQL 按主键读取完整行，通常也要先访问主键索引，再访问 heap；按其他索引查行则直接由该索引定位 heap，不需要再经过主键树。

### 3.2 TID 与 ctid

TID 由页号和页内条目标识组成，定位一个物理元组版本。页内条目标识可以在元组内容移动时维持引用关系，但 UPDATE 或表重写可能改变某行当前版本的 ctid。

SQL 可查看系统列 `ctid`，但它不应作为稳定业务身份。主键标识逻辑行，ctid 标识物理版本，两者生命周期不同。[官方系统列](https://www.postgresql.org/docs/18/ddl-system-columns.html)

### 3.3 主键宽度的成本变化

InnoDB 的二级索引通常携带聚簇键，所以主键加宽会放大多个二级索引。PostgreSQL 普通索引主要携带自己的键和 TID，并不会默认附带业务主键。因此宽主键的空间放大路径不同。

宽键仍会增加 PostgreSQL 主键索引本身的尺寸、比较成本及外键列成本；随机键插入也仍可能降低该索引的局部性。不能由“其他索引不携带主键”推导出随机 UUID 没有成本。

PostgreSQL UUID 类型可紧凑表达 UUID，比将所有 UUID 表示为长文本更直接。是否选择递增、随机或带时间顺序的标识，仍需要结合生成方式、访问分布和索引热点。

### 3.4 CLUSTER 是一次性重排

`CLUSTER table USING index` 可按指定索引重排表，改善当时的物理局部性。但后续插入和更新不会持续维持这种排序，操作本身还涉及表重写和强锁。[官方 CLUSTER](https://www.postgresql.org/docs/18/sql-cluster.html)

因此 CLUSTER 不是将 PostgreSQL 表转换为 InnoDB 式永久聚簇索引。重排收益需要与维护成本比较，查询结果顺序仍必须通过 ORDER BY 表达。

## 4. 元组版本与大字段

### 4.1 更新通常产生新元组

PostgreSQL 的普通 UPDATE 通常生成新的 heap 元组，旧版本保留到不再被快照需要时。逻辑上同一行可能暂时对应多个物理版本。

```text
旧元组：balance=100，创建者 xmin=A
    │ 更新后旧版本的结束状态与新版本建立关联
    ▼
新元组：balance=200，创建者 xmin=B
```

`xmin` 描述创建版本的事务；`xmax` 与删除、更新或行锁等状态有关，可能还涉及 MultiXact。不能仅凭 `xmax!=0` 判断该元组已经被成功删除。

可见性还需要事务提交 / 中止状态、快照活跃集合和当前事务命令顺序，不是只比较两个数字。[官方多版本并发简介](https://www.postgresql.org/docs/18/mvcc-intro.html)

### 4.2 回滚不沿用 InnoDB 的 undo 版本链模型

若创建新元组的事务中止，该版本不会成为其他事务的有效提交版本；原先有效的旧版本仍可以保留其可见性。后续清理回收无效或不再需要的元组。

PostgreSQL 默认 heap 不采用 InnoDB 式的“当前聚簇记录加 undo 历史重建”组织。这不表示不存在恢复日志、事务状态或子事务，也不表示回滚完全没有工作，只表示不能把 InnoDB 的 roll pointer、purge 和 undo 表空间原样套用。

由此形成不同的空间压力：InnoDB 需要关注 undo 历史保留；PostgreSQL 需要关注 heap 和 index 中的旧版本、死元组及后续清理。

### 4.3 TOAST 对长值压缩或外置

heap 元组不能简单跨页无限延伸。对于支持 TOAST 的变长类型，PostgreSQL 可以压缩或把长值拆分到关联的 TOAST 存储中，heap 中保留相应引用。[官方 TOAST](https://www.postgresql.org/docs/18/storage-toast.html)

TOAST 与 InnoDB 页外存储都用于降低本地记录大小，但布局、压缩和访问方式不同。能够存储较长 text 或 JSONB，不代表频繁访问、更新这些值没有成本。

订单列表不读取 remark 时，通常可避免为返回该字段而展开长值。频繁读取整个 JSONB 或 text 仍可能引入额外页访问和解压；频繁修改大型对象也需要评估新版本和日志体积。

### 4.4 text 与 varchar

`varchar(n)` 是长度约束，`text` 不要求声明相同的长度上限。在 PostgreSQL 中，text 与 varchar 的常规存储和访问特性相近，不应默认认为声明一个很大的 varchar 比 text 更高效。[官方字符类型](https://www.postgresql.org/docs/18/datatype-character.html)

字段是否需要最大长度应首先由业务约束决定。MySQL 的行定义大小模型与 PostgreSQL TOAST 模型不同，不能直接沿用“65535 字节一行”的推导。

## 5. 索引设计与列覆盖

### 5.1 联合 B-tree 的共同基础

两库普通 B-tree 多列索引都按键元组建立顺序。等值前缀有利于限定范围，剩余列可能用于范围、过滤或顺序输出；SQL 中条件书写顺序通常不改变等价的索引机会。

PostgreSQL 18 的 B-tree 支持 skip scan 优化，在满足成本条件时，可以为缺少前导列的查询重复定位不同前导值；前导列不同值少时更可能有收益。这个能力不能不加版本说明地套到 PostgreSQL 17，也不取消元组排序的基础约束。[官方多列索引](https://www.postgresql.org/docs/18/indexes-multicolumn.html)

### 5.2 同一订单查询的候选索引

候选 A：

```sql
CREATE INDEX idx_feed
ON orders(user_id, status, created_at DESC, id DESC);
```

固定用户和状态后，索引可提供所需顺序，具备提早返回 20 行的条件。实际是否使用仍取决于成本估算。

候选 B：

```sql
CREATE INDEX idx_feed_cover
ON orders(user_id, status, created_at DESC, id DESC)
INCLUDE (amount);
```

INCLUDE 列作为载荷供读取，不作为这棵索引的搜索和排序键。与将 amount 直接追加到键列的 MySQL 覆盖候选相比，PostgreSQL 可明确区分键与载荷；若使用 UNIQUE INDEX，唯一性也只针对键列。[官方 INCLUDE 语义](https://www.postgresql.org/docs/18/sql-createindex.html)

被查询的 id 不会因为它是主键就自动出现在 `idx_user(user_id)` 中。若要覆盖 id，需显式将它加入键或 INCLUDE；这是从 InnoDB 迁移索引时容易遗漏的条件。

### 5.3 Index Only Scan 仍需证明可见性

普通索引记录未保存 heap 元组的全部事务可见性信息。查询列都在索引里，只解决“值从哪里取”，没有解决“该版本是否可见”。

PostgreSQL 使用 visibility map 记录 heap 页的 all-visible 等状态。如果相关页已确认全部元组对适用事务可见，Index Only Scan 可以跳过 heap 访问；否则仍需访问 heap 检查。计划中的 `Heap Fetches` 用于观察这种额外访问。[官方 Index Only Scan](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)

```text
索引能提供查询值
    → 检查对应 heap 页的 visibility map
        → all-visible：可避免本次 heap 可见性访问
        → 否则：访问 heap 验证版本
```

写入会使相关可见性标志失效，VACUUM 可在条件满足时重新标记。因而一张频繁更新的表即使有覆盖索引，也未必达到很低的 Heap Fetches。

### 5.4 维护状态参与查询性能

visibility map 同时包含 all-visible 和 all-frozen 信息，二者用途不同：前者支持跳过可见性验证等工作，后者用于事务冻结管理。[官方 visibility map](https://www.postgresql.org/docs/18/storage-vm.html)

InnoDB 覆盖访问也存在某些 MVCC 条件下访问聚簇记录的边界，但不是通过同一套 PostgreSQL visibility map 管理。因此两库都不应将“覆盖”直接当作运行时的绝对零表访问承诺。

## 6. 部分索引与多种访问方法

### 6.1 部分索引只覆盖满足谓词的记录

若订单查询长期固定为 status=1，而这一状态只占全表很小一部分，可评估：

```sql
CREATE INDEX idx_pending_feed
ON orders(user_id, created_at DESC, id DESC)
INCLUDE (amount)
WHERE status=1;
```

这个索引不为所有订单建立相同条目，因此可能降低体积和对不相关记录的维护工作。代价是状态进出该集合时需要变更索引，且查询必须能够让优化器证明条件蕴含索引谓词。[官方部分索引](https://www.postgresql.org/docs/18/indexes-partial.html)

使用 generic plan 的参数化条件 `status=$1` 不一定能够证明始终满足 `status=1`；custom plan 是否能利用具体参数要看实际规划。语义相似但优化器无法证明的表达式，也不保证可用。

MySQL 没有 PostgreSQL 这种通用的 `CREATE INDEX ... WHERE ...` 机制。通过生成列等方案表达某些业务集合时，索引内容、约束和优化路径也不等价，不能直接迁移同一条 DDL。

### 6.2 表达式索引改变被索引对象

```sql
CREATE INDEX idx_users_lower_email ON users(lower(email));
```

这个索引按 lower(email) 的结果组织，而不是按原始 email。查询表达式需要与索引定义匹配；用于索引的函数还需要满足相应不可变性要求。写入时也要计算表达式并维护条目。[官方表达式索引](https://www.postgresql.org/docs/18/indexes-expressional.html)

MySQL 8 支持函数索引或生成列相关能力，因此“PostgreSQL 能给表达式建索引而 MySQL 完全不能”不准确。差异应比较具体支持范围、语法、类型与优化器匹配。

### 6.3 不同索引回答不同查询

| 方法 | 适用关系 | 主要取舍 |
|---|---|---|
| B-tree | 等值、范围、有序读取 | 常规结构化查询的主要选择 |
| Hash | 等值 | 不提供一般范围和顺序能力，不因名字就必然更快 |
| GIN | 一个值包含多个可检索元素 | 适合某些 JSONB、数组、全文场景，维护可能较重 |
| GiST | 由操作符类定义的搜索结构 | 常用于范围、空间和相似关系，能力取决于操作符类 |
| SP-GiST | 适合特定分区搜索结构 | 适用数据类型和操作符需要对应支持 |
| BRIN | 对物理页范围做摘要 | 体积较小，依赖数据与物理位置相关性，候选需重检 |

索引方法不是类型标签，而是不同访问协议。例如时间顺序追加的日志可用 BRIN 摘要跳过大量无关块，但若时间在物理位置上高度混杂，摘要筛选效果会下降。[官方索引类型](https://www.postgresql.org/docs/18/indexes-types.html)

MySQL 也有全文、空间和部分 JSON 索引能力，不能将差异概括为“一方有非 B-tree 索引，另一方没有”。应比较需要查询的操作是否被对应结构直接支持。

## 7. 更新成本与 HOT

### 7.1 新版本定位会影响索引维护

普通 UPDATE 产生新的 heap 位置后，如果索引仍只指向旧位置，就需要安排新版本的可达路径。对于非 HOT 更新，即使某索引键值没有改变，通常也可能需要为新元组维护索引条目。

因此 PostgreSQL 的索引写入成本不只来自“索引列是否变化”。新版本的物理位置、HOT 条件及清理都需要纳入分析。

### 7.2 HOT 让同页版本链减少索引更新

Heap-Only Tuple 更新主要在两类条件满足时可用：相关被索引的列没有发生不允许的变化，且新版本能放在同一个 heap 页中。索引可以继续通过既有入口到达页内的版本链，减少新增索引条目的需求。[官方 HOT](https://www.postgresql.org/docs/18/storage-hot.html)

```text
索引入口 → heap 页内旧入口 → 新元组 → 更新后的元组
                     同页 HOT 链
```

表达式索引、部分索引谓词和 INCLUDE 列也可能影响 HOT 条件。对 BRIN 等 summarizing index 的现代版本规则存在例外，不能把所有索引方法都压缩成“任意被索引列变化必然禁止 HOT”。

### 7.3 覆盖索引可能增加更新成本

在订单覆盖候选 B 中，amount 被 INCLUDE。金额更新可能因此不再符合原先的 HOT 条件，即使 amount 不是搜索键。

这形成一个直接的取舍：减少查询 heap 访问，可能增加更新索引成本；如果表频繁更新，visibility map 又经常失效，覆盖收益还可能低于静态表。设计时应同时比较读取比例、HOT 比例、WAL、索引体积和维护压力。

InnoDB 同样会在 amount 被索引后增加索引维护，但代价来源是其聚簇 / 二级索引与 undo 机制，不能直接用 HOT 比例解释。

### 7.4 fillfactor 留出页内更新空间

为表设置适当 fillfactor，可使初次填充留下部分空间，提高后续同页更新机会。它会增加同样记录数量所需的页数，可能扩大缓存工作集，并不是无成本的写优化。

设置参数本身也不表示既有满页立即重排。收益需要结合真实更新分布和后续物理布局观察，而不是统一为所有表设定一个固定比例。

## 8. 查询执行与执行计划

### 8.1 常见扫描方式

| 节点 | 工作方式 | 判读重点 |
|---|---|---|
| Seq Scan | 扫描 heap | 候选量大或表小，可能合理 |
| Index Scan | 按索引逐条定位并访问 heap | 顺序、随机访问和候选量 |
| Index Only Scan | 从索引取值，必要时验证 heap | 列覆盖、Heap Fetches、可见性维护 |
| Bitmap Index Scan | 建立候选位置位图 | 可合并多个条件，不直接返回完整行 |
| Bitmap Heap Scan | 按 heap 页访问候选 | 降低分散访问，可能需 Recheck |

Bitmap 路径通常不维持原索引的输出顺序，因此有 ORDER BY 时可能仍需排序。内存不足等条件下，位图可以变成页级 lossy 信息，需要重新判断候选元组，不能把全部位图命中都当作精确匹配。

### 8.2 实际执行计划

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, created_at
FROM orders
WHERE user_id=42 AND status=1
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

ANALYZE 会执行语句，BUFFERS 展示缓存块访问；cost 是优化器成本单位，不是毫秒。actual time、rows、loops 用于判断实际工作。节点重复运行时，行数和时间常按循环平均报告，不能忽略 loops，也不能简单累加包含子节点的所有时间。[官方 EXPLAIN 阅读](https://www.postgresql.org/docs/18/using-explain.html)

PostgreSQL 可以对 UPDATE 等 DML 使用 EXPLAIN ANALYZE，修改会真实发生。即使安排事务回滚，序列取值、外部函数副作用和资源消耗等也未必全部撤销，不能将它作为任意生产语句的无副作用检查。

### 8.3 BUFFERS 不等于磁盘读次数

`shared hit` 表示在 shared_buffers 命中；`shared read` 表示需要将块读入该缓存，但操作系统缓存可能已拥有内容，因此不一定实际访问存储设备。temp read / written 则是临时工作文件的访问线索。

InnoDB 的 Buffer Pool 未命中也不能脱离 I/O 方式和系统缓存做简单推论。两库计划中的缓存字段应按各自实现解释，不按名称逐个替换。

### 8.4 连接与统计信息

Nested Loop 的代价需要计算内层重复次数；Hash Join 需要关注输入和哈希容量；Merge Join 需要适合的有序输入。算法名称不表示固定优劣。

ANALYZE 收集近似分布，CREATE STATISTICS 可为相关列建立扩展统计。例如用户与状态高度相关时，独立选择率可能失真，扩展统计在支持的估算场景中有助于改善计划。[官方规划统计](https://www.postgresql.org/docs/18/planner-stats.html)

扩展统计不是所有 JOIN 估算的万能修复。统计收集、可用场景和真实参数仍需核对。 prepared statement 的 generic / custom plan 差异也可能使相同语句在不同参数下表现不同。

## 9. VACUUM 与事务年龄

### 9.1 多版本把清理变成持续工作

更新、删除、中止事务都可能留下不再需要的元组。保留这些对象是多版本并发的代价；可回收时间又受到仍在使用的快照影响。

普通 VACUUM 在条件允许时回收死元组空间、处理索引清理、更新 visibility map，并推进冻结等维护。页内 pruning 也可以在普通访问中清理某些版本，因此不是所有清理都只能等待一次 VACUUM。[官方日常 VACUUM](https://www.postgresql.org/docs/18/routine-vacuuming.html)

ANALYZE 负责统计信息收集，与 VACUUM 的旧版本回收职责不同。两者可以组合执行，但“查询计划估算变准”和“死元组被清理”不是同一件事。

### 9.2 空间复用与文件缩小

```text
旧版本不再被快照需要
  → 清理相关版本与索引入口
  → 空间可供后续写入复用
  → 文件不必立即缩小
```

普通 VACUUM 通常以内部复用为主要目标，某些尾部空页满足条件时可截断。VACUUM FULL 则重写表，返还更多空间，但需要更强的锁和额外空间。[官方 VACUUM](https://www.postgresql.org/docs/18/sql-vacuum.html)

InnoDB DELETE 后空间也不必立即返还给操作系统，但 PostgreSQL 的表膨胀、索引膨胀和重写机制应分别评估。频繁 VACUUM FULL 不是代替正常 autovacuum 的常规策略。

### 9.3 autovacuum 的触发与进度

autovacuum 根据表的活动和阈值安排清理与统计工作，还承担防止事务 ID 过老的必要维护。大表如果仅采用统一比例阈值，可能积累很多死元组才触发；高更新表应按真实负载评估表级设置。[官方 vacuum 参数](https://www.postgresql.org/docs/18/runtime-config-vacuum.html)

清理执行速度受工作进程、I/O、成本限制和并发访问影响。触发不足与执行跟不上是两类问题；有长快照时，即使更快执行，也不能回收仍合法需要的版本。

### 9.4 长事务与副本反馈

长事务尤其是持有旧快照的事务，可能推迟回收。`idle in transaction` 连接虽然没有正在运行 SQL，仍可能持锁或保留事务状态。

物理备库如果启用 hot_standby_feedback，可向主库反馈快照需求，减轻备库查询与主库清理冲突，但可能让主库保留更多旧版本。复制槽也可能影响 WAL 或特定事务保留边界，需结合槽类型与状态分析。

InnoDB 对应关注长 Read View、purge 和 history list；PostgreSQL 对应关注事务 xmin、死元组、autovacuum、槽与备库反馈。相同的“长事务问题”需要不同证据。

### 9.5 freeze 处理事务标识循环

PostgreSQL 元组事务字段使用需要按循环语义解释的事务标识，不能永远把很老的 xmin 当作普通有序整数比较。冻结使足够老且已提交的创建事务不再依赖常规 XID 年龄判断，避免回绕破坏可见性语义。[官方事务标识](https://www.postgresql.org/docs/18/transaction-id.html)

即使表几乎只插入、不删除，也可能需要冻结维护。接近危险年龄时，系统必须安排反回绕维护，并可能限制写入以保护数据正确性。这个维护目标与单纯减少死元组不同。

因此 PostgreSQL 运维不能只监控表大小和 QPS，还需要事务年龄、冻结进度和长期阻碍清理的会话。该问题不能直接用 InnoDB 的 undo 体积指标替代。

## 10. 快照与隔离级别

### 10.1 默认级别的差异

PostgreSQL 默认 RC，MySQL InnoDB 默认 RR。PostgreSQL 请求 RU 时，行为按 RC 处理；RR 采用快照隔离，Serializable 在快照基础上增加可串行化依赖检测。

| 隔离行为 | PostgreSQL | MySQL / InnoDB |
|---|---|---|
| 默认普通读取 | RC，语句级快照 | RR，显式事务通常复用首次一致性读视图 |
| RU | 与 RC 相同 | 允许更弱的可见性，可能脏读 |
| RR 普通读取 | 使用稳定事务快照 | 使用稳定 Read View，加自身修改可见性 |
| RR 更新冲突 | 可能因快照后并发更新而报错 | 常可等待并基于可更新当前版本继续 |
| Serializable | SSI 与事务中止 / 重试 | 更严格的锁定行为 |

隔离级别是行为契约，不是同名实现保证。驱动和框架即使提供同名枚举，迁移后仍需核对读写结果。[官方隔离行为](https://www.postgresql.org/docs/18/transaction-iso.html)

### 10.2 RC 的语句快照

普通 SELECT 看到语句开始前已提交、对该快照可见的记录，以及当前事务此前的相关修改。两次 SELECT 之间其他事务提交，第二次可以看到变化。

```text
A：BEGIN
A：SELECT balance → 100
B：UPDATE balance=200；COMMIT
A：SELECT balance → 200       PostgreSQL 默认 RC
```

相同时序在 InnoDB 默认 RR 的显式事务中，第二次普通一致性读通常仍得到 100。若业务原本依赖默认级别维持跨语句稳定读取，迁移后需要显式选择相应策略。

RC 也不等于一条复杂更新对所有相关行都使用同一份全局最新状态。碰到目标行并发修改后，PostgreSQL 会等待，并可能重新判断更新后行是否满足 WHERE；其余候选仍来自语句快照，复杂关联条件需要单独推演。

### 10.3 RR 的快照时间

RR 的事务快照在首次非事务控制语句建立相应快照时确定，不是仅执行 BEGIN 就保证已有快照。后续读取复用该视图，并看到自身修改。

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id=1;
```

没有进行这次读取前，B 已提交的状态可以进入 A 后来建立的快照。这与 InnoDB 常见的 BEGIN 与首次一致性读之间的区别类似，但后续写入冲突处理显著不同。

### 10.4 MVCC 可见性与物理新版本

快照记录事务边界和活跃集合，再结合每个元组版本的事务状态决定可见性。较小事务 ID 不必先提交；中止事务创建的新版本也不能成为其他会话的合法提交版本。

InnoDB 在当前聚簇记录不可见时可沿 undo 重建旧版本；PostgreSQL 通常在 heap 中保留不同元组版本并配合索引和版本关系访问。两者都使用多版本，但访问对象和清理路径不同。

## 11. 同一并发程序的不同结果

### 11.1 RR 下的余额增量

初始余额为 100；A、B 使用不同连接。A 为 RR，B 更新后提交。两库采用相同的业务时序：

| 步骤 | A | B |
|---|---|---|
| 1 | 开始 RR 事务，普通读取得到 100 | — |
| 2 | — | 将余额改为 200 并提交 |
| 3 | 再次普通读取 | — |
| 4 | `UPDATE accounts SET balance=balance+10 WHERE id=1` | — |

步骤 3 在两库通常都保持旧值 100。步骤 4 的预期不同：InnoDB 可基于当前可更新状态计算出 210；PostgreSQL RR 对快照后已被另一事务实际更新的目标，预期报 `could not serialize access due to concurrent update`，SQLSTATE 为 40001。

PostgreSQL 需要结束失败事务，从新快照重新读取并重做完整操作，不能在同一失败事务里只重复那条 UPDATE。若 A 使用 PostgreSQL RC，在满足该简单单行场景条件时，可基于 B 已提交版本进行增量更新。

这个案例表明：将 InnoDB 的“普通读取看旧值，UPDATE 继续读取当前值”当成 PostgreSQL RR 的通用模型，会直接导致错误处理缺失。

### 11.2 读出后写常量

```text
A 读取余额 100，应用计算出 110
B 将余额更新为 200 并提交
A 写入常量 110
```

在 RC 下，PostgreSQL 和 InnoDB 都不能仅凭普通读取自动识别“110 是按旧值算出来的业务结果”。UPDATE 写常量与数据库内 `balance=balance+10` 的语义不同。

PostgreSQL RR 的相关并发更新检测可以中止这一给定时序，但不能将它宣传为所有业务丢失更新的完整方案。版本列、条件更新和明确加锁适用于需要表达业务冲突的场景。

### 11.3 RR 的写偏差

两个值班人员都在岗，规则要求至少一人值班。A、B 先读取两人状态，再各自更新自己的那行。

```text
A 快照：两人都值班 → 更新人员 1 为离岗
B 快照：两人都值班 → 更新人员 2 为离岗
```

两库 RR 都可能允许这种跨行写偏差：写入不同记录，稳定快照并没有把共同业务规则变成同一冲突点。PostgreSQL RR 防止了给定的同目标并发更新，并不意味着它等价于 Serializable。

可采用共同控制行、按统一顺序锁定完整相关集合，或为所有参与该规则的事务采用 Serializable 并处理重试。单独锁住最终修改行并不足够。

### 11.4 Serializable 的 SSI

Serializable Snapshot Isolation 记录读写依赖，识别可能破坏可串行化的危险结构，并中止相关事务。谓词读的跟踪可以包含读到的记录，也可以覆盖“读取时没有符合记录”的条件影响。

PostgreSQL 的 SIReadLock 用于依赖检测，本身不以 InnoDB gap lock 的方式阻止插入，也不因此参与普通锁等待死锁。检测可能保守，因此 40001 不表示应用已经真正提交了错误状态，而表示数据库拒绝了不安全的并发组合。[实现者论文：Serializable Snapshot Isolation in PostgreSQL](https://arxiv.org/abs/1208.4179)

对值班案例，若所有相关事务采用 Serializable，系统通过中止至少一个不安全事务，使成功提交的组合符合某种串行顺序。事务程序需重新读取状态并重新判断能否离岗。

MySQL Serializable 主要用更严格的锁协调读取与写入，可能先阻塞冲突操作。两库都追求提交效果可串行化，不是一次只允许执行一个事务，但阻塞、内存跟踪和重试代价不同。

### 11.5 重试是完整事务边界

```text
有限重试循环
  → 新事务与新快照
  → 重新读取决策状态
  → 重新计算并执行全部相关写入
  → 提交成功才返回最终结果

遇到可重试并发失败
  → 回滚 / 清理事务
  → 有限退避与抖动
  → 从新的事务重新开始
```

提交成功但客户端未收到响应，是结果不确定问题；40001 是可识别的并发失败。两者不能使用同一种“盲目再执行”策略。涉及外部付款或消息时，幂等与结果查询仍是必要设计。

## 12. 行锁与不存在的记录

### 12.1 行锁模式与外键协作

PostgreSQL 提供 FOR UPDATE、FOR NO KEY UPDATE、FOR SHARE 和 FOR KEY SHARE 等行锁模式。

| 模式 | 主要意图 | 典型取舍 |
|---|---|---|
| FOR UPDATE | 强排他行保护 | 与其他冲突行锁竞争 |
| FOR NO KEY UPDATE | 允许比强排他更弱的非关键键更新保护 | 可与 KEY SHARE 兼容 |
| FOR SHARE | 共享保护读取状态 | 阻止相关更新 / 删除 |
| FOR KEY SHARE | 保护引用键的稳定性 | 可允许某些非键字段更新 |

行锁模式差异使外键引用和非关键字段更新有机会避免不必要互斥，但具体键列识别仍以实现规则为准。[官方显式锁](https://www.postgresql.org/docs/18/explicit-locking.html)

记录锁不替代结构协调。SELECT 和 UPDATE 还会持有相应 relation 锁；名称中的 RowExclusiveLock 实际是一种表级锁模式，不表示已经排他锁住全部行，也不是一条具体记录的锁名称。

### 12.2 查无记录时不会产生 InnoDB 式间隙保护

假设主键为 10、20、30，A 在 PostgreSQL RR 事务中执行：

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM lock_demo WHERE id=15 FOR UPDATE;
```

没有找到匹配元组，因此不存在该位置上的可锁行。仅由这个操作不会建立 InnoDB RR 对 `(10,20)` 的 gap lock。B 在没有其他冲突的条件下，可以插入 15 并提交。

| 后续操作 | PostgreSQL RR | InnoDB RR |
|---|---|---|
| B 插入缺失的 id=15 | 不因 A 的上述行锁搜索被间隙锁阻塞 | 通常被对应间隙保护阻塞 |
| A 再次普通读取 id=15 | 仍可因快照而看不到 B 新插入的行 | B 尚被阻塞时也看不到插入结果 |
| A 尝试插入同一唯一键 | 需由唯一性机制裁决，可能报冲突 | 与锁等待及唯一性检查共同决定 |

PostgreSQL RR 的稳定读取阻止的是快照集合变化，不是禁止别人向范围内插入。可见性保证与物理写入保护必须分开。

### 12.3 缺失位置与业务不变量

“先查不存在，再插入”若用于去重，首选明确的非空唯一约束，并使用合适的冲突处理。若用于保护“某用户的活动预约不能超过 N 个”等跨行规则，单独唯一某条预约也不够。

可锁定一条始终存在的用户或额度控制记录，使所有修改按同一个协议串行判断；也可选择事务级 advisory lock 或 Serializable。advisory lock 只有所有相关写入都遵守时才有效，数据库不会从业务键自动强制参加该协议。

```sql
BEGIN;
SELECT pg_advisory_xact_lock(:business_lock_key);
-- 在同一事务中重新查询并校验业务状态，再执行变更。
COMMIT;
```

锁键的生成和作用域需要明确，避免碰撞或不同代码使用不同键。事务级锁随事务结束释放，比会话锁更便于与事务边界绑定。[官方 advisory lock 函数](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)

### 12.4 NOWAIT 与 SKIP LOCKED

NOWAIT 使不能立即获取的相关行锁请求报错；SKIP LOCKED 跳过锁定的候选，常用于任务领取。它们不消除 relation 锁及所有其他等待来源。

```sql
BEGIN;
SELECT id FROM job_queue
WHERE state=0
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- 在事务内标记领取者和租约，然后提交；长时间工作在提交后进行。
COMMIT;
```

两库都可以实现这种领取模式，但结果会跳过部分候选，不是完整一致业务集合。失败重领、租约和执行幂等仍需设计。[官方 SELECT 锁定子句](https://www.postgresql.org/docs/18/sql-select.html)

### 12.5 观察行锁不能直接照搬 data_locks

PostgreSQL 的持有行锁信息通常主要体现在元组状态中，不保证在 pg_locks 中逐行完整列出。行锁等待常以等待另一事务 ID 的锁表现，因此看不到很多 tuple 行不等于没有行冲突。

`pg_blocking_pids(pid)` 适合识别阻塞关系，再结合 pg_stat_activity 和 pg_locks 解释对象与等待类型。简单自连接 pg_locks 不易完整处理兼容模式和等待队列。[官方 pg_locks](https://www.postgresql.org/docs/18/view-pg-locks.html)

## 13. 错误处理与写入协议

### 13.1 显式事务中的错误状态

PostgreSQL 显式事务中普通 SQL 错误通常使事务进入失败状态。捕获客户端异常后继续发普通 SQL，可能得到 `current transaction is aborted`；需要回滚整个事务，或回滚到事先建立的有效 savepoint。[官方事务控制](https://www.postgresql.org/docs/18/tutorial-transactions.html)

```text
BEGIN
  → 成功语句
  → 失败语句
  → 普通后续语句被失败事务状态拒绝
  → ROLLBACK 或 ROLLBACK TO SAVEPOINT
```

MySQL InnoDB 某些错误只回滚失败语句，剩余事务可以保留；死锁又通常回滚整个事务。因此不能将两库异常处理都写成“捕获后无条件继续”。

驱动默认 autocommit 也可能不同，某些 PostgreSQL 驱动会自动开启事务。应用应检查实际连接状态，避免以为只做了几次查询、实际上却保留着长事务。

### 13.2 savepoint 的用途与限制

```sql
BEGIN;
SAVEPOINT optional_step;
-- 执行可能失败且允许局部放弃的数据库步骤。
-- 若该步骤失败，应用发送下面的回退语句：
ROLLBACK TO SAVEPOINT optional_step;
-- 事务恢复到该保存点的可继续状态。
COMMIT;
```

savepoint 用于表达局部回退语义，不是自动忽略所有错误。并发序列化失败通常需要从完整事务重新读取决策状态；外部副作用也不由 savepoint 撤销。[官方 ROLLBACK TO](https://www.postgresql.org/docs/18/sql-rollback-to.html)

### 13.3 SQLSTATE 比错误文字稳定

| PostgreSQL 状态码 | 含义 | 处理方向 |
|---|---|---|
| 40001 | serialization_failure | 适用时完整事务重试 |
| 40P01 | deadlock_detected | 回滚并有限重试，分析等待环 |
| 23505 | unique_violation | 根据明确约束区分重复请求和业务冲突 |
| 55P03 | lock_not_available | 分析 NOWAIT、锁等待限制等条件 |
| 25P02 | in_failed_sql_transaction | 清理已有失败事务，定位最初错误 |
| 57014 | query_canceled | 分析超时、取消及调用方策略 |

不同驱动映射到的异常类型可能不同，SQLSTATE 是较稳定的分类依据。不能把 25P02 当成首个业务失败，它往往只是前一错误未清理的后果。[官方错误码](https://www.postgresql.org/docs/18/errcodes-appendix.html)

### 13.4 ON CONFLICT 明确冲突身份

```sql
INSERT INTO biz_request(request_id, payload_hash, state)
VALUES (:request_id, :payload_hash, 'processing')
ON CONFLICT (request_id) DO NOTHING
RETURNING request_id;
```

预期的冲突目标需要有适用唯一约束或唯一索引。未返回行表示这次没有成功插入请求记录，不代表业务已完成，也不代表旧请求的参数一定相同。

完整协议应读取旧记录并核对参数和状态，将请求身份与业务效果置于正确事务边界。RC 下，DO NOTHING 可以因另一事务的结果没有插入，而该冲突行未必对本语句快照可见；随后的新语句可以使用新快照读取，RR 则需要考虑稳定快照和冲突错误。[官方 INSERT 冲突处理](https://www.postgresql.org/docs/18/sql-insert.html)

MySQL 的 ON DUPLICATE KEY UPDATE 按发生的唯一冲突进入更新，表达方式不同。拥有多个唯一条件时，迁移应明确期望的冲突身份；MERGE 也不能简单视为具有完全相同并发保证的 UPSERT。

### 13.5 RETURNING 与原子修改

```sql
UPDATE product
SET stock=stock-:qty
WHERE id=:product_id AND stock>=:qty
RETURNING id, stock;
```

给定正数 qty 和唯一 id，这条语句将条件和修改合并，并返回本次成功修改产生的状态。没有返回行，需要按业务区分不存在或库存不足。

RETURNING 能减少再发一个 SELECT 的需求，但不能保证提交最终成功；RR 或 Serializable 的冲突可能要求完整重试。MySQL 8.0 / 8.4 不提供同样的通用 UPDATE RETURNING 语法，迁移不能只依靠更换关键字。

## 14. WAL 与提交恢复

### 14.1 一套 WAL 服务于多个层次

PostgreSQL WAL 记录恢复所需的变更，使脏页可以延迟写回；物理复制重放这些日志，逻辑解码则从适用 WAL 中提取事务性逻辑变化。[官方 WAL](https://www.postgresql.org/docs/18/wal-intro.html)

```text
事务修改 heap / index 等状态
    → 生成 WAL
    → 提交记录与必要日志按配置达到持久位置
    → 成功提交可对外确认
    → 后台继续将脏页写回
```

MySQL 对照模型需要区分 InnoDB redo 和 Server binlog，再讨论内部提交协调。PostgreSQL 不能描述成“redo 等价物写一次，再将独立 binlog 等价物写一次”的同构流程。

WAL 也不是保存每条业务 SQL 的审计文本。逻辑解码、归档保留和业务审计各有配置与边界，不能由存在 WAL 自动推导出所有历史都可直接查询。

### 14.2 回滚与崩溃恢复

WAL 保证在写出相关数据页前，必要日志先满足持久化要求。事务中止时，无效的新元组通过事务状态被排除，后续清理回收；崩溃恢复重放必要修改并根据提交状态处理版本可见性。

这与 InnoDB 恢复页后通过 undo 撤销应回滚修改的路径不同。PostgreSQL 没有传统 InnoDB 式 undo 文件，不表示数据库无法保证原子性，而是原子性依赖不同的版本与状态组织。

### 14.3 synchronous_commit 与 fsync

| 配置含义 | PostgreSQL 的作用 | 对照边界 |
|---|---|---|
| fsync 开启 | 维持必要的持久写入顺序和存储同步 | 属于基础可靠性，不能当成仅减少副本等待 |
| synchronous_commit=on | 常规提交等待本地 WAL；配置同步副本时还等待其必要持久阶段 | 不等于所有副本都已应用 |
| synchronous_commit=local | 等待本地 WAL 持久化，不等待同步副本 | 将本地持久与远端确认分开 |
| synchronous_commit=off | 可在 WAL 尚未完成同步前返回 | 故障可能丢近期提交，但仍保持恢复一致性机制 |
| remote_write | 等待配置同步副本写到其 OS 层等阶段 | 不等于远端存储已完成持久同步 |
| remote_apply | 等待配置同步副本重放到相应提交 | 增加查询可见性相关保证和等待 |

远端模式是否有效，取决于 synchronous_standby_names 等同步配置；不能仅设置 remote_apply 就假定任意备库参与确认。[官方 WAL 参数](https://www.postgresql.org/docs/18/runtime-config-wal.html)

关闭 synchronous_commit 与关闭 fsync 不同：前者主要放宽提交确认时点，后者可能破坏故障后的恢复完整性。它们也不能与 InnoDB 的日志配置逐值一一对应。[官方异步提交](https://www.postgresql.org/docs/18/wal-async-commit.html)

### 14.4 组提交与 prepared transaction

并发事务可以共享 WAL 同步工作的收益，提交一次不等于一个事务独占一次磁盘同步。具体吞吐与延迟受并发、存储和配置影响。

PostgreSQL 也有 PREPARE TRANSACTION / COMMIT PREPARED，用于外部协调器管理的两阶段提交；它与普通单库事务提交路径、以及 MySQL redo / binlog 的内部协调不是同一概念。长期 prepared 事务可保留锁和维护边界，需要外部协调者负责完成。[官方 prepared transaction](https://www.postgresql.org/docs/18/sql-prepare-transaction.html)

### 14.5 full-page image 与 doublewrite

PostgreSQL 常规配置启用 full_page_writes，在 checkpoint 后页的首次相关修改等条件下，将完整页镜像纳入 WAL，帮助恢复不完整的页写。它不是每次修改都无条件记录整页。[官方可靠性与页镜像](https://www.postgresql.org/docs/18/wal-reliability.html)

```text
InnoDB：将待刷页保存到 doublewrite 区域 → 再写正式页
PostgreSQL：必要的完整页镜像进入 WAL → 用于恢复正式页
```

两种机制都弥补“操作系统写一个数据库页不保证原子完成”的缺口，但恢复副本位置和日志体积不同。频繁 checkpoint 可能增加页首次修改镜像产生量，WAL 压缩等配置又影响实际体积。

## 15. 内存与 checkpoint

### 15.1 shared_buffers 与系统缓存协作

shared_buffers 是 PostgreSQL 的共享页缓存，普通文件访问通常还与操作系统缓存协作。不能直接照搬某个 InnoDB Buffer Pool 占总内存的经验比例。

页缓存之外，查询工作区、连接进程和维护任务也使用内存。effective_cache_size 主要影响优化器对可用缓存的估计，并不按该数值分配一块真实缓存。[官方资源参数](https://www.postgresql.org/docs/18/runtime-config-resource.html)

### 15.2 work_mem 不是实例总上限

work_mem 为排序、哈希等执行操作提供内存预算；一个查询可能有多个相关节点，并发会话和并行 worker 又可能放大用量。哈希操作还涉及 hash_mem_multiplier 等规则。

```text
总工作内存量级
  ≈ 并发查询数 × 活跃内存节点数 × 节点预算
    + 并行与其他维护工作
```

这个式子只是容量估算，实际分配并非每个节点始终达到上限。增大 work_mem 可减少部分临时文件，却可能增加总内存压力，不能因为某条排序落盘就全局大幅提高。

MySQL 也存在连接和执行工作区的内存，不能认为只需配置 Buffer Pool；差异在于具体参数作用域和执行算法，迁移应重新估算。

### 15.3 checkpoint 推进恢复边界

checkpoint 协调必要的数据页和状态写回，使后续恢复可以从更近的位置开始。后台刷写与前台提交不是同一个进度，提交成功不表示全部相关 heap 页已同步。

checkpoint_timeout、max_wal_size、checkpoint_completion_target 等影响触发与写入节奏。checkpoint 过频可能增加刷写与 full-page image；间隔扩大又增加保留和恢复工作的评估。[官方 WAL 配置](https://www.postgresql.org/docs/18/wal-configuration.html)

`max_wal_size` 是影响自动 checkpoint 的软限制，不是 pg_wal 目录绝不超过的硬容量上限。复制槽、归档失败和保留需求都可能使 WAL 超过预期，因此不能用它代替磁盘占用监控。

### 15.4 缓存与计划需要联合解释

Bitmap Heap Scan、按索引逐条访问和 Seq Scan 对页局部性的需求不同。数据分布改变后，即使 SQL 与索引没变，访问同样数量结果也可能需要更多页。

因此性能解释要同时考虑候选记录数、页布局、缓存命中和等待事件。InnoDB 的回表和 PostgreSQL 的 heap fetch 都是额外访问，但不能直接假定其物理代价完全相同。

## 16. 复制与备份恢复

### 16.1 物理复制重放 WAL

```text
主库生成 WAL
  → WAL sender 发送
  → 备库接收并写入
  → WAL 达到所需 flush 位置
  → 备库 replay
  → 适用的新查询快照可以读取
```

write、flush 和 replay 是不同位置。PostgreSQL 常规物理复制基于 WAL，通常要求匹配的大版本及相应兼容条件；它不是按每张表逐条执行源库 SQL。[官方流复制](https://www.postgresql.org/docs/18/warm-standby.html)

MySQL 常规复制基于 binlog 事件，由副本接收并应用；两者都需要区分接收和执行，但传输对象与恢复路径不同。

### 16.2 同步确认与写后读

MySQL 半同步通常确认日志已在要求副本的 relay log 中保存，并不等待其应用。PostgreSQL 在配置同步备库时，synchronous_commit 不同模式可以要求 remote_write、远端持久或 remote_apply 等阶段。

remote_apply 提供配置要求的同步备库已应用的确认，但不表示任意未参与确认的备库都追平，也不改变早先 RR 快照的可见性。读写路由、同步名单和读事务快照仍需要协调。

如果采用复制位置等待，应明确等待哪个实例、哪个 LSN，以及等待成功后是否重新建立查询快照。源库切换产生的新时间线还需要在位置判断中考虑，不能跨任意历史分支机械比较数字。

### 16.3 逻辑复制不是物理复制的别名

逻辑复制通过 publication / subscription 等机制传输适用的表变更，目标可有不同索引和物理布局，适用于按表选择和某些迁移场景。逻辑解码依赖适当 wal_level 和其他条件，不是开箱即有完整业务审计。[官方逻辑复制](https://www.postgresql.org/docs/18/logical-replication.html)

UPDATE / DELETE 需要适用 replica identity 识别行，通常使用主键；无主键时可评估 FULL 等方案，但会增加数据与定位成本。[官方 publication 与 replica identity](https://www.postgresql.org/docs/18/logical-replication-publication.html)

常规内置逻辑复制不自动复制全部 DDL 和序列状态。目标结构需协调，切换写入前还要校验 identity / sequence，避免把“数据已经同步”理解成“整个数据库环境可以直接替换”。[官方逻辑复制限制](https://www.postgresql.org/docs/18/logical-replication-restrictions.html)

### 16.4 replication slot 保留必要日志

复制槽跟踪消费者所需位置，防止必要 WAL 被过早回收。消费者长时间离线时，也可能使 pg_wal 持续增长。

`max_slot_wal_keep_size` 等配置可限制相关保留，但日志超出允许范围后，槽可能失效，消费者需要重新建立数据基线。限制磁盘风险与消费者持续可恢复性存在取舍。[官方复制参数](https://www.postgresql.org/docs/18/runtime-config-replication.html)、[官方槽状态](https://www.postgresql.org/docs/18/view-pg-replication-slots.html)

物理槽与逻辑槽的保留信息不同，监控应结合 restart_lsn、confirmed_flush_lsn、xmin / catalog_xmin 和具体槽状态，不把这些位置当作同一个进度。

### 16.5 备库查询与日志重放冲突

主库 VACUUM 产生的清理结果可能与备库长查询仍需要的旧版本冲突。备库需要在等待重放、取消查询和向主库反馈保留需求之间取舍。

hot_standby_feedback 可以减少某些清理冲突，却可能增加主库膨胀；允许更长重放等待又可能增加复制延迟。这与普通锁等待不是同一问题。[官方 Hot Standby](https://www.postgresql.org/docs/18/hot-standby.html)

### 16.6 PITR 需要基线与连续日志

PostgreSQL 时间点恢复通常以有效物理基线备份和连续 WAL 归档为基础，重放到指定目标。pg_dump 是逻辑导出工具，不能直接作为物理 WAL 重放的同类基线。

MySQL 常见 PITR 路径是备份加 binlog；PostgreSQL 常见物理 PITR 路径是基线加 WAL。两者都需要验证日志链、目标事务边界和恢复结果。[官方连续归档与 PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)

误删除已提交后，数据库不会通过普通崩溃恢复自动撤销该合法提交，副本也可能已经重放。独立备份、日志保留和恢复演练仍然必要。

## 17. DDL 与数据生命周期

### 17.1 多数普通 DDL 可事务回滚

```sql
BEGIN;
CREATE TABLE ddl_demo(id bigint PRIMARY KEY);
ALTER TABLE ddl_demo ADD COLUMN note text;
ROLLBACK;
```

这个普通 DDL 示例的预期是创建与修改随事务回滚。MySQL 中多种 CREATE / ALTER 会隐式提交，不能保持同样事务边界。

PostgreSQL 不是所有管理语句都允许在事务块中执行：CREATE DATABASE、普通 VACUUM 和 CREATE INDEX CONCURRENTLY 等有专属限制。DDL 可回滚也不意味着没有长锁或大表重写成本。[官方 CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html)、[官方并发索引限制](https://www.postgresql.org/docs/18/sql-createindex.html)

### 17.2 普通建索引与并发建索引

```sql
CREATE INDEX CONCURRENTLY idx_orders_created_at
ON orders(created_at);
```

CONCURRENTLY 允许普通写入在构建期间继续，但需要多阶段扫描、等待相关事务和快照，并不能放在普通显式事务块中。失败还可能遗留 invalid index，查询不能正常使用，写入仍可能承担维护成本；唯一并发索引还可能在未最终有效前就开始执行唯一检查。

InnoDB Online DDL 用算法与锁要求描述能力，PostgreSQL 用并发索引构建协议提供该场景。两者都需评估资源、等待和失败恢复，不能因为名称含“在线”或“并发”就认定零影响。

### 17.3 约束分阶段验证

对适用的 CHECK 或外键，`NOT VALID` 可以把新写入约束与已有数据验证分阶段安排，随后通过 VALIDATE CONSTRAINT 验证历史记录。

这种机制改变验证节奏，不允许新写入无限违反规则，也不表示所有约束类型均支持相同方式。操作锁级别和扫描成本需按具体 ALTER 子命令核对。[官方 ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html)

### 17.4 分区裁剪与全局唯一性

PostgreSQL 声明式分区可用于按范围、列表或哈希组织数据，查询条件在适用情况下实现计划或执行阶段裁剪。它通常仍在单实例内，不自动提供跨机器容量。

分区表上父级唯一 / 主键约束具有分区键相关限制。按 created_at 分区时，若约束由 `(id)` 改为 `(id,created_at)`，禁止的只是组合重复，而不是单独保证 id 全局唯一。[官方分区](https://www.postgresql.org/docs/18/ddl-partitioning.html)

这与 MySQL 分区的相关唯一键问题具有相似工程后果，但支持范围、维护命令与锁行为仍需分别核对。删除旧分区有助于数据生命周期管理，却仍要评估结构锁、依赖与归档可恢复性。

### 17.5 容量需要加入维护维度

PostgreSQL 容量评估除行宽、索引、缓存和 I/O 外，还应加入更新版本产生速度、HOT 比例、autovacuum 吞吐、冻结进度、WAL 保留及备份恢复窗口。

两库都不存在普遍适用的“单表达到某个固定行数就必须分片”规则。PostgreSQL heap 与索引分离也不意味着能够忽略表体积和随机 heap 访问。扩展应针对已确认瓶颈，并评估跨片事务、唯一性和迁移成本。

## 18. 类型与 SQL 语义迁移

### 18.1 迁移映射不是只改类型名称

| MySQL 表达 | PostgreSQL 候选表达 | 必须核对 |
|---|---|---|
| BIGINT UNSIGNED | bigint 加范围约束，或按值域选 numeric | 有符号 bigint 不覆盖完整 unsigned 上界 |
| AUTO_INCREMENT | GENERATED ... AS IDENTITY | 显式值、序列位置和唯一约束 |
| DECIMAL | numeric | 精度、小数位及舍入规则 |
| DATETIME | timestamp without time zone，按业务选择 | 本地时间语义与精度 |
| TIMESTAMP | 常评估 timestamptz | 时区转换、范围、默认值和接口语义 |
| JSON | json 或 jsonb | 文本保留、比较、索引与路径操作 |
| TINYINT(1) 惯例 | boolean 或其他合适类型 | 原列是否真的只表达真假 |
| database.table | schema.table 或重设计连接边界 | database 与 schema 不等价 |

数据迁移需要验证存储值域、查询含义和约束，而不是只保证 CREATE TABLE 能通过。

### 18.2 identity 与序列

identity 列通过关联序列生成值。ALWAYS 与 BY DEFAULT 对显式赋值有不同规则，但 identity 本身不自动等同于唯一约束；示例中仍使用 PRIMARY KEY。[官方 identity](https://www.postgresql.org/docs/18/ddl-identity-columns.html)

nextval 消耗的值不因普通事务回滚重新归还，ON CONFLICT、失败和缓存也可形成空洞。因此 PostgreSQL identity 与 MySQL AUTO_INCREMENT 都不能保证无间断业务编号。[官方序列函数](https://www.postgresql.org/docs/18/functions-sequence.html)

导入显式 ID 后，序列可能没有自动追到最大业务 ID，需要在受控切换中核验。`RETURNING id` 直接取得本次生成的行身份，通常比依赖“最后使用的任意序列”更明确。

### 18.3 timestamptz 与时间函数

`timestamp without time zone` 保存没有时区换算语义的日期时间。`timestamptz` 表达绝对时刻，按会话 TimeZone 进行输入解释和输出显示，不保留原输入的时区名称；若需保留原始时区，应另存相应信息。[官方日期时间类型](https://www.postgresql.org/docs/18/datatype-datetime.html)

PostgreSQL CURRENT_TIMESTAMP / now() 对应事务开始时刻；statement_timestamp() 对应语句开始时刻；clock_timestamp() 随实际时间变化。MySQL NOW() 的常见行为是语句级稳定时间，两者在长事务中可能产生不同时间戳。[官方时间函数](https://www.postgresql.org/docs/18/functions-datetime.html)

缓存过期、任务租约和审计时刻若依赖实时推进，迁移需要选择符合语义的函数，不能只替换函数名。

### 18.4 NULL 与唯一性

PostgreSQL 普通 UNIQUE 默认允许多条 NULL，MySQL 可空唯一列也允许这种情况。PostgreSQL 15 起支持 `NULLS NOT DISTINCT`，可将 NULL 按不可区分值参与适用唯一性约束。

```sql
CREATE TABLE external_binding (
    tenant_id bigint NOT NULL,
    external_id text,
    UNIQUE NULLS NOT DISTINCT (tenant_id, external_id)
);
```

这会限制同一 tenant_id 下重复的 NULL 组合。是否采用取决于业务身份语义，并不是所有可空字段都应变成这种唯一性。[官方约束](https://www.postgresql.org/docs/18/ddl-constraints.html)

PostgreSQL 某些 UNIQUE、外键和排斥约束可设置延迟检查，便于事务内暂时出现中间状态；不是所有约束均可延迟。MySQL 不提供同样的通用 DEFERRABLE 约束契约。

### 18.5 排序规则与 NULL 顺序

PostgreSQL 默认 ASC 时 NULLS LAST，DESC 时 NULLS FIRST；MySQL 的常规 NULL 默认位置相反。因此相同 ORDER BY 在可空列上可能产生不同分页结果。

```sql
ORDER BY created_at DESC NULLS LAST, id DESC
```

PostgreSQL 可以直接声明 NULL 位置，索引也需与目标顺序匹配。MySQL 的等价表达可能需要额外条件排序，不能只复制上述语法。[官方索引与排序](https://www.postgresql.org/docs/18/indexes-ordering.html)

字符排序与唯一性还依赖 collation。MySQL 常见的大小写不敏感配置不能直接当作 PostgreSQL 所有 text 列的默认比较规则，邮箱、用户名和请求 ID 都需要明确规则与配套索引。

### 18.6 JSONB 与适用索引

json 保留输入文本的若干表示特征，jsonb 使用分解后的表示，不保留空白、键顺序或重复键的全部原形式，便于相关运算和索引。

```sql
CREATE INDEX idx_events_payload ON events USING gin(payload);

SELECT id FROM events
WHERE payload @> '{"type":"purchase"}'::jsonb;
```

示例要求 payload 为 jsonb。GIN 操作符类影响支持的操作及索引特点：jsonb_ops 与 jsonb_path_ops 并非对所有查询等价；经常查询单个路径时，表达式 B-tree 也可能更合适。[官方 JSON 类型与索引](https://www.postgresql.org/docs/18/datatype-json.html)

MySQL 也能通过生成列、函数或多值索引等支持一些 JSON 查询，不应描述成完全不能索引 JSON。真正差异在于操作符与索引组合、查询表达力和维护成本。

结构稳定且经常约束、关联的字段，仍可优先建模为常规列。将所有业务字段移入 JSONB 会改变约束、统计和更新成本，不由类型丰富性自动证明合理。

### 18.7 范围类型与排斥约束

PostgreSQL 范围类型可以直接表达时间或数值区间，配合适用 GiST 与排斥约束，可声明某些区间不得重叠。例如资源预约可将“同一资源时间不能重叠”作为数据库约束表达，组合资源等值可能需要 btree_gist 等扩展。[官方范围类型](https://www.postgresql.org/docs/18/rangetypes.html)

MySQL 常规唯一键不能直接表示一般区间不重叠，需要额外的业务并发协议或不同模型。PostgreSQL 的约束表达也有操作符、边界和扩展条件，不能仅建一个 GiST 索引就声称自动禁止重叠。

## 19. 分页与统计的共同边界

### 19.1 COUNT 仍受版本可见性约束

两库 `COUNT(*)` 都统计查询可见行，`COUNT(column)` 忽略该表达式的 NULL。PostgreSQL 精确计数通常需要访问可见元组或适用 Index Only Scan，不能只读取一个对所有快照都正确的全局计数器。

VACUUM 和 visibility map 可能影响计数访问 heap 的比例，统计视图中的 n_live_tup 等则是近似指标，不是精确 COUNT 的语义替代。

### 19.2 OFFSET 与游标

两库 OFFSET 通常都需要处理并跳过前缀，索引不提供对任意结果集合的免费第 N 行定位。PostgreSQL 的语法为 `LIMIT 20 OFFSET 100000`，不是 MySQL 的 `LIMIT 100000,20`。

```sql
SELECT id, amount, created_at
FROM orders
WHERE user_id=42 AND status=1
  AND (created_at, id) < (:cursor_time, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

案例中 created_at 与 id 均非空，顺序同为降序，可用行值比较表达游标位置。混合升降序或可空字段时，不能不加判断地沿用这一表达。

游标包含完整排序键，能避免同一时间的记录遗漏。频繁跨请求查询仍使用不同快照，不能自动保证导出集合固定；长快照导出又会影响旧版本维护。

### 19.3 优化不得隐含改变语义

精确计数改为估算、随机跳页改为连续游标、按本地时间改为绝对时刻、NULL 排序改变，都是接口语义变化。性能对照应先确认结果一致，再比较访问量、页访问和等待。

## 20. 排障证据与观察语句

### 20.1 活动、事务与阻塞

```sql
SELECT version(), current_database();
SHOW transaction_isolation;
SHOW search_path;

SELECT pid, usename, state,
       xact_start, query_start, backend_xmin,
       wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blockers,
       query
FROM pg_stat_activity
WHERE datname=current_database()
  AND pid<>pg_backend_pid()
ORDER BY xact_start NULLS LAST;
```

xact_start 与 query_start 区分事务年龄和当前查询年龄；wait_event 用于区分锁、I/O、客户端等等待。active 不保证持续消耗 CPU，idle in transaction 也不表示没有事务影响。[官方统计系统](https://www.postgresql.org/docs/18/monitoring-stats.html)

```sql
SELECT pid, locktype, mode, granted,
       relation::regclass AS relation_name,
       transactionid, virtualxid, waitstart
FROM pg_locks
WHERE pid IN (:waiting_pid, :blocking_pid);
```

relation 名称解释需在正确 database 中进行。row-lock 等待可能表现为 transactionid 等待，不能仅筛选 tuple 类型。

### 20.2 表维护与体积

```sql
SELECT schemaname, relname,
       n_live_tup, n_dead_tup,
       n_tup_upd, n_tup_hot_upd,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

SELECT pg_size_pretty(pg_relation_size('orders')) AS heap_main_size,
       pg_size_pretty(pg_indexes_size('orders')) AS index_size,
       pg_size_pretty(pg_total_relation_size('orders')) AS total_size;

SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

n_live_tup / n_dead_tup 是估算，HOT 计数需要比较适当时间窗口内的增量。n_dead_tup 少也不证明没有冻结压力，表体积大也不证明全部是可回收膨胀。[官方尺寸函数](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE)

### 20.3 复制位置与槽

```sql
SELECT application_name, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;

SELECT slot_name, slot_type, active,
       restart_lsn, confirmed_flush_lsn,
       xmin, catalog_xmin
FROM pg_replication_slots;
```

这些位置不能互相替代。字节差距、提交流量和应用速度共同决定追平时间；没有新事务时，延迟字段也不应机械解释成持续故障。

### 20.4 语句聚合统计

pg_stat_statements 可按归一化语句统计执行次数、总时间、均值、块访问和 WAL 等信息，适合区分单次慢与高频累计负载。它需要扩展及预加载等环境条件，本文没有修改实例配置。[官方 pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html)

聚合指标可能混合不同参数和冷热缓存，异常尾延迟仍需具体执行和等待证据。统计重置与版本字段差异也需要记录。

### 20.5 两库排障入口对照

| 关注问题 | MySQL / InnoDB 常用入口 | PostgreSQL 常用入口 |
|---|---|---|
| 当前连接与执行状态 | PROCESSLIST、Performance Schema | pg_stat_activity |
| 数据锁等待 | data_locks、data_lock_waits | pg_blocking_pids、pg_locks、事务状态 |
| 结构变更阻塞 | metadata_locks | relation 锁与活动会话 |
| 查询工作量 | EXPLAIN ANALYZE、语句统计 | EXPLAIN ANALYZE BUFFERS、pg_stat_statements |
| 历史版本清理 | undo、history list、purge | 死元组、HOT、VACUUM、xmin、事务年龄 |
| 提交慢 | redo / binlog 同步、复制确认 | WAL 同步、同步备库与相关等待事件 |
| 副本追平 | 接收与应用状态、GTID | write / flush / replay LSN、槽 |

这些是证据入口，而不是一组可以直接互换的指标名称。先区分工作过多和等待过久，再选择改变访问路径、事务边界或维护配置。

## 21. 差异检索与设计核对

### 21.1 从现象定位机制

| 查询主题 | 对应章节 | 需要避免的假设 |
|---|---|---|
| PostgreSQL 主键查全行也需 heap | [3](#3-堆存储与主键索引) | 主键必然承载整行 |
| idx_user 不自动覆盖 id | [3](#3-堆存储与主键索引)、[5](#5-索引设计与列覆盖) | 二级索引默认携带主键 |
| 覆盖索引仍有 Heap Fetches | [5](#5-索引设计与列覆盖)、[9](#9-vacuum-与事务年龄) | 只要列都在索引就绝无 heap 访问 |
| 加 INCLUDE 后更新变重 | [7](#7-更新成本与-hot) | 载荷列不影响写入维护 |
| DELETE 后文件没有缩小 | [9](#9-vacuum-与事务年龄) | 清理空间必然立即返还文件系统 |
| 只插入表仍有维护任务 | [9](#9-vacuum-与事务年龄) | VACUUM 只用于删除记录 |
| 默认两次 SELECT 结果变化 | [10](#10-快照与隔离级别) | PostgreSQL 默认也是 RR |
| RR 下 UPDATE 报 40001 | [11](#11-同一并发程序的不同结果) | 同名 RR 的写入行为相同 |
| 两个 RR 事务破坏跨行规则 | [11](#11-同一并发程序的不同结果) | 稳定快照等价于可串行化 |
| FOR UPDATE 查空后 B 仍插入 | [12](#12-行锁与不存在的记录) | PostgreSQL 存在同样的 gap lock |
| pg_locks 没有逐条行锁列表 | [12](#12-行锁与不存在的记录)、[20](#20-排障证据与观察语句) | 没有 tuple 列表就没有行竞争 |
| 捕获错误后所有 SQL 都失败 | [13](#13-错误处理与写入协议) | 错误只撤销一条语句 |
| ON CONFLICT 未插入又没读到旧行 | [13](#13-错误处理与写入协议) | 冲突裁决与本语句快照完全相同 |
| WAL 不等于独立 binlog | [14](#14-wal-与提交恢复) | 两库存在三类一一对应日志 |
| max_wal_size 外仍有大量 WAL | [15](#15-内存与-checkpoint)、[16](#16-复制与备份恢复) | 参数是目录容量硬限制 |
| 数据已逻辑复制，序列 / DDL 未同步 | [16](#16-复制与备份恢复) | 复制了表数据就复制了全部环境 |
| CONCURRENTLY 失败留下索引 | [17](#17-ddl-与数据生命周期) | 并发 DDL 失败后一定无残留 |
| 导入 ID 后新插入冲突 | [18](#18-类型与-sql-语义迁移) | 显式 ID 自动同步 identity 计数 |
| 相同 ORDER BY 的 NULL 位置不同 | [18](#18-类型与-sql-语义迁移)、[19](#19-分页与统计的共同边界) | 排序默认语义跨库相同 |
| now() 在长事务中保持不变 | [18](#18-类型与-sql-语义迁移) | 时间函数始终返回当前实时时刻 |


### 21.2 从设计约束选择实现

设计评审应先说明需要维护的业务不变量、主要 SQL、更新模式、故障窗口与恢复目标，再比较两库机制能否直接表达。

对订单列表，应比较候选扫描、顺序、heap / 聚簇访问与写维护；对幂等，应比较请求身份、冲突对象、事务状态和结果回查；对预约，应比较区间约束与并发协议；对读写分离，应比较提交确认阶段和读快照。

PostgreSQL 的部分索引、范围约束、丰富访问方法和事务 DDL 能简化某些模型；InnoDB 的聚簇组织、成熟访问模式和既有运维体系也可能适合某些负载。性能结论需要同一业务语义、相近数据与硬件、明确配置和维护负载下的证据，不能从特性数量直接推出全面优劣。

### 21.3 版本与验证范围

重点版本边界包括 PostgreSQL 18 的 B-tree skip scan、PostgreSQL 15 起的 NULLS NOT DISTINCT，以及不同版本的统计字段、HOT 规则、复制与并发 DDL 支持范围。MySQL 对照采用 8.0 / 8.4 InnoDB，不延伸到 MariaDB 或其他 MySQL 引擎。
