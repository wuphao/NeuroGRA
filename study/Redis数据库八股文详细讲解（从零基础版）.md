## 二、Redis 是什么

### 1. Redis 是一个什么类型的数据库

Redis 的英文名称来自 Remote Dictionary Server，可以理解成“远程字典服务”。它是一个开源的键值数据库，也可以称为数据结构服务器。

最简单的使用方式是：

```redis
SET name "Tom"
GET name
```

这两条命令完成：

```text
key   = name
value = Tom
```

Redis 与普通字典的区别是，它不是当前 Python 或 Java 进程里的一个变量，而是独立运行的服务，多个应用进程通过网络访问它。

### 2. Redis 与 MySQL 的区别

| 对比项 | MySQL | Redis |
|---|---|---|
| 基本模型 | 表、行、列 | key 和 value |
| 查询方式 | SQL，可表达复杂条件 | 命令和数据结构操作 |
| 主要访问 | 磁盘数据页配合内存缓存 | 主要操作内存数据 |
| 常见角色 | 权威业务数据库 | 缓存、临时状态、数据结构服务 |
| 事务特点 | 支持回滚、隔离级别、MVCC | MULTI/EXEC，执行错误不自动回滚 |
| 持久化 | 数据文件和日志 | 可选 RDB、AOF |

不能简单理解为“MySQL 慢、Redis 快”。MySQL 也会把热点数据放进 Buffer Pool；Redis 的优势主要来自内存数据结构、短命令路径和较少的关系型查询工作。

### 3. Redis 的数据是否一定是缓存

不一定。

```text
商品缓存：MySQL 有原始数据，Redis 是副本
登录会话：可能只保存在 Redis，丢失后用户重新登录
排行榜：可以重新计算，也可以把 Redis 当主要存储
任务队列：丢失后可能导致任务没有执行
```

因此不要一听 Redis 就认为“数据丢了没关系”。应该先问：这份数据是否可以重建，丢失后业务能否接受。

## 三、一个 Redis key 是怎么保存的

### 1. key 是什么

执行：

```redis
SET user:1001:name "Tom"
```

`user:1001:name` 是完整 key。冒号只是程序员约定的命名方式，Redis 不会把它当成数据库、表、行和列。

常见命名规则是：

```text
业务:对象类型:对象编号:属性
```

例如：

```text
login:token123
user:1001
article:88:likes
```

### 2. Redis 怎样找到 key

Redis 使用哈希表保存数据库中的 key。哈希表可以先理解为一个数组，数组中的位置叫哈希桶。

```text
key
 ↓ 哈希函数
哈希值
 ↓ 对桶数量取模
桶下标
 ↓
找到 key 对应的值
```

平均情况下，查找复杂度接近 O(1)。如果多个 key 算到同一个桶，会发生哈希冲突，Redis 使用链式结构保存冲突节点。

### 3. 什么是渐进式 rehash

随着 key 越来越多，原来的桶可能不够用，需要扩容哈希表并重新计算 key 的位置，这个过程叫 rehash。

如果一次性迁移一千万个 key，主线程可能长时间阻塞。因此 Redis 通常把迁移拆成很多小步：

```text
旧哈希表和新哈希表同时存在
→ 每次处理请求时迁移一部分
→ 旧表逐渐变空
→ 释放旧表
```

这就是渐进式 rehash。它牺牲一段时间内的额外内存和双表查询，换取更平滑的延迟。

## 四、Redis 是单线程吗

### 1. 面试中为什么说 Redis 是单线程

通常说的单线程，是指下面这条主路径由主线程完成：

```text
接收客户端请求
→ 解析命令
→ 执行数据读写
→ 返回结果
```

这样做的好处是，Redis 的核心数据结构不需要在每条普通命令之间频繁加锁，也减少了线程切换开销。

### 2. Redis 进程不是只有一个线程

Redis 还可能有后台线程，处理关闭文件、AOF 刷盘、异步释放内存等耗时工作。Redis 6 以后还支持网络 I/O 多线程。

所以面试时应回答：

> Redis 的普通命令执行主要由单线程完成，但整个进程并不是只有一个线程；后台任务和部分网络 I/O 可以使用其他线程。

### 3. 什么是 I/O 多路复用

假设 Redis 有一万个客户端，大部分时间客户端都没有发送数据。如果给每个连接都创建一个线程等待，会浪费大量资源。

I/O 多路复用让一个线程同时监听许多 socket：

```text
主线程等待多个连接
→ 操作系统通知哪些连接已经可读/可写
→ Redis 只处理这些已经就绪的连接
```

Linux 中常见实现是 epoll。它解决的是“同时管理大量网络连接”，不是把一条耗时命令自动并行化。

### 4. 为什么一个慢命令会影响其他请求

普通命令主要在同一个命令执行线程上顺序处理。如果一个命令遍历百万个元素，后面的请求就要等待。

因此以下操作要谨慎：

- 对大 List、Set、Hash 使用全量返回。
- 使用 `KEYS *` 扫描整个数据库。
- 执行过长的 Lua 脚本。
- 用 `DEL` 同步删除巨大集合。

## 五、一条 Redis 命令的完整执行流程

以：

```redis
GET user:1001
```

为例，执行流程是：

```text
客户端把命令编码
→ 通过 TCP 发送
→ Redis 事件循环发现连接可读
→ 读取并解析命令
→ 检查命令和参数
→ 在键空间查找 user:1001
→ 检查是否过期
→ 检查 value 是否适合 GET
→ 生成响应
→ 发送给客户端
```

如果 key 不存在，通常返回空值；如果 key 实际是 List，却使用 `GET`，会出现类型错误。

这和 MySQL 的 SQL 执行流程不同：MySQL 需要解析 SQL、优化执行计划、访问索引和数据页；Redis 的基础命令通常已经明确了操作对象和执行方式。

## 六、Redis 的五种基础数据类型

### 1. String：一整个值

String 可以保存文本、数字、JSON 或二进制数据。

```redis
SET product:1001 '{"name":"keyboard","price":199}' EX 600
GET product:1001
```

Redis 不会自动理解 JSON 中的字段。如果只想修改 price，需要由应用取出 JSON、解析、修改、重新写回。

String 还可以保存整数并执行原子计数：

```redis
SET article:88:views 0
INCR article:88:views
INCRBY article:88:views 10
```

`INCR` 的“原子”表示 Redis 不会把读、加一、写回这三个步骤暴露给其他命令插入。它并不代表包含 `INCR` 的整个业务流程都自动回滚。

### 2. Hash：一个 key 里面再放多个字段

```redis
HSET user:1001 name "Tom" age 20 city "Shanghai"
HGET user:1001 name
HINCRBY user:1001 age 1
```

逻辑结构是：

```text
user:1001
├── name → Tom
├── age  → 21
└── city → Shanghai
```

Hash 适合用户资料、购物车、对象字段等。它仍然不是 MySQL 表，没有外键、列约束和 SQL 关联查询。

### 3. List：有顺序的列表

```redis
RPUSH jobs job1 job2 job3
LPOP jobs
```

`RPUSH + LPOP` 是先进先出队列；`LPUSH + LPOP` 是后进先出栈。

没有消息时，消费者可以使用：

```redis
BLPOP jobs 5
```

这会让当前客户端等待最多 5 秒，Redis 仍能处理其他客户端。

List 的问题是消息弹出后就不在原列表中。消费者取到消息后崩溃，消息可能丢失。可以把消息转移到处理中列表，成功后再删除，并设计超时恢复和重复处理防护。

### 4. Set：不重复、无序的集合

```redis
SADD article:88:likes user:1 user:2 user:1
SISMEMBER article:88:likes user:1
SCARD article:88:likes
```

同一个用户加入两次，集合仍只有一份。Set 适合点赞、收藏、共同关注、抽奖候选。

集合运算：

```redis
SINTER follows:alice follows:bob
SUNION group:a group:b
SDIFF group:a group:b
```

分别表示交集、并集和差集。Set 不保证元素顺序。

### 5. ZSet：带分数的有序集合

```redis
ZADD ranking 100 alice 200 bob 150 carol
ZREVRANGE ranking 0 2 WITHSCORES
ZRANGEBYSCORE ranking 100 180
```

ZSet 的每个成员都有 score。它适合排行榜、按时间戳排序的任务、按分数范围查询。

member 唯一，score 可以重复。分数相同还要根据成员的字典序排序；如果业务要求同分按到达时间排序，需要把时间放进自己的排序设计。

## 七、四种扩展数据类型

### 1. Bitmap：用 bit 保存状态

例如保存每天是否签到：

```redis
SETBIT sign:1001:202609 0 1
SETBIT sign:1001:202609 2 1
BITCOUNT sign:1001:202609
```

一个 bit 只有 0 和 1，适合登录状态、签到状态、在线状态。注意 offset 很大时，字符串可能出现稀疏空间。

### 2. HyperLogLog：近似统计去重数量

```redis
PFADD uv:20260922 user:1 user:2 user:1
PFCOUNT uv:20260922
```

它适合网站 UV 等允许少量误差的统计，内存固定且较小，但不能准确列出用户，也不适合财务统计。

### 3. GEO：地理位置

```redis
GEOADD shops 121.4737 31.2304 shop:1
GEODIST shops shop:1 shop:2 km
```

GEO 适合附近门店、附近车辆等场景。经纬度距离通常是地理直线距离，不等同于道路导航距离。

### 4. Stream：带确认机制的消息流

```redis
XADD orders * order_id 1001 status created
XGROUP CREATE orders inventory 0 MKSTREAM
XREADGROUP GROUP inventory worker-1 COUNT 1 STREAMS orders >
XACK orders inventory message-id
```

Stream 自动生成消息 ID，支持消费组。

消息被消费组读取后，会进入 PEL，也就是 Pending Entries List，中文可称为“待确认消息列表”。消费者处理成功后执行 `XACK`，表示这条消息已被该消费组处理。

注意：`XACK` 删除的是 PEL 中的待确认记录，不会自动删除 Stream 的消息正文。消息正文什么时候删除，需要使用 `XDEL` 或长度裁剪策略另行决定。

消费者宕机后，可以通过 `XPENDING` 查看未确认消息，并使用 `XCLAIM` 或 `XAUTOCLAIM` 重新分配。即使如此，消息仍可能被重复处理，所以业务必须设计幂等。

## 八、Redis 底层数据结构

### 1. 数据类型与底层结构不是一回事

String、List、Hash、Set、ZSet 是对外的数据类型；SDS、哈希表、跳表、listpack 等是内部实现。

可以抽象为：

```text
redisObject
├── type：对外类型
├── encoding：内部编码方式
└── ptr：指向底层结构
```

### 2. SDS：Redis 自己实现的字符串

C 字符串通过末尾 `\0` 判断结束，获取长度需要遍历，也不能安全保存中间包含零字节的数据。

SDS 保存：

```text
len：已经使用的长度
alloc：已经分配的容量
buf：实际内容
```

于是读取长度可以直接看 `len`，追加数据前可以判断容量，还能保存二进制内容。

### 3. Hash 表冲突

不同 key 可能计算到同一个哈希桶：

```text
桶 3 → keyA → keyB → keyC
```

这就是链式哈希。链条变长时查询会变慢，因此需要扩容和 rehash。

### 4. ziplist、listpack、quicklist

小数据使用连续紧凑结构，可以减少指针和对象开销；但中间查找通常需要遍历，插入也可能移动后续数据。

旧 ziplist 记录前一个节点长度。前一个节点变大时，后一个节点保存长度的字段可能从 1 字节扩成 5 字节，并继续影响后面的节点，这称为连锁更新。

listpack 采用更独立的条目编码，减少这种连锁更新；quicklist 可以理解为“多个紧凑小块组成的双向链表”。

不同版本会调整编码，具体阈值应以实际版本配置为准。

### 5. intset：小整数集合

Set 里的元素全是较小整数且数量较少时，可以用连续整数数组保存。新加入的整数超出当前宽度时，数组升级为更宽的编码。

这样小整数不用为每个元素承担完整哈希节点开销。经典实现升级后不会因为删除大整数而自动降级。

### 6. skiplist：跳表

普通有序链表查找需要逐个移动。跳表在链表上增加多层索引：

```text
高层：10 ─────────→ 50 ─────────→ 90
底层：10 → 20 → 30 → 40 → 50 → 60 → 70 → 80 → 90
```

查找先走高层，超过目标后下降到下一层，平均复杂度 O(logN)。ZSet 通常同时使用字典和跳表：字典按 member 找 score，跳表按 score 做范围查询和排名。

## 九、Pipeline、事务和 Lua

### 1. Pipeline 只解决网络往返

逐条执行：

```text
发送命令 1 → 等结果 → 发送命令 2 → 等结果
```

Pipeline 一次发送一批命令，再批量读取结果。它减少网络往返，但本身不保证事务隔离，其他客户端可能插入命令。

### 2. MULTI/EXEC 事务

```redis
MULTI
INCR a
INCR b
EXEC
```

MULTI 后命令先入队，EXEC 时按顺序执行。执行过程中不会被其他客户端的普通命令插入。

Redis 事务与 MySQL 事务的重要区别：

```text
命令入队阶段语法错误：可能导致事务不能执行
命令执行阶段类型错误：其他命令仍可能执行
Redis 不会像 MySQL 一样自动回滚已成功的命令
```

### 3. WATCH：乐观锁

WATCH 不是把 key 锁住，而是记录“我读过这个 key”。如果 EXEC 前 key 被改过，事务就放弃执行，应用需要重新读取和重试。

### 4. Lua 脚本

需要把“读取、判断、修改”作为一个整体执行时，可将逻辑写在 Redis 服务器端。脚本执行期间不会被其他命令插入，但脚本太长会阻塞其他客户端，脚本出错也不会自动回滚已经执行的写操作。

## 十、持久化：RDB 与 AOF

### 1. 为什么需要持久化

Redis 的主要数据在内存中。进程退出或机器重启后，内存数据可能消失，因此需要把恢复所需的信息保存到磁盘。

### 2. RDB 快照

RDB 是某个时间点的完整数据快照。`SAVE` 在主线程执行，可能阻塞；`BGSAVE` fork 子进程生成快照。

快照不是实时记录。假设最后一次成功快照是 12:00，12:03 发生故障，12:00 之后的修改可能丢失。

### 3. AOF 日志

AOF 记录写操作对应的命令或恢复信息：

```text
执行写命令
→ 写入 Redis AOF 缓冲区
→ write 到操作系统页缓存
→ fsync 到磁盘
```

`appendfsync always` 持久化更严格但延迟更高；`everysec` 常作性能与持久性的折中；`no` 由操作系统决定刷盘时机。

### 4. AOF 重写

AOF 长期追加会越来越大。重写读取当前内存状态，用更精简的恢复内容生成新文件，减少历史重复命令。

重写期间主进程仍会接收新写入，所以必须额外记录重写期间的增量，最后再合并。Redis 7 以后还使用 base 文件、incremental 文件和 manifest 的多文件组织方式。

### 5. 写时复制

fork 后父子进程开始共享物理内存页。父进程修改某页时，操作系统复制这一页，父子进程分别看到自己的内容。

这让子进程可以生成一个相对稳定的快照视图，但 fork、写时复制和磁盘写入仍会消耗 CPU、内存和 I/O。修改大 Key 时，复制成本尤其明显。

## 十一、过期删除和内存淘汰

### 1. 过期时间

```redis
SET code:1001 123456 EX 60
TTL code:1001
```

TTL 表示剩余有效时间。过期删除解决“时间到了的数据不再有效”。

### 2. 惰性删除

访问 key 时才检查它是否过期。优点是没有访问的 key 不必立即检查；缺点是没人访问的过期 key 可能暂时占用内存。

### 3. 定期删除

Redis 后台周期性从设置过期时间的 key 中抽样检查，删除已经过期的 key，并设置时间上限，避免清理过程长期占用主线程。

### 4. 内存淘汰

当 Redis 达到 `maxmemory`，就要决定删除哪些 key：

```text
noeviction：不淘汰，部分写入报错
allkeys-lru：所有 key 中淘汰近似最久未使用
allkeys-lfu：所有 key 中淘汰近似最低频率
volatile-lru：只从设置过期时间的 key 中选
volatile-lfu：只从设置过期时间的 key 中选
volatile-ttl：优先剩余 TTL 较短的 key
random：随机选择
```

过期删除和淘汰要分开记忆：

```text
过期删除：时间到了，key 不再有效
内存淘汰：内存不够，可能删除尚未过期的 key
```

## 十二、大 Key、热 Key 和内存碎片

### 1. 大 Key

大 Key 是单个 String 很大，或一个集合中元素数量很多。它会影响读取、网络、删除、持久化、复制和 Cluster 的数据分布。

删除大 Hash 可使用 HSCAN 分批 HDEL；删除大 List 可使用 LTRIM 分批；Redis 4.0 以后可以使用 UNLINK 让释放工作异步化。

### 2. 热 Key

热 Key 是访问频率特别高的 key。一个 key 即使很小，也可能让单节点成为瓶颈。可以考虑本地缓存、请求合并、拆分 key 或降低集中访问。

### 3. 内存碎片

删除对象后，内存分配器可能只留下很多不连续的空闲块：

```text
[对象 A][空闲块][对象 B]
```

空闲块可供 Redis 后续复用，但因为 A、B 仍存在，进程 RSS 不一定马上下降。因此要区分 Redis 数据内存、分配器内存、操作系统 RSS 和写时复制产生的额外内存。

## 十三、主从复制

### 1. 为什么需要主从

单节点发生故障时，即使有持久化，也需要等待恢复。主从复制让其他节点保存数据副本，并可以承担部分读流量。

```text
主节点：处理写入
从节点：复制主节点数据，通常只读
```

### 2. 第一次全量同步

```text
从节点发送复制请求
→ 主节点准备 RDB
→ 从节点清空/加载 RDB
→ 主节点把同步期间的新写命令补发
→ 进入持续命令传播
```

### 3. 断线后的增量同步

主节点通过复制 backlog 保存最近复制流，从节点带着自己的复制偏移量重连。如果缺失数据仍在 backlog 中，可以增量同步；如果已经被覆盖，就必须全量同步。

### 4. 为什么不能说主从强一致

主节点执行写入后通常立即向客户端返回，不等待从节点执行完。因此主从之间存在复制延迟，客户端读从节点可能读到旧值。复制提高冗余和可用性，但不天然提供强一致性。

## 十四、Sentinel 哨兵

### 1. Sentinel 解决什么问题

主从复制能保存副本，但主节点挂掉后，谁来把从节点提升为新主节点？Sentinel 负责监控、故障判断、主从切换和通知客户端。

### 2. 主观下线和客观下线

一个哨兵认为节点在规定时间没有响应，叫主观下线；多个哨兵通过投票达到 quorum，才可以将主节点判为客观下线。

判定故障和选出负责故障转移的 Sentinel 是两个阶段。生产环境一般部署奇数个哨兵并分散到不同故障域。

### 3. 故障转移流程

```text
判断主节点客观下线
→ 选出负责切换的 Sentinel
→ 从副本中选择合适节点提升为主
→ 其他副本复制新主
→ 通过通知让客户端更新主节点地址
→ 旧主恢复后降为新主的从节点
```

### 4. 主从切换仍可能丢数据

如果主节点已经向客户端返回写成功，但这条写入还未复制到任何副本，随后主节点故障，新主可能没有该写入。Sentinel 解决的是自动恢复服务，不是绝对零数据丢失。

## 十五、Cluster 集群

### 1. 为什么 Sentinel 不够

Sentinel 的主从副本保存相同数据。增加从节点不会把所有节点的内存简单合并成更大的数据空间。

Cluster 把不同 key 分到不同主节点：

```text
节点 A：一部分数据
节点 B：另一部分数据
节点 C：剩余数据
```

因此：

```text
复制：同一份数据存多份
分片：不同数据放到不同节点
```

### 2. 哈希槽

Cluster 把整个 key 空间划分为 16384 个哈希槽：

```text
slot = CRC16(key) % 16384
```

一个槽可以包含很多 key，16384 不是最多只能存 16384 个 key。

### 3. MOVED 和 ASK

客户端请求发到错误节点时，可能收到 MOVED，表示应更新槽到节点的映射；迁移期间可能收到 ASK，表示本次请求临时去另一个节点，并不能直接把它当成永久映射。

### 4. 多 key 操作

Cluster 中需要同节点执行的多 key 命令，通常要求 key 在同一槽。可以用 hash tag：

```text
order:{1001}:info
order:{1001}:items
```

花括号中的部分参与哈希，让两个 key 进入同一槽。但所有 key 使用同一个 tag 会形成热点。

## 十六、分布式锁

### 1. 为什么本地锁不够

服务器 A 的本地锁与服务器 B 的本地锁互相看不见，不能保护跨进程共享资源。Redis 锁通过大家共同访问一个 key，形成统一的竞争点。

### 2. 正确加锁

```redis
SET lock:order:1001 unique-token NX PX 30000
```

含义：key 不存在时才创建，值是本次请求唯一标识，30 秒后自动过期。

不能把 SETNX 和 EXPIRE 分成两条命令，否则 SETNX 成功后进程崩溃，锁可能永远不释放。

### 3. 为什么释放锁要 Lua

错误流程：

```text
A GET，发现 value 是自己的
→ 锁过期
→ B 加锁
→ A DEL，误删 B 的锁
```

正确做法是原子地判断和删除：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

### 4. 锁过期和看门狗

任务耗时超过 TTL 时，锁会自动释放，原任务可能仍然执行；新请求拿到锁后，两个请求可能同时修改资源。

看门狗会周期性续期，但网络故障、GC、进程暂停仍可能导致续期失败。唯一 token 防止误删，不等于防止旧客户端继续写业务资源。

严格业务可以使用 fencing token：每次取得锁得到递增编号，资源端拒绝比已见编号更小的请求。

### 5. Redlock

Redlock 在多个相互独立的 Redis 实例上加锁，超过半数成功且获取耗时小于有效租期，才认为成功。它解决部分单节点故障问题，但增加网络开销和实现复杂度，不能替代数据库唯一约束、幂等和资源端版本控制。

## 十七、缓存雪崩、击穿、穿透

### 1. 缓存雪崩

大量 key 同时过期，或者 Redis 整体不可用，导致大量请求访问数据库。

解决方法：TTL 加随机值、缓存预热、限流、熔断、降级、Redis 高可用和限制回源并发。

### 2. 缓存击穿

单个热点 key 过期，许多请求同时访问数据库。可以使用互斥锁/singleflight 只允许一个请求重建，其他请求等待或返回允许的旧值；也可以后台提前刷新热点数据。

### 3. 缓存穿透

请求的数据在缓存和数据库中都不存在，导致每次都访问数据库。可以进行参数校验、缓存短期空值、使用布隆过滤器。

布隆过滤器由位数组和多个哈希函数组成：判断不存在时结果可靠，判断存在时可能只是“可能存在”，仍需查询真实数据库。

## 十八、数据库和缓存如何保证一致性

### 1. 先删缓存再更新数据库的问题

```text
A 删除缓存
B 缓存未命中，查到数据库旧值 100
B 把 100 写入缓存
A 更新数据库为 120
```

结果数据库是 120，缓存是 100。

### 2. 先更新数据库再删缓存

这是常见 Cache Aside 写法：

```text
数据库事务成功提交
→ 删除缓存
```

它通常比“先删后改”更合理，但仍存在删除失败、旧读回填等窗口，不是无条件强一致。

### 3. 消息重试和 binlog

可以把删除缓存事件写入消息队列，失败时重试；也可以订阅 MySQL binlog，再由 CDC/Canal 触发删除。

消费消息时要“缓存删除成功后再确认”，否则先 ACK 后删除失败，就失去了重试机会。

### 4. 为什么删除通常比更新更合适

删除操作简单，缓存可能由多张表聚合，直接更新需要重新查询和计算全部内容。删除后按需回填，属于 Lazy Loading 思想。

## 十九、把整套 Redis 放进一个商品系统

```text
商品详情：String/Hash 缓存
用户点赞：Set
商品排行榜：ZSet
签到状态：Bitmap
访问 UV：HyperLogLog
异步库存事件：Stream
登录会话：String + TTL
热点重建：互斥锁或 singleflight
库存扣减：数据库条件更新或完整的 Redis 补偿方案
Redis 故障：限流、降级、主从/Sentinel/Cluster
```

完整读取流程：

```text
请求商品详情
→ 查询 Redis
→ 命中直接返回
→ 未命中时限制并发回源
→ 查询 MySQL
→ 回填 Redis 并设置 TTL
→ 返回
```

完整更新流程：

```text
MySQL 事务提交
→ 产生缓存失效事件
→ 删除 Redis
→ 删除失败就重试
→ 后续请求重新回填
```

## 二十、和 MySQL 八股文的对应关系

| MySQL 知识 | Redis 对应 | 关键区别 |
|---|---|---|
| B+ 树 | 哈希表、跳表 | 磁盘页索引与内存数据结构目标不同 |
| Buffer Pool | Redis 内存和淘汰 | MySQL 淘汰页副本，Redis 淘汰 key |
| redo/binlog | AOF/复制流 | 记录对象和恢复职责不同 |
| 事务回滚 | MULTI/EXEC、WATCH、Lua | Redis 不提供执行错误自动回滚 |
| 行锁/乐观锁 | 分布式锁/条件更新 | Redis 锁是有 TTL 的租约 |
| 主从复制 | Redis 主从 | 异步复制造成读旧和丢失窗口 |
| 数据库一致性 | 缓存一致性 | MySQL 更新和 Redis 删除不在同一事务 |

## 二十一、面试背诵版

### Redis 为什么快？

Redis 主要在内存中操作数据，使用高效的数据结构，并通过 I/O 多路复用管理大量网络连接。普通命令主要由单线程顺序执行，减少了线程切换和核心数据结构加锁开销。但大 Key、长脚本和返回大量数据仍会造成阻塞。

### Redis 为什么有多种数据类型？

不同业务需要不同操作：String 适合整体值和计数，Hash 适合对象字段，List 适合顺序列表，Set 适合去重和集合运算，ZSet 适合按分数排序，Stream 适合带消费组和确认机制的消息流。

### RDB 和 AOF 有什么区别？

RDB 保存某个时刻的数据快照，恢复通常较快但快照间数据可能丢失；AOF 记录写操作变化，数据丢失窗口可以更小，但文件重放和写入开销更大。AOF 重写用于压缩历史日志，Redis 7 以后还支持多部分 AOF 文件。

### 过期删除和内存淘汰有什么区别？

过期删除处理已经达到 TTL 的 key；内存淘汰处理内存达到上限时应该删除哪些 key，可能删除尚未到期的数据。

### 主从、哨兵、Cluster 有什么区别？

主从复制保存数据副本；Sentinel 负责监测故障和自动主从切换；Cluster 将数据按哈希槽分片，并提供分片内复制和故障转移。

### Redis 事务支持回滚吗？

Redis 的 MULTI/EXEC 可以保证事务命令按顺序、隔离地执行，但执行阶段某条命令出错时不会自动回滚已经成功的命令。WATCH 提供乐观并发控制，Lua 可以把多步逻辑放在服务端原子执行。

### 为什么分布式锁释放时要使用 Lua？

因为“检查锁的 value”和“删除锁”如果分成两条命令，锁可能在中间过期并被别人重新获得，旧客户端会误删新客户端的锁。Lua 可以让检查和删除不可被其他命令插入。

### 缓存雪崩、击穿、穿透有什么区别？

雪崩是大量缓存同时失效或缓存整体不可用；击穿是一个热点 key 失效后大量并发回源；穿透是请求的数据缓存和数据库都不存在。三者的触发原因不同，解决方案也不同。

## 二十二、最终学习顺序

第一轮：先学 Redis 模型、String、Hash、List、Set、ZSet，把自己的认证和缓存代码对应进去。

第二轮：学习单线程、底层哈希表、跳表、listpack，理解为什么 Redis 快。

第三轮：学习过期、淘汰、RDB、AOF，理解数据如何留下来和如何被删除。

第四轮：学习主从、Sentinel、Cluster，理解单节点故障和大数据量扩展。

第五轮：学习事务、Lua、分布式锁、缓存三大问题和数据库缓存一致性。

最终目标不是背命令，而是能够把任何一个 Redis 方案讲成：

```text
数据是什么
→ 为什么选这种结构
→ 命令如何执行
→ 并发时如何交错
→ 失败时留下什么状态
→ 通过什么机制恢复
→ 仍然有哪些边界
```
