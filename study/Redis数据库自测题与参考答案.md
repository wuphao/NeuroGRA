## 五、简答题参考答案

### 16. Redis 为什么快

常用数据主要在内存中访问，合适的数据结构降低查找和更新成本。核心命令串行执行减少了这一路径上的线程切换和锁竞争；I/O 多路复用让服务端可以管理许多连接，不必为每个连接安排一个阻塞线程。

但命令复杂度、处理元素数量、返回字节数、网络和资源争用都影响实际耗时。大范围扫描、长 Lua 脚本、大集合遍历仍可能占用主线程，拖慢其他请求；“单线程”也不是性能无限提升的保证。

### 17. 类型选择

| 场景 | 类型 | 代表性命令 |
|---|---|---|
| 整体读写商品 JSON | String | `SET product:1 '{"name":"book","price":100}' EX 300` |
| 修改昵称字段 | Hash | `HSET user:1 nickname Tom` |
| 简单先进先出队列 | List | 生产用 `LPUSH jobs task1`，消费用 `RPOP jobs` |
| 点赞去重 | Set | `SADD likes:article:1 user:1001` |
| 积分榜 | ZSet | `ZADD ranking 100 user:1001` |

List 从一端放入、另一端取出形成 FIFO。直接弹出后消息已离开列表，消费者若在业务处理前宕机，任务可能丢失。需要恢复能力时，可以设计处理中列表及超时重试，或使用 Stream 消费组，同时考虑 Redis 自身的数据可靠性。

### 18. SDS 与渐进式 rehash

SDS 显式保存长度，获取长度无需每次扫描整个字符串，并支持含零字节的二进制数据。它记录容量等信息，便于安全扩容，空间预留也能减少部分重新分配成本。

哈希表扩容或收缩时，若一次搬完所有条目，可能造成较长停顿。渐进式 rehash 将迁移拆成小步，在一段时间内完成；迁移期间部分数据在旧表、部分在新表，因此查找可能需要访问两张表。它平摊迁移工作，并不意味着扩容完全没有时间和内存成本。

### 19. 紧凑编码与跳表

紧凑编码减少指针、独立对象及分配开销，局部性较好，适合较小集合。代价是某些查找需要顺序扫描，修改可能涉及移动数据，因此规模扩大后未必合适。

较大 ZSet 的字典便于按成员查找分数，跳表维护按分数及同分成员顺序排列的结构，支持有序访问与范围查询。并不是所有 ZSet 都使用这套组合，小 ZSet 可以采用紧凑编码。InnoDB 的 B+ 树设计要兼顾页式存储与磁盘访问；Redis 主要在内存中工作，选型需要结合操作需求、内存成本和实现复杂度。

### 20. Pipeline、事务与 Lua

| 机制 | 主要用途 | 主要边界 |
|---|---|---|
| Pipeline | 批量发送，减少逐条等待的通信成本 | 不保证整个批次不可被其他客户端插入 |
| MULTI/EXEC | 入队后集中执行，执行期间不穿插其他客户端命令 | 不提供执行错误后的自动回滚；需要条件控制时可配合 WATCH |
| Lua | 在服务端完成依赖中间结果的读、判断、修改 | 脚本会占用命令执行线程，必须控制时长；运行时错误不自动撤销先前写入 |

“不可被并发命令穿插”和“失败后全部撤销”是两种不同保证。涉及脚本写入时，应在修改前尽量完成参数、类型和业务条件校验。

### 21. 持久化与写时复制

RDB 保存某个时间点的数据快照；AOF 用可重建数据状态的写入记录支持恢复。AOF 重写根据当前数据生成更精简的恢复内容，消除无须保留的历史变化，并非简单压缩旧文件，也不是完整的业务审计日志。

BGSAVE 通常通过 fork 创建子进程，父子进程起初共享物理页，父进程修改页面时才发生写时复制。fork 本身仍有页表等开销，持续写入会增加复制页和额外内存，后台写文件也会争用资源。[官方持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 22. 过期与淘汰

过期删除关注“有效期是否已到”；内存淘汰关注“是否需要为内存限制腾出空间”，尚未过期的键也可能被淘汰。惰性删除在访问键时检查过期，定期主动清理则在后台周期性抽样检查和清理过期键。

`allkeys-lru` 从所有键中选取近似最近最少使用的候选；`volatile-lru` 只考虑带过期时间的键。到达 TTL 表示键在访问语义上失效，不代表物理内存恰好在那一瞬间全部回收；不能把定期清理理解为每轮遍历所有键。

### 23. 高可用与分片

- 主从复制：维护数据副本，可支持读扩展和故障恢复，但需要处理复制延迟。
- Sentinel：监测主从状态，协调故障转移并提供主节点发现；不会自动分片数据。
- Cluster：把 16384 个槽分配到不同主节点，提供分片及结合副本的故障转移；每个槽可容纳许多键。

主观下线是单个 Sentinel 的判断，客观下线需要达到配置的 quorum；真正执行故障转移还涉及领导者选举和多数 Sentinel 授权，quorum 与多数派不能直接等同。

MOVED 通常提示客户端更新槽位路由并访问目标节点；ASK 常见于迁移期间，客户端对这次请求向目标节点先发 ASKING，再发原命令，不应仅凭 ASK 永久修改该槽的归属。

### 24. 三类缓存问题

| 问题 | 例子 | 对应措施 |
|---|---|---|
| 雪崩 | 大量缓存同一时刻过期，或整个缓存服务不可用 | 分散 TTL、预热、高可用、限流降级及数据库保护 |
| 击穿 | 一个高频商品缓存过期，大量请求同时回源 | 合并回源请求、互斥重建，或允许旧值时采用逻辑过期与后台刷新 |
| 穿透 | 持续查询不存在的商品 ID | 参数校验、短 TTL 的空结果缓存、布隆过滤器、限流 |

随机 TTL 只能分散到期时间，不能修复整个 Redis 服务故障。维护正确的布隆过滤器可用于排除确定不存在的成员，但“可能存在”有误判，仍需查询后续存储；新数据写入时还要处理过滤器更新。缓存空值时，应区分“数据库确定无数据”和“数据库暂时查询失败”。

### 25. 消息与近似统计

PEL 记录消费组中已投递但未确认的消息，XACK 将消息从相应待确认记录中移除。消费者失败后，其他消费者可以通过 XAUTOCLAIM 或 XCLAIM 等方式认领满足条件的待处理消息，再次尝试处理。

业务已提交但 ACK 丢失时，重新消费会重复执行，因此通常以消息 ID 或业务唯一键做幂等，并尽量将“记录已处理”和业务变更放在同一数据库事务中。能否恢复消息还依赖消息保留策略、持久化和复制等条件。

HyperLogLog 适合近似去重计数，但有统计误差，也不能列出原始访客 ID；如果需要精确成员列表，应选择其他结构。

## 六、综合大题参考答案

### 26. WATCH 与库存

**① 有 WATCH：**B 修改了 A 监视的键，A 的 EXEC 放弃执行事务队列，返回空结果（客户端具体表示可能不同）。最终库存为 0；这不是“先扣减再回滚”。

**② 没有 WATCH：**A 的 DECR 会在 B 扣减之后继续执行，最终库存为 -1。两次 DECR 各自原子，不代表“有库存才扣减”这个业务条件自动成立。

**③ 重试方式：**重新 WATCH，重新读取最新库存并检查，再决定是否开启和提交事务；设置重试次数、退避或失败返回。直接重发 DECR 会跳过库存校验；连接池使用时还应避免把同一连接交给别的并发请求。

**④ Lua 示例：**

```lua
local value = redis.call('GET', KEYS[1])
if not value then
    return 0
end
local stock = tonumber(value)
if stock < 1 then
    return 0
end
redis.call('DECR', KEYS[1])
return 1
```

将脚本保存为 `deduct.lua` 后，可在命令行调用：

```sh
redis-cli --eval deduct.lua stock
```

这里文件名只是调用示例，本题无需额外创建脚本文件。脚本的检查与扣减之间不会插入其他客户端命令。

**⑤ 超时重试：**超时可能发生在执行成功之后，直接重试可能再次扣减。应引入业务请求 ID，记录并复用处理结果；去重与扣减也必须正确协调。在 Cluster 中，用脚本一起访问的键还需满足同槽约束。上述库存脚本只解决并发条件判断，不自动解决幂等、订单落库或故障丢失问题。

### 27. 缓存一致性

**① 场景一：**数据库为 200，缓存为 100。B 在数据库更新前读到了旧数据，却在更新后回填，使旧值重新成为缓存内容。

**② 删除失败：**进程可能在重试前崩溃，内存中的待重试任务会丢失；持续网络故障也不能靠一次重试消除。需要可恢复的任务记录、重试机制和失败监控。

**③ 可恢复失效流程：**一种方案是在修改业务数据的同一个 MySQL 事务里写入 outbox 事件，提交后由后台工作者读取事件并删除缓存，失败则重试，成功后记录处理状态。另一种方案是订阅已提交的 binlog 变化并转成缓存失效任务，维护消费进度和重放能力。先提交数据库、再尽力发一条普通消息，中间仍有故障窗口。

**④ 两步成功仍有竞争：**假定缓存最初未命中，B 先从数据库读到旧值 100 后暂停；A 更新数据库到 200 并成功删除缓存；B 恢复后才把 100 写回。关键是 B 的旧读取发生在提交前，旧值回填发生在删除后。

**⑤ 缓解及边界：**TTL 使一次旧值回填后通常不会无限期保留，但过期前仍可能读旧值。延迟双删尝试在晚到的回填之后再次删除，但读请求耗时没有固定上界，也可能再次删除失败，不能选一个通用睡眠时间就得到强一致。强一致需求应单独设计读取权威数据、并发协调或版本校验流程。

### 28. 分布式锁

**① 误删：**第 7 秒同名锁属于 B，A 直接 DEL 会删除 B 的锁，随后第三个客户端还可能获取锁，进一步破坏互斥。

**② 安全释放脚本：**

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

调用时传入锁键和本次获取锁的唯一标识。比较和删除必须作为一个不可被其他命令穿插的操作执行。[官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

**③ 不能停止旧业务：**脚本能避免 A 误删 B 的锁，却不能让已过期的 A 自动停止修改数据库；第 7 秒 A 与 B 的业务仍可能重叠。

**④ 续约边界：**续约可以缓解正常长任务超过固定 TTL 的问题，但进程暂停、网络中断等仍可能使续约失败。续约也应原子验证锁标识；丢失锁后的业务处理不能假定由 Redis 自动回滚。

**⑤ fencing token：**每次获取权限时取得可靠、单调递增的令牌，资源端将令牌检查与业务写入原子结合，记录已接受的令牌，并拒绝之后到达的更旧令牌。例如资源端已接受 B 的 42，就拒绝 A 的 41。随机唯一标识能区分持有者，但没有大小顺序，不能直接替代 fencing token；令牌生成本身也需避免故障后倒退或重复。

### 29. 持久化与故障转移

**① 成功仍可能丢失：**题设中写入只在原主内存，既未可靠落盘，也未到达副本。断电后提升的副本没有收到它，因此新主缺少这条数据。

**② 原主落盘不等于新主拥有：**即使写入已存在于原主 AOF，新主仍可能没复制到。原主恢复后也不能假定这条独有数据会自动合并到新主；重新加入复制关系时需要服从新的数据历史。

**③ Sentinel 的职责：**三个 Sentinel 改善故障判定和故障转移的可用性，不参与每条业务写入的数据复制确认，不能消除异步复制窗口。

**④ WAIT 的边界：**在发出写入的同一连接上使用 WAIT，可等待指定数量副本确认此前写入对应的复制进度，从而降低部分丢失风险。但需检查实际返回的副本数量；超时不撤销已执行写入，也不意味着所有副本已刷盘，更不能自动获得强一致保证。

**⑤ 三种不同目标：**持久化支持从磁盘恢复，复制维护节点副本，故障转移帮助服务恢复可用。对于不能丢的订单、支付等业务事实，应以满足可靠性要求的事务存储为依据，并设计幂等、重试、对账及补偿；不能把 Redis 返回成功当成整个跨系统业务已可靠完成。

### 30. 延迟排查

数十万字段的 Hash 是大 Key 候选，主要问题是数据规模及操作成本；几百字节的商品键是热 Key，主要问题是单位时间访问量。一个键可能同时具备两种特征，也可能只满足一种。

| 可能原因 | 应收集的证据 | 优化方向 |
|---|---|---|
| 大集合遍历、KEYS 等占用主线程 | SLOWLOG、命令频率、集合规模、返回字节数 | 按需读取、分批遍历、控制单次工作量 |
| 热 Key 或总体请求过多 | 各键/业务访问量、CPU、网络带宽、各分片负载 | 合并请求、本地缓存、限流，按业务评估复制读 |
| fork、写时复制及持久化资源争用 | 持久化时间线、latest_fork_usec、COW 指标、内存余量、磁盘延迟 | 降低单实例规模、预留内存、平滑写入、评估存储能力 |
| 客户端连接池排队 | 获取连接耗时、池占用、等待队列、应用线程状态 | 修复连接泄漏、控制并发，结合服务端容量调整连接池 |
| 网络与大响应传输 | RTT、丢包、带宽、响应体积、客户端解析耗时 | 缩小响应，改善链路和部署位置 |

慢日志主要记录命令执行耗时，不包含客户端连接池等待，也不完整反映网络传输等时间；短命令还可能排在慢命令后等待，因此要按端到端访问阶段拆分延迟，并考虑慢日志阈值和保留数量。

- **HGETALL：**只需少数字段时改为 HGET/HMGET；确需遍历时使用 HSCAN 分批处理，并理解它不提供整次遍历的快照，需要处理重复及并发变化。
- **KEYS：**运维遍历使用 SCAN，循环到游标返回 0，并限制批次及速率；COUNT 不是硬性数量保证。
- **删除大 Key：**评估使用 UNLINK，降低同步内存释放造成的阻塞，同时关注后台回收积压，不能认为资源消耗消失了。
- **热 Key：**本地短期缓存和请求合并能减少 Redis 压力，但要接受或处理多份缓存的一致性；副本读要接受复制延迟。单纯增加 Cluster 节点不会自动把一个键分散到多个主节点。
- **持久化压力：**控制单实例数据规模、为 COW 预留内存并平滑写入，结合磁盘能力调整策略。减少持久化频率可能扩大数据丢失窗口，不能只按吞吐量决定。
