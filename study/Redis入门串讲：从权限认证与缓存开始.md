# Redis 入门串讲：从权限认证与缓存开始

> 适合的基础：使用过 Redis 做权限认证、登录状态保存和缓存，但还没有形成完整的知识体系。
>
> 本文按业务问题逐步展开：先理解你已经使用过的功能，再连接数据类型、并发、过期、持久化和多节点部署。跳表、写时复制等内部实现可以留到第二轮学习。
>
> 示例代码用于解释流程，不是可直接上线的完整实现；未连接本地 Redis 执行。

## 一、为什么之前的文档读起来接不上

Redis 资料经常把四个层次放在一起讲：

1. **业务用途**：缓存、登录状态、排行榜。
2. **使用方式**：SET、GET、Hash、Set、ZSet。
3. **内部实现**：哈希表、跳表、事件循环。
4. **可靠性问题**：持久化、复制、故障切换、缓存一致性。

刚理解缓存，就开始研究跳表或哨兵，很容易失去主线。

对你而言，更自然的顺序是：先回顾认证和缓存的请求流程，再问数据怎样组织、并发怎样处理、出故障怎么办。

## 二、从权限认证开始：你往 Redis 里存的是什么

假设用户登录成功，后端生成一个随机 token：

```text
token = abc123
```

然后在 Redis 中保存：

```text
键：login:abc123
值：用户 1001 的登录信息
有效期：30 分钟
```

用简化命令表示：

```redis
SET login:abc123 '{"user_id":1001,"role":"admin"}' EX 1800
```

三个部分分别是：

- `login:abc123`：用来找到这份数据的名字，即 key。
- JSON 内容：实际保存的数据，即 value。
- `EX 1800`：1800 秒后过期。

这里的 abc123 只是演示值，实际会话标识需要足够随机且难以猜测。

用户之后访问接口，携带 token：

```text
浏览器发送请求，携带 abc123
          ↓
后端提取 token
          ↓
后端查询 Redis：GET login:abc123
          ↓
找到登录信息：知道请求者是用户 1001
          ↓
后端判断用户是否有权执行这次操作
```

**Redis 负责保存和查询登录状态，真正判断权限的是后端代码。**

```python
# 流程伪代码
login_info = redis.get("login:" + token)

if login_info is None:
    return "请重新登录"

user = parse(login_info)

if user["role"] != "admin":
    return "没有权限"

return perform_admin_operation()
```

这个场景里有三个不同概念：

| 概念 | 回答的问题 | 谁负责 |
|---|---|---|
| 身份认证 | 你是谁？是否已登录？ | 后端结合 token、登录状态等判断 |
| 权限校验 | 你能不能执行这个操作？ | 后端权限逻辑 |
| 状态存储 | 登录信息放在哪里，如何查询？ | 可以由 Redis 承担 |

如果你之前使用的是 JWT，流程可能不同：后端可以校验 JWT 签名，Redis 用于保存退出记录、黑名单或其他会话状态。本文先用“随机 token + Redis 登录记录”的模型建立理解。

还有一个需要留意的问题：如果用户的角色变了，而登录记录仍保存旧角色，后端可能继续按旧权限判断。因此角色变更后，可能需要更新或失效相关会话，也可以在敏感操作时重新读取权限。Redis 不会自动知道权限表发生了变化。

## 三、为什么登录状态适合放在 Redis

先假设不用 Redis，把登录信息放在 Python 字典或 Java Map 中：

```python
login_users = {
    "abc123": {
        "user_id": 1001,
        "role": "admin"
    }
}
```

只有一个后端进程时，这样可以工作。

但部署两个后端实例后：

```text
                 ┌── 后端 A：保存了 abc123
用户 → 负载均衡 ─┤
                 └── 后端 B：没有 abc123
```

用户在 A 上登录，下一次请求却到了 B。B 查询自己的内存，没有找到对应登录信息。

问题是：**不同进程里的普通字典，默认不共享数据。**

引入 Redis 后：

```text
                 ┌── 后端 A ──┐
用户 → 负载均衡 ─┤            ├── Redis：统一保存登录状态
                 └── 后端 B ──┘
```

不管请求落在哪个后端，都去同一个 Redis 查询。

Redis 还提供有效期管理：

```text
登录成功 → 保存登录记录，设置 30 分钟有效期
用户退出 → 后端删除登录记录
记录过期 → 后端查询不到，要求重新登录
```

你之前使用 Redis，不只是因为它快，还因为它解决了：

> 多个后端共享临时状态，并管理这些状态的生命周期。

## 四、Redis 本身是什么

可以先把 Redis 理解成一个**能通过网络访问、提供多种数据操作的大字典服务**。

普通字典位于应用程序内部：

```python
data["name"] = "Tom"
```

Redis 独立运行，应用通过网络向它发送命令：

```redis
SET name "Tom"
GET name
```

基本对应关系是：

```text
普通字典：
应用程序 → 自己进程里的内存

Redis：
应用程序 → 网络连接 → Redis 服务 → Redis 管理的内存
```

Redis 也是数据库，因为它负责组织、存储和访问数据，只是数据模型与 MySQL 不同。

MySQL 中你习惯这样操作：

```sql
SELECT name FROM users WHERE id = 1001;
```

Redis 中，通常需要先设计键：

```redis
GET user:1001:name
```

`user:1001:name` 是一个完整字符串。冒号是命名习惯，不意味着 Redis 自动创建了 user 表、1001 行和 name 列。

**Redis 很擅长在你已经知道键名时，快速找到对应数据。**

但如果要查询：

```text
所有年龄大于 20 岁、
居住在上海、
最近一个月下过单的用户
```

基础 Redis 键值操作不会自动像 SQL 一样完成关联查询。你需要提前设计数据组织方式，或者交给适合这类查询的数据库。

先建立这个认识：

> MySQL 擅长围绕表、关系、条件和事务处理业务数据；Redis 的基础能力围绕键和数据结构操作展开。

MySQL 也使用内存缓存数据页，不能把性能差异简单理解成“MySQL 每次读磁盘，Redis 每次读内存”。具体性能还与操作复杂度、网络、数据大小等有关。

## 五、从缓存理解 Redis 与 MySQL 的配合

假设有一个查询用户信息的接口：

```http
GET /users/1001
```

最开始每次都查询 MySQL：

```text
请求 → 后端 → MySQL → 返回用户信息
```

如果同一用户的信息被反复查询，而数据很少变化，就可以把查询结果临时放到 Redis：

```text
key：user:1001
value：{"name":"Tom","age":20}
```

读流程变成：

```text
请求查询用户 1001
        ↓
先查 Redis
        ├── 有数据 → 直接返回
        │
        └── 没数据 → 查 MySQL
                      ↓
                 把结果写入 Redis
                      ↓
                    返回
```

用伪代码表示：

```python
def get_user(user_id):
    key = f"user:{user_id}"

    cached = redis.get(key)

    if cached is not None:
        return deserialize(cached)

    user = mysql.query_user(user_id)

    if user is not None:
        redis.set(key, serialize(user), ex=600)

    return user
```

找到缓存叫**缓存命中**；没有找到叫**缓存未命中**；未命中后查询原始数据源，常称为**回源**。

**Redis 不会因为自己没找到数据，就自动查询 MySQL。**

是 get_user 函数完成了查询 Redis、判断结果、查询 MySQL、回填 Redis 这些步骤。

因此：

> 缓存是应用围绕 Redis 设计的一种使用方式。

Redis 自己只知道有人要求它保存、读取或删除某个键。

## 六、登录状态和缓存的数据地位不同

它们看起来都在执行 SET 和 GET，但数据的作用不同。

| 场景 | Redis 中的数据是什么 | 数据没了之后 |
|---|---|---|
| 用户资料缓存 | MySQL 数据的一份临时副本 | 可以重新查询 MySQL |
| 只保存在 Redis 的登录会话 | 当前有效登录状态 | 可能需要用户重新登录 |
| 可重新计算的排行榜 | 计算结果 | 可以重新生成，但可能有成本 |
| 只保存在 Redis 的任务记录 | 尚未完成的工作 | 丢失后可能漏处理 |

因此，“Redis 数据丢了能不能接受”不能统一回答。

应先问：

> 这份数据有没有其他来源？丢失后能否重建？重建需要多久？

这也是后面学习持久化和主从复制之前，必须想清楚的问题。

## 七、为什么还要学 String、Hash、List、Set、ZSet

因为 **value 可以是一整块数据，也可以是一个能直接操作的数据结构**。

先看熟悉的 JSON 缓存：

```redis
SET user:1001 '{"name":"Tom","age":20}'
```

Redis 将其作为整段字符串保存，不会自动理解 age 字段。

如果要把年龄加一，最直观的应用流程是：

```text
取出整个 JSON
→ 解析 JSON
→ 修改 age
→ 重新序列化
→ 写回整个 JSON
```

如果使用 Hash，可以用另一个示例键表示：

```redis
HSET user:1001:profile name "Tom" age 20
```

结构是：

```text
user:1001:profile
├── name → Tom
└── age  → 20
```

可以直接修改字段：

```redis
HINCRBY user:1001:profile age 1
```

这里使用不同键名，是因为已经保存为 String 的键不能直接用 HSET 当作 Hash 操作，否则会出现类型错误。

**数据类型的意义，是让 Redis 提供适合这种数据的操作。**

| 业务需要 | 合适的类型 | 原因 |
|---|---|---|
| 保存整份 JSON、token 对应信息 | String | 整体读取和写入 |
| 单独读取、修改对象字段 | Hash | 可以按字段操作 |
| 按顺序放入和取出任务 | List | 支持两端插入、弹出 |
| 记录哪些用户点过赞 | Set | 成员去重 |
| 根据分数生成排行榜 | ZSet | 支持分数排序、排名、范围查询 |

第一轮先问“需要对这份数据做什么操作”，再选择类型。跳表和 listpack 是下一层的实现问题。

## 八、点赞场景：数据结构怎样减少业务代码

如果只存点赞数：

```text
article:88:likes = 100
```

你知道有 100 个赞，却不知道用户 1001 是否已经点过赞。

使用 Set：

```redis
SADD article:88:liked_users 1001
```

表示把用户 1001 加入点赞者集合。重复执行，也不会多出第二个 1001。

可以直接查询：

```redis
SISMEMBER article:88:liked_users 1001
SCARD article:88:liked_users
```

分别回答：

```text
用户 1001 点过赞吗？
总共有多少个不同用户点赞？
```

不必每次把所有点赞者取到应用中，再自己去重。

类似地，排行榜可以使用：

```redis
ZADD game:ranking 100 alice 200 bob 150 carol
ZREVRANGE game:ranking 0 2 WITHSCORES
```

在这个独立示例中，按分数从高到低返回 bob、carol、alice。应用不必每次取回所有成员再重新排序。

## 九、并发计数：一条命令和多条命令不一样

假设访问次数初始为 10，应用这样更新：

```python
count = int(redis.get("views"))
redis.set("views", count + 1)
```

两个请求同时执行时：

```text
请求 A 读到 10
请求 B 也读到 10
请求 A 写入 11
请求 B 也写入 11
```

访问两次，却只增加一次。

改成：

```redis
INCR views
```

两个请求各执行一次：

```text
第一次：10 → 11
第二次：11 → 12
```

需要区分：

- 单条 INCR 将读、加一、写回封装成一个原子操作。
- 应用中的 GET 加 SET 是两个独立操作，中间可以插入其他请求。

> Redis 普通命令主要顺序执行，不意味着整个后端函数自动没有并发问题。

以后学习事务、Lua 和分布式锁，就是继续解决“多个步骤之间如何协调”。

## 十、缓存过期解决什么问题

给用户资料设置十分钟有效期：

```redis
SET user:1001 '{"name":"Tom","age":20}' EX 600
```

可以限制临时数据存活时间，也给旧缓存提供失效机会。

但它不能保证缓存与数据库实时一致：

```text
12:00 缓存 age=20，有效期十分钟
12:01 MySQL 中改成 age=21
12:02 请求命中缓存，仍读到 age=20
```

Redis 不知道 MySQL 变了，所以仍返回自己保存的值。

一种常见更新路径是：

```text
更新 MySQL 并成功提交
→ 删除对应 Redis 缓存
→ 下次查询从 MySQL 获取新值并回填
```

先理解这条正常路径。并发旧值回填、删除失败和消息补偿，是在这条路径上继续分析异常情况。

这里不能直接得出强一致保证：两次操作可能部分失败，不同请求也可能交错。这正是详细文档中缓存一致性章节要解决的问题。

## 十一、内存有限：过期与淘汰是两回事

假设很多缓存都设置了一小时 TTL，只过了十分钟，Redis 就已经接近设置的容量限制。

此时有两个问题：

```text
数据已经到期了吗？
→ 过期机制处理

数据还没到期，但空间不够了怎么办？
→ 内存淘汰策略处理
```

可以选择优先移除很久没访问的数据、访问频率低的数据，或者不淘汰而拒绝某些需要更多内存的写入。

因此：

> 设置一小时 TTL，不代表缓存一定能保留一小时。

它可能被应用提前删除，也可能被内存淘汰。

这与登录认证相关：如果登录记录提前被移除，用户可能提前失去登录状态。重要状态和可重建缓存是否混用、采用什么淘汰策略，应结合业务决定。

另外，Redis 淘汰键后，不会在下一次 GET 时自动按键从 AOF 文件读回来。缓存回源仍由应用负责。

## 十二、内存数据重启怎么办：持久化

理解保存、访问和清理数据之后，自然会问：

```text
Redis 进程关闭，内存里的数据怎么办？
```

这时引入 RDB 和 AOF。

### 1. RDB：保存某个时刻的数据状态

```text
12:00 保存一份快照：
user:1001 = ...
views = 100
ranking = ...
```

恢复时读取快照。如果 12:03 故障，仅靠 12:00 的快照，无法恢复之后所有修改。

### 2. AOF：保存用于恢复状态的写操作记录

可以先这样理解：

```text
设置 views=100
增加 views
增加 views
……
```

恢复时根据记录重建数据。写入是否已经安全保存到磁盘，还取决于刷盘策略与实际执行情况。

| 机制 | 第一层理解 |
|---|---|
| RDB | 保存一个时点的数据状态 |
| AOF | 保存写入变化，帮助恢复状态 |

fork、写时复制和 AOF 重写，解释的是“怎样更高效地完成这些工作”。可以在理解持久化目的后再深入。

## 十三、为什么还需要主从、哨兵和 Cluster

持久化主要回答：

```text
重启后，怎样恢复数据？
```

它没有完整回答：

```text
机器现在坏了，谁来接请求？
数据太多，一台机器放不下怎么办？
```

### 1. 主从复制：再保存一份数据

```text
主节点
  ├── 复制到从节点 A
  └── 复制到从节点 B
```

主节点接受写入，把变化复制给从节点。这样有其他数据副本，但复制通常有延迟，不能默认所有节点随时完全相同。

### 2. 哨兵：主节点故障后组织切换

```text
发现主节点故障
→ 选择适合的从节点
→ 提升为新主节点
→ 客户端连接新主节点
```

哨兵负责监测和故障管理，通常不替每个业务请求转发数据。

### 3. Cluster：把不同数据分开放

```text
节点 A：保存一部分键
节点 B：保存另一部分键
节点 C：保存其余键
```

与复制对照：

```text
复制：同一份内容，多存几份
分片：不同的内容，分到不同地方
```

Cluster 中各个分片还可以有副本，同时处理数据规模和部分故障恢复问题。

| 遇到的问题 | 引出的机制 |
|---|---|
| 进程重启，内存数据怎么恢复 | 持久化 |
| 想在其他节点保存副本 | 主从复制 |
| 主节点故障，怎样自动换一个 | 哨兵 |
| 单个节点容量或负载不够 | Cluster 分片 |

自动切换仍可能有短暂停顿，异步复制也可能留下数据丢失窗口。它们提高可靠性，但不能被理解成任何情况下零丢失、零中断。

## 十四、将 Redis 知识串成一条学习主线

你做过的认证和缓存，属于最上层的业务使用。每深入一层，都是回答实践中自然出现的问题：

```text
我要保存登录信息、缓存用户资料
             ↓
Redis 是什么，SET/GET 怎样使用？
             ↓
数据不只有字符串，怎样选择类型？
             ↓
多个请求一起修改，怎样避免冲突？
             ↓
数据什么时候过期，内存满了怎么办？
             ↓
进程重启，数据怎样恢复？
             ↓
机器故障，服务怎样继续？
             ↓
数据和流量增长，怎样分散到多台机器？
             ↓
Redis 与 MySQL 同时保存信息，怎样控制不一致？
             ↓
这些功能内部为什么能高效实现？
```

底层数据结构可以放到后面深入。当你知道 ZSet 能做排行榜，再研究跳表为什么适合它，就有了明确目的。

## 十五、结合你已有项目，先回答这些问题

### 1. 认证功能

- 登录成功后，Redis 中的键名是什么？
- 值里保存用户 ID、角色，还是其他信息？
- 请求到来时，后端如何查到这份记录？
- 有效期多久？访问时是否续期？
- 退出登录时删除什么？
- 用户角色被修改后，旧权限怎样失效？

### 2. 缓存功能

- 缓存的原始数据在哪里？
- Redis 未命中时，哪段代码查询数据库？
- 数据库更新后，谁删除或刷新缓存？
- 缓存失效后，很多请求会不会同时回源？
- Redis 暂时不可用时，应用会怎样处理？

### 3. 学习任何一个 Redis 用法时的三个核心问题

1. **这条数据是谁写入、谁读取、什么时候删除？**
2. **它是唯一状态，还是可以从 MySQL 重建的副本？**
3. **需要对它做哪些操作，因此应该选择什么类型？**

先把自己项目中这两条完整链路讲清楚，再进入底层原理，会更容易把新知识接到已有经验上。
