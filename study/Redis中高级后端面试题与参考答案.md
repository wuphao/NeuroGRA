## 一、单选题：基础机制与关键边界

### 1. SET 覆盖与 TTL

依次执行以下命令，中间没有等待到过期，也没有其他操作：

```redis
SET interview:session token-1 EX 60
SET interview:session token-2
TTL interview:session
```

TTL 的结果是？

- A. 接近 60，旧 TTL 自动保留。
- B. 120，两次 SET 的有效期累加。
- C. -1，键存在，但已没有过期时间。
- D. -2，第二次 SET 删除了键。

## 二、多选题：识别正确性边界

每题有两个或以上正确选项。

### 21. 线程与延迟

下列说法正确的有？

- A. 网络 I/O 并行不等于普通写命令可以任意并行修改同一 key。
- B. 少量长命令可能拖高许多短命令的端到端延迟。
- C. SLOWLOG 没有记录某条 GET，就证明该请求一定没经历排队。
- D. 评估 I/O 线程应先确认版本、配置和实际瓶颈。

### 22. 事务、WATCH 与 Lua

下列说法正确的有？

- A. WATCH 是在 EXEC 时检查相关变化，不是阻止其他请求修改的悲观锁。
- B. Lua 返回运行时错误，就会撤销此前所有写入。
- C. Lua 可将 Redis 内的检查和修改放在不可穿插的执行段中。
- D. 使用连接池时，WATCH/MULTI 序列需要正确绑定连接，避免状态被其他请求混用。

### 23. 持久化与 COW

下列说法正确的有？

- A. write 写到操作系统页缓存，不等于已经完成稳定存储同步。
- B. COW 的成本与修改过的不同共享页有关，不能只按新值的几个字节计算。
- C. BGSAVE 在子进程执行，所以没有 fork、内存和 I/O 成本。
- D. Redis 7 的多部分 AOF 使用基础文件、增量文件及 manifest 管理恢复集合。

### 24. 缓存一致性

下列说法正确的有？

- A. Outbox 可将业务修改与待发送事件记录放在同一个数据库事务中。
- B. CDC 失效事件一旦最终送达，就自动排除了所有旧读回填。
- C. TTL 和可靠失效能降低风险，但需要结合在飞行读请求和陈旧度目标分析。
- D. 只要先更新数据库再删缓存，就无条件获得全局强一致。

### 25. 缓存故障保护

下列措施合理的有？

- A. Redis 故障时，让所有请求无限制直接查数据库。
- B. 根据数据库承载能力设置回源并发或速率预算。
- C. 对同一查询做进程内请求合并，必要时再协调跨实例重建。
- D. 允许旧值时，定义旧值最长可服务期限，而不只规定刷新时间。

### 26. 锁和资源端安全

下列说法正确的有？

- A. 解锁时比较 token 与删除必须原子协调。
- B. 租约失效后，旧持有者仍可能继续访问数据库。
- C. 任何异步复制的 Redis INCR 都无条件提供永不回退的 fencing 令牌。
- D. fencing 需要资源端把令牌检查与业务写入正确结合。

### 27. 复制与 Sentinel

下列说法正确的有？

- A. 复制 offset 表示复制流的字节进度，不是业务记录数。
- B. Sentinel 的多数投票意味着每条 Redis 数据写入都按多数派提交。
- C. 部分重同步需要兼容的复制历史身份与仍被保留的缺失历史。
- D. 故障判断 quorum 与故障转移授权中的多数要求应分别分析。

### 28. Cluster 与热点

下列说法正确的有？

- A. 有效 hash tag 可将相关键放到同一槽，方便共同操作。
- B. 增加 Cluster 主节点不会自动把一个普通 hot key 分散到多个主节点。
- C. 客户端拆分跨槽批量读取再合并结果，不等于提供全局一致快照。
- D. 各节点槽数量相同，就保证字节量和命令成本相同。

### 29. 版本变化

下列说法正确的有？

- A. Redis 7.4 引入 Hash 字段级过期，不能把“Hash 只能整 key 过期”当成通用结论。
- B. WAITAOF 从 Redis 7.2 起提供，对应 AOF fsync 确认需求。
- C. Redis 7.4 的 EVAL 脚本缓存永远不会丢失，EVALSHA 不必处理 NOSCRIPT。
- D. Redis 8.4 的 DELEX IFEQ 可用于简单 String 锁的原子比较后删除。

### 30. Stream 消费

下列说法正确的有？

- A. Redis 7.2 中，持续使用 XREADGROUP 的 `>` 会自动重投所有消费者的旧 PEL。
- B. 待确认消息被另一个消费者认领，不代表原消费者已经停止外部业务。
- C. 业务提交成功但 ACK 前崩溃，可能导致重复交付。
- D. PEL、正文保留、数据库幂等及 Redis 持久化需要分别设计。

## 四、综合场景题：画时序、算预算、说明验证

### 46. 商品价格缓存的旧读回填

初始数据库价格为 100、版本为 10，缓存不存在。发生以下时序：

```text
t1  R 查询数据库，得到 price=100、version=10，随后暂停。
t2  W 提交 price=120、version=11。
t3  W 成功删除缓存。
t4  R 恢复，将 price=100、version=10 回填。
```

## 六、选择题逐题解析

### 第 1 题：C

成功的普通 SET 会丢弃旧 TTL，键仍存在，TTL 返回 -1。需要保留时使用适用的 KEEPTTL，或明确设置新的有效期；不能把覆盖值与更新 TTL 混为一谈。[官方 SET 说明](https://redis.io/docs/latest/commands/set/)

### 第 2 题：D

超时可能发生在命令执行之后、客户端收到结果之前。DECR 本身原子，不等于重复执行安全。相同业务重试应沿用 request_id，并查询或复用处理结果；还要分析去重状态丢失的边界。

### 第 3 题：A

Pipeline 优化传输和等待，不自动提供整批隔离、回滚或跨节点原子提交。若后续逻辑依赖前面读到的状态，应评估原生命令、WATCH 或短脚本。[官方 Pipeline 说明](https://redis.io/docs/latest/develop/using-commands/pipelining/)

### 第 4 题：B

脚本已完成 SET，再发生 INCR 错误。Redis 不会自动撤销先前写入。应先验证输入与类型，并控制写入步骤；不可穿插与错误回滚是两种不同保证。[Redis 官方：事务与回滚](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)

### 第 5 题：D

Redis 7.2 中，WATCH 期间的过期会导致 EXEC 放弃队列。WATCH 不冻结 TTL。官方特别指出 6.0.9 之前的过期行为不同，因此必须注明版本。[官方 WATCH 与过期说明](https://redis.io/faq/doc/11ed4zroc6/can-a-key-expire-within-a-multi-exec-transaction)

### 第 6 题：C

`0.99 × 20 + 0.01 × 5000 = 69.8μs`。1% 慢命令贡献了 50μs 的平均成本，大于 99% 短命令贡献的 19.8μs。理想能力约 1.43 万条/秒，不能按短命令估成 5 万条/秒。

### 第 7 题：A

`3000 × 200 × 1024 × 8 = 4,915,200,000 bit/s`，约 4.92Gbit/s，只计算正文就超过题设链路能力。连接与 I/O 线程不会增加物理带宽，需要减小响应、减少请求或改善链路。

### 第 8 题：D

小规模线性扫描可能很短，紧凑布局还能节省指针和分配元数据、改善局部性。规模与元素大小增长后，再评估转换编码。listpack 不保证所有操作 O(1)，中间修改仍可能移动字节。[官方内存优化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

### 第 9 题：B

span 表示前进指针跨越的底层成员数，查找时累计这些数量以计算排名。插入和删除还要维护跨度，否则顺序统计会错误。[Redis 7.2.0 ZSet 源码](https://github.com/redis/redis/blob/7.2.0/src/t_zset.c)

### 第 10 题：C

SCAN 可以一次不返回元素，COUNT 也只是工作量提示。完整遍历以游标回到 0 为结束条件；结果可能重复，且不是整次过程的一致性快照。[官方 SCAN 说明](https://redis.io/docs/latest/commands/scan/)

### 第 11 题：A

本地持久化与复制是两条进度线。题设副本未收到更新，新主可能缺少它；旧主重新加入后，也不能假定其独有数据会自动合并为正确业务历史。[官方复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

### 第 12 题：D

返回数组分别表示本地与副本的 AOF fsync 确认数量。[1,0] 未满足请求的一个副本确认。确认不足不回滚业务写入，也不能直接按“未执行”再次扣减。[官方 WAITAOF 说明](https://redis.io/docs/latest/commands/waitaof/)

### 第 13 题：C

缓存值被删除，version 也一起消失。若“没有值就接受”，旧读可以回填。需要保留足以阻止旧写的状态，或选择另一套满足陈旧度目标的协议；单独增加一个字段没有完成一致性设计。

### 第 14 题：B

随机 token 区分每次租约的所有者，原子比较后删除能防误删。它不停止旧持有者、不保证续约成功，也不消除所有复制故障窗口。[官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 第 15 题：D

资源已经接受 42，之后必须拒绝 41。检查与修改应在资源端正确结合。fencing 比较的是使用权代际，随机 UUID 没有可用的新旧顺序。

### 第 16 题：A

quorum 用于客观下线判断，故障转移还要满足多数授权。5 个已知 Sentinel 的多数至少为 3；仅两个互通不能据此完成授权。[官方 Sentinel 说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

### 第 17 题：C

经典 Cluster 共同访问多键的操作一般要求同槽。同一物理节点可能拥有很多槽，并不替代槽约束。有关只读脚本等特殊能力也应按明确版本和配置讨论，不能当通用例外。

### 第 18 题：B

题目限定 Redis 7.2 的经典迁移路径。迁移中，同槽多键分散或部分不存在时，可返回 TRYAGAIN。同槽是基本资格，不保证迁移期立即成功；不要把后续迁移机制变化直接套入此题。[官方 Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

### 第 19 题：A

XACK 移除该消费组的待确认记录，不会自动删除正文。没有其他删除或裁剪，XLEN 仍为 1。[官方 XACK 说明](https://redis.io/docs/latest/commands/xack/)

### 第 20 题：B

固定窗口约束的是各自的一分钟区间，不是任意连续 60 秒。题设两个窗口分别计数，短时间可以出现双倍突发。是否能接受，要由业务的流量形状要求决定。

### 第 21 题：A、B、D

区分网络收发、普通命令执行和后台任务。长命令会形成等待，慢日志主要记录执行时间，不能完整反映排队与网络。C 把测量范围扩大成了端到端证明，错误。[官方 SLOWLOG 说明](https://redis.io/docs/latest/commands/slowlog/)

### 第 22 题：A、C、D

WATCH 是乐观检查，Lua 可以协调 Redis 内的判断与写入，连接状态操作应绑定合适的连接。B 错在把异常返回当成自动回滚。[官方事务说明](https://redis.io/docs/latest/develop/using-commands/transactions/)

### 第 23 题：A、B、D

区分页缓存与稳定存储、按共享页理解 COW、按版本理解 AOF 文件组织。C 错在把后台工作视为零成本，fork、写时复制和资源争用仍可能影响请求。[官方持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 第 24 题：A、C

Outbox 改善“数据提交而事件没有可靠记录”的窗口；TTL 提供某些生命周期兜底。B/D 没有考虑事件延迟、旧读回填及部分失败，不能证明全局强一致。

### 第 25 题：B、C、D

缓存故障时，下游预算比“直接查库”的代码分支更重要。同键合并降低重复工作，硬期限限定旧值使用范围。A 可能把缓存故障扩大成数据库故障。

### 第 26 题：A、B、D

锁释放、旧持有者继续运行、资源端新旧代际校验是三个不同层次。C 忽略异步复制后的计数器回退/历史丢失风险；令牌来源本身也必须满足业务所需条件。

### 第 27 题：A、C、D

offset 是字节进度；部分重同步还依赖历史身份与保留区间；Sentinel 故障判断和切换授权不同。B 混淆控制故障转移的投票与数据复制协议。

### 第 28 题：A、B、C

hash tag 支持共同操作，但也可能集中压力；普通单 key 不自动拆分。跨槽拆分读取是多次独立读取。D 错在把槽数均衡当成负载均衡。

### 第 29 题：A、B、D

Hash 字段过期、WAITAOF 和 DELEX 都有版本边界。C 错在把临时脚本缓存当永久部署状态；Redis 7.4 起，EVAL/EVAL_RO 加载的脚本还有缓存淘汰行为。

对应一手资料：[Hash 字段过期](https://redis.io/docs/latest/develop/data-types/hashes/)、[WAITAOF](https://redis.io/docs/latest/commands/waitaof/)、[EVAL](https://redis.io/docs/latest/commands/eval/)、[DELEX](https://redis.io/docs/latest/commands/delex/)。

### 第 30 题：B、C、D

Redis 7.2 的 `>` 主要领取组内尚未交付的新消息，不自动重投所有旧 PEL。认领不能停止旧进程的外部动作；业务提交到 ACK 间存在重复交付窗口，还要管理正文保留。[官方 XAUTOCLAIM 说明](https://redis.io/docs/latest/commands/xautoclaim/)

## 七、问答题参考答案

### 第 31 题：Redis 为什么快，又为什么会慢

**主干答案：**常用数据在内存中访问；按键与相应数据结构执行操作，路径较短；事件驱动管理连接，普通命令的顺序执行减少核心数据结构的并发协调。实际性能还取决于命令工作量、字节数、网络和客户端。

**需要展开：**

1. 一个 key 查找快，不代表返回大对象快；结果编码、传输和解码都处理实际字节。
2. 长脚本、全量集合操作、同步释放大对象会影响执行线程或其他资源。
3. 短 GET 可在慢命令后等待，应用也可能在借连接或事件线程调度时等待。
4. 持久化、fork/COW、复制与资源争用可能带来突发成本。
5. 评价容量要固定版本、数据规模、命令组合、并发、Pipeline、部署距离和持久化条件，同时看吞吐、P99、错误率与资源余量。

**追问：**99% 短命令为何仍可能有很差的尾延迟？回答服务成本分布与排队，而不只背“内存很快”。

**2 分要点：**性能来源与成本范围 1 分；能解释长命令/大响应/排队及测量条件 1 分。

### 第 32 题：类型、编码与数据结构取舍

**主干答案：**type 决定对外语义和命令，encoding 决定当前内部表示。同一个 Hash 或 ZSet 可因规模、元素大小、内容及版本采用不同编码。

| 结构 | 解决的问题 | 取舍 |
|---|---|---|
| SDS | 维护长度、容量等信息，支持二进制内容 | 读取长度不必遍历到结束字符；仍需实际处理内容字节 |
| listpack | 连续紧凑保存小集合 | 节省元数据、改善局部性；扫描和中间修改仍有成本 |
| 哈希表 | 平均较快的按键/字段定位 | 指针与桶表开销、冲突、扩缩容及临时两表 |
| 跳表 | 按分数有序查找、范围遍历和排名 | 维护层级与 span；还要计算输出 M 个成员的成本 |

小 Hash 的 N 很小，线性扫描的常数可能低于建立分散节点的固定成本。大对象转换编码体现时间和空间取舍。

跳表编码的 ZSet 中，字典便于按 member 查 score，跳表负责有序访问与排名。相同 score 按 member 字典序；业务若要求“先达到分数者优先”，需要明确额外排序规则。

**验证：**按运行版本查询配置，在独立数据上用 TYPE、OBJECT ENCODING、MEMORY USAGE 观察不同规模与元素大小。

**2 分要点：**正确区分类型/编码并说明结构作用 1 分；给出规模与操作方式的取舍或验证方法 1 分。

### 第 33 题：Pipeline、事务、WATCH 与 Lua

| 机制 | 适合的问题 | 关键边界 |
|---|---|---|
| Pipeline | 一批独立操作的网络等待 | 不自动形成隔离执行或回滚；批量有缓冲与延迟代价 |
| MULTI/EXEC | 已知命令队列的顺序、不可穿插执行 | 执行阶段错误不自动回滚；入队错误与执行错误不同 |
| WATCH | 客户端依赖读取结果作判断，发现并发变化时拒绝提交 | 不锁住键；冲突后要重新读取判断，不能盲目重发扣减 |
| Lua | Redis 内的读、判断、修改要作为一个执行段 | 运行时错误不回滚；长脚本影响服务；不包含 MySQL/外部调用 |

WATCH/MULTI 要正确保持连接上下文；Cluster 多键共同操作还要满足相应同槽条件。脚本传入所有访问键，用 ARGV 传业务数据。

脚本执行阈值不是自动回滚期限；SCRIPT KILL 不能安全终止已经写入数据集的脚本。[官方 SCRIPT KILL 说明](https://redis.io/docs/latest/commands/script-kill/)

**追问：**“库存检查与扣减原子”之后还缺什么？请求结果未知时的幂等、订单提交、库存补偿及故障恢复。

**2 分要点：**按场景区分四种机制 1 分；回滚/连接/执行时间/跨系统边界至少说明两项 1 分。

### 第 34 题：数据库提交后失效缓存

**主干答案：**先以数据库提交形成权威状态，再失效缓存并按需重建，通常比“先删后改”缩小旧数据库值重新填入的直观窗口，也避免每次都重算复杂缓存。

仍有两类核心问题：

```text
部分失败：数据库提交 → 删除前进程崩溃或删除失败 → 旧缓存仍在。
并发回填：旧读已拿到旧值 → 写提交并删除 → 旧读稍后回填。
```

Outbox 将业务修改与失效事件记录放在同一个数据库事务中，后台可靠投递、重试；CDC 订阅已提交变更，维护消费进度及失败恢复。两者还要处理重复、积压、事件与相关缓存的映射。

TTL 是兜底生命周期，不自动解决所有旧读延迟；可靠事件也不自动禁止事件处理后的旧读回填。根据陈旧度目标，选择接受风险、版本控制或关键读走权威路径。

**2 分要点：**正常写路径及至少一种失败时序 1 分；区分可靠失效、TTL 与回填控制 1 分。

### 第 35 题：版本屏障的条件

**主干答案：**删除缓存值后，值内版本也消失，必须保留“至少已知到哪个版本”的信息，或改用另一套有明确保证的协议。

一种教学设计：

```text
cache:{product:1001}:value -> payload + version
cache:{product:1001}:guard -> 最低可接受版本
```

- 数据库提供符合业务顺序的版本，查询时原子地取得相互对应的数据和版本。
- 失效事件带版本，在短脚本中将 guard 推进为 max，清除比屏障旧的值。
- 回填脚本同时校验 guard 与当前缓存版本；旧版本被拒绝，乱序事件不能使屏障倒退。
- guard 不存在时，不能简单当作“没有限制”；先暂缓回填，再进入经过设计的权威恢复或新代际流程。

版本信息的淘汰、TTL、故障回退都可能破坏保护。数据库副本延迟可能反复提供旧版本，只能拒绝回填，不能靠脚本制造新数据。版本若超出 Lua 精确整数范围，需要约束表示或可靠的字符串比较。

**保证边界：**guard=11 已生效且所有回填遵守协议时，可拒绝版本 10；事件未到达、屏障丢失或读路径忽略新鲜度要求时，不能据此证明全局强一致。

**2 分要点：**解释删除会丢比较依据及原子屏障校验 1 分；说明事件延迟、屏障恢复、读版本匹配中至少两项 1 分。

### 第 36 题：锁、fencing 与幂等

**主干答案：**随机锁 token 标识某次租约，保护续约和释放；递增 fencing token 比较新旧资源代际；request_id 标识同一业务请求，防重试重复效果。

```text
A 持有 41 后暂停 → 租约失效 → B 获得 42
→ 资源原子接受 42 → A 恢复带 41 → 资源拒绝。
```

假设 last_fence 非空且初始为 0，以下示例只允许一次租约一次写入：

```sql
UPDATE resource_state
SET payload = :new_payload,
    last_fence = :token
WHERE resource_id = :resource_id
  AND last_fence < :token;
```

应用检查影响行数。多行资源需要合适事务；同租约多步操作需要另外定义操作顺序和幂等，不能机械改成 `<=` 就宣布安全。

UUID 没有代际顺序，不能直接比较新旧。令牌来源本身要满足单调性与故障模型，资源端必须实际校验。fencing 也不阻止资源尚未见到新代际时接受旧请求，不能使已过期进程瞬间停止。

**2 分要点：**区分三类信息与旧持有者反例 1 分；原子资源校验及令牌/幂等边界 1 分。

### 第 37 题：写入确认的不同层次

**主干答案：**主节点内存执行、本地 AOF 落盘、副本复制、副本持久化、客户端收到结果是不同进度；服务重新可用也不等于原有全部历史保留。

- 普通成功回复：主节点处理成功；保证要结合实际持久化配置，不能直接推导所有副本拥有。
- WAIT：在同一连接上下文中，等待此前写入进度被指定数量副本确认，并检查实际数量。
- WAITAOF：等待对应的本地和/或副本 AOF fsync 确认，并检查两个返回数量。
- min-replicas：按满足副本数量与滞后条件限制主节点接受写入，不是该条写入的同步确认。

WAIT/WAITAOF 不足时不会撤销之前写入。不要把它当作业务没执行；按 request_id 查询、复用结果或推进可恢复状态。进入事务/脚本等不能阻塞的上下文，不能假定命令按普通方式等待。[官方 WAIT 说明](https://redis.io/docs/latest/commands/wait/)

重要数据还要明确故障组合、实际提升的节点、RPO/RTO 和对账。确认命令不会自动提供跨 Redis/MySQL 的事务。

**2 分要点：**正确区分四种机制 1 分；连接上下文、返回阈值、不可盲目重试及切换边界 1 分。

### 第 38 题：重写、快照与写时复制

**主干答案：**AOF 重写从当前数据状态生成恢复表示，压缩不再需要的操作历史；不要求逐条读取旧文件再删除重复记录。RDB 保存时点状态；Redis 7 多部分 AOF 用基础内容与后续增量组织恢复，manifest 跟踪有效集合。

后台任务期间父进程继续写，要保留新变化。经典 fork/COW 起初共享物理页，写到共享页时才发生复制。fork 页表处理、复制、磁盘和带宽争用仍有成本。

设普通页 4KiB，首次写到 60 万个不同共享页，复制部分约 `600000 × 4096 / 1024³ = 2.29GiB`。这不包含其他新增数据、缓冲或页表成本；父子 RSS 有共享，不能直接相加当独立物理页总量。

“everysec 一般按约一秒同步”不是任何异常下严格丢失上限；恢复要看最后成功保存和实际确认进度。AOF 是恢复记录，重写会压缩历史，不适合作为完整业务审计日志。

**2 分要点：**状态重建、增量保留与版本文件机制 1 分；按页理解 COW 并分析资源/恢复边界 1 分。

### 第 39 题：backlog 与同步成本

**主干答案：**基础历史量 `5MiB/s × 120s = 600MiB`，再为流量峰值、同步延迟等留余量。统计复制流字节，不直接按业务行数估算。

部分重同步需要缺失区间仍在 backlog，且复制身份/历史兼容。断线超过保留范围、历史不兼容等情况可触发全量同步。

backlog 用于保留近期复制历史；复制连接的待发送缓冲处理正在传输的积压。逻辑职责不同，具体版本可能共享底层资源。

全量同步包括基础状态生成/传输、副本加载和后续增量追赶，形成额外 CPU、内存、网络和磁盘成本。副本因资源不足变慢，随后全量同步又加重压力，可能形成反馈环。

**2 分要点：**600MiB 与字节进度/历史条件 1 分；说明缓冲职责和全量同步资源反馈 1 分。

### 第 40 题：内存预算与数据职责

**主干答案：**maxmemory 是触发容量控制的条件，不是进程 RSS 硬上限。数据与元数据、分配器固定开销/碎片、部分复制/AOF 缓冲、COW 和新分配峰值都要留空间。

used_memory 与 RSS 测量范围不同。释放对象后的空闲块可能仍留在分配器中供复用；比例高也可能受小数据集和历史峰值影响。不能只看一个碎片率或把存在包含关系的字段全部相加。

部分传播缓冲不计入淘汰比较，避免淘汰生成传播数据、传播数据又促成更多淘汰的反馈；可结合 mem_not_counted_for_evict 观察。[官方淘汰说明](https://redis.io/docs/latest/develop/reference/eviction/)

可重建缓存允许淘汰，锁/去重/版本屏障/消息被淘汰可能改变正确性。逻辑 DB 编号不隔离整个实例的内存、执行和故障。按用途拆分策略，采用 noeviction 也要处理写入拒绝与总体资源耗尽。

**2 分要点：**明确 RSS 与 maxmemory、额外内存来源 1 分；解释淘汰对业务状态的影响及隔离取舍 1 分。

### 第 41 题：超时与少量慢日志

**主干答案：**先固定异常时间窗口、影响实例/分片与变更，再拆应用等待、服务端等待、命令执行、网络和客户端处理。少量慢日志不能替代全部链路证据。

| 假设 | 证据 |
|---|---|
| 长命令阻塞其他请求 | 同窗口慢日志、命令类型/规模、脚本执行记录 |
| 分片容量或热点 | 每分片 CPU、命令成本、key 访问量与响应大小 |
| 网络或输出压力 | 带宽、RTT、丢包、响应体积与输出缓冲 |
| fork/COW/磁盘 | latest_fork_usec、持久化状态、COW 指标与磁盘延迟 |
| 到期/淘汰或同步事件 | expired/evicted 增量、命中率、复制/全量同步状态 |
| 应用连接或线程堵塞 | 借连接时长、队列、线程栈、事件线程与回调耗时 |

慢日志有阈值和保留范围；INFO 累计指标取窗口差值，平均成本不能直接代表 P99。LATENCY 空结果也需核对是否启用和采集条件。

Lettuce 的事件线程不能承载任意阻塞或重计算；BLPOP 等阻塞命令、连接状态序列与异步队列也需正确管理。并非所有异步模型都依赖相同的连接池策略，扩大连接未必解决服务端工作量问题。[Lettuce 官方 FAQ](https://redis.github.io/lettuce/faq/)

**2 分要点：**至少四类假设与各自证据 1 分；说明慢日志测量范围和客户端/时间窗口验证 1 分。

### 第 42 题：Cluster 建模与路由

**主干答案：**经典路由为 `key → slot → node`；有效 hash tag 指定共同哈希部分。单商品库存与请求结果可设计为：

```text
stock:{sku:1001}
request:{sku:1001}:request-abc
```

这方便短脚本共同访问。但十个商品可能分属十个槽，单个 Lua 不会变成跨槽事务。统一全局 tag 会集中容量与执行压力。

MOVED 通常要求更新相应槽路由；ASK 是迁移中的本次临时重定向，需在目标连接使用 ASKING 后执行；经典多键迁移可遇 TRYAGAIN。业务重试还要考虑结果未知与幂等。

客户端拆批读取再合并结果不提供全局快照。槽数量均匀也不意味着热点、字节和命令成本均匀；单热 key 需要减少请求、合并或业务拆分，不能靠加节点自动分散。

**2 分要点：**同槽设计及多商品约束 1 分；路由/迁移/热点或分批语义至少说明两项 1 分。

### 第 43 题：本地缓存的收益与代价

**主干答案：**进程内命中省去 Redis 请求，可减少热 key 压力；同时增加容量、失效、冷启动和陈旧度管理。

- 本地 TTL：简单兜底，但到期前可能陈旧，整体暂停和延迟回填也影响实际新鲜度。
- Pub/Sub：可广播失效，但断线时可能漏通知，需要短 TTL、代际或可恢复机制补足。
- Tracking：服务器对相关读键发送失效通知，客户端正确处理协议与连接生命周期；仍不自动感知 MySQL 数据变更。[官方客户端缓存说明](https://redis.io/docs/latest/develop/clients/client-side-caching/)

连接断开后，应用应按一致性要求清空、暂缓使用或重新建立有效状态。不要在无法证明未漏通知时继续无限期相信本地缓存。

**验证：**写入时测通知延迟，断开通知连接后更新键再恢复，测试本地返回是否符合最长陈旧时间，并观察 Redis 请求减少量。

**2 分要点：**热读收益与三类机制的区别 1 分；断线、陈旧度、恢复或实验条件 1 分。

### 第 44 题：限流算法与系统边界

| 算法 | 适合的要求 | 成本与边界 |
|---|---|---|
| 固定窗口 | 容忍窗口边界突发的简单计数 | 便宜；相邻窗口可短时集中放量 |
| 滑动窗口日志 | 精确检查最近一段时间的请求集合 | 请求时间记录占空间，清理也有工作量 |
| 令牌桶 | 长期速率受控，允许最多 B 的有限突发 | 维护 token 与时间，需处理时钟与精度 |

检查与更新要协调，短 Lua 可实现 Redis 内的原子决策。若用 INCR 和过期控制，需要考虑创建后未设 TTL、错误输入、被拒请求是否计数等语义。

使用服务器 TIME 可减少应用间时钟差异，不证明全局时钟永不跳变。多维额度在不同槽时，也不能用普通脚本自动原子扣减。

重试是否算一次新尝试，应明确约定；若要复用准入决策，需稳定请求标识及相应生命周期。Redis 故障时按业务选择本地保守额度、拒绝或放行，并保护下游。[官方限流方案](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)

**2 分要点：**三种算法与流量形状取舍 1 分；原子性/时间/跨槽/故障/重试至少说明两项 1 分。

### 第 45 题：重复交付与业务效果

**主干答案：**消费组维护独立进度；组内消费者分担消息，交付后有 PEL，业务成功后 ACK。提交业务到 ACK 之间崩溃会重复交付，必须让业务效果幂等。

在数据库事务中插入稳定业务事件的处理记录，使用合理的唯一约束，并与实际业务修改一起提交。重复时检查已提交结果，不再重复副作用，再 ACK。去重作用域可包含处理器/业务阶段，不能把不同事件误合并。

认领只转移待确认消息的处理归属，不停止旧进程；正文裁剪要覆盖全部消费组进度、待确认重试和回放要求。XACK 不自动删除正文，Redis 本身的保留与恢复另受配置影响。

外部扣款或发货不在这笔数据库事务里，需要外部幂等操作号、可恢复推进和对账。Stream ID 的标识作用域也不能直接当跨系统全局业务唯一标识。

**可以表达的保证：**在所需存储与协议条件满足时，同一业务事件只产生一次相应数据库效果；不能泛化为任意故障、任意外部调用下的端到端 exactly-once。

**2 分要点：**PEL/ACK/重复交付及同库事务幂等 1 分；认领、裁剪、外部动作或 Redis 故障边界 1 分。

## 八、综合场景题参考答案与评分点

### 第 46 题：旧读回填与版本恢复

**参考答案：**

1. **最终状态：**数据库为 price=120、version=11；缓存为 price=100、version=10。R 的读取在提交前，回填在删除后，因此 W 两步成功也不能证明后续缓存一直新鲜。
2. **可靠 CDC：**它可可靠产生和恢复失效处理，但删除若在 R 回填之前到达，仍保留同一窗口；即使这一次晚到的删除能清掉旧值，也不能证明所有时序安全。事件传播延迟还存在。
3. **版本校验：**guard=11 已生效后，所有回填在短脚本中检查最低版本和现有值版本，R 的 10 被拒绝。数据库数据与版本必须匹配；拒绝回填并不直接规定接口如何响应，要结合新鲜度要求选择重新取值或允许陈旧结果。
4. **屏障边界：**guard 丢失时不能默认允许所有版本，要进入恢复/新代际流程。事件尚未到达时，屏障可能还落后，保护尚未生效；故障转移和淘汰都要纳入屏障生命周期。
5. **读路径：**展示按约定陈旧度使用缓存，配合可靠失效、TTL、有限刷新；结算在权威事务路径中重新校验价格及相关约束，不能只信展示缓存。
6. **验证：**在“数据库查询完成、回填尚未执行”的位置设置可控暂停，完成 W 的提交和删除，再恢复 R；分别测试事件延迟、重复、乱序、屏障丢失与重启，记录最终版本、陈旧持续时间和回源量。

**评分：**每个编号 1 分。必须把陈旧回填与失效事件可靠性分开；仅回答“延迟双删”或“上消息队列”不能覆盖后面各评分点。

**常见扣分点：**把一个固定睡眠时间当成所有读请求的最长耗时；只比较缓存值版本，却在 DEL 后丢掉了比较依据。

### 第 47 题：旧持有者与原子资源校验

**参考答案：**

1. **安全解锁：**A 直接 DEL 可能删除 B 的锁。用 A-uuid 原子比较后删除，发现当前是 B 的 token，返回未删除；这保护锁键，不禁止 A 的数据库动作。
2. **续约：**整体暂停时看门狗可能一起暂停，不能保证按时续约。网络与调度故障也能打断续约；平均业务耗时不是租约始终有效的证明。
3. **客户端先检查：**不足。检查通过后到数据库写入前仍可能暂停、过期并被新持有者替代，属于检查与行动之间的窗口。
4. **原子 UPDATE：**资源端必须在接受写入时执行条件，示例如下：

```sql
UPDATE resource_state
SET payload = :payload,
    last_fence = :token
WHERE resource_id = :resource_id
  AND last_fence < :token;
```

   last_fence 已为 42，A 带 41 不满足条件，影响行数为 0。应用必须按拒绝结果处理，不能忽略。

5. **幂等：**该例使用严格小于，只支持一次租约一次写入。若允许同租约多步操作，需要稳定操作号、顺序及同资源事务等设计；fencing 处理新旧使用权，不自动处理重复发货/扣款。
6. **验证：**控制 A 暂停与 B 提交的先后，验证 41 被拒绝；重复提交相同业务请求，验证无第二次副作用；模拟续约失败与响应未知，验证状态可查询/可恢复。若令牌来源失去单调性，测试必须暴露而不能忽略。

**评分：**每个编号 1 分，第 4 点要求同时说明原子校验和影响行数。随机 UUID、防误解锁、fencing、业务去重应区分。

**常见扣分点：**只在 Redis 检查后直接写数据库；假定看门狗能覆盖任意长的暂停；不说明同 token 多次操作的语义。

### 第 48 题：多商品订单与可恢复库存流程

**参考答案：**

1. **跨槽：**题设两个库存 key 不同槽，普通写 Lua 不满足经典共同执行条件。客户端拆成两个脚本，也不能把它们变成一个原子提交。
2. **全局 tag：**可让相关键同槽，但把全局库存的容量、执行和热点集中到一个槽；不是无代价的扩容方案，也没把 MySQL 提交纳入 Lua。
3. **跨系统：**Redis 扣减成功之后，订单事务可能失败，进程可能退出，回复可能丢失；脚本只能证明其中的 Redis 执行段。
4. **业务幂等：**客户端重试沿用稳定 request_id；订单在数据库设置业务请求唯一约束，存储可复用的结果。Redis 预留可按商品保存与扣减正确协调的请求状态，但单靠易丢失的去重键不能证明全部故障下不重复。
5. **补偿幂等：**定义预留 PENDING、确认 CONFIRMED、取消 CANCELLED 等状态及允许迁移。回补与“一次取消生效”协调，重复取消不再重复加库存；支付成功与超时取消也必须按权威规则解决竞争。
6. **方案比较及验证：**见下表。验证重复、并发、跨商品中途失败、响应未知、补偿重复和 Redis 状态丢失，检查库存/预留/订单的不变量并对账。

| 方案 | 主要实现 | 适用前提与成本 |
|---|---|---|
| 数据库权威事务 | 同事务内条件扣减多商品库存、创建订单、记录请求；按需产生 Outbox 事件 | 约束直接；评估数据库写容量、锁顺序、死锁重试与事务长度 |
| Redis 预留 | 分商品原子预留，可靠协调订单状态，提交/取消补偿，恢复与对账 | 只有在准入/预留收益值得额外协议复杂度时采用；跨商品和跨系统失败都需处理 |

数据库方案下，可按约定顺序更新商品、保持短事务，并用稳定业务标识执行可恢复重试。Redis 方案不能把“两个 SKU 各自不为负”直接当作整张订单已原子完成。

**评分：**每个编号 1 分，第 6 点需包含方案比较及至少一种有针对性的验证。没有业务事实或容量要求时，不应直接声称 Redis 方案必然优于事务方案。

**常见扣分点：**跨槽脚本自动成功；失败就无条件 INCR；重复订单只依赖一个会过期的 Redis 标记。

### 第 49 题：容量计算、证据与回源保护

**参考答案：**

1. **回源预算：**正常 `100000 × 1% = 1000QPS`；命中 95% 时为 5000QPS；全部回源为 100000QPS。后两者超过 3000QPS 的题设读预算。实际保护上限还要留余量并考虑其他读流量，不能让每个应用实例各自都放行 3000。
2. **执行能力：**平均为 69.8μs，简化理想能力约 `1 / 69.8μs ≈ 14327 条/秒`。2.5 万条/秒超过该模型能力，所需执行时间约 `25000 × 69.8μs = 1.745 秒/秒`，不能由一个执行线程持续完成。需核对真实命令分布与资源，再减少长工作或修正倾斜。
3. **正文带宽：**约 586MiB/s、4.92Gbit/s，超过 1Gbit/s 原始链路。增加连接可能只扩大队列；考虑按需读取、减少体积、合并/本地缓存或改善网络路径。
4. **慢日志边界：**题设未说明完整采集与足够保留，不能用少量记录排除长命令影响。即使 GET 自己很短，仍可能有服务端等待、网络传输、应用借连接或事件线程等待；核对阈值、实例与时间窗口。
5. **容灾：**按全系统预算控制回源，合并同键查询；允许时服务有硬期限的旧值，其他请求限流/降级或拒绝。设置总 deadline 和重试预算；恢复后渐进放量、优先重建热点，不能一恢复就同时预热全部对象。
6. **证据和复测：**收集每分片命令/CPU、响应字节与网络、客户端等待/线程、latest_fork_usec、COW/持久化/磁盘时间线。用可比业务负载分别验证措施，再同时看 P99、吞吐、错误率、数据库压力与内存余量。

**评分：**每个编号 1 分。第 1～3 点要求计算和结论正确；第 4～6 点要求提供对应证据及容量约束，不只列工具名称。

**常见扣分点：**按全部短 GET 估 5 万 QPS；把 bit/s 和 byte/s 混用；用无限回源或无限重试“兜底”；只调整连接池。

### 第 50 题：可靠消费、正文保留与 Redis 故障

**参考答案：**

1. **重叠执行：**可能。A 在 ACK 前暂停，B 认领后可能重新处理，A 复活仍可继续访问外部资源；认领不等于停止 A。
2. **同库事务：**用稳定业务事件 ID 与合理处理器/阶段作用域建立唯一约束；在同一个数据库事务内插入处理记录并执行实际修改。重复消息确认已有提交结果后不再执行副作用，再 ACK。不要先独立记“已处理”再做业务。
3. **外部效果：**发货接口需要支持稳定幂等操作号，或由可恢复的状态/Outbox 推进并对账。数据库内去重不自动把外部动作纳入事务；结果未知时也不能无条件重复发货。
4. **ACK 与裁剪：**XACK 清除本组待确认记录，正文仍在。MAXLEN 不应只凭固定数量配置；需要覆盖全部消费组的未交付进度、PEL 重试、最长处理/故障时间和回放要求，防止正文先被裁掉。Redis 7.2 不能直接套用后续版本的新引用控制选项。
5. **节点故障：**题设消息尚未到新主副本，XADD 的成功回复不能保证新主保留。根据可靠性要求选择持久化/复制等待与故障策略；重要事件还需可恢复来源、补发和对账。仅把事件标记“已发到 Redis”也不证明最终业务完成。
6. **监控与实验：**观察业务完成延迟、未交付积压、PEL 数量和最老空闲、重投/失败次数、消费者耗时、裁剪范围及 Redis 复制/持久化。控制“业务提交后、ACK 前”暂停，测试认领和复活；再独立测试正文不足和节点切换，检查实际业务效果及恢复来源。

**评分：**每个编号 1 分。必须区分消息交付状态、数据库效果、外部效果、正文保留和节点故障。

**常见扣分点：**把 ACK 当删除正文；把认领当旧消费者已死亡；把 XADD 成功当端到端可靠完成；只看 Stream 长度推断业务健康。
