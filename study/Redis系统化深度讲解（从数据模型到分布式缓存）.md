# Redis 系统化深度讲解：从数据模型到分布式缓存

> 依据《图解Redis-小林coding-浅色版-v2.0.pdf》重写。
>
> 目标：把 Redis 的知识按“为什么需要 → 如何使用 → 内部如何实现 → 故障时如何工作 → 业务上如何落地”串成一条主线。你已经用过 Redis 做权限认证和缓存，因此本文从这两个场景出发，逐渐过渡到数据类型、底层结构、持久化、内存管理、高可用、分布式锁和缓存一致性。
>
> 本文区分三种内容：对外可见的命令和业务语义、Redis 内部实现原理、工程上需要额外设计的可靠性。三者不能混为一谈。

## 0. 先看全局：Redis 到底解决什么问题

你可以把后端系统中 Redis 的角色分成四类：

```text
1. 快速状态：登录会话、验证码、限流计数、临时标记
2. 快速访问：MySQL 数据的缓存副本
3. 数据结构服务：点赞集合、排行榜、队列、地理位置
4. 分布式协调：锁、发布订阅、Stream、节点之间的状态协作
```

这些场景都利用了 Redis 的几个共同特点：数据主要在内存中操作；命令是面向数据结构的；单条命令通常具有原子执行语义；可以设置过期时间；可以选择持久化和多节点部署。

但是 Redis 不会自动替应用解决以下问题：

- Redis 中的数据与 MySQL 什么时候同步。
- 一条业务流程跨 Redis 和 MySQL 时如何回滚。
- 锁过期后旧客户端是否还能修改真实资源。
- 消费者重复处理消息后怎样保证业务不重复。

学习 Redis 的主线应始终围绕三个问题：

1. 数据以什么结构保存，才能高效完成所需操作？
2. 并发、过期、重启和故障时，状态如何变化？
3. Redis 中的数据丢失或变旧时，业务是否能接受，如何补偿？

## 1. Redis 的基本模型：一个远程的、可编程的数据结构服务器

### 1.1 它与进程内 Map 的区别

进程内 Map 只属于当前进程：

```text
后端实例 A 的 Map ≠ 后端实例 B 的 Map
```

用户在 A 登录后，下一次请求可能被负载均衡转发到 B。B 看不到 A 的 Map 内容，于是用户被认为没有登录。

Redis 作为独立服务：

```text
后端 A ─┐
后端 B ─┼── 网络连接 ── Redis
后端 C ─┘
```

多个实例访问同一个状态中心，正是登录会话、验证码、限流计数常使用 Redis 的原因。

### 1.2 它与 MySQL 的区别

MySQL 的核心抽象是表、行、列、索引和事务；Redis 的基础抽象是 key 加一个值对象。

```redis
SET user:1001:name "Tom"
GET user:1001:name
```

`user:1001:name` 是一个完整字符串 key。冒号只是命名约定，Redis 不会因此建立 user 表。

MySQL 擅长表达“查询满足多个条件的关系数据”；Redis 擅长在已知 key 或已设计好数据结构的情况下快速完成访问。Redis 也不是“完全不使用磁盘”的系统：它可以通过 RDB、AOF 把数据持久化到磁盘；只是普通命令的主要数据操作发生在内存。

### 1.3 Redis 的数据库内部如何找到一个 key

可以先用逻辑模型理解：

```text
key
 ↓ 哈希函数
哈希桶
 ↓ 冲突链或其他处理
dictEntry
 ↓
value 对象
```

Redis 的数据库键空间本身通过哈希表组织，平均查找复杂度接近 O(1)。这不是绝对保证：哈希冲突、渐进式 rehash、访问大对象以及返回巨大结果都会增加耗时。

## 2. 从你熟悉的权限认证完整走一遍

### 2.1 Session 方案

登录成功后，后端生成不可预测的随机 token：

```redis
SET login:abc123 '{"user_id":1001,"role":"admin"}' EX 1800
```

请求流程是：

```text
浏览器携带 token
→ 应用提取 token
→ GET login:token
→ 未找到：未登录或会话已失效
→ 找到：得到 user_id、role 等会话信息
→ 应用继续执行权限判断
```

Redis 负责状态存储，不负责完整的 RBAC 判断。角色是否能访问接口，要由后端根据权限规则判断。

### 2.2 过期、退出和踢人下线

```text
登录：SET ... EX 1800
退出：DEL login:abc123
踢人：删除指定用户的会话，或写入版本号/黑名单
过期：GET 返回空，要求重新认证
```

如果一个用户可以多端登录，通常需要维护多个 token；如果要“一处退出、全部失效”，要再设计用户级会话索引，例如 `user:1001:sessions`。

### 2.3 Session 与 JWT 的区别

Session 方案中，服务端通过 Redis 查 token 对应的状态。JWT 中，token 自带声明，服务端可以验证签名后直接读取内容，但退出、踢人、权限变更的即时失效往往仍需要 Redis 黑名单、版本号或会话记录。

因此 Redis 不是只能保存 Session，也不是用了 JWT 就完全不需要 Redis。关键是：认证结果是否需要服务端集中控制和即时撤销。

## 3. 缓存的完整读写模型

### 3.1 Cache Aside（旁路缓存）

读流程：

```text
查 Redis
├── 命中：直接返回
└── 未命中：查 MySQL → 回填 Redis → 返回
```

写流程通常是：

```text
更新 MySQL 并提交
→ 删除 Redis 缓存
```

应用要明确区分“缓存未命中”和“数据确实不存在”。不存在结果可以短暂缓存，避免恶意请求反复穿透数据库。

### 3.2 为什么更新后常删除，而不是直接更新缓存

缓存可能来自多张表聚合。更新数据库后，重新计算整份缓存可能比删除一个 key 更复杂；有些数据更新后长时间没人访问，立即重建也是浪费。

删除缓存使用懒加载：等下次有人访问，再根据权威数据库生成。

但删除缓存不是原子魔法。数据库提交成功、删除缓存失败时，旧缓存可能继续被命中；所以要结合 TTL、重试队列、outbox、MySQL binlog/CDC 等机制做补偿。

### 3.3 缓存与 MySQL 的时序分析方法

不要背“先更新数据库再删除缓存就一定一致”。要同时画并发图和故障图。

并发旧值回填例子：

```text
A：从数据库读到旧值 100，暂未回填
B：数据库更新为 120，并删除缓存
A：恢复执行，把旧值 100 写回缓存
```

最终数据库是 120，缓存是 100。实际系统可通过版本号、读写锁、延迟双删或更可靠的失效事件降低风险，但方案要按一致性要求选择。

故障事件例子：

```text
数据库更新成功
→ 应用在删除缓存前崩溃
→ 数据库新、缓存旧
```

可以把“更新数据库”和“待删除缓存事件”写在同一个 MySQL 事务的 outbox 表中，由后台可靠投递和重试。

## 4. Redis 数据类型：先按操作选择，再理解实现

### 4.1 String：整块数据、计数器和简单锁

```redis
SET product:1001 '{"name":"keyboard","price":199}' EX 600
GET product:1001
```

String 可以保存文本、JSON、数字和二进制数据。Redis 不会自动理解 JSON 字段；需要字段级修改时，Hash 通常更适合。

计数器使用原子命令：

```redis
INCR article:88:views
INCRBY article:88:views 10
```

不要用 `GET → 应用加一 → SET` 替代 `INCR`，否则并发读改写会丢更新。

简单的租约锁常见写法：

```redis
SET lock:product:1001 unique-token NX PX 30000
```

NX、唯一 token 和过期时间缺一不可；解锁不能无条件 DEL，后面专门解释。

### 4.2 Hash：对象字段和购物车

```redis
HSET user:1001 name "Tom" age 20 city "Shanghai"
HGET user:1001 name
HINCRBY user:1001 age 1
```

Hash 适合字段经常单独读写的对象。它没有 MySQL 表的字段类型约束、外键和关系查询能力。

购物车可表示为：

```redis
HSET cart:1001 product:88 2 product:99 1
HINCRBY cart:1001 product:88 1
```

不要对超大 Hash 频繁 `HGETALL`；返回结果规模本身会成为耗时和网络压力。

Redis 7.4 起支持 Hash 字段级过期命令，但部署时要根据实际 Redis 版本确认，不要把单个字段永远不能过期当作跨版本事实。

### 4.3 List：两端操作和简单队列

```redis
RPUSH jobs job1 job2 job3
LPOP jobs
BLPOP jobs 5
```

`RPUSH + LPOP` 实现 FIFO；`LPUSH + LPOP` 可实现栈。`BLPOP` 在没有元素时让当前客户端等待，不会让 Redis 整个服务停止处理其他客户端。

List 的问题是消费者弹出消息后，消息就从待处理列表消失；消费者此时崩溃，消息可能丢失。可以转移到处理中列表，成功后删除，并设计超时恢复和幂等。

### 4.4 Set：去重和集合运算

```redis
SADD article:88:likes user:1 user:2 user:1
SISMEMBER article:88:likes user:1
SCARD article:88:likes
SINTER follows:alice follows:bob
```

Set 不保证顺序，适合点赞、标签、共同关注、抽奖候选等。大集合交集、并集、全量返回仍可能很重。

### 4.5 ZSet：分数排序、排行榜和延迟任务

```redis
ZADD ranking 100 alice 200 bob 150 carol
ZINCRBY ranking 60 alice
ZREVRANGE ranking 0 2 WITHSCORES
ZRANGEBYSCORE ranking 100 180
```

member 唯一，score 可重复；同分时还要考虑 member 的字典序。ZSet 适合排行榜、按时间戳排序的延迟任务和范围查询，但“查到并删除任务”若分成两步，多消费者仍可能重复领取，需要原子脚本或其他协调。

### 4.6 Bitmap、HyperLogLog、GEO

Bitmap 用 bit 保存二值状态：

```redis
SETBIT sign:1001:202609 0 1
BITCOUNT sign:1001:202609
```

适合签到和登录标记，但最大 offset 很大时会造成稀疏空间问题。

HyperLogLog 做近似去重计数：

```redis
PFADD uv:20260922 user:1 user:2 user:1
PFCOUNT uv:20260922
```

它节省空间，但结果是概率估计，不适合必须精确的结算。

GEO 以经纬度保存位置并计算距离：

```redis
GEOADD shops 121.4737 31.2304 shop:1
GEOSEARCH shops FROMLONLAT 121.47 31.23 BYRADIUS 5 km
```

直线距离不等于道路距离，附近门店推荐若要求路线时间还要调用地图服务。

### 4.7 Stream：比 List 更完整的消息流

```redis
XADD orders * order_id 1001 status created
XGROUP CREATE orders inventory 0 MKSTREAM
XREADGROUP GROUP inventory worker-1 COUNT 1 STREAMS orders >
XACK orders inventory message-id
```

Stream 自动生成消息 ID，支持消费组和 Pending Entries List（PEL）。消息被消费组交付后，未 ACK 的记录保留在 PEL 中，可以用 `XPENDING` 查看，并通过 `XCLAIM` 或 `XAUTOCLAIM` 重新分配。

重要区别：`XACK` 移除的是该消费组的待确认记录，不会自动删除 Stream 消息正文。正文保留、裁剪和消费确认是三件事。

Stream 仍可能重复投递，业务必须幂等。Redis Stream 适合中等规模、需要消费组和确认的场景；海量积压、严格消息语义和复杂投递能力仍应评估专业消息队列。

## 5. Redis 的执行模型：为什么快，什么会阻塞

### 5.1 事件循环和 I/O 多路复用

Redis 主线程使用事件循环：

```text
等待连接/读写事件
→ 读取请求
→ 解析命令
→ 执行命令
→ 写入响应队列
→ 发送响应
```

I/O 多路复用让一个线程管理许多 socket，避免为每个空闲连接分配线程等待。

### 5.2 “Redis 单线程”不能理解成进程只有一个线程

普通命令执行主要由主线程负责，但后台可能有关闭文件、AOF fsync、lazyfree 等线程。Redis 6 还支持网络 I/O 多线程，具体是否开启要看配置。

单线程的核心优点是减少核心数据结构的并发加锁和线程切换；代价是一个耗时命令可能阻塞后续命令。因此“命令短、返回数据小、避免长脚本和大集合全量操作”是重要的性能原则。

### 5.3 O(1) 不代表业务一定快

`GET` 一个几十字节 String 和 `LRANGE` 返回一百万个 List 元素，虽然都可能包含键查找，但总工作量完全不同。

要同时看：

- 算法复杂度。
- 返回结果数量。
- 序列化和网络传输量。
- 是否在主线程中同步释放大对象。
- 是否与持久化、复制争用 CPU、磁盘和网络。

## 6. 底层数据结构：为什么不同类型需要不同实现

### 6.1 redisObject 的三层关系

可以用下面结构理解 Redis 的对象：

```text
redisObject
├── type：String、List、Hash、Set、ZSet
├── encoding：当前内部编码
└── ptr：指向底层数据结构
```

对外的数据类型与内部实现不是一一固定关系。小对象和大对象会选择不同编码，以平衡内存和操作速度。

### 6.2 SDS：Redis 的字符串

C 字符串靠 `\0` 找结尾，长度查询需要遍历，也不适合保存中间含有零字节的二进制内容。SDS 保存已用长度和容量：

```text
len：已使用字节数
alloc：已分配容量
buf：数据内容
```

因此长度可直接读取，追加时能判断剩余容量，也能安全处理二进制。扩容会预留空间，减少频繁 realloc。

### 6.3 哈希表与渐进式 rehash

冲突通过链式结构连接同桶条目。数据不断增加时，Redis 需要扩容并重新分布条目。

一次搬完可能长时间阻塞，所以使用两个哈希表，把迁移分散到多次操作和周期任务中：查找阶段可能先查旧表，再查新表；新增条目通常直接写新表，旧表逐步变空。

### 6.4 ziplist、listpack、quicklist

紧凑连续结构省内存、利用 CPU cache，但中间查找需要遍历，插入可能移动数据。

旧 ziplist 还保存前一节点长度，一个节点变大可能导致后续长度字段连续扩展，称为连锁更新。listpack 通过更独立的条目编码减少这种依赖；quicklist 则把多个紧凑块组织成链表，兼顾分块和紧凑性。

版本不同，具体编码也不同。学习重点是：小数据用紧凑结构，大数据换成更适合查找和更新的结构；实际阈值应看部署版本和配置。

### 6.5 intset 与 skiplist

小整数 Set 可以使用按整数宽度升级的连续数组，节省每个哈希节点的开销；一旦升级为更宽的编码，经典实现不会因为删除大整数自动降级。

ZSet 的大数据实现通常是“字典 + 跳表”：字典支持 member 快速找到 score，跳表支持按 score 范围、排序和排名。跳表用多层链表指针把平均查找降到 O(logN)，但输出 M 个元素仍要付出 O(M) 成本。

## 7. Pipeline、事务和 Lua：三个容易混淆的并发工具

### 7.1 Pipeline 解决网络往返

逐条发送：

```text
发命令 1 → 等结果 1 → 发命令 2 → 等结果 2
```

Pipeline 是批量发送、批量读取，减少网络 round trip。但它本身不是事务，其他客户端可能在其中插入命令；批次过大也会堆积缓冲区。

### 7.2 MULTI/EXEC 的保证

```redis
MULTI
INCR a
INCR b
EXEC
```

EXEC 触发队列顺序执行，执行期间其他客户端的普通命令不会插入。

但 Redis 事务不是 MySQL 事务：执行阶段某条命令因类型错误，其他已排队命令仍可能继续执行；Redis 不提供执行错误后的自动回滚。

### 7.3 WATCH 的乐观并发控制

```text
WATCH stock
GET stock
根据读取值计算
MULTI
SET stock new-value
EXEC
```

如果 WATCH 后到 EXEC 前 stock 被其他客户端修改，EXEC 放弃执行。客户端应重新读取和重试。WATCH 不会把 key 锁住。

### 7.4 Lua 把多步逻辑放到服务端

例如检查并扣减库存，客户端分成 GET、判断、DECR 会有竞争窗口；Lua 可以把判断和修改作为一次服务端执行。

```lua
local value = redis.call('GET', KEYS[1])
if not value then return -1 end
local stock = tonumber(value)
if stock <= 0 then return 0 end
redis.call('DECR', KEYS[1])
return 1
```

脚本执行时不会被其他客户端命令插入，但脚本过长会阻塞其他客户端；脚本运行错误也不会自动回滚已经完成的写操作。

## 8. 持久化：RDB、AOF 与恢复窗口

### 8.1 RDB：时点快照

RDB 保存某一时刻的数据状态。`SAVE` 在主线程生成快照，可能阻塞；`BGSAVE` fork 子进程生成快照，主线程继续服务。

RDB 不是增量日志，每次快照通常表达整个数据集。快照间的写入可能无法恢复，因此快照频率越低，故障丢失窗口可能越大；频率越高，CPU、磁盘和 fork 压力越大。

### 8.2 AOF：记录写入变化

逻辑流程：

```text
执行写命令
→ 放入 AOF 缓冲区
→ write 到操作系统页缓存
→ 按 appendfsync 策略 fsync
→ 持久存储
```

`always` 持久性更强但延迟更高；`everysec` 是常见折中；`no` 把更多时机交给操作系统。`write` 成功不等于已经安全落盘。

### 8.3 AOF 重写

历史日志可能重复记录同一个 key 的多次变化。重写读取当前内存状态，生成新的恢复表示，压缩历史。

重写期间主进程继续处理写入，必须把这期间的新变化保留下来，避免重写结果落后。Redis 7 起 AOF 还采用基础文件、增量文件和 manifest 的多部分组织方式，不能只按旧版本的单文件流程理解。

### 8.4 Copy-On-Write 与大 Key

fork 初始时父子进程共享物理页。父进程修改某个内存页时，操作系统复制该页，父子随后拥有不同内容。

```text
fork 后：父进程和子进程共享页
父进程修改：复制受影响页
子进程继续读取自己的快照视图
```

大 Key 修改可能引发更多写时复制和内存压力；大 Key 的删除、复制、AOF、RDB、网络返回也都可能产生延迟。

## 9. 大 Key、过期删除和内存淘汰

### 9.1 大 Key 与热 Key

大 Key 是内容大或集合元素多；热 Key 是访问频率高。大但不热的键会影响内存和持久化；小但极热的键会形成访问热点；两者可能同时存在。

大 Key 可能导致客户端超时、网络带宽耗尽、主线程处理或删除耗时、Cluster 数据倾斜。发现后应分批删除，或使用 `UNLINK` 让释放工作异步化；但读取和传输压力仍需从数据模型上解决。

### 9.2 过期删除

访问 key 时检查是否过期是惰性删除；后台周期性抽样清理是主动删除。Redis 不给每个 key 都维护精确定时器，因为大量定时器本身成本高。

过期的语义是“不再作为有效数据返回”；内存什么时候实际回收，可能略晚。

### 9.3 内存淘汰

达到 `maxmemory` 后根据策略淘汰：

```text
noeviction：不淘汰，部分写入报错
allkeys-lru / volatile-lru：按近似最近最少使用
allkeys-lfu / volatile-lfu：按近似最低访问频率
random：随机
volatile-ttl：优先剩余 TTL 更短的候选
```

`volatile-*` 只从设置过期时间的键中选；如果没有合适候选，写入仍可能失败。LRU 关注最近访问，LFU 关注访问频率且会衰减，避免一次热点事件永久占用缓存。

## 10. 主从复制：全量、增量和一致性边界

### 10.1 首次同步

```text
从节点请求复制
→ 主节点准备全量数据（通常通过 RDB）
→ 从节点加载基础数据
→ 主节点在同步期间积累的新写入补给从节点
→ 转入长连接命令传播
```

### 10.2 断线重连

主节点维护复制 backlog 环形缓冲区，记录最近传播的复制流。从节点重新连接时带上 offset：如果缺失内容仍在 backlog，可以增量同步；如果已被覆盖，就只能全量同步。

可用的估算思路：

```text
backlog 最小量 ≈ 每秒写入复制流大小 × 预计断线秒数
```

再为流量波动增加余量。

### 10.3 为什么副本可能读到旧值

主节点通常不等待从节点执行完才向客户端返回，因此复制是异步的。主节点已写入 95，从节点暂时仍可能是 100。读副本适合降低主节点读压力，但不能默认提供强一致读。

## 11. Sentinel 与 Cluster：分别解决故障和规模

### 11.1 Sentinel

哨兵持续 PING 节点。单个哨兵认为节点超时，是主观下线；多个哨兵投票达到 quorum 后，可以把主节点判断为客观下线。

判断下线与选出负责执行故障转移的哨兵是两个阶段；quorum 也不等于所有选举授权。生产部署通常使用奇数个哨兵并分散故障域。

故障转移通常包括：选择状态健康、优先级合适、复制进度靠前的从节点，提升为主节点，让其他副本改为复制新主，通知客户端，旧主恢复后降为从节点。

### 11.2 Cluster 的哈希槽

```text
slot = CRC16(key) mod 16384
key → slot → 负责该槽的主节点
```

16384 是槽数量，不是最多只能存 16384 个 key。一个槽可以包含很多 key。

槽迁移期间，客户端可能收到 `MOVED` 或 `ASK`：MOVED 通常代表稳定的槽归属变化；ASK 是迁移期间的临时指引。客户端应维护槽映射并按协议重试。

需要多 key 原子操作时，相关 key 通常必须位于同一槽，可利用 hash tag：

```text
order:{1001}:info
order:{1001}:items
```

但给所有 key 使用同一 tag 会形成热点，失去分片的意义。

## 12. 分布式锁：锁住的是 Redis 中的租约，不是现实世界

### 12.1 正确的基础写法

```redis
SET lock:order:1001 unique-token NX PX 30000
```

NX 保证只有 key 不存在时设置；PX 防止持有者崩溃造成永久锁；unique-token 让释放者证明“这是我本次取得的锁”。

### 12.2 原子释放

不能先 GET 再 DEL，因为锁可能在两条命令之间过期并被别人重新取得。用 Lua 原子执行：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

### 12.3 续约和租约失效

任务超过 TTL 时，客户端可在锁仍属于自己时续期。但网络分区、GC、进程暂停会使续约失败；锁过期后旧客户端可能仍继续访问业务资源。

因此唯一 token 只能防止误删新锁，不能防止旧客户端继续写数据库。严格场景可以增加 fencing token：每次取得锁获得递增序号，资源端拒绝小于已见最大序号的请求。

### 12.4 Redlock 的位置

主从异步复制下，主节点上的锁可能还没复制就故障，提升后的副本没有这把锁。Redlock 在多个相互独立实例上按多数派取得锁，并检查获取耗时小于有效租期。

它增加了可用性和复杂度，不是自动获得强一致性的万能方案。支付、库存等关键业务还需要数据库约束、幂等、资源端版本检查等手段。

如果问题只是“库存不能减成负数”，数据库条件更新：

```sql
UPDATE inventory
SET stock = stock - 1
WHERE sku_id = 1001 AND stock > 0;
```

可能比跨节点分布式锁更直接。分布式锁不是解决并发的唯一工具。

## 13. 缓存雪崩、击穿、穿透

### 13.1 雪崩

大量 key 同时过期，或 Redis 整体不可用，大量请求回源 MySQL。

应对：TTL 加随机差异、提前预热、限流、熔断、降级、构建高可用 Redis，并限制缓存故障时的数据库回源。

### 13.2 击穿

单个热点 key 过期，大量请求同时访问数据库。

应对：互斥重建、singleflight、热点永不过期并后台刷新、逻辑过期返回允许的旧值。

### 13.3 穿透

请求的数据在缓存和数据库都不存在，反复查询数据库。

应对：入口参数校验、短 TTL 空结果、布隆过滤器。布隆过滤器判定“可能存在”时仍要查真实数据，判定“不存在”时才能快速拒绝；它可能误判存在，不能误判已经加入的数据不存在（前提是过滤器维护正确）。

## 14. 一条完整业务链：商品查询与下单

```text
商品详情：Redis 命中则返回，未命中回源 MySQL
商品更新：MySQL 提交 → 可靠失效 Redis
热点商品：合并并发回源，防止击穿
不存在商品：空值缓存或布隆过滤器，防止穿透
商品排行：ZSet 维护分数和排名
库存扣减：数据库条件更新或经过完整补偿设计的 Redis 方案
异步任务：Stream 消费组、PEL、XACK、幂等
Redis 故障：限流降级，等待副本/哨兵/Cluster 恢复
```

这个流程说明了为什么 Redis 不能只按命令表学习。每个命令都要放回“数据来源、并发顺序、故障恢复和一致性目标”中理解。

## 15. 与 MySQL 知识的对应关系

| MySQL | Redis 对照 | 关键区别 |
|---|---|---|
| B+ 树索引 | 哈希表、跳表 | 磁盘页访问与内存结构优化目标不同 |
| Buffer Pool | Redis 内存与淘汰 | Buffer Pool 淘汰页副本，Redis 淘汰 key |
| redo/binlog | AOF/复制流 | 日志对象、格式和恢复职责不同 |
| 事务回滚 | MULTI/EXEC、WATCH、Lua | Redis 事务不提供执行错误自动回滚 |
| 行锁/乐观锁 | 分布式锁/条件更新 | Redis 锁是带 TTL 的租约，需考虑旧持有者 |
| 主从复制 | Redis replication | Redis 复制通常异步，有读旧和丢失窗口 |
| 事务一致性 | 缓存一致性 | MySQL 更新和 Redis 删除不在同一事务内 |

## 16. 学习顺序与检查标准

第一轮按此顺序：

1. 用 Session 和 Cache Aside 讲清 Redis 的角色。
2. 熟悉 String、Hash、List、Set、ZSet，并能按操作选择类型。
3. 理解单线程、I/O 多路复用、O(1) 与大结果返回的区别。
4. 理解 RDB/AOF 的数据恢复窗口。
5. 区分过期删除和内存淘汰，掌握大 Key 风险。
6. 再学习 Stream、事务、Lua 和分布式锁。
7. 最后学习主从、Sentinel、Cluster，以及缓存一致性和异常。
8. 第二轮再看 SDS、渐进式 rehash、listpack、quicklist、跳表。

能回答下面问题，说明主线已经建立：

- Redis 未命中时是谁查询 MySQL？
- String 和 Hash 怎样选择？
- 为什么 `INCR` 比 GET 后 SET 安全？
- 过期删除和内存淘汰有什么区别？
- RDB 与 AOF 分别记录什么？
- 主从复制为什么可能读到旧值？
- Sentinel 和 Cluster 分别解决什么问题？
- 为什么锁释放必须校验唯一 token？
- XACK 删除的是消息正文还是 PEL 记录？
- 为什么“更新数据库后删除缓存”仍不是无条件强一致？

最后请记住一句总纲：

> Redis 的学习不是记住一组命令，而是理解“数据结构如何支持操作、单线程如何处理并发、持久化如何恢复状态、多节点如何提供可用性，以及应用如何承担跨系统一致性”。
