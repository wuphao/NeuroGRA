### 统一案例与表达约定

案例使用商品和订单系统。MySQL 或 PostgreSQL 保存商品、订单、库存与业务请求的权威记录；Redis 缓存展示对象、保存排行榜、协调短期工作及承载适用消息。

```text
product:1001                 商品展示缓存
product:{1001}:guard         该商品的版本屏障示意
product:{1001}:data          与屏障同槽的缓存数据示意
stock:{1001}                短期库存准入计数示意
cart:42                     用户购物车 Hash
rank:campaign:2026           活动排行榜 ZSet
events:{orders}             订单事件 Stream
lock:{1001}:rebuild          缓存重建租约
```

冒号是命名约定，不创建表或层级目录；花括号在 Cluster 中可指定 hash tag，作用见第 19 章。不同章节的键属于独立案例，不能据此假定已构建一套完整生产协议。

`<token>`、`<message-id>` 和 Lua 的 KEYS / ARGV 需要由应用提供。涉及连接作用域的 WATCH、MULTI、WAIT 等操作必须保持相应连接，不能任意拆给连接池中的其他连接。

## 1. 设计约束与数据职责

### 1.1 从内存访问到数据结构服务

Redis 提供按键访问和在服务器端直接操作值内结构的能力。String、Hash、List、Set 和 ZSet 分别表达不同操作关系，应用不必每次都下载完整对象后再上传修改结果。

如果一个排行榜保存成单个 JSON 字符串，每次加分都要读取、解析、修改和写回，并处理并发覆盖。ZSet 直接提供成员加分、排名和范围访问，使部分计算在数据所在位置完成。

常见低延迟来自内存访问、适用数据结构和较少的执行协调成本，但网络、返回字节、命令工作量和排队仍存在。Redis 不是把任意复杂操作都转换成常数时间。

当前 Redis 官方类型范围已超出经典五类；JSON、概率结构及其他能力应按实际部署版本与组件核对，不能把现代官网全部类型都视为 Redis 7.2 最小实例的既有能力。[官方数据类型概览](https://redis.io/docs/latest/develop/data-types/)

### 1.2 与关系数据库的不同抽象

| 维度 | Redis 经典模型 | MySQL / PostgreSQL 常规事务模型 |
|---|---|---|
| 访问单位 | 键及值内部的特定操作 | 行、关系和声明式查询 |
| 查询路径 | 应用选命令和数据结构 | 优化器选择索引、连接、排序等路径 |
| 活跃数据 | 普通键空间主要位于内存 | 数据页在内存与持久存储间管理 |
| 并发协调 | 普通执行段顺序处理，支持原子命令和脚本 | 锁、MVCC、隔离级别与提交协议 |
| 历史读取 | 不提供通用行级 MVCC 快照查询 | 可按事务快照读取历史可见版本 |
| 生命周期 | TTL 与内存淘汰可使键消失 | 普通表记录不因页缓存不足直接消失 |
| 业务约束 | 由结构、命令与应用协议共同表达 | 唯一键、外键、CHECK 及事务程序 |

InnoDB 淘汰 Buffer Pool 页后仍可从数据文件重新读取；Redis 淘汰普通键后，GET 不会自动逐键从 AOF 查回该值。两者的“缓存淘汰”删除对象不同。

### 1.3 可重建状态与权威状态

商品展示缓存丢失可从数据库重建，锁、去重记录和消息进度丢失却可能改变业务行为。它们即使都保存在 Redis，也需要不同淘汰、持久化和恢复策略。

Redis 可以在明确故障模型下承担某些主存储职责，但不能仅因为有 AOF 就默认获得关系数据库同样的事务和约束。数据是否可丢、可否重复执行、如何恢复必须由业务定义。

### 1.4 四条独立的正确性边界

```text
并发边界：操作之间能否穿插，业务检查与修改是否共同执行
保留边界：已执行结果在重启与主从切换后是否仍存在
可知边界：响应丢失后，客户端是否知道操作完成了几次
协作边界：Redis 与数据库 / 消息 / 外部服务是否协调
```

INCR 解决单次增量的并发覆盖，不解决主从切换丢失。AOF 解决本地恢复的一部分，不解决数据库与 Redis 双写。唯一 request_id 解决请求身份，不自动授予锁的使用权。这些边界构成后续章节的共同分析框架。

## 2. 键空间与哈希定位

### 2.1 从键到对象

经典键空间通过哈希结构建立键与值的关联。查找先计算键的哈希，定位桶，再确认键是否匹配，最后按值的类型和编码执行操作。

```text
键字符串
   → 哈希计算
   → 桶 / 条目定位与冲突处理
   → 值对象的类型和编码
   → 类型专属操作
```

键长、冲突、扩容和被访问值的结构会影响成本。平均 O(1) 查找不表示与输入字节长度完全无关，也不保证每次都具有固定微秒上限。

Redis 7.2 的字典实现适合用作固定版本解释；后续键空间组织可能调整，不能把某个版本的字典数量和结构字段当作全部 8.x 的永久契约。[Redis 7.2.0 字典源码](https://github.com/redis/redis/blob/7.2.0/src/dict.c)

### 2.2 冲突与负载因子

哈希函数将较大的键集合映射到有限桶，多个键可能进入同一桶。经典字典采用相关冲突链结构维护条目，比较时仍要确认完整键。

负载因子描述条目数相对桶数的比例。桶太少会提高冲突和查找成本，桶太多则增加空桶内存。扩缩容是在平均访问成本和容量之间调整。

### 2.3 渐进式 rehash

一次性将大量条目搬到新表会造成长时间停顿。渐进式 rehash 在迁移期间保留旧表与新表，将工作分散到后续操作和维护中。

```text
旧表：未迁移桶与已有条目
新表：已迁移条目与新插入条目
          │
          └→ 迁移进度向前推进，完成后释放旧桶表
```

查找需要按迁移状态检查相关位置，新写入按实现规则进入新表。临时两套桶数组增加内存，迁移仍消耗 CPU；桶中的条目数量也不固定，因此渐进式并不等于每次迁移绝对等时。

### 2.4 数据库编号不提供资源隔离

独立数据库编号可在适用部署中分开键名，但通常共享进程执行资源、内存预算与持久化范围。将缓存放 DB 0、锁放 DB 1，不会自动建立不同淘汰策略或故障域。

经典 Redis Cluster 仅支持 DB 0。数据库编号也不是多租户权限边界，命名、权限和资源管理需要另外设计。

## 3. 命令执行与延迟模型

### 3.1 一条 GET 的执行链路

```text
应用取得连接、编码命令
  → 网络发送与服务器接收
  → 解析请求、检查权限与命令条件
  → 检查键状态，查找对象
  → 执行命令并构造结果
  → 发送响应、客户端读取与解码
```

写命令还影响过期状态、AOF、复制和其他维护，但这些进度不必都在同一时刻完成。成功执行、响应生成和客户端收到响应是不同事件。

RESP 协议用明确的类型和长度等信息编码请求与响应，可以承载含零字节的内容，不依赖将全部网络数据视为以零结尾的字符串。RESP2 与 RESP3 的回复类型存在差异，客户端解析应匹配协议模式。[官方协议规范](https://redis.io/docs/latest/develop/reference/protocol-spec/)

### 3.2 顺序执行与多线程的作用范围

经典模型中普通键空间命令主要由主执行路径顺序处理，使常见结构修改不需要在多个命令线程之间反复加锁。网络事件复用让一个线程能够处理很多连接，不必等待某个空闲连接的数据。

后台线程可承担部分 fsync 和对象释放，Redis 6 引入网络 I/O 多线程，8.x 又有实现演进。因此“进程只有一个线程”和“所有工作都由同一线程执行”不准确。[官方延迟与线程相关说明](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

I/O 并行不意味着一段普通长 Lua 可以被其他业务命令任意穿插。单个节点的主要命令执行瓶颈与网络瓶颈应分别分析，新增 I/O 线程不是所有热点问题的解决方案。[Redis 8.0 I/O 实现变化](https://redis.io/docs/latest/operate/oss_and_stack/stack-with-enterprise/release-notes/redisce/redisos-8.0-release-notes/)

### 3.3 长命令形成队首等待

某个命令连续处理大量元素时，后续短命令可能在其后等待。复杂度低的 GET 也会受到前方大范围操作影响。

设 99% 命令执行 20 微秒，1% 命令执行 5 毫秒，简化平均服务时间为：

```text
0.99 × 20 + 0.01 × 5000 = 69.8 微秒
纯执行路径的理想能力量级约为 1 / 69.8μs ≈ 1.43 万次/秒
```

这是假设算例，不是性能基准。它说明少量长任务可以显著改变平均成本和等待，而仅测短 GET 会高估真实负载能力。

### 3.4 字节规模参与成本

每次返回 100KiB、每秒 1000 次，仅正文就约 97.7MiB/s，尚未包含协议、TLS、复制和其他流量。平均查找 O(1) 无法消除传输这批字节的成本。

对象大小、集合元素数量、单次输出、客户端处理速度和节点 CPU 都需要参与评估。“QPS 相同”不意味着两组负载具有相同资源需求。

### 3.5 请求超时后的结果未知

```text
客户端发送 DECR
  → Redis 已经扣减
  → 响应丢失
  → 客户端超时
  → 直接重试导致再次扣减
```

超时既可能发生在执行前，也可能发生在执行后。接口需要稳定的请求 ID、可查回结果和明确重试策略；改变客户端超时时间不能消除结果不确定性。

## 4. 对象编码与 SDS

### 4.1 类型与编码是不同层次

类型决定命令语义，编码决定物理表示。同一 Hash 可以在较小时用紧凑结构，较大时转换为哈希表，对外仍使用 HGET / HSET。

| 逻辑对象 | 经典实现的常见表示 | 主要考虑 |
|---|---|---|
| String | int、embstr、raw | 数值范围、长度与分配成本 |
| Hash | listpack、hashtable | 小对象空间与较大对象定位成本 |
| List | quicklist 等分块表示 | 顺序操作、指针开销与局部搬移 |
| Set | intset、listpack、hashtable 等，按版本和条件 | 值域、数量和紧凑性 |
| ZSet | listpack 或有序结构加成员定位结构 | 小集合成本与排名 / 范围能力 |

这些不是永久的全部编码枚举。阈值和带字段过期等特殊布局应查所用版本，不通过记忆固定数字代替实际观察。[官方内存优化](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

### 4.2 SDS 保存长度与容量

普通 C 字符串通常以零字节结束，需要扫描求长度；Redis 的 SDS 用显式长度表示内容，并按长度类别安排头部元数据。

```text
概念布局：长度 / 容量或相应头部信息 / 标记 / 数据字节
```

显式长度使含零字节的内容也能正确保存，长度获取可直接读元数据。容量管理允许追加时先判断剩余空间，必要时扩容，减少重复分配。二进制安全指字节保存语义，不表示加密或内容验证。[Redis 7.2.0 SDS 定义](https://github.com/redis/redis/blob/7.2.0/src/sds.h)

不同 SDS 头部不必全部具有完全相同字段；概念图不用于推算所有字符串的精确字节成本。

### 4.3 String 的编码取舍

适用整数可用 int 表示，避免单独保存十进制文本；较短字符串可采用 embstr，将对象头和字符串相关布局合并分配，减少分配次数并改善局部性；raw 适合分开管理和修改较大字符串。

对外 String 仍保存按命令语义解释的字节，整数增量只适用于合法整数范围。将 embstr 描述为用户无法修改的字符串不准确，修改过程中可以转换编码。[Redis 7.2.0 对象源码](https://github.com/redis/redis/blob/7.2.0/src/object.c)

编码转换会产生分配和复制等成本，达到阈值附近的对象未必只按新增几个字节消耗资源。

### 4.4 小对象线性表示的收益

一个只有几个字段的 Hash，如果每个条目都维护多个指针和独立分配，固定开销可能超过有效内容。连续紧凑表示虽需线性查找，但 N 较小、访问局部性较好，可能更节省内存和时间。

对象变大后，逐项比较和搬移成本增加，转为其他结构更合理。编码选择的核心是常数开销、字节数、元素数与访问模式共同作用，不是仅比较渐近复杂度。

## 5. 紧凑结构与分块序列

### 5.1 ziplist 的历史问题

ziplist 曾广泛用于紧凑对象。条目记录前一个条目的长度，前项长度跨越编码边界时，后一条目的元数据可能扩张，后续边界又可能被触发，形成连锁调整。

连锁更新发生在适用边界，不是每次插入都修改全部条目。它体现了用连续紧凑布局节省空间时，元数据依赖可能放大局部改动。

### 5.2 listpack 减少前项长度依赖

listpack 通过记录条目自身相关长度信息支持遍历，减少 ziplist 式的前项依赖连锁。插入中间位置仍可能移动后方字节，扩容也仍可能重新分配，因此它没有把任意插入变成 O(1)。[Redis 7.2.0 listpack 源码](https://github.com/redis/redis/blob/7.2.0/src/listpack.c)

将历史 ziplist 结构图直接标记为所有现代 Hash / ZSet 的实现，会混淆版本。需要先确认当前 OBJECT ENCODING，再讨论其代价。

### 5.3 quicklist 将连续结构分块

单独连续大块的中间插入可能搬移很多字节；每个元素独立链表节点又有指针和分配开销。quicklist 将多个紧凑块通过链结构连接，在两个方向之间折中。

```text
块 A：多个元素 ←→ 块 B：多个元素 ←→ 块 C：多个元素
      局部连续             分块连接
```

Redis 7.2 的相关实现使用 listpack 等布局，历史版本则有差异。节点大小与压缩深度等设置影响局部访问、压缩和内存占用，不存在对所有 List 都最优的统一值。

### 5.4 intset 用受限值域降低开销

适用的小整数 Set 可以用有序整数数组表示。元素宽度随值域选择，插入更大范围整数可能需要整体升级表示；有序性支持查找，但中间插入仍可能搬移。

当元素类型、数量等不再满足条件时，可以转换其他表示。内部整数有序不意味着 Set 的对外遍历顺序获得稳定保证。[Redis 7.2.0 intset 源码](https://github.com/redis/redis/blob/7.2.0/src/intset.c)

### 5.5 编码转换是容量评估边界

对象接近转换条件时，新增一个字段可能触发整对象重表示，瞬时工作量大于普通单字段写入。将对象拆得很小可以减少某些转换，却增加键元数据；合并太大又会制造热点和迁移困难。

观察应同时记录 TYPE、OBJECT ENCODING、MEMORY USAGE、元素数量和操作耗时，不能只按业务内容字节估算 Redis 内存。

## 6. ZSet 的定位与排名设计

### 6.1 同时需要成员查找和有序访问

排行榜需要按成员更新分数，也需要按分数或排名读取。单个无序哈希表不直接提供排名；单个有序结构又未必具有最便捷的成员定位路径。

经典大 ZSet 表示配合成员字典和跳表：字典支持成员到分数的定位，跳表支持 `(score,member)` 的有序访问。两种结构可共享部分内容，不表示所有数据完整复制两份。[Redis 7.2.0 ZSet 源码](https://github.com/redis/redis/blob/7.2.0/src/t_zset.c)

### 6.2 跳表层级减少逐项移动

```text
高层：A ───────────────────→ H
中层：A ─────→ D ──────────→ H
底层：A → B → C → D → E → F → G → H
```

搜索从较高层前进，不能继续跨越目标时下降一层。随机层级让结构以期望成本支持查找和更新，普通大集合的相关定位通常为期望 O(log N)，范围输出还要加上返回 M 个元素的成本。

平衡树同样可以支持有序查询，增加子树计数也可支持排名。选择跳表可以从实现复杂度、范围遍历和元数据维护解释，不能仅以“方便无锁并发”描述普通 Redis 顺序执行路径的核心理由。

### 6.3 span 让跳跃具有排名含义

高层边还维护跨越的底层数量。搜索时累加 span，就能得到排名，而不必逐个遍历此前全部成员。

插入和删除会改变跨越数量，需要同步更新相关 span。额外元数据使排名访问更快，也增加写入维护职责。

### 6.4 相同分数与数值精度

同分成员按成员字节的字典顺序排列，不默认按首次到达时间排序。排行榜如果要求先达到分数者优先，需要额外建模。

score 使用浮点数表示，不能无限精确地保存任意大整数和拼接出来的复合分数。把时间与业务分数机械乘加，可能改变精度和排序语义。

### 6.5 排行榜分页与延迟任务

排名分页过程中有人进入前排，会移动后续排名，可能造成重复和遗漏。冻结榜单版本、保存快照或定义明确游标是不同需求，普通 ZRANGE 不产生跨请求快照。

用 ZSet 的 score 保存到期时间可以实现延迟任务候选查询，但“查到到期任务”和“独占领取”必须共同协调。完成移除后进程崩溃可能丢任务，需设计处理中状态、租约和恢复，而不能只用一个 ZREM 代表可靠执行。

## 7. String 与 Hash 的对象建模

### 7.1 整体替换与字段修改

商品对象可以序列化后用 String 保存，也可以分字段用 Hash 保存。

```redis
SET product:1001 "{\"name\":\"Book\",\"price\":100}" EX 300
HSET product:1002 name Book price 100 version 7
HGET product:1002 price
```

String 适合整体读取和替换，序列化格式由应用决定；Hash 适合按字段访问和局部修改。Hash 并不自动理解字段之间的业务关系，也不天然提供字段查询索引。

| 模型 | 主要收益 | 主要成本 |
|---|---|---|
| 一个 JSON String | 对象作为整体替换，读取协议简单 | 单字段读取也可能传整对象；应用解析和重写 |
| 一个 Hash | 按字段读取，原子字段增量 | 多字段组合语义、编码转换、大 Hash 访问 |
| 每字段独立键 | 生命周期和访问可分开 | 键元数据、跨键协调及 Cluster 槽约束 |

多字段读取应选择 HMGET 等适用命令，不必为了取一个价格而 HGETALL 整个对象。

### 7.2 原子增量与读后覆盖

```text
A GET counter → 10
B GET counter → 10
A SET counter 11
B SET counter 11
最终 11，而不是 12
```

INCR 把读取、整数加一和写回合并为一条命令，避免这类交错。它不自动判断库存上限，也不能使“INCR 后写订单”跨系统原子提交。

整数命令有合法格式和溢出边界，浮点增量也不适合替代精确金额模型。计数为零、键不存在和业务状态失效，需要应用定义不同含义。

### 7.3 条件写入与生命周期

```redis
SET lock:{1001}:rebuild owner-token NX PX 5000
```

NX 表达键不存在时写入，PX 同时建立租期，避免 SETNX 成功后进程崩溃、EXPIRE 尚未执行而形成无租期键。这个操作保护的是创建瞬间的条件，并不保证持有者会在 5 秒内结束。

普通成功 SET 覆盖通常会清除原 TTL，除非使用 KEEPTTL 或同时指定新的到期条件。INCR、HSET 等对值内部的修改通常保留整键 TTL；不能由“键有 TTL”推导出后续每次写都保持相同生命周期。[官方 SET](https://redis.io/docs/latest/commands/set/)、[官方 EXPIRE](https://redis.io/docs/latest/commands/expire/)

### 7.4 Hash 字段过期的版本边界

旧的通用结论“Hash 只能整键过期，不能字段过期”不适用于全部版本。Redis 7.4 起提供 HEXPIRE 等字段过期能力，字段生命周期与整键生命周期需要分开判断。

字段过期会增加状态管理和维护成本，也不将 Hash 变成关系表。字段写入、覆盖和过期时间保留规则应按具体命令核对，不能默认字段写入始终续期或始终保留原字段 TTL。[官方 Hash 与字段过期](https://redis.io/docs/latest/develop/data-types/hashes/)

### 7.5 对象大小与职责边界

将大量用户状态塞入一个 Hash，可以减少键级元数据，却会使对象迁移、整键删除、整键 TTL 和热点集中更难管理。节省内存需要与独立生命周期、查询输出和故障恢复一起比较。

Session 适合某些短期访问模式，但其丢失或撤销延迟会影响身份状态；购物车 Hash 的修改结果是否需要长期保留，也应明确是否有数据库或其他恢复来源。

## 8. List、Set 与有界遍历

### 8.1 List 的顺序与端点操作

List 保存有序元素，适合从端点推入和弹出。中间访问和较大范围读取需要跨越相关元素，不是所有 List 操作都恒定成本。

```redis
RPUSH jobs:ready job-1001 job-1002
LPOP jobs:ready
LRANGE jobs:ready 0 99
```

阻塞命令 BLPOP 等在没有元素时挂起该客户端等待，服务器仍可服务其他连接。“阻塞读取”不能解释成整个 Redis 停止运行。

### 8.2 弹出与业务完成的故障窗口

```text
消费者弹出任务
  → List 已移除该任务
  → 消费者尚未完成业务就崩溃
  → 没有其他记录可恢复任务
```

可以用 LMOVE / BLMOVE 把任务从 ready 移到 processing，完成后删除处理中记录，再设计超时重新领取。任务必须有稳定身份，不能仅按可能重复的消息正文确认。

这个协议解决部分消费者故障窗口，仍需要处理重复执行、并发认领、持久化和复制丢失。要求消费组与待确认管理时，可评估 Stream，而不是自行假定 List 已具备全部消息协议。[官方 List](https://redis.io/docs/latest/develop/data-types/lists/)

### 8.3 Set 的成员身份

```redis
SADD product:1001:likes user-42 user-43
SISMEMBER product:1001:likes user-42
SCARD product:1001:likes
```

Set 以成员身份去重，重复添加同一成员不会形成两个相同元素。适合点赞成员和标签集合，但业务写入数据库、消息发送等副作用仍需幂等。

集合交、并、差可以在服务器执行，工作量受输入大小与结果大小影响。SMEMBERS 大集合或多集合运算可能消耗明显 CPU、内存与输出带宽，不能仅按单成员查找平均复杂度评估。

### 8.4 KEYS 与 SCAN 的不同职责

KEYS 对键空间进行集中遍历，较大实例中可能形成明显执行停顿。SCAN 将遍历拆成游标调用，降低单次集中工作，但不是固定大小分页和一致性快照。

```redis
SCAN 0 MATCH product:* COUNT 100
```

应用使用返回的新游标继续，直到返回游标 0。COUNT 是提示，不保证返回 100 个键；空结果也不表示完整遍历结束，游标才是完成条件。[官方 SCAN](https://redis.io/docs/latest/commands/scan/)

完整遍历期间始终存在的元素在适用约定下会返回，也可能重复；新增或消失元素的返回结果没有统一保证。HSCAN、SSCAN、ZSCAN 对各自对象也需要考虑紧凑编码等行为。

### 8.5 扫描协议与业务幂等

在线扫描用于清理或迁移时，处理流程需容忍重复和对象变化；游标不等于可永久复用的快照位置。Cluster 全局扫描通常需要遍历相关主节点，单节点 SCAN 不代表整个集群。

有界读取应同时限制元素数量和返回字节。100 个小成员与 100 个大成员不是相同批次，某次扫描也可能超出 COUNT 提示。

## 9. 位图、近似统计与地理索引

### 9.1 Bitmap 以位置映射状态

Bitmap 基于 String 的位操作，适合将稠密、范围可控的对象编号映射到签到或开关状态。

```redis
SETBIT attendance:2026-10-12 42 1
GETBIT attendance:2026-10-12 42
BITCOUNT attendance:2026-10-12
```

内存取决于最高位偏移对应的范围，不仅取决于置 1 的数量。如果只设置一个极大 ID 对应位，也可能扩张出很大的稀疏字符串。编号压缩或分桶需要与业务身份映射共同设计。

BITCOUNT 和位运算需要处理相关字节，不能因为位状态紧凑就忽略大范围扫描。适用时 Bitmap 可显著减少单状态表示开销，但不直接表达复杂记录。

### 9.2 HyperLogLog 用误差换空间

HyperLogLog 从哈希结果的统计特征估算基数，不保存全部成员。适合独立访客估算等允许误差的指标，不支持准确成员查询和任意删除成员。

```redis
PFADD uv:2026-10-12 user-42 user-43
PFCOUNT uv:2026-10-12
```

典型密集表示的寄存器量级约 12KiB，常用标准误差约 0.81%，不是每次结果绝对误差都小于该百分比的保证。小基数还可能采用不同表示。[官方 HyperLogLog](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)

多个时间桶可按所需指标合并估算，不能简单相加每天 UV 当作整月去重人数。准确计费或权限判断不能用近似基数代替精确成员状态。

### 9.3 GEO 用位置编码缩小候选

GEO 将适用坐标编码到有序索引，范围查询先借助编码定位候选，再做几何过滤等处理。

```redis
GEOADD shops 121.47 31.23 shop-1001
GEOSEARCH shops FROMMEMBER shop-1001 BYRADIUS 5 km
```

附近查询不等于道路通行距离或最优路线。坐标范围、距离近似和候选数量都需要与产品需求匹配；返回大量周边对象仍有输出成本。[官方 GEO](https://redis.io/docs/latest/develop/data-types/geospatial/)

### 9.4 Bloom filter 的概率与维护

基础布隆过滤器使用位数组和多个哈希位置。存在某个必需位为 0，可判断该元素未加入；全部为 1 仅表示可能加入。

在全部有效对象都已加入、结构正确维护的前提下，不会因算法误差拒绝已加入对象，但可能放过不存在对象。新增商品未及时加入造成的错误拒绝，是系统维护遗漏，不是概率误判。

理想容量关系为：

```text
m = -n × ln(p) / (ln 2)^2
```

n 为预期元素数，p 为目标误判率，m 为位数。容量增加、误判目标更严格都需要更多空间，实际实现还包括元数据与扩容开销。基础位共享模型不能直接清零几个位来删除一个成员。

Redis Bloom 相关命令是否存在，要看部署版本和组件，不能仅因为实现了 Bitmap 就认为 BF.ADD 等必然可用。[官方 Bloom filter](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)

### 9.5 精确结构与近似结构的选择

Set 保存成员，用更多空间提供精确成员语义；Bitmap 在适用编号映射下精确表示位状态；HyperLogLog 提供基数估算；Bloom filter 提供低成本的可能存在判定。

选择依据是需要回答的查询，不是只比较占用内存。把不兼容的结果语义替换成近似值，属于业务行为改变。

## 10. Stream 与消费确认

### 10.1 从有序记录到消费进度

Stream 保存带 ID 的消息记录，提供追加、读取和消费组管理。传统 ID 包含毫秒时间部分与序号，但不应将其作为所有服务业务提交顺序或绝对真实时钟的唯一依据。

```redis
XADD events:{orders} * order_id 1001 event created request_id req-42
XGROUP CREATE events:{orders} order-workers 0 MKSTREAM
XREADGROUP GROUP order-workers worker-a COUNT 10 STREAMS events:{orders} >
```

消费组创建起点 0 表示允许消费已有记录；`$` 等起点具有不同含义。`>` 请求尚未作为新消息交付给该组的记录，不表示自动重试全部待确认记录。

### 10.2 PEL 保存待确认状态

常规组读取未使用 NOACK 时，交付记录进入 Pending Entries List。PEL 表达交付和确认状态，不是消息正文的第二份持久副本。

```text
消息正文仍在 Stream
  → 消费组交付给 worker-a
  → PEL 记录其待确认状态
  → worker-a 完成业务
  → XACK 移除该组的 pending 状态
```

XACK 不删除 Stream 正文，也不替其他消费组确认。消息 ID、每组进度和正文保留是不同层次。[官方 XACK](https://redis.io/docs/latest/commands/xack/)

### 10.3 消费者崩溃后的认领

XPENDING 用于观察待确认状态；XCLAIM / XAUTOCLAIM 可将达到条件的 pending 交给其他消费者。应用需安排这个恢复路径，不能只循环 XREADGROUP 的 `>`。

认领依赖空闲时间等条件，不证明原消费者已死亡。原消费者可能因暂停或慢外部请求尚未完成，重新认领后两个执行者仍可能同时处理同一业务。

因此 pending 恢复需要稳定消息身份、业务幂等和适当超时，不是单纯缩短认领门槛就能加快且保证正确。[官方 XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/)

### 10.4 业务提交与 ACK 的时序

```text
先 ACK 后业务：ACK 成功 → 进程崩溃 → 业务可能永久漏执行
先业务后 ACK：业务提交 → ACK 前崩溃 → 业务可能再次执行
```

通常让数据库唯一业务身份、去重记录与业务效果在同一事务提交，再发送 ACK。重投时从数据库识别原结果，可以避免重复扣款或发货。

这在允许重投的前提下形成业务幂等，不意味着 Redis 和数据库之间存在自动原子提交。数据库提交结果不确定时，也需先查回而非直接 ACK 或再做一次副作用。

### 10.5 正文裁剪与 pending 恢复

Stream 可以通过裁剪控制容量，但不能假设未 ACK 的正文一定会永久保留。传统裁剪可能移除仍被 pending 引用的消息正文，使恢复只剩 ID 而缺少内容。

Redis 8.2 引入部分新的确认 / 删除和引用处理能力，具体命令选项应按版本核对；不能将新策略直接套到 7.2 / 7.4。所有组的处理时间、正文保留、死信和回放目标需要共同设计。[官方 Stream](https://redis.io/docs/latest/develop/data-types/streams/)、[官方 XTRIM](https://redis.io/docs/latest/commands/xtrim/)

### 10.6 Pub/Sub 的在线广播边界

Pub/Sub 向当前订阅者广播，经典模型不为离线订阅者保存消费进度或自动补发全部历史。AOF 保存数据集不把 PUBLISH 变成持久可重放队列。

允许错过并能重新查询完整状态的通知，可使用在线广播；需要确认、重试和历史回放的业务，需要具有相应协议的消息结构。Stream、List 与 Pub/Sub 不能只按“都能传消息”互换。[官方 Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)

## 11. Pipeline、事务与 WATCH

### 11.1 Pipeline 减少逐次往返

Pipeline 让应用连续发送多条命令，不必等待前一条回复后再发下一条，也可以降低部分读写系统调用成本。

设 RTT 为 1 毫秒，100 条各执行 20 微秒的命令逐条等待，简化耗时约为 102 毫秒；理想批量下界近似一次 RTT 加总执行时间，为约 3 毫秒。真实链路还包含缓冲、排队和客户端调度。[官方 Pipeline](https://redis.io/docs/latest/develop/using-commands/pipelining/)

Pipeline 不把读取结果后的业务判断自动移到服务器，也不建立整个批次的不可穿插或回滚保证。每条响应都需要检查，连接中断时还可能只能确认批次的一部分。

### 11.2 批次大小是资源与延迟取舍

批次过大增加客户端和服务器响应缓冲，使一批数据占用连接更久，并可能放大其他请求等待。应同时限制命令数、输入 / 输出字节和批次时间。

Cluster 客户端可能按节点拆批并合并结果，但跨节点执行仍不是同一个原子批次。客户端 API 的便利性不改变服务器的执行作用域。

### 11.3 MULTI 与 EXEC

MULTI 后相关命令进入事务队列，EXEC 时在相应执行段顺序运行，其他客户端普通命令不会在该段之间插入。应用是在排队时收集命令，不是在每次 QUEUED 时已经完成修改。

Redis 的事务语义不等同于 InnoDB 事务。它不提供通用 MVCC 读取，也不在所有运行时错误后撤销已执行命令。[官方事务](https://redis.io/docs/latest/develop/using-commands/transactions/)

### 11.4 排队错误与执行错误

排队阶段的错误，例如参数数量不合法，在适用版本中可导致 EXEC 放弃整个队列；EXEC 中的类型错误则通常作为某一项错误返回，其他已执行修改保留，后续相关命令继续。

```redis
SET demo:count 0
SET demo:string hello
MULTI
INCR demo:count
HSET demo:string field value
INCR demo:count
EXEC
```

给定初始状态，预期计数依次增至 1、2，中间 HSET 因目标不是 Hash 报错。不能因 EXEC 返回数组中有错误，就假定计数仍为 0。

DISCARD 取消尚未执行的队列，不用于撤销已经完成的 EXEC。事务内一条业务校验命令返回“不满足”，也不会像应用 if 分支一样自动跳过后续命令。

### 11.5 WATCH 检测前置状态变化

```text
A WATCH stock
A GET stock，按读取值计算
B 修改 stock
A MULTI，排队写入
A EXEC 因被观察状态变化而不执行队列
```

WATCH 属于乐观冲突检测，不是让 B 在 A 读取后禁止写入。失败后 A 需要重新读取并计算，不能只重复旧写入。

Redis 7.2 / 7.4 下，被观察键的过期或淘汰也可能使事务失效；早期版本的过期细节不同。WATCH、读取、MULTI 和 EXEC 需要绑定连接，断线也会改变会话状态。

### 11.6 并发执行与数据保留

事务执行不可穿插不等于已同步全部副本和磁盘，也不保证响应丢失后可以安全重复 EXEC。应用仍需结合持久化、复制确认和业务请求身份分析。

## 12. Lua 与 Functions 的作用域

### 12.1 将依赖结果的判断移到数据侧

GET、判断、扣减分成多个网络请求会有并发窗口。短 Lua 可以在同一执行段内读取和检查，再修改相关 Redis 状态。[官方 Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)

下面脚本只说明单键库存准入，限定库存与数量为可精确表示的非负整数，且不超过 10 亿；qty 必须大于零。

```lua
-- KEYS[1]：stock:{1001}；ARGV[1]：请求数量
local qty = tonumber(ARGV[1])
if not qty or qty <= 0 or qty ~= math.floor(qty) or qty > 1000000000 then
    return redis.error_reply('invalid quantity')
end

local raw = redis.call('GET', KEYS[1])
if not raw then
    return {-1, 0} -- 未初始化，不能把缺失当作充足库存
end
local stock = tonumber(raw)
if not stock or stock < 0 or stock ~= math.floor(stock) or stock > 1000000000 then
    return redis.error_reply('invalid stock')
end
if stock < qty then
    return {0, stock}
end

local remaining = stock - qty
redis.call('SET', KEYS[1], string.format('%.0f', remaining), 'KEEPTTL')
return {1, remaining}
```

脚本先验证再进行唯一写入，正常执行时其他业务命令不能在读取与扣减之间穿插。GET 遇到错误类型也会在修改前失败。但脚本没有实现请求去重、订单提交、复制确认或故障回补，不能直接作为完整秒杀系统。

### 12.2 Lua 原子执行不等于自动回滚

```lua
redis.call('INCR', KEYS[1])
redis.call('HSET', KEYS[2], 'field', 'value')
```

若 KEYS[2] 是 String，第二步报错，第一步可能已经递增。redis.call 和 redis.pcall 的错误处理方式不同，但捕获错误也不会自动撤销前面的写入。

写前检查参数和类型可以缩小错误窗口，不构成支持任意失败回滚的通用协议。复杂多步业务需要对每个写入后的故障点单独分析。

### 12.3 执行时间必须有界

脚本执行阈值不是达到时间后自动终止并回滚的期限。长脚本可能使其他普通请求受到 BUSY 或等待影响。SCRIPT KILL 只可安全终止尚未修改数据集的相关脚本，已经产生写入不能依靠它撤销。[官方 SCRIPT KILL](https://redis.io/docs/latest/commands/script-kill/)

因此循环次数、读取集合大小、返回字节和每次调用工作量应有上界。服务器端执行减少网络往返，不消除工作本身。

### 12.4 KEYS、脚本缓存与部署

脚本访问的键应由 KEYS 明确提供，业务参数通过 ARGV 传入，不把每次参数拼成一份新脚本文本。Cluster 中共同访问键还需满足相应槽规则。

EVALSHA 依赖节点脚本缓存，重启、缓存变化或路由到其他节点后可能 NOSCRIPT，客户端需提供合适加载与重试逻辑。该重试与响应超时后的盲目业务重放是不同情况。

### 12.5 Functions 与版本管理

Redis 7.0 起提供 Functions，将函数库作为服务器管理状态，可与相应持久化和复制配合，减少依赖临时脚本缓存的部署问题。

函数仍有执行作用域和时间成本，不能自动访问外部数据库形成跨库事务；多节点加载、版本升级和回滚也需要管理。[官方 Functions](https://redis.io/docs/latest/develop/programmability/functions-intro/)

## 13. 过期时间与清理

### 13.1 到期定义可访问生命周期

TTL / PTTL 表示剩余时间，单位分别为秒和毫秒；常见返回 -1 表示没有相应过期时间，-2 表示键不存在。过期元数据与实际释放内存不是同一个动作。

过期可通过相对时间或绝对到期时刻设置。持久化与重启需要保留生命周期语义，机器离线时间不会普遍将 TTL 冻结；系统时间异常也可能影响绝对到期判断。

### 13.2 惰性检查与主动清理

读取或操作键时可以检查是否已过期，避免把过期状态继续当作普通有效值；如果很少访问旧键，还需要主动周期性清理以释放空间。

```text
到期键被访问 → 访问路径检查与处理
到期键长期不访问 → 主动过期周期发现与处理
```

主动清理受时间和工作预算控制，不能为每个 TTL 到期建立一个无成本的精确定时物理删除承诺。大量同时到期会增加维护工作和回源压力。

### 13.3 删除与释放的不同进度

从键空间中移除对象和释放其全部分配内存可以分开。DEL 的某些大对象释放可能较重；UNLINK 将键从可访问空间移除，并把适用释放工作交给后台。[官方 UNLINK](https://redis.io/docs/latest/commands/unlink/)

UNLINK 不是内存瞬间完全归还，也不缩小已经产生的复制和业务失效范围。后台积压仍需监控，连续大量异步释放会消耗资源。

### 13.4 TTL 不代表数据必定保留到期

TTL 表达最长生命周期的一部分，键还可能被主动删除、淘汰或因故障丢失。不能用“还剩 10 秒”证明去重记录一定能覆盖下次重试。

缓存刷新若重新 SET 并设置完整 TTL，会重置期限；访问是否续期应由业务明确决定。TTL 是状态的一部分，不只是可忽略的运维属性。

## 14. 淘汰、内存与热点

### 14.1 过期与淘汰的目标不同

过期按生命周期决定键是否仍有效；淘汰在内存压力下选择移除哪些键。无 TTL 键不会因普通过期清理消失，但仍可能被 allkeys 策略淘汰。

| 策略族 | 候选范围与倾向 | 适用边界 |
|---|---|---|
| noeviction | 不通过淘汰键解决压力 | 部分需额外内存的写命令可能被拒绝 |
| allkeys-lru / lfu | 全部键中按近似访问特征选择 | 可重建数据通常更适合 |
| volatile-lru / lfu | 只考虑设 TTL 的适用键 | 无足够候选时不能凭空释放所需空间 |
| allkeys-random / volatile-random | 在对应候选中随机选择 | 不区分长期访问价值 |
| volatile-ttl | 倾向淘汰更接近到期的候选 | 期限短不必等于业务价值低 |

策略作用域不按业务键前缀自动区分。把锁和商品缓存放在同一会 allkeys 淘汰的实例，会给锁的保留语义增加风险。[官方淘汰](https://redis.io/docs/latest/develop/reference/eviction/)

### 14.2 近似 LRU 与 LFU

维护严格全局 LRU 链会增加元数据和每次访问维护成本。Redis 使用采样等近似机制降低这类开销，不保证总是淘汰数学意义上最久未访问的那个键。

LFU 用概率计数和衰减反映访问频率，避免历史热点永久占据高优先级。访问次数不是一个无限精确递增的完整累计计数器。

LRU 更敏感于近期访问，LFU 可在适用负载下抵抗一次性扫描；热点变化快时还要评估适应速度。工作集远大于内存时，换策略不能消除容量缺口。

### 14.3 maxmemory 与物理内存

maxmemory 约束相关 Redis 内存比较，不是进程 RSS 或容器物理内存的绝对硬上限。部分复制和持久化缓冲不计入淘汰判断，避免淘汰产生传播记录又触发更多淘汰的反馈。

```text
峰值物理需求
  ≈ 活跃数据与元数据
   + 分配器及进程开销
   + 未计入淘汰比较的相关缓冲
   + 后台任务 COW 增量
   + 必要余量
```

公式是预算分类，不是将 INFO 各内存字段直接相加，字段可能包含彼此。达到 maxmemory 后的命令拒绝、后台峰值和操作系统 OOM 是不同事件。

### 14.4 碎片与释放后的 RSS

对象尺寸变化和分配器管理可能产生未被有效内容充分使用的空间。键删除后，分配器未必立即将所有页归还操作系统，RSS 因而可能保持较高。

碎片比例需结合数据集大小和绝对字节，小实例固定开销也能造成很高比例。主动碎片整理有实现、分配器和配置条件，不能把某个比例大于阈值当作统一启用或重启依据。

### 14.5 大 Key 与热 Key 的不同瓶颈

| 现象 | 需要测量 | 设计方向 |
|---|---|---|
| 大字符串频繁读取 | 每次字节 × 请求率 | 减少返回、压缩取舍、合并或本地缓存 |
| 大集合集中操作 | 元素数量、扫描 / 输出工作 | 有界操作、合理拆分 |
| 大对象释放慢 | 分配数量、释放时间、后台积压 | UNLINK 与生命周期安排 |
| 热读集中 | 同键访问率、节点负载、陈旧度目标 | 合并请求、本地缓存、适用副本读 |
| 热写集中 | 同键修改率、热点分片 CPU | 业务拆分、批量合并、分区统计 |
| 单键迁移重 | 单键体积和迁移峰值 | 从模型上分解独立对象 |

固定“超过多少 KiB 即大 Key”的阈值缺少工作负载语义。1MiB 每小时读一次与每秒读千次，影响完全不同。

### 14.6 按数据职责隔离

可重建缓存、锁和版本屏障、请求去重、消息可以拥有不同容量与保留目标，必要时按实例或服务边界分开。

noeviction 减少关键键被淘汰的风险，但需要应用处理写拒绝并监控容量；它不保证进程永不崩溃，也不解决复制丢失。逻辑数据库编号不足以建立这类资源隔离。

## 15. RDB 与快照资源

### 15.1 数据快照作为恢复基线

RDB 将某个快照时点的数据状态写成恢复文件，不是逐条保存全部历史命令。恢复可直接加载状态，适合备份、复制基线和相应重启场景。

最近快照之后的修改若没有其他可靠恢复来源，故障后可能丢失。因此快照间隔应结合可接受丢失窗口，而不能只以文件较小评价。

### 15.2 SAVE 与 BGSAVE

SAVE 在前台执行保存，可能使普通服务受到长时间阻塞；BGSAVE 在经典 Unix 部署中通过 fork 后的子进程生成文件，父进程继续服务。[官方 BGSAVE](https://redis.io/docs/latest/commands/bgsave/)

后台不是完全无停顿。fork 需要处理地址空间等工作，实例越大或环境越不适合，停顿可能越明显；子进程写文件还竞争 CPU、内存和磁盘。

### 15.3 写时复制保存快照视图

fork 后父子进程起初共享部分物理页；父进程修改共享页时，操作系统按页进行复制，使子进程保持快照视图。

```text
fork 时：父、子共同引用原页
父修改：父获得相应复制页；子仍读取旧页
子输出：将旧视图序列化为快照
```

新增数据、缓冲和分配器状态又是其他开销。不能将写时复制估算成“新值大小总和”，也不能认为后台保存总要立即复制整个数据集。[官方持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 15.4 COW 峰值取决于不同脏页

假设共享普通页大小为 4KiB，后台期间首次写到 50 万个不同共享页，仅该部分复制量约为：

```text
500000 × 4096 B ≈ 1.91 GiB
```

反复修改同一页不等于每次都再复制完整原共享页；实际页大小、分配布局、THP 和修改分布会改变结果。父子 RSS 包含共享页，不能直接相加当作独立物理内存。

高写入、长保存时间和大实例会扩大峰值，因此 maxmemory 不能吃满容器预算。评估应覆盖高峰写入期间的 COW 和 fork 延迟。

### 15.5 备份完成与可恢复性

RDB 文件生成成功只证明一次保存流程结束，恢复还涉及文件可用、版本兼容、生命周期和业务校验。备份若只在同一故障域内保存，不能覆盖该故障域整体损坏。

恢复时间包含加载、服务重新连接和缓存预热；可重建缓存的 RTO 还需要计入数据库回源能力，不能只计算 Redis 进程启动时间。

## 16. AOF 与日志重写

### 16.1 从内存修改到持久文件

AOF 记录恢复所需的写操作表示，写入缓冲、写到操作系统页缓存和完成 fsync 是不同进度。

```text
命令处理改变内存状态
  → 生成适用 AOF 记录
  → 写入文件 / OS 缓存
  → 按策略完成同步
```

经典 AOF 主要围绕命令处理后的传播结果组织，不是 InnoDB 页级 WAL 的同构实现。不能把 AOF 直接称为保护每个 Redis 内存对象物理页的 redo。

### 16.2 appendfsync 的故障边界

| 策略 | 常规含义 | 代价与限制 |
|---|---|---|
| always | 对相应写入安排同步后再完成相关确认 | 同步成本进入延迟，可有批量处理收益 |
| everysec | 通常约每秒安排后台同步 | 近期修改可能未达到可靠存储 |
| no | 将同步节奏更多交给操作系统 | 丢失窗口与 OS 刷写和故障相关 |

everysec 不能作为所有异常条件下“最多精确丢一秒”的严格契约，调度和 I/O 异常可能改变窗口。always 也依赖存储真正兑现同步，不自动约束故障转移选择。[官方 AOF 策略](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 16.3 重写从当前状态重建紧凑基线

同一计数器递增百万次后，恢复所需不必是百万条原始 INCR。AOF rewrite 从当时有效数据生成新的恢复基线，减少历史冗余。[官方 BGREWRITEAOF](https://redis.io/docs/latest/commands/bgrewriteaof/)

它不是直接对旧日志文本做简单去重，因为当前状态还涉及删除、覆盖和过期。后台生成基线时，父进程仍需记录后续修改，防止快照后写入出现缺口。

### 16.4 Redis 7 的多部分 AOF

Redis 7 起的多部分 AOF 由基础文件、增量文件和 manifest 等协作。基础文件可采用 RDB 格式或相应 AOF 表示，增量文件保存后续变化。

```text
manifest 描述当前有效文件集合
   ├─ base：某个状态基线
   └─ incremental：基线后的写入历史
```

重写期间安排新基线与增量，并在完成后切换有效集合。旧式“一个 AOF 文件加重写缓冲”的图不能无版本说明地当作全部现代路径。

备份与恢复必须把有效 manifest 和相关文件作为一致集合处理，不能只复制目录里名字看起来最新的一个文件。

### 16.5 加载、损坏与历史恢复

配置启用 AOF 时，启动通常根据其有效文件集合恢复，不能假定看到一个 RDB 文件就一定优先加载它。截断、损坏和错误修复策略还影响能够恢复的边界。

运行中的键淘汰不意味着 AOF 能像磁盘索引一样按键自动补读。AOF 是重建数据集的恢复输入，不是普通 GET 的后台存储层。

已提交并传播的误删除会成为恢复历史的一部分，普通重启不会自动识别并撤销错误业务命令。备份保留、日志分析和恢复演练属于额外能力。

### 16.6 持久化和复制独立配置

本地 AOF 可靠保存不等于故障后一定提升拥有该写入的副本；副本收到写入也不等于它已本地 fsync。需要同时分析本地恢复、复制进度和新主选择。

数据职责决定配置：可重建缓存可接受某些丢失，但恢复洪峰需要预算；不可随意重复的协调状态则应重新评估是否足以满足其故障模型。

## 17. 主从复制与确认

### 17.1 有序复制流与异步传播

主节点将适用修改传播到副本，副本接收并处理复制流。经典主从复制默认异步，主节点成功响应时，副本不必全部已拥有最新结果。[官方复制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

副本读可能陈旧。延迟不仅来自网络，还可能来自长命令、加载基础数据、资源不足和输出缓冲压力。读取旧值与读取失败是不同业务结果。

### 17.2 全量同步建立基线

没有可用共同复制历史时，副本通常通过全量同步取得基线，再接收并应用基线期间产生的增量。

```text
建立同步关系
  → 主节点生成或传输 RDB 基础状态
  → 保存期间继续记录相关增量
  → 副本加载基础状态
  → 继续处理复制增量，逐步追平
```

基线可以通过有盘或适用无盘方式传输，具体资源和时序不同。全量同步不是无成本拷贝，可能增加 fork、COW、网络和副本加载压力。

### 17.3 部分重同步需要身份与历史

复制 ID 标识历史分支，offset 标识流中的进度，backlog 保留近期流内容。重连副本在身份兼容且缺失历史仍保留时，才有条件部分重同步。

只比较 offset 数字不足以证明属于同一历史；故障转移后的相关 ID 继承机制也需按协议判断。[官方 PSYNC](https://redis.io/docs/latest/commands/psync/)

### 17.4 backlog 按字节率估算

设复制流峰值约 10MiB/s，目标覆盖 90 秒短断线，基本历史量约为 900MiB，再按波动和资源留余量。

这个计算采用复制流字节，不是业务请求数。backlog 加大也不能解决不兼容历史、极慢副本或加载能力不足。

```text
副本落后 → 超出保留历史 → 全量同步
   → 主从资源增加 → 追平更困难 → 可能再次同步
```

这个反馈环提示容量设计应共同考虑实例体积、写入率、慢副本和同步峰值，而不是只调一个 backlog 数字。

### 17.5 WAIT 的连接与返回条件

```redis
SET demo:progress done
WAIT 1 100
```

示例必须在同一条适用连接上执行。WAIT 等待该连接此前写入相关进度获得要求数量副本的确认；返回数量不足不会撤销之前的 SET。

WAIT 不证明副本全部已 fsync，也不保证任何未来切换都选中这些副本。在不能阻塞的事务或脚本上下文中，不能假定具有同样的普通阻塞等待行为。[官方 WAIT](https://redis.io/docs/latest/commands/wait/)

### 17.6 WAITAOF 与持久确认

Redis 7.2 起提供 WAITAOF，可等待同一连接此前写入的本地与副本 AOF 同步确认。

```redis
SET demo:durable done
WAITAOF 1 1 1000
```

需配置相应 AOF 条件并检查返回的本地和副本计数。它比普通复制确认多涉及持久化进度，但不是共识复制、跨分片提交或数据库与 Redis 的全局事务。[官方 WAITAOF](https://redis.io/docs/latest/commands/waitaof/)

确认不足仍可能意味着写入已经发生，只是未达到请求的等待条件。库存扣减等不能因此无条件再做一次。

### 17.7 min-replicas 的可用性取舍

min-replicas-to-write 和 min-replicas-max-lag 可以在副本健康条件不足时限制主节点接受写入，降低某些网络分区中继续独立写的风险。

它们检查相关副本数量与滞后条件，不是这一次写入已获得 N 个副本确认的逐条同步协议。保护代价是某些故障期间拒绝写入，应与业务可用性目标一起定义。

## 18. Sentinel 与故障转移

### 18.1 监测和发现不等于复制

Sentinel 监测主从、协调故障转移，并向客户端提供主节点发现。数据仍由 Redis 主从复制，不是存进 Sentinel 自身。

```text
复制：让副本拥有数据
Sentinel：判断故障并协调提升
客户端：发现新主并恢复连接
应用：处理切换期间超时、失败和未知结果
```

Sentinel 不分片数据，也不因增加监测进程数量提升单主的写入容量。

### 18.2 主观与客观下线

单个 Sentinel 按自己的观察判断主观下线；对主节点达到配置 quorum 的相关判断后，可形成客观下线判断。

真正执行故障转移还需要 Sentinel 的多数授权条件。quorum 和多数选举不是同一个数，达到较小 quorum 不表示网络分区中的少数监测者可以独立完成提升。[官方 Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

### 18.3 提升副本与客户端切换

候选副本需满足适用条件，选择还涉及优先级、复制进度等。提升后重新安排复制关系，客户端通过 Sentinel 或适用发现机制更新目标连接。

发现、选举、提升、连接池恢复和请求恢复分别耗时。服务端切换已结束，不表示应用还持有的旧连接立即全部正确路由。

### 18.4 异步复制保留风险

旧主可能已经响应成功，但写入尚未到达被提升的副本；新主历史因而可能缺失这条写入。旧主稍后回归时，不能假设两边独立写入会自动按业务语义合并。

网络分区中旧主还可能暂时接受写入，需结合客户端路由、复制健康限制和资源端协议降低风险。Sentinel 的选举多数并不等同于每条业务写入的多数持久确认。

### 18.5 恢复目标与部署

RPO 表达可接受丢失窗口，RTO 表达恢复服务时间。Sentinel 缩短故障恢复的一部分，复制和持久化影响数据保留，客户端与应用决定最终用户可见恢复。

多个副本或 Sentinel 若位于同一故障域，不能当作同样数量的独立容错域。目标应以实际部署和故障演练验证。

## 19. Cluster 的路由与原子边界

### 19.1 哈希槽将键映射到节点

经典 Redis Cluster 使用 16384 个槽，由键的 CRC16 相关计算映射到槽，再由槽映射到主节点。

```text
key → slot → 所有者节点
           │
           └→ 扩缩容时迁移槽，不直接改变全部应用键名
```

槽是路由单位，不是 16384 个独立进程，也不意味着每个槽都有相同数据量或请求量。[官方 Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

### 19.2 hash tag 将相关键放到同槽

```text
product:{1001}:data
product:{1001}:guard
lock:{1001}:rebuild
```

符合规范的非空花括号片段用于共同槽计算。这样可让相关键共同执行适用多键命令或脚本，但所有相关压力也集中到相同槽。

花括号解析有明确规则，不是从任意位置选取一个看起来合适的片段。将全部业务固定为一个 tag 会限制扩展，合理分组需要围绕最小共同原子范围。

### 19.3 多键操作的部署约束

经典 Cluster 的相关多键命令、事务和 Lua 需要键满足同槽等条件。单机可用的多键方案不能不改模型就推广到任意分片。

客户端可能通过跨节点调用模拟一个 API，但结果可能部分成功，并不获得原生跨槽事务。需要先检查服务器命令与客户端实际执行路径。

### 19.4 MOVED、ASK 与迁移

MOVED 表示该槽应向新的所有者路由，客户端通常更新槽缓存；ASK 是迁移阶段的临时转向，客户端对目标发 ASKING 后执行相关下一命令，不必将其当作永久所有权变化。

迁移期间，多键即使同槽，也可能因键分别位于源与目标而暂时不满足共同执行条件，出现 TRYAGAIN 等结果。同槽是必要模型条件，不保证迁移中的每次调用一定成功。

### 19.5 故障转移与多数条件

Cluster 使用节点间故障判断和提升协议，但数据仍主要沿异步复制路径传播。主节点多数、槽状态和配置影响可用性，不能简单理解成任何存活节点都可独立继续服务全部槽。

已确认但未被新主保留的写入风险仍需分析。Cluster 增加分片与路由能力，不自动把普通命令变成跨节点持久共识事务。

### 19.6 均匀槽数与热点

节点槽数量均匀，也可能某一个键承受绝大部分写入。一个普通键不会随 Cluster 扩容自动拆到多个主节点并行修改。

热读可评估本地缓存或适用副本；热写需要考虑业务拆分和合并。拆分计数、排行榜或库存又会引入聚合与一致性问题，应说明得到的容量收益和改变的语义。

## 20. 数据库与缓存一致性

### 20.1 先定义陈旧度和权威来源

商品描述允许短时陈旧，管理员更新后要求看到自己提交的结果，最终结算不得使用旧价格，属于不同约束。

| 需求 | 可考虑的协议 | 核心限制 |
|---|---|---|
| 展示允许短时陈旧 | Cache Aside、可靠失效、TTL | 必须定义陈旧度与失败恢复 |
| 会话读到自己的写 | 返回已提交状态，或携带最低版本要求 | 不直接证明所有用户都立即看到新值 |
| 核心决策使用有效状态 | 在权威事务存储中检查与修改 | 普通缓存不能替代业务约束 |

读写路径决定谁负责失效、回填、排序和恢复。Redis 不会仅因为缓存来自 MySQL，就自动订阅其所有变更。

### 20.2 两个写请求直接更新缓存

```text
W1：数据库提交价格 110
W2：数据库提交价格 120
W2：缓存写入 120
W1：延迟的缓存写入 110
```

最终数据库为 120，缓存为 110。单次 SET 都原子执行，仍不能阻止跨系统交错。直接更新需要明确提交版本和事件顺序，不是简单按最后网络到达顺序覆盖。

### 20.3 先删缓存再更新数据库

```text
W：删除缓存
R：缓存未命中，从数据库读到旧价格 100
R：回填旧价格 100
W：数据库提交新价格 120
```

旧值可以在更新完成后继续留在缓存。先删再更新暴露了读取旧数据库状态并回填的窗口。

### 20.4 先提交数据库再删缓存

通常写路径为数据库事务提交，然后删除相关缓存；读取路径为缓存未命中时查库并回填。这个顺序避免了前述常见窗口，但仍有两类剩余问题。

```text
可靠性窗口：数据库提交 → 进程崩溃 / 删除失败 → 新状态没有可靠失效任务

旧读窗口：R 已取得旧值 100，但尚未回填
          W 提交 120 并删除缓存
          R 随后回填 100
```

因此“先更新数据库再删除缓存”是可分析的基础协议，不是所有并发和故障下的强一致证明。

### 20.5 Outbox、CDC 与可靠传播

Outbox 在数据库事务内同时保存业务修改和待传播事件，后台投递；CDC 读取适用的已提交变更流。它们减少“数据库成功但失效任务永久遗漏”的风险。

投递可能重复、延迟或乱序，消费者需要适用幂等和版本规则。可靠产生事件不自动解决事件到达前的陈旧读取，也不自动阻止已经在途的旧读回填。

删除通常易于重复执行，但延迟旧删除可能清掉更新后的缓存，降低命中率；直接更新则需要防止旧事件覆盖新状态。选择应比较投影复杂度、回源预算和版本维护。

### 20.6 仅把 version 放在缓存值中仍有缺口

```text
缓存保存 version=11
删除缓存后，版本信息一起消失
旧读携带 version=10 回填，发现键不存在
没有更高版本可比较，旧值再次进入缓存
```

版本比较需要一个没有随着普通数据删除而丢失的比较依据。单纯增加 payload.version 并不自动形成完整协议。

### 20.7 独立版本屏障

下面是用于解释的协议模型，不是 Redis 内置功能，也不宣称跨库强一致。

```text
product:{1001}:guard → 已知的最低可接受版本
product:{1001}:data  → 对应 version 与 payload
```

数据库侧在同一事务形成可靠对象版本及变更事件；查询同时取对应数据与版本，避免“旧数据加新版本”。

失效侧在短脚本内将 guard 推进为旧值与事件版本的较大者，删除低于屏障的数据；回填侧在短脚本内检查 guard 和现有缓存版本，只接受没有落后于二者的候选。

```text
guard 缺失       → 进入恢复流程，不能自动把不存在当作最低版本 0
incoming < guard → 拒绝回填
current > incoming → 拒绝覆盖
其余满足条件     → 写入对应版本与内容
```

版本可能超过 Lua 精确整数范围时，不可直接 tonumber 后比较，应限制值域或采用可靠字符串表示与比较规则。

### 20.8 屏障保留与恢复

屏障也可能被淘汰、过期或因主从切换回退。要求所有回填走校验路径，并证明屏障不丢失、不后退，才能保护“已经知道更新版本之后，不再接受更旧的回填”。

缺屏障恢复必须处理并发事件和在途旧请求，可采用权威状态重建、代际命名空间等协议。只读一次数据库后无条件 SET guard，仍可能覆盖已经到达的更高版本。

即使屏障完好，数据库新版本提交到事件推进之间仍存在传播窗口。需要严格实时状态的核心决策应在权威事务内完成，不能将这一模型误称为全系统即时一致。

### 20.9 TTL 与延迟双删

TTL 可限制某次回填后的保留时间，但旧读可能在很久之后才回填并获得新 TTL，陈旧时间还受到旧快照和副本延迟影响。

延迟第二次删除只能覆盖设定时间内的部分竞争；不存在一个固定睡眠时长能保证所有请求、暂停和故障都已结束。应明确改善了哪些窗口，以及哪些不确定性仍保留。

## 21. 缓存故障与下游容量

### 21.1 三类未命中的区别

| 情形 | 主要特征 | 处理重点 |
|---|---|---|
| 雪崩 | 大片键集中失效或缓存整体不可用 | 分散到期、限制回源、降级与恢复节奏 |
| 击穿 | 一个合法热点缺失，许多请求同时重建 | 同键合并、重建权限、允许的旧值 |
| 穿透 | 目标在权威来源也不存在 | 输入校验、空结果缓存、过滤器 |

这些概念用于选择对策。TTL 抖动不能保护所有非法 ID，Bloom filter 不能阻止合法热点到期，主从高可用也不能独立限制数据库回源量。

### 21.2 用命中率推导回源压力

设总读流量为 10 万 QPS，命中率 99%，忽略其他路径，平时数据库约承担 1000 QPS；命中率降至 95%，约为 5000 QPS；完全未命中约为 10 万 QPS。

```text
回源负载量级 ≈ 总请求率 × (1 - 缓存有效命中率)
```

这个简化模型没有包含合并、重试和业务扇出，实际还可能更复杂。“Redis 失败就全部查数据库”只定义了代码分支，没有定义容灾容量。

### 21.3 请求合并与重建权限

```text
未命中
  → 进程内同键合并
  → 获取适用跨实例重建权限
  → 再检查缓存
  → 在总回源预算内查询数据库
  → 按一致性规则回填
  → 唤醒等待者
```

获取权限后复查可避免等待期间别人已完成回填而继续重复查询。等待者需要截止时间、取消与降级；抢锁失败后全部直查数据库，会绕过设计的保护目标。

### 21.4 逻辑过期与硬期限

值可以附带 fresh_until 和 stale_until。软期限后允许暂时返回旧值并安排有限刷新，硬期限后不再正常使用旧状态。

“物理永不过期”不能保证永远存在，还可能淘汰或故障丢失。冷启动、未预热对象和硬期限后的回源仍需预算。价格结算等不允许陈旧的决策不能直接使用此展示策略。

### 21.5 空结果与过滤器生命周期

空结果缓存需明确区别“查过不存在”和“没有缓存”，创建对象后应适当失效。TTL 太长影响新对象可见性，太短削弱减流效果。

过滤器建设要衔接基础数据和增量；有效记录未加入时，算法层面无假阴性的性质也不能保证系统放行所有真实对象。误判放行流量仍需数据库容量保护。

### 21.6 超时、重试与恢复预算

总请求期限应传到下游，不能 Redis 已用掉大部分时间后，又叠加多轮独立长超时。多层各自重试可能相乘，放大故障负载。

重试应由理解业务幂等的层控制，使用有限次数、退避和抖动；缓存恢复阶段分批预热和放量，避免所有实例同时刷新全部键形成第二次洪峰。

### 21.7 本地缓存增加新的副本

本地缓存减少热点网络访问，也增加一层 TTL、失效顺序与进程生命周期。Redis 失效并不自动使每个进程中的旧值立即消失。

使用客户端跟踪失效或通知时，需要处理断连、遗漏与重连恢复；允许陈旧度、写后读和权限撤销等要求仍需逐层定义。更多缓存层不是免费获得的一致性提升。[官方客户端缓存](https://redis.io/docs/latest/develop/reference/client-side-caching/)

## 22. 分布式锁与资源保护

### 22.1 锁是一段有期限的使用权

`SET key token NX PX ttl` 在适用单主执行边界内竞争一个租约。随机 token 标识这次所有者，TTL 限制持有时间。

持有者可以因进程暂停、网络故障或调度延迟超过租期。Redis 删除过期锁不意味着已经停止旧进程的数据库或外部服务操作。[官方分布式锁](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 22.2 校验与释放需要共同执行

```lua
-- KEYS[1]：锁键；ARGV[1]：本次所有者 token
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

如果 GET 校验与 DEL 分开，旧持有者可能校验后暂停，租期结束、其他人获得新锁，再由旧 DEL 删除新锁。短脚本共同检查和删除避免这类误解锁。

它没有证明旧业务操作不能继续，也没有处理异步复制切换导致的锁丢失。

### 22.3 续期与结果不确定

续期需要同样校验 token，不能无条件 PEXPIRE 任意同名锁。看门狗帮助正常长任务保持租期，但自身也受暂停和连接状态影响。

续期请求超时时，持有者不一定知道是否成功，业务应明确何时停止继续操作。固定 lease time 与自动续期是不同策略，不能由“用了框架”推导出所有时间风险都消失。

### 22.4 检查锁后再写数据库仍有窗口

```text
A 确认仍拥有锁
A 暂停
锁到期，B 获得新锁并修改数据库
A 恢复，继续修改数据库
```

Redis 侧校验与数据库写入属于两个操作，不能作为一个原子边界。真正的资源保护需要资源接受写入时检查相应代际或业务条件。

### 22.5 fencing token 与业务身份

| 状态 | 职责 | 不能替代 |
|---|---|---|
| 所有者随机 token | 释放 / 续期时确认身份 | 新旧持有者代际 |
| 递增 fencing token | 拒绝已被新代际取代的旧执行者 | 同代际操作去重 |
| 数据 version | 检查是否基于预期状态修改 | 请求是否此前已经完成 |
| request_id | 识别同一业务请求及重复副作用 | 资源租约和修改顺序 |

假设可靠分配器发出代际 41、42，资源行保存非空的 last_fence，初始为 0。以下只演示每个代际的一次受保护写入：

```sql
UPDATE resource_state
SET payload=:new_payload, last_fence=:token
WHERE resource_id=:resource_id AND last_fence<:token;
```

资源已接受 42 后，旧 41 不再通过。若允许同代际多步写，不能只将 `<` 改为 `<=` 就认为重复副作用问题已解决，还需步骤身份与顺序。

fencing 保护资源已经接受新代际之后不再接受旧代际，并不让过期进程立即死亡。代际来源必须满足所需单调性，异步复制后可能回退的 Redis INCR 不能无条件承担这一证明。

### 22.6 Redlock 的假设范围

Redlock 在多个独立实例上获取多数租约，涉及获取耗时、租期、时钟与暂停等假设。过半获取不等于形成一份持久共识业务日志，也不替外部资源执行 fencing。

缓存重复重建可能只是浪费，重复扣款则破坏不变量。应先根据允许后果选择资源协议，避免把任何分布式锁都作为支付、订单和外部副作用的唯一正确性基础。

### 22.7 直接表达业务不变量

库存可通过数据库条件更新和订单事务维护，请求重复由唯一业务身份处理。锁用于减少竞争或重复工作，核心约束仍由可验证的事务 / 幂等协议承担。

是否需要锁应从同一资源的操作关系推导，不必先选锁框架再设法证明整个业务。

## 23. 限流与库存准入

### 23.1 选择允许的流量形状

| 算法 | 主要行为 | 代价与边界 |
|---|---|---|
| 固定窗口 | 每个固定时间段限制累计量 | 边界附近可能出现集中突发 |
| 滑动日志 | 记录窗口内请求时刻 | 高请求率下记录和清理成本较大 |
| 滑动计数 | 用多个时间桶近似 | 精度与桶数量、规则有关 |
| 令牌桶 | 按速率补充额度，允许有限突发 | 时间、容量与状态更新需协调 |
| 漏桶类整形 | 限制放行节奏或排队 | 队列、等待和拒绝语义需定义 |

算法不只是实现细节，它规定业务允许何种突发和等待。没有明确流量目标，无法判断计数正确是否足够。

### 23.2 固定窗口的边界反例

设每分钟上限 100，上一窗口最后一秒放行 100，下一窗口第一秒又放行 100，约两秒内可能通过 200。

固定窗口计数没有违反自身规则，却不满足“任意连续一分钟最多 100”的滑动要求。不能用一条原子 INCR 修复算法契约不匹配。

### 23.3 计数与 TTL 需要共同建立

INCR 后再独立 EXPIRE，进程可能在两者之间崩溃，形成无期限计数。短脚本可以共同完成适用检查、计数和期限设置，避免网络间隔窗口。

仍需考虑写入拒绝、运行时错误和重试是否重复消耗额度。限流键被淘汰或故障丢失后，相应历史可能消失，导致放宽限制；这种后果必须符合用途。

### 23.4 时间与多维度边界

时间可来自应用或适用服务器时间，各自存在时钟和重试语义。多实例时间偏差可能错划窗口，重复请求是否再次扣额度也需要定义。

按用户、商品、租户和全局同时限流，可能涉及多个 Cluster 槽。单个 Lua 不能直接在任意分片上实现统一原子判断，可通过分层额度、协调服务或明确部分成功规则处理。

### 23.5 Redis 准入与权威库存

Lua 扣减可在给定 Redis 执行边界内防止负数，但完整下单还需要回答：重复请求是否再次扣减、订单是否持久成功、主从切换是否丢状态、失败如何回补、数据库如何对账。

```text
请求身份
  → Redis 短期准入
  → 权威数据库订单 / 库存事务
  → 返回可查回结果
  → 失败和未知结果进入恢复 / 对账
```

Redis 准入降低数据库竞争，不自动成为最终库存的唯一事实来源。若确实选择 Redis 为权威库存，则应给出相应持久性、切换和恢复证明，不能沿用普通缓存可丢失假设。

### 23.6 回补也需要幂等

同一取消事件重复执行 INCR 会重复增加库存。需要将“该预占是否还允许释放”的状态判断与回补放在对应原子范围，使用稳定预占身份，并设计最终对账。

数据库提交结果未知时，不能直接判断失败并回补，再在后台发现订单其实成功。结果查询和超时恢复必须与业务状态机配合。

## 24. 运维证据与全链路排障

### 24.1 工作量与等待分开

```text
接口延迟
  ≈ 应用排队 / 借连接
   + 网络与服务端等待
   + 命令执行
   + 输出与客户端解码
   + 适用的持久化 / 复制等待
```

SLOWLOG 主要测量命令执行，不包含全部客户端通信和排队。一个 GET 自身很快，也可能在长命令之后等待，或在客户端线程上被延后处理。[官方 SLOWLOG](https://redis.io/docs/latest/commands/slowlog/)

接口 P99 高而慢日志不多，并不能排除 Redis 路径问题；也不能直接证明都是网络。需要按同一事件时间窗口收集证据。

### 24.2 常用观察入口

```redis
INFO server
INFO memory
INFO stats
INFO commandstats
INFO persistence
INFO replication
SLOWLOG GET 20
LATENCY LATEST
CLIENT LIST
TYPE product:1001
OBJECT ENCODING product:1001
MEMORY USAGE product:1001 SAMPLES 5
PTTL product:1001
```

权限、配置和版本影响可用字段。MEMORY USAGE 对嵌套对象的采样影响估算；不能只取样一个键就推出全部数据成本。[官方 INFO](https://redis.io/docs/latest/commands/info/)、[官方 CLIENT LIST](https://redis.io/docs/latest/commands/client-list/)、[官方 MEMORY USAGE](https://redis.io/docs/latest/commands/memory-usage/)

LATENCY 相关事件采集需相应配置。累计命中、到期、淘汰和命令计数要比较窗口增量，实例启动以来的累计数不直接代表当前速率。

### 24.3 内存字段的测量对象

used_memory、used_memory_rss、used_memory_dataset 和 mem_not_counted_for_evict 的统计对象不同，部分字段存在包含关系。不能将所有字段相加再与容器上限比较。

持久化字段可观察 fork 和 COW 等进度，复制字段可观察主从身份、偏移和同步状态。参数名称和字段名需要以所用版本为准，避免把旧监控直接迁移到新版本而不校准。

### 24.4 证据与假设对应

| 假设 | 需要的证据 | 改动方向 |
|---|---|---|
| 长命令阻塞短请求 | 慢日志、命令分布、元素数、脚本工作量 | 限制执行段与输出 |
| 大响应或慢客户端 | 字节率、输出缓冲、网络、客户端调度 | 减少返回与修复客户端 |
| 执行路径饱和 | 节点 CPU、命令成本和热点分布 | 调整模型、合并、分片 |
| fork / COW 峰值 | fork 时间、后台状态、COW 与物理内存 | 控制实例规模和峰值资源 |
| 淘汰增加回源 | 淘汰增量、有效命中率、数据库负载 | 调整工作集与回源预算 |
| 副本追平困难 | 偏移差、同步频率、backlog、慢副本资源 | 处理同步反馈环 |
| 应用连接 / 事件线程拥堵 | 借连接时间、队列、线程栈 | 调整并发与调度 |

先证明瓶颈，再选择参数或结构。增大 Pipeline、缓存或线程可能改善一类成本，也可能增加缓冲、排队或其他工作。

### 24.5 验证条件与测试边界

比较改动应记录 Redis 版本、客户端、持久化策略、数据类型与编码、对象尺寸、并发、网络、实例内存和是否正在后台保存。

性能基准需要真实返回体和命令组合，不仅测试一个循环 PING。可靠性验证需要在明确故障点观察成功、失败和未知结果，不能由普通压测通过推导出故障转移安全。

本次文档未执行这些实验。文中的复杂度和数量级算例用于解释机制，不能当作本地 Redis 的运行成绩。

## 25. 业务链路与检索索引

### 25.1 商品详情读取

```text
请求进入并受总期限约束
  → Redis / 适用本地缓存读取
  → 有效命中：返回允许的新鲜度状态
  → 未命中：同键合并与回源限额
  → 从权威来源读取对应数据及版本
  → 按所选一致性协议回填
  → 返回结果，保留可观察证据
```

这条路径同时受命令工作量、TTL、淘汰、热点和版本协议影响。Redis 读取快，只是总请求延迟的一部分。

### 25.2 商品改价与订单创建

改价在数据库事务中形成新状态与可靠变更事件，缓存按既定协议失效或更新。管理员确认可返回已提交版本；最终下单在权威事务内核验价格和库存，不依赖展示缓存恰好已追平。

请求超时后通过业务 request_id 查询原结果，库存预占、消息和取消事件按各自状态机恢复。Redis 锁、Lua 和 Stream 可以减少工作或协调进度，但不能代替跨系统业务契约。
