## 二、先建立四条独立的正确性问题

把下面四个问题写在草稿纸上，很多 Redis 追问就会变得清晰。

| 问题 | 你要证明的东西 | Redis 内的一条原子命令能否单独证明 |
|---|---|---|
| 并发正确性 | 两个请求交错后，业务约束是否仍成立 | 只能证明该命令的范围；不能自动证明多步业务 |
| 故障保留 | 已执行的结果在重启、切换后是否还在 | 还要分析持久化、复制和故障模型 |
| 结果可知性 | 客户端是否确定操作执行了几次 | 超时或断连可能留下结果未知 |
| 跨系统正确性 | Redis、MySQL、外部服务的结果是否协调 | 不会自动获得跨系统事务 |

### 1. “原子”要说清作用范围

`INCR` 能防止多个并发递增互相覆盖。它不能把应用的 `GET → 判断 → INCR` 三步合成一个不可穿插的操作。

Lua 和 `MULTI/EXEC` 也要说具体保证：在普通命令执行模型下，相应执行段不会被其他客户端命令穿插；运行时错误没有数据库式的自动回滚。脚本访问 MySQL 的那部分不在 Redis 的保证范围内。[官方事务说明](https://redis.io/docs/latest/develop/using-commands/transactions/)、[Redis 官方：事务与回滚](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)

可以把一段不可穿插的 Redis 操作理解为有一个对外生效的顺序位置。但这只是分析并发时的入口；异步复制后的故障切换还可能改变客户端后来看到的历史。

### 2. 超时产生的是第三种状态

很多代码只考虑“成功”和“失败”。分布式请求还需要“结果未知”：

```text
客户端发出 DECR stock
Redis 执行，库存由 10 变为 9
响应在网络中丢失
客户端超时
客户端重试 DECR，库存又变为 8
```

超时只证明在期限内没有获得完整结果。命令可能没到服务器，也可能已经成功执行。客户端的自动重连和待发送命令处理，还可能影响重试行为；要查所用客户端和版本的配置。[Lettuce 官方连接与重连说明](https://redis.github.io/lettuce/user-guide/connecting-redis/)

更完整的接口协议应包含稳定的 `request_id`，重试沿用它，并能查询或复用同一次请求的结果。若只在 Redis 中保存去重记录，它仍有过期、淘汰和故障丢失边界；不能据此宣称支付或订单“永远只执行一次”。

### 3. 幂等也分三个层次

- **命令层：**重复执行 `SET k v` 看似相同，但携带 TTL 时可能延长有效期；并发写之间重发旧值还可能覆盖新值。
- **接口层：**同一个 request_id 返回同一个已完成结果，不因客户端重试创建第二张订单。
- **业务层：**消息重复投递、服务重启、并发请求后，库存、扣款、发货等副作用仍符合约束。

所以“这个命令是幂等的”与“这个业务接口可安全重试”不能直接划等号。面试时把重复执行与并发覆盖一起分析，会比只背一个术语完整。

### 4. Lua 超时阈值不是自动终止与回滚期限

脚本超出执行阈值后，不会自动恢复修改前的状态。服务器可能进入对其他普通请求回复 BUSY 等受限处理状态；`SCRIPT KILL` 只能安全终止尚未修改数据集的脚本，已经写入的脚本不能靠该命令撤销。[官方 SCRIPT KILL 说明](https://redis.io/docs/latest/commands/script-kill/)

因此，“设一个五秒阈值”不能替代限制循环次数、元素数和单次工作量。写入前先检查参数与类型，能减少部分错误窗口，但不能把脚本变成支持任意错误回滚的事务。

脚本访问的键应通过 KEYS 明确传入，业务数据通过 ARGV 传入。动态拼接脚本文本会制造大量不同脚本；使用 EVALSHA 时还要正确处理 NOSCRIPT。把逻辑部署到 Functions，也仍需管理对应节点、版本和升级流程。

## 三、性能深读：为什么命令很快，接口仍然会慢

### 1. 从端到端时间开始

```text
T访问 = 应用排队/借连接
      + 请求编码与发送
      + 网络与服务端等待
      + 命令执行
      + 响应发送
      + 客户端读取、解码与调度
```

`SLOWLOG` 主要观察命令执行时间，不包括与客户端通信的时间。某条 GET 只执行几十微秒，仍可能在一个长命令后等待，或在客户端事件线程上迟迟得不到处理。[官方 SLOWLOG 说明](https://redis.io/docs/latest/commands/slowlog/)

这解释了一个典型现象：**接口 P99 上升，慢日志却没有对应数量的慢 GET。** 慢日志没有直接测量这条 GET 在应用和服务端等待的全部时间。

### 2. 少数长命令如何改变容量

下面是一个只考虑单个命令执行线程的简化算例：

- 99% 命令耗时 20μs。
- 1% 命令耗时 5ms。
- 平均执行时间：`0.99 × 20μs + 0.01 × 5000μs = 69.8μs`。
- 理想的执行能力约 `1 / 69.8μs ≈ 1.43 万条/秒`。

如果只看短命令，会误以为能处理 5 万条/秒。慢命令比例只有 1%，却已明显改变平均服务成本。

在每秒 1 万次请求的到达率下，一个 5ms 长命令执行期间，平均又有约 50 个请求到达。这些请求即使各自很短，也要受到前面长任务的影响。

这些数字只用于推导，不是 Redis 基准成绩。真实容量还受网络、内存、CPU、I/O 和客户端并发影响。关键结论是：**看命令耗时分布和工作量，不能只看命令数量。**

### 3. O(1) 不是“响应大小不重要”

`GET` 的查找路径很短，但返回值仍要经过内存访问和网络传输。

假设一次返回 200KiB，每秒读 3000 次：

```text
响应正文流量 ≈ 200 × 1024 × 3000 B/s
             ≈ 586 MiB/s ≈ 4.92 Gbit/s
```

这还没算协议、TLS、复制和其他流量。在一个原始带宽为 1Gbit/s 的链路上，这个负载已经无法满足，打开更多 I/O 线程也不能增加这条链路的物理带宽。

因此设计目标可以是按字段读取、减少对象大小、在应用侧合并请求或增加本地缓存。先确定瓶颈，再选措施。

### 4. Pipeline 的收益和代价都能算

假设 RTT 为 1ms，每条独立命令执行 20μs，连续执行 100 条且每条等结果再发：理想耗时约 `100 × (1ms + 0.02ms) = 102ms`。

如果组成一批 Pipeline，理想下界近似 `1ms + 100 × 0.02ms = 3ms`。真实链路不一定只出现一个往返，也仍有缓冲、排队和解码成本。

Pipeline 节省逐条等待，还能减少部分系统调用成本；它不把多步判断变成事务。若后一步依赖前一步结果，要评估原生命令或短 Lua。[官方 Pipeline 说明](https://redis.io/docs/latest/develop/using-commands/pipelining/)

批次大小要按**字节和延迟**控制。1000 条各返回 1KiB 的命令，与 1000 条各返回 1MiB 的命令，缓冲压力完全不同。增大批次时，至少观察吞吐、P99、输出缓冲和应用内存，而不是只追求批次数减少。

### 5. 线程模型要结合版本讲

经典模型中，普通键空间命令主要顺序执行，后台线程承担部分 fsync、内存释放等工作。Redis 6 引入网络 I/O 多线程；Redis 8.0 又更新了 I/O threading 实现。不能拿旧版本的流程图断言所有 8.x 细节。[Redis 8.0 官方发布说明](https://redis.io/docs/latest/operate/oss_and_stack/stack-with-enterprise/release-notes/redisce/redisos-8.0-release-notes/)

中高级回答还应补一句：I/O 并行主要改善对应阶段的成本；单个热点资源和长命令的业务问题，仍需根据实际执行路径解决。多分片增加独立执行资源，但一个普通 key 不会自动跨分片并行修改。

**面试表达：**“我会先区分网络、命令 CPU 和排队瓶颈。只有确认网络处理占比高，才评估 I/O 线程；长 Lua、大范围读取和热点写，分别通过缩短执行段、减少结果和业务拆分处理。”

## 四、底层结构深读：从结构名称到成本模型

### 1. 小对象线性扫描为什么仍然划算

一个 8 字段的 Hash，连续紧凑存储可能比指针分散的哈希表更省空间，也有较好的局部性。虽然查找是逐项比较，但 N 很小；哈希计算、指针访问和对象分配的固定成本不能忽略。

当字段数量或字段长度超过适用条件时，紧凑编码转换成更适合大对象的结构。学习重点是**常数开销、元素数量、字节长度和访问方式共同影响选择**，不是“哈希表 O(1)，所以永远更快”。编码与阈值应按版本查配置，并用 `OBJECT ENCODING` 和 `MEMORY USAGE` 观察。[官方内存优化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

进一步的项目问题是：为了省内存，把很多用户塞进一个巨型 Hash 是否合理？要同时分析字段访问、整键迁移、TTL、热点和局部故障。省下 key 的元数据，可能换来一个难以拆分的大对象。

### 2. listpack 解决了哪一种成本

原笔记已经解释了 ziplist 的前项长度依赖和连锁更新。继续往下推：

- 去掉这种依赖，解决的是一类元数据连锁修改。
- 连续存储的中间插入仍可能搬动后面的字节。
- 大小转换与内存重新分配仍然可能形成一次额外开销。
- 因此需要“小对象紧凑，大对象转换或分块”的设计。

你应该能比较三个方向：逐元素指针结构、单块紧凑结构、分块紧凑结构。它们分别在指针开销、局部性和单次移动规模上做取舍。

### 3. 跳表的 span 为什么让排名查询变快

跳表高层指针不仅指向远处，还记录跨度 span。假设一条高层边跨过 8 个底层成员，沿它前进时就能把 8 加进累计排名，不必逐个走过去。

插入一个成员后，相关边的跨度必须调整；删除也要反向调整。否则按分数查找可能仍正常，排名却会错误。**跨度是为了支持顺序统计而维护的额外元数据。**

使用跳表编码的 ZSet 同时维护成员到分数的字典；底层有序比较使用 score 和 member。Redis 7.2.0 源码还显示两种结构共享成员字符串，不能把“两个索引”理解成所有内容都完整复制两遍。[Redis 7.2.0：ZSet 源码](https://github.com/redis/redis/blob/7.2.0/src/t_zset.c)

面试官问“为什么不用红黑树”时，可以回答：平衡树也能做有序索引，增加子树大小也能支持排名；Redis 选择跳表是在有序遍历、排名扩展、实现复杂度和内存成本之间取舍。普通 ZSet 命令主要顺序执行，因此不能把“跳表容易无锁并发”当成这里的核心设计理由。

### 4. 排行榜业务还要补的两个问题

**相同分数怎么排？** 相同 score 使用 member 的字典序。若业务要求“先达到分数者排前”，必须另外设计排序规则，不能假定 Redis 默认记录到达先后。

**分页会不会漂移？** 按排名读第一页后，有人插入前排，第二页的排名边界就变了，可能出现重复或遗漏。按 score 和 member 设计游标有助于明确边界，但动态修改下也不是天然快照；冻结赛季榜或带快照版本的分页是另一类需求。

### 5. 渐进式 rehash 并不等于每步严格定时

原笔记已讲“两表共存、逐步迁移”。更深的问题是迁移单位：经典实现会迁移桶中的条目，并对扫描空桶等工作加限制。桶中条目数量仍可能不同，渐进式减少一次全表停顿，不代表每一步都有固定微秒上限。[Redis 7.2.0：dictRehash 源码](https://github.com/redis/redis/blob/7.2.0/src/dict.c)

可以从这里推导三个观察点：临时两张桶表的内存、扩缩容期间的额外工作、键/值字节长度的影响。平均 O(1) 与尾延迟目标是两种不同的描述。

### 6. SCAN 提供的是遍历约定

官方约定：一次完整遍历期间始终存在的元素会被返回；可能重复；遍历期间新增或消失的元素是否出现没有统一保证。COUNT 是提示，小型紧凑集合可能在一次调用中返回全部元素。[官方 SCAN 说明](https://redis.io/docs/latest/commands/scan/)

所以拿 SCAN 做在线导出，要先回答：是否允许重复？数据变化怎样处理？需要一致性快照吗？如果需要“某一时刻的完整数据”，仅换成 SCAN 并没有完成需求。

## 五、缓存一致性深读：版本号究竟怎样才有用

### 1. 先定义一致性要求，再挑方案

| 要求 | 商品系统中的例子 | 设计方向 |
|---|---|---|
| 允许短时陈旧 | 商品描述可延迟几秒展示 | Cache Aside、可靠失效、TTL、陈旧度监控 |
| 自己写完应读到自己的结果 | 管理员改价后确认页面 | 返回已提交的新值；相关读走权威源，或校验最小版本 |
| 业务决策不能依赖旧状态 | 扣款、库存、最终结算价格 | 在权威事务存储内检查条件和提交结果 |

“读到自己的写”是会话层需求；“所有客户端在写完成后都不能看到旧状态”更强。不能用一次管理员页面的正确回显证明全系统强一致。

### 2. Cache Aside 的两个剩余问题

通常写路径是“数据库事务提交 → 删除缓存”。原笔记已准确指出两个窗口：

```text
可靠性窗口：数据库提交后，应用在删除或记录删除任务前崩溃。
并发窗口：读请求先拿到旧值，写请求提交并删除，旧读随后回填。
```

Outbox/CDC 与重试主要补第一类问题。它们可以可靠传播已提交的变更，但传播延迟及传播后仍在飞行的旧读，需要另外处理。

TTL 是兜底生命周期，也不能自动把“旧值只存在 T 秒”变成严格保证。若读请求早已拿到旧值、很久之后才回填并设置新的 TTL，那么陈旧时间还包括这次延迟；旧事务快照和数据库副本延迟也要计入。

### 3. 只在缓存值里放 version 为什么不够

设数据库当前版本为 11，读请求 R 已经拿到版本 10。

```text
W：提交版本 11
W：DEL cache
R：准备回填版本 10
R：检查 cache，发现不存在
R：认为没有更高版本可比较，写入版本 10
```

问题在于删除同时抹掉了“至少已经到 11”的信息。**要比较新旧，必须保留比较所依据的状态。**

### 4. 一种可分析的改进：独立版本屏障

以下是为理解正确性构造的协议，不是 Redis 内置功能，也不声称获得跨库强一致。

```text
cache:{product:1001}:value  -> {version, payload}
cache:{product:1001}:guard  -> 已知的最低可接受版本
```

两键使用同一个 hash tag，便于在 Cluster 中由短脚本共同处理。

**数据库侧：**每个对象有可靠递增的版本，更新数据与生成变更事件在相应数据库事务中完成。不能用任意应用机器的当前时间充当可靠提交顺序。

**失效侧：**消费已提交版本 v 的事件，在一个短脚本中将 guard 取 `max(旧guard, v)`，并删除比 guard 更旧的缓存值。乱序或重复事件不能让 guard 后退，也不应无条件删除已经更新的值。

**回填侧：**数据库查询必须一起取出对应的数据和版本，避免拼成“旧 payload + 新 version”。在另一个短脚本内同时检查 guard 与当前缓存版本，再决定是否回填：

```text
若 guard 缺失：进入重新建立屏障/暂不回填的恢复流程
若 incoming.version < guard：拒绝
若 current.version > incoming.version：拒绝
否则写入 incoming，附合理 TTL
```

这段是协议伪代码。实际脚本要考虑版本表示：若版本可能超过 Lua 可精确表示的整数范围，不能直接 `tonumber` 后假定比较可靠；可以约束范围，或采用可证明的字符串比较方式。

### 5. 这个改进保护了什么

当版本 11 的事件**已经成功更新 guard** 后，版本 10 的旧读无法再通过回填脚本写入。两个关键条件是所有相关回填都走校验路径，以及 guard 不丢失、不回退。

为什么仍不是全局强一致？

1. 数据库已提交到 11，但事件尚未处理时，缓存仍可能是 10。
2. 读数据库的副本有延迟时，可能一直取到低版本，只能拒绝回填，不能凭空得到新值。
3. Redis 故障转移可能丢失最新 guard。
4. 应用读路径如果忽略最低版本要求，仍可能返回不符合会话要求的结果。

这是一种**阻止已知版本之后发生旧值覆盖**的手段。一致性目标还要由读路径、恢复协议和权威存储共同定义。

### 6. 最容易漏掉的追问：guard 被淘汰怎么办

如果 guard 与普通缓存同处于会淘汰所有键的实例，屏障消失后旧读可能再次写入。给 guard 设置 TTL 也有同样问题：你必须知道所有旧请求与旧事件最长会活多久，才能证明安全清理时间。

恢复可以设计为：缺 guard 时禁用普通回填，先从权威状态建立新屏障；建立过程也要处理并发提交的事件，不能简单读一次数据库就宣布恢复完成。对于要求更强的系统，可能需要独立保存版本状态、切换新命名空间，并丢弃旧请求携带的代际。

面试中不用把这种协议推荐给所有缓存。更好的回答是：“如果展示允许陈旧，我先用较简单的可靠失效与 TTL；如果旧值覆盖造成明显风险，我再引入版本协议，同时计算元数据成本、恢复复杂度和维护要求。”

### 7. CDC 更新缓存与 CDC 删除缓存怎么比较

| 方案 | 需要重点处理 | 适合考虑的情形 |
|---|---|---|
| 事件删除缓存 | 回源成本、旧读回填、相关缓存定位 | 多表聚合、按需重建的展示缓存 |
| 事件直接更新缓存 | 按对象的事件顺序、版本比较、删除事件、全量恢复 | 可明确构造缓存状态的简单读模型 |
| 版本化物化视图 | 数据投影语义、历史/代际、补偿、重建 | 读模型较复杂且愿意承担维护成本 |

删除操作本身通常容易重试，但延迟的旧删除仍可能清掉新回填值，使命中率降低。更新操作则需要特别防止旧事件最后到达覆盖新状态。选择要同时看正确性和回源成本。

## 六、缓存故障深读：真正要保护的是下游容量

### 1. 用命中率算回源放大

假设总流量为 10 万 QPS，缓存命中率为 99%，忽略其他路径，数据库平时约承担 1000 QPS。

- 命中率变为 95%：约 5000 QPS 回源，是平时 5 倍。
- 缓存完全不可用：约 10 万 QPS 回源，是平时 100 倍。

所以“Redis 失败就查数据库”只是代码分支，还不是容灾方案。要明确数据库可承受的读预算，并把它落实为**全系统回源并发或速率的上限**。

### 2. 请求合并要分层设计

进程内 singleflight 合并相同查询，减少一个实例中的重复工作；跨实例重建锁进一步减少全系统回源。

完整重建路径至少包括：

```text
缓存未命中
→ 进程内同键合并
→ 获得重建权限后再次检查缓存
→ 在回源并发预算内查数据库
→ 按所选一致性规则回填
→ 唤醒等待者
```

等待者必须有截止时间、可取消等待和明确降级方式。锁获取失败后如果全部改为直接查库，重建锁就失去了保护下游的目的。

### 3. 逻辑过期要同时有软期限与硬期限

可以让缓存值带两个时间：

```text
fresh_until：到这时需要刷新。
stale_until：超过这时不能继续按旧数据提供正常服务。
```

在两者之间可按业务允许返回旧值，并由有限工作者刷新；超过硬期限则降级、拒绝或在预算内回源。

“物理上永不过期”并不能保证永远读得到：键仍会被淘汰、删除或因节点故障而消失。未预热的新对象还会真实未命中；逻辑过期也需要冷启动路径。

### 4. 超时与重试也要有预算

假设接口总期限 200ms。一次 Redis 等待 150ms 后，再执行三轮各 100ms 的重试，已经与接口目标不相容。每一步应使用剩余 deadline，而不是独立叠加一组很长的超时。

多层重试还可能相乘：如果三层调用各最多尝试 3 次，最坏可形成 27 次下游尝试。应让最了解业务幂等的层负责主要重试，配合退避、抖动、并发限制和总尝试预算。

### 5. 空缓存和布隆过滤器的生命周期

空结果缓存应有明确标记，并在创建业务对象时失效；否则新创建的商品会暂时被当成不存在。TTL 太长影响可见性，太短削弱保护效果。

布隆过滤器的“不存在”判断，依赖所有应被放行的对象都已加入。数据库新记录尚未进入过滤器时，系统层面可能错误拒绝真实对象。可以选择先放行未覆盖的新数据范围、维护增量集合，或确保上线/切换期间的过滤器构建与增量衔接。

容量也能算：基础布隆过滤器理想位数 `m = -n ln(p) / (ln 2)^2`。设 n=1000 万，误判率 p=0.001，需要约 1.44 亿 bit，即 17.1MiB 的位数组；真实实现还包含元数据、扩容和对齐成本。[官方 Bloom filter 说明与容量公式](https://redis.io/docs/latest/data-types/probabilistic/bloom-filter/)

若无效查询为每秒 5 万次、过滤器在设计条件下误判率为 0.1%，理想情况下仍有约 50 次/秒无效请求穿过。过滤器是减流措施，数据库保护仍要保留。

### 6. 故障恢复也会产生洪峰

恢复时同时预热全部键、放开全部限流、让所有实例一起刷新，本身可能再次压垮下游。恢复协议应分批提升流量，优先重建高价值热点，并观察回源延迟和数据库负载。

**面试表达：**“我把缓存容灾设计成数据库预算问题：先确定最大回源量，再用同键合并、并发限制、允许的旧值和逐步预热控制流量；Redis 高可用负责缩短中断，应用保护负责避免中断扩散。”

## 七、分布式锁深读：资源端怎样拒绝过期执行者

### 1. 锁首先是一段有期限的使用权

`SET lock token NX PX ttl`、唯一 token、原子校验再释放，解决的是单实例租约竞争与误解锁。要成为完整方案，还必须分析持有者暂停、续约失败、主从切换及外部副作用。[官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

原笔记已有“锁到期后旧客户端还活着”的关键反例。继续往下：**程序在写之前再 GET 一次锁，也不能解决全部问题。**

```text
A 校验自己仍持锁
A 暂停
锁过期，B 获得锁并操作
A 恢复，向数据库写入
```

Redis 校验与数据库写入之间又出现了窗口。要保护数据库，检查必须在数据库接受写入时生效。

### 2. 随机 token、fencing token、version、request_id 的职责

| 信息 | 解决的问题 | 不能自动解决 |
|---|---|---|
| 随机所有者 token | 我是否有权释放或续期这次锁 | 谁是更新的持有者 |
| 递增 fencing token | 资源拒绝已经被新代际取代的旧执行者 | 同代际中的重复副作用 |
| 数据版本 version | 这次修改是否仍基于预期状态 | 请求是否已经处理过 |
| request_id | 重试是否属于同一个业务请求 | 请求间的资源使用权和更新顺序 |

这四类信息可以组合，但不能相互替代。

### 3. 一个数据库侧的 fencing 例子

假设可靠的使用权分配器给 A 发出 41，给 B 发出 42；数据库资源行保存非空的 `last_fence`，初始为 0。以下 SQL 只演示**每次租约的一次受保护写入**：

```sql
UPDATE resource_state
SET payload = :new_payload,
    last_fence = :token
WHERE resource_id = :resource_id
  AND last_fence < :token;
```

校验和修改在同一条 UPDATE 中完成，应用检查影响行数。B 的 42 已提交后，A 的 41 无法再写入这行。

条件使用 `<`，同一个 token 只允许一次这种写入。若一个租约允许多步写，不能机械改成 `<=` 就宣布完成：还需要定义每一步的顺序、幂等键，以及如何禁止重复副作用。多行资源也要在对应事务中统一校验。

fencing 的边界也要说清：A 的 41 在资源尚未见到 42 时，可能仍被接受。它保护的是资源已经接受新代际之后不再接受旧代际，并不会把过期的进程瞬间杀死。

令牌来源要满足所需的单调性与故障模型。一个异步复制后可能回退的 Redis INCR 不能无条件承担这个证明；资源还必须实际执行校验。如果外部接口不支持 fencing，应考虑其幂等协议、唯一操作号或由可控事务系统串行推进。

### 4. Redisson 需要说到哪些实现条件

看门狗缓解正常长任务超过租期的问题；指定固定 `leaseTime` 与依赖自动续约是两种用法。还应区分获取锁的等待时间与获取后的租约时间。Redisson 的不同版本/锁类型可能有副本同步检查、重入和 fencing 等能力，面试时应以项目实际版本说明。[Redisson 官方锁与同步器文档](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)

避免背“用了 Redisson 所以不存在锁安全问题”。进程暂停时续约也可能暂停，网络故障时仍存在无法确认使用权的状态；框架也不能替资源端执行数据库业务约束。

### 5. Redlock 的多数派为什么不能直接类比共识日志

Redlock 是在多个独立实例上获取有时间约束的租约，要考虑获取耗时、时钟漂移、重启和暂停假设。它没有因为“过半成功”就自动提供跨节点的持久化共识日志及外部资源校验。

面试不必只选“绝对安全”或“完全不能用”。先问锁的用途：重复重建缓存可能只是浪费资源；重复扣款则破坏业务约束。对后者优先让数据库约束、幂等记录和资源端协议承担正确性，锁用于减少冲突或重复工作。

### 6. 锁不一定是最直接的业务原语

库存可用数据库条件更新：

```sql
UPDATE inventory
SET stock = stock - :quantity
WHERE sku_id = :sku_id
  AND stock >= :quantity;
```

在与订单相关的数据库事务中检查影响行数，并以业务请求唯一约束处理重试。这个方案直接表达“库存不能不足”的不变量，数据库内部仍有并发控制与锁。

**面试表达：**“Redis 锁提供租约协调。唯一标识保护解锁，续约改善租期适配，fencing 保护资源代际；真正的订单和扣款约束，我仍放在可验证的事务或幂等协议里。”

## 八、持久化与复制深读：一条成功回复承诺了什么

### 1. 写入有多条进度线

```text
内存线：    命令执行 → 主节点内存改变
本地磁盘线：AOF 缓冲 → write/page cache → fsync
复制线：    复制流 → 副本接收/处理 → 副本持久化
客户端线：  响应生成 → 网络传输 → 客户端收到
```

这些进度不是自动同时完成的。AOF always、WAIT 和 WAITAOF 分别改变某些等待条件，还需要检查配置、返回结果和故障模型。[官方持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

| 观察到的结果 | 可以据此说明 | 不能直接说明 |
|---|---|---|
| 普通写命令返回成功 | 当前主节点成功处理了该命令 | 任意副本都拥有、切换后必保留 |
| everysec 正常运行 | 通常按约一秒的节奏安排 AOF 同步 | 所有异常下严格最多丢一秒 |
| WAIT 返回 n | 同一连接此前写入对应进度被 n 个副本确认 | n 个副本都刷盘、任意切换必选这些副本 |
| WAITAOF 返回本地/副本计数 | 相应数量已对此前写入完成 AOF fsync 确认 | 系统自动获得共识复制与跨库事务 |
| Sentinel 切换完成 | 已发现并提升可用副本，客户端可重新发现主节点 | 旧主独有写入已自动合并到新主 |

### 2. WAIT 的实际调用条件

```text
固定到某个主节点的一条连接：
执行业务写入
执行 WAIT 1 100
检查返回的确认数量是否达到 1
```

这里 `100` 的单位是毫秒。超时返回不足不会撤销前面的写入；业务状态可能已经改变，只是没有满足指定复制确认条件。

因此，不要在 WAIT 返回不足时无条件重做一次扣库存。也不要从连接池取任意另一条连接执行 WAIT，假定它在等待第一条连接的写入。

在 `MULTI` 或不能阻塞的脚本上下文里，WAIT 不能按普通阻塞调用方式等待。正确性还取决于故障后实际提升的节点，官方明确说明 WAIT 不会让 Redis 成为强一致存储。[官方 WAIT 说明](https://redis.io/docs/latest/commands/wait/)

### 3. WAITAOF 多证明了哪一层

Redis 7.2 起有 `WAITAOF numlocal numreplicas timeout`。例如同一连接上写后执行 `WAITAOF 1 1 1000`，请求等待本地及至少一个副本对该进度的 AOF fsync 确认，并检查返回数组。

这比单纯复制接收确认更接近“数据已落盘”，但仍要核对 AOF 条件、确认数和故障转移规则。它不是跨分片或跨 Redis/MySQL 的全局提交协议。[官方 WAITAOF 说明](https://redis.io/docs/latest/commands/waitaof/)

中高级面试应能说：**落盘解决持久性的一部分；系统对已确认历史的选择，还属于复制与故障转移协议。**

### 4. min-replicas 不是每次写入的同步 ACK

`min-replicas-to-write` 与 `min-replicas-max-lag` 根据满足条件的副本数量及滞后情况限制主节点接受写入，降低分区期间继续写的风险。

它检查的是副本健康/进度条件，不能等同于“这条写入已被 N 个副本确认”。代价是失去足够健康副本时主节点拒绝写入。[官方复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

这也是面试里讨论可用性与数据安全时的具体取舍：愿意在什么条件下拒绝服务，换取怎样的风险降低。

### 5. fork 与 COW 为什么要按页估算

原笔记解释了父子进程起初共享物理页。继续推导时，要统计后台任务期间被修改的**不同共享页**，而不是只统计修改次数或新值长度。

设普通页为 4KiB，快照期间首次写到 60 万个原本共享的页，仅这些复制页就约占：

```text
600000 × 4096 B ≈ 2.29 GiB
```

同一页后续重复修改，不会因为每次都是一个新命令就再次复制原来的共享页；新分配的数据和其他缓冲则是另外的内存开销。实际页大小、分配布局、THP 和写入模式会影响结果。

因此，单实例 20GiB 的 maxmemory 不代表 24GiB 容器就足够。要把实际数据、分配器开销、缓冲、后台 COW 峰值和余量一起评估。父子 RSS 含共享页，直接相加也不等于独立物理页使用量。

### 6. 复制 backlog 和全量同步有一个反馈环

先按复制流字节率估算：假设峰值 10MiB/s，希望覆盖 90 秒短断线，基本历史量约 900MiB，再按波动留余量。

这里统计的是复制协议字节，不是“业务更新行数 × 某个固定记录大小”。部分重同步还需要复制历史身份兼容，光把 backlog 放大不保证所有重连都能部分同步。

```text
副本变慢
→ 缺失历史超出保留范围
→ 触发全量同步
→ 主节点生成/发送基础数据，副本加载
→ CPU、内存和网络额外承压
→ 副本可能更难追上
```

优化时要同时考虑 backlog、慢副本的资源、单实例数据规模、复制连接缓冲和同步频率。避免只调一个数字。

### 7. RPO 与 RTO 应进入项目答案

- **RPO：**这类数据允许丢失多少已发生的修改？根据快照、刷盘、复制与切换条件评估。
- **RTO：**多久恢复服务？包括故障发现、提升副本、客户端发现新地址、重连，以及必要的数据加载和预热。

商品详情可重建，不代表重建时间和数据库压力无所谓；去重记录可短暂保存，不代表丢失后业务可以安全重复执行。

三副本放在同一故障域，无法获得三份独立的机房容错。恢复目标需要部署、数据策略、客户端和应用降级共同支撑。

## 九、内存与排障深读：从指标到可验证的结论

### 1. maxmemory 是容量控制条件，不是 RSS 的硬上限

部分复制和持久化缓冲不计入触发淘汰的比较值，避免淘汰产生传播数据后又触发更多淘汰的反馈问题。`INFO memory` 的 `mem_not_counted_for_evict` 可用于观察这部分成本。[官方 Key eviction 说明](https://redis.io/docs/latest/develop/reference/eviction/)

同时，分配器碎片、运行时固定开销、COW 和页归还行为都影响物理内存。预算可概念化为：

```text
峰值物理内存需求
≈ 数据及元数据 + 分配器/进程开销
 + 未计入淘汰比较的缓冲 + COW/后台任务增量 + 安全余量
```

这不是把 INFO 所有内存字段直接相加的公式；字段可能存在包含关系。先明确每个指标测量范围，再组合解释。

### 2. LRU/LFU 的问题其实是“保留什么工作集”

LRU 对近期访问敏感；LFU 的概率计数和衰减帮助适应访问频率。选择还要结合工作负载：

- 大量一次性扫描可能挤走长期热点，LFU 是可评估的方向。
- 热点频繁切换时，要评估频率衰减与适应速度。
- 所有键都很热、工作集远超容量时，换策略无法凭空补足内存。

缓存淘汰移除的是 Redis 中的键。AOF 中记录过某个值，不意味着 GET 未命中时会自动按键从磁盘把它重新装回来。

### 3. 为什么应按数据职责拆实例

商品缓存可以淘汰。锁、请求去重、消息和版本屏障被淘汰，可能改变业务语义。

同一实例上只给锁“不设 TTL”不能防 allkeys 淘汰；锁本来还需要租期。volatile 策略也可能选中设了 TTL 的锁或去重记录。逻辑数据库编号不会让 maxmemory、执行资源和故障域自然隔离。

实际可把可重建缓存与协调/消息等用途按容量、淘汰、持久化和延迟目标分开。对重要状态选择 noeviction 时，也必须处理部分申请额外内存的命令被拒绝，以及整体资源不足的风险。

### 4. 大 Key 与热 Key 要按影响分类

| 现象 | 更有效的衡量方法 | 常见方向 |
|---|---|---|
| 大响应占带宽 | 每次响应字节 × 请求率 | 按需字段、分页、减少序列化体积 |
| 大集合遍历占 CPU | 单次元素数、命令耗时分布 | 有界读取、分批操作、改变数据模型 |
| 删除释放耗时 | 元素/分配数量、释放耗时 | UNLINK 与后台积压监控 |
| 热读集中 | 同键 QPS、命中与响应大小 | 本地缓存、请求合并、允许时副本读 |
| 热写集中 | 单个分片执行量、更新竞争 | 业务拆分、批量合并、分区计数 |
| 大对象迁移困难 | 单键字节、迁移耗时和峰值 | 在建模时拆对象，预演迁移 |

不要固定背“超过 10KiB 就是大 Key”。一个大小阈值要联系延迟目标、访问频率和操作方式才有意义。

### 5. 线上延迟的排查顺序

先固定事件时间窗口、影响范围和版本/配置变化，再比较应用访问延迟与 Redis 执行侧证据。

| 要排查的假设 | 收集的证据 | 若假设成立，下一步 |
|---|---|---|
| 长命令影响其他请求 | SLOWLOG、命令类型、结果数量、长脚本 | 缩小单次工作量，隔离重任务 |
| 单个分片执行饱和 | 每分片 CPU、命令率、热点键的工作量 | 修正倾斜或业务模型，评估分片 |
| 网络/大响应 | RTT、丢包、吞吐、响应字节、输出缓冲 | 减少响应或改善网络路径 |
| fork/COW/磁盘 | latest_fork_usec、持久化状态、COW 峰值、磁盘延迟 | 控制实例规模、预留资源、评估策略 |
| 大量到期/淘汰 | expired_keys、evicted_keys 的窗口增量、命中率 | 错开到期、调整容量与工作集 |
| 应用池或调度拥堵 | 借连接耗时、等待队列、线程栈、事件线程 | 修复泄漏或阻塞，限制并发 |
| 副本追赶/全量同步 | replication 信息、同步状态、字节偏移差 | 检查副本资源与 backlog 覆盖 |

`INFO commandstats` 的累计量要取时间窗口差值；每次调用的平均耗时仍不能替代 P99。`LATENCY` 监测没有数据时，要核对是否启用、阈值和保留条件，不能把空结果当成没发生问题。[官方延迟诊断](https://redis.io/docs/latest/management/optimization/latency/)、[官方延迟监测](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency-monitor/)

可先使用以下只读观察命令；某些命令可能受权限或监测配置限制：

```redis
INFO memory
INFO stats
INFO commandstats
INFO persistence
INFO replication
SLOWLOG GET 20
LATENCY LATEST
LATENCY DOCTOR
```

读取客户端信息、全键扫描或 MONITOR 也有自身工作量与数据暴露风险，应按问题范围使用。把在线全量观察当成无成本操作，会干扰正在排查的系统。

### 6. Java 客户端要查到事件线程

Lettuce 的异步模型不意味着每个调用都免费并行。阻塞其事件线程、在回调中做耗时工作、连接被长时间阻塞命令占用，都可能造成超时；连接队列、刷新行为与超时配置也要检查。[Lettuce 官方 FAQ](https://redis.github.io/lettuce/faq/)

对 WATCH/MULTI 这类连接状态操作，要确保整个序列绑定到合适的独占连接，避免其他请求混用。不要一看到延迟就扩大连接池：更多并发可能只是让服务器排队更长。

**面试表达：**“我先按时间窗口拆应用等待、Redis 执行和网络响应，排查分片倾斜与资源事件；用证据决定减少工作量还是增加容量，优化后同时比较吞吐、P99 和错误率。”

## 十、Cluster 深读：把槽约束变成业务建模约束

### 1. 同槽是共同执行的基本条件

```text
stock:{sku:1001}                库存
request:{sku:1001}:request-abc   此商品的请求结果
```

这两个键共享有效 hash tag，可在同槽内由脚本共同访问。不同槽的键，即使当前恰好放在同一台服务器，也不满足经典多键操作的同槽要求。

这能协调单商品库存和请求结果，但如果一张订单包含 10 个不同商品，它们的库存可能分散到多个槽。增加一个 Lua 并不能把 10 个槽变成一个全局原子单元。

可选择在数据库事务中处理多商品约束，或设计分步预留、补偿与对账；不能为了省事给所有库存加同一个 tag，把分片能力又集中到一个槽。

### 2. 同槽还不代表迁移期间所有调用必成功

迁移过程中，同一槽的部分键可能在源节点、部分已到目标节点。多键操作可能因键分布或不存在而返回 TRYAGAIN，需要客户端稍后重试或按业务处理。**同槽是执行资格，并非迁移期每次都能立即执行的保证。**

MOVED 通常提示槽映射已变化；ASK 是本次迁移相关临时转向，客户端在目标连接上发送 ASKING 再执行请求。具体行为以服务器版本及迁移实现为准。[官方 Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

### 3. 多键客户端 API 要查看最终语义

某些客户端会把跨槽的批量读取拆成多个单槽命令再拼结果。它提高了 API 使用便利性，但这些读取发生在不同节点和时间，不能把拼出来的列表视为全局一致快照。

同理，一批跨节点 Pipeline 不会自然变成跨节点事务。客户端看起来“一个方法调用”，服务端可能执行多个独立步骤。

### 4. 槽数量均匀，压力不一定均匀

一个节点接收 5000 个很冷的槽，另一个节点接收一个极热的槽，槽数不是性能平衡的指标。扩容时还要看每分片数据字节、命令成本、请求率和响应流量。

单个热 key 不能通过搬迁到另一个主节点而被拆成多个 key。迁移只能把瓶颈换到另一个地方；若要并行处理，必须设计业务拆分。

例如把浏览计数分成多个分区可降低热点写压力，但读取总量要汇总；全局唯一排名或严格库存扣减则有额外约束，不能直接套同一拆法。

### 5. Sentinel 的两种多数条件

quorum 用于主节点客观下线判断，执行故障转移还需要获得相应授权和已知 Sentinel 的多数支持。例如 5 个 Sentinel、quorum=2，只剩两个互通时，可能形成故障判断，却无法获得多数授权。[官方 Sentinel 说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

Sentinel 的投票主要管理故障判定和切换，它没有把每条数据写入变成一个 Sentinel 多数派提交。

### 6. 本地缓存又增加了一份副本

```text
MySQL 权威状态 → Redis 副本 → 每个应用进程的本地副本
```

本地缓存减少热读，但一致性链路更长。需要定义本地 TTL、容量、失效通知、通知连接断开后的清理或重建行为。

Redis 客户端 Tracking 支持对相关键发送失效通知，但仍需要客户端协议正确处理失效与连接生命周期；它也不会自动把 MySQL 的变化同步到 Redis。[官方客户端缓存说明](https://redis.io/docs/latest/develop/clients/client-side-caching/)

若自己用 Pub/Sub 广播失效，断线可能漏掉消息。可接受短 TTL 兜底，或设计可恢复的代际/版本协议；不应声称收到实时通知就已经有可靠失效。

## 十一、限流与秒杀深读：Lua 之外还要证明什么

### 1. 限流算法要围绕允许的流量形状选择

| 算法 | 核心状态/行为 | 主要取舍 |
|---|---|---|
| 固定窗口 | 一个窗口内计数 | 简单；两个相邻窗口边界附近可有集中突发 |
| 滑动窗口日志 | 保存窗口内的请求时间 | 可精确检查窗口；空间随流量增长 |
| 滑动窗口计数 | 分段计数并近似组合 | 省空间；定义近似误差和边界 |
| 令牌桶 | 随时间补充 token，最多 B 个 | 长期速率 r，允许有限突发 B |
| 漏桶 | 按目标速率消耗积压 | 平滑输出；真实排队需要处理长度和等待期限 |

Redis 原子命令和 Lua 便于在共享状态上实现检查与更新，但算法语义与故障策略仍由应用确定。[官方限流方案](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)

### 2. 固定窗口边界能怎样超出直觉

假设每分钟最多 100 次，客户端在 59.9 秒发 100 次、60.1 秒再发 100 次。两个窗口都没超限，但 0.2 秒内出现 200 次。

若业务接受这种突发，固定窗口可以合适；若要任意连续 60 秒不超过 100 次，就需要相应滑动窗口语义。

### 3. 一个有明确前提的教学 Lua

以下示例检查单个固定窗口计数。调用者必须提供正整数 limit 和正整数窗口 TTL（毫秒），key 中应包含明确的窗口编号。它只演示 Redis 内限流判断，未在实例执行：

```lua
-- KEYS[1]: rate:{user:1001}:<window_id>
-- ARGV[1]: limit; ARGV[2]: ttl_ms
local limit = tonumber(ARGV[1])
local ttl = tonumber(ARGV[2])
if not limit or limit < 1 or limit ~= math.floor(limit)
   or not ttl or ttl < 1 or ttl ~= math.floor(ttl) then
    return redis.error_reply('positive integer limit and ttl required')
end

local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('PEXPIRE', KEYS[1], ttl)
end
if count <= limit then
    return {1, count}
end
return {0, count}
```

它将创建计数和设置过期放入同一执行段，减少分两条命令时进程崩溃留下永久计数的窗口。它会统计被拒绝的尝试；若业务只统计通过的请求，应另行设计语义。

进一步追问：key 类型不对怎么办？旧键丢了 TTL 怎么办？拒绝请求也一直计数是否合理？时间窗口由谁计算？结果超时后重试算一次还是两次？这些不能由“脚本原子”替你回答。

### 4. 时间与多维限流的限制

令牌桶可使用：`tokens = min(B, tokens + r × elapsed)`。随后检查、扣减并保存新时间。要考虑负时间差、时钟跳变、单位与精度；使用服务器 TIME 可减少不同应用时钟的差异，但并不会得到永不跳变的全局单调时间。[官方 Redis 限流教程](https://redis.io/tutorials/howtos/ratelimiting/)

若同时检查用户额度和全局额度，两份状态在不同槽时，就不能用普通跨槽 Lua 自动原子扣减。可以采用分级限流、额度预分配或集中协调，分别说明误差、热点和故障风险。

Redis 不可用时，还要明确策略：展示接口可以按本地保守额度降级，扣费或关键防滥用接口可能需要拒绝。不同业务不能默认统一 fail-open 或 fail-closed。

### 5. 秒杀问题至少分四层

```text
流量准入 → 可售资格/库存预留 → 订单提交 → 支付/超时释放与对账
```

Redis Lua 主要保护 Redis 内的检查、扣减和本地请求去重。它不自动完成后面的订单事务、消息可靠产生、支付状态和补偿。

一个可讨论的请求状态应至少区分 `PENDING / CONFIRMED / CANCELLED`，并定义允许的状态迁移。客户端超时后按 request_id 查询或重试推进同一个状态，不能产生第二份独立预留。

### 6. 回补库存为什么也需要幂等

```text
订单落库失败
补偿程序 INCR stock
补偿结果未知
重试补偿，再 INCR stock
库存被回补两次
```

“失败就加回去”会引入新问题。应把一次预留的取消状态与回补效果正确协调，重复取消不再产生额外回补，并以权威库存与订单做对账。

系统还必须回答：Redis 预扣结果故障后丢失，但订单已成功怎么办？超时释放时支付回调同时到达怎么办？哪些状态由数据库事务约束，哪些允许异步协调？

中高级项目答案的价值，是把这些边界讲清，并解释为什么选这套复杂度；不必为了“用了 Redis”把原本简单的订单事务拆成不完整的跨系统流程。

## 十二、Stream 深读：消息确认与业务效果是两套状态

### 1. ACK 之前和之后都要画故障点

```text
XREADGROUP 交付
→ PEL 记录待确认
→ 数据库事务完成业务
→ XACK 移除该组 PEL 记录
```

- 先 ACK、后做业务：中间崩溃可能没有重试依据。
- 先做业务、后 ACK：中间崩溃可能重复交付，需要业务幂等。

ACK 移除该消费组的待确认记录，不是删除消息正文。[官方 XACK 说明](https://redis.io/docs/latest/commands/xack/)

### 2. 怎样让重复交付不产生重复业务效果

可以在一个数据库事务中：

```text
插入 processed_event(业务事件唯一标识)，有唯一约束
执行业务修改
提交
提交成功后 ACK
```

再次消费时，根据数据库内已提交的幂等记录确认无需重复业务修改，再 ACK。插入记录与业务效果必须同一事务，否则仍可能出现“记录已处理，业务却没做”或“业务做了，记录却丢了”。

如果业务效果是外部发货或扣款调用，数据库记录并不能自动把外部动作纳入事务。还需要对方支持幂等操作号，或由 Outbox 状态机可靠推进并对账。

因此可以承诺“在给定条件下，同一业务事件只产生一次数据库效果”，不应把 Stream 描述成无条件 exactly-once 的端到端消息系统。

### 3. 认领超时也可能制造并发消费者

`XAUTOCLAIM` 等机制可以按待确认空闲时长认领消息。但原消费者可能只是慢，并没有死：

```text
A 处理很慢，消息长时间未 ACK
B 超过认领阈值后获得同一消息
A 恢复，与 B 都可能执行业务
```

阈值按耗时分布和故障恢复目标设置，业务仍要承受重叠执行。PEL 所有者改变不是对原进程外部写入的物理禁止。[官方 XAUTOCLAIM 说明](https://redis.io/docs/latest/commands/xautoclaim/)

### 4. PEL 与消息保留必须一起管理

消费者落后时，过早裁剪消息正文可能让待确认记录失去可重试的数据。不能看到 PEL 有 ID 就认定消息内容仍然存在。

Redis 8.2 对裁剪与消费组引用增加了 KEEPREF、DELREF、ACKED 等控制选项，还引入 XACKDEL；它们需要按版本和保留目标选择。经典 XACK 本身仍只做确认。[官方 Streams 说明](https://redis.io/docs/latest/develop/data-types/streams/)、[官方 XACKDEL 说明](https://redis.io/docs/latest/commands/xackdel/)

### 5. 监控要区分进度、积压和业务健康

- 新消息尚未交付的积压，以及消息从产生到业务完成的时间。
- PEL 数量、最老待确认空闲时间、重复交付与失败次数。
- 消费者处理耗时、毒消息、死信或人工处理状态。
- Redis 内存、持久化、复制和裁剪策略。

不能只看 Stream 长度：长度可能因保留历史而很大，也可能因提前裁剪而很小。队列看起来很短，不代表业务已成功完成。

**面试表达：**“我把消息系统保证和业务幂等分开。先提交业务再 ACK 允许重复交付，唯一约束与同库事务防重复效果；认领、裁剪、Redis 故障和外部调用则分别设计恢复条件。”

## 十四、六个验证实验：把反例变成你看过的现象

本节是待执行的实验手册，不是已完成的实测报告。使用独立学习实例，例如 `127.0.0.1:16379`；以下 `redis` 代码块是进入交互式 redis-cli 后的命令。实验只使用 `interview:` 前缀。首次连接前确认实例用途及版本，不需要清空整个数据库。

每轮实验从明确的初始状态开始；重复实验时，按确切键名清理自己上一轮的数据，避免已有锁、消费组或键类型影响预期结果。

```powershell
redis-cli -h 127.0.0.1 -p 16379
```

先记录 `INFO server`、`INFO persistence`、`INFO replication`，明确实验是在单机、主从还是 Cluster 上进行。不要把不同环境的结果混在一起。

### 实验 1：事务和 Lua 都不会替你自动回滚运行时错误

**单机前置状态与命令：**

```redis
SET interview:bad abc
MULTI
SET interview:before done
INCR interview:bad
SET interview:after done
EXEC
MGET interview:before interview:after
```

**预期：**INCR 报错，但两次 SET 都成功。执行阶段错误不是整个队列失败回滚。

再检查 Lua：

```redis
EVAL "redis.call('SET', KEYS[1], 'done'); return redis.call('INCR', KEYS[2])" 2 interview:lua-written interview:bad
GET interview:lua-written
```

**预期：**脚本报错，但已经完成的 SET 仍在。不要因为返回异常就假定没有产生效果。

**补充验证：**改用命令参数数量错误制造入队阶段错误，比较 EXEC 的行为。解释为什么同样是“事务错误”，结果不同。

**你要记录：**完整返回、最终值、错误发生阶段。若现象不同，先确认客户端是否额外处理异常或更改了发送序列。

### 实验 2：手动复现旧值回填，再验证版本屏障

这个实验在 Redis 中模拟“数据库已被读出的旧值与版本”。它验证回填协议，不验证真实 MySQL 事务或 CDC 的可靠性。

先假设读请求 R 已拿到 `version=10, payload=price:100`，但尚未回填。写请求 W 已提交新版本 11，并删除缓存。手动执行：

```redis
UNLINK interview:cache:{product:1001}
HSET interview:cache:{product:1001} version 10 payload price:100
HGETALL interview:cache:{product:1001}
```

**预期：**删除后仍可写回旧值；删除成功不等于后面没有旧读。

现在建立版本屏障，并模拟版本 11 失效事件已经完成：

```redis
SET interview:guard:{product:1001} 11
UNLINK interview:cache:{product:1001}
```

用一个短脚本校验并回填。它仅用于这里的小整数版本和已经验证的教学参数：

```redis
EVAL "local g=redis.call('GET',KEYS[1]); if not g then return -1 end; local v=tonumber(ARGV[1]); if v<tonumber(g) then return 0 end; local c=redis.call('HGET',KEYS[2],'version'); if c and tonumber(c)>v then return 0 end; redis.call('HSET',KEYS[2],'version',ARGV[1],'payload',ARGV[2]); redis.call('PEXPIRE',KEYS[2],60000); return 1" 2 interview:guard:{product:1001} interview:cache:{product:1001} 10 price:100
```

**预期：**返回 0，旧值未写入。再把结尾参数改为 `11 price:120`，预期返回 1。

然后删除 guard，再重试同一个脚本：

```redis
UNLINK interview:guard:{product:1001}
```

**预期：**返回 -1，进入“屏障缺失”路径，而不是允许任意旧值回填。

**你要解释：**事件尚未到达时保护是否生效？删除 guard 后该怎样恢复？为什么要限制版本数值范围？两键的 hash tag 是否相同？

### 实验 3：安全解锁与阻止旧业务是两种能力

客户端 A：

```redis
SET interview:lock A-token NX PX 2000
```

等待直到 `PTTL interview:lock` 返回 -2，再由 B 获取：

```redis
SET interview:lock B-token NX PX 60000
```

A 使用安全解锁脚本：

```redis
EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) end; return 0" 1 interview:lock A-token
GET interview:lock
```

**预期：**返回 0，B-token 仍存在。确保在 B 的租期内完成观察。

**关键追问：**A 仍可以执行一条普通业务写命令，因为它的进程没有被 Redis 杀死。若用数据库保护资源，分别带 42、41 执行第七节的条件 UPDATE，第二次在 42 已提交后应不满足条件。

**你要解释：**把 token 校验放在客户端再执行 SQL，为什么仍有暂停窗口？数据库影响行数为 0 时业务应怎样处理？

### 实验 4：WAIT 返回不足，不会撤销写入

在**没有副本的单机学习实例**上：

```redis
SET interview:confirmed-or-not written
WAIT 1 20
GET interview:confirmed-or-not
```

**预期：**WAIT 返回 0，但键值仍为 written。等待条件不足与业务写入未执行不是同一个结论。

若使用 Redis 7.2+ 且学习实例已启用 AOF，可继续在同一连接测试：

```redis
WAITAOF 1 0 1000
```

**预期条件：**本地 AOF fsync 在期限内完成时返回 `[1, 0]`。超时或 AOF 配置不满足时，按真实返回分析；不要把示例预期当成必然结果。

**扩展故障实验：**在隔离的一主一从环境中，控制副本不接收某次写入，再让主节点故障并提升副本，检查该次写入。要记录实际复制进度；随意 kill 一次无法证明指定窗口发生。

进程被 kill 与整机断电也不等价：操作系统页缓存可能在前一种情况下仍然保留。不要用普通进程退出实验推断 everysec 的断电丢失上限。

### 实验 5：PEL 恢复、ACK 与正文保留

```redis
XGROUP CREATE interview:stream interview:group 0 MKSTREAM
XADD interview:stream * event_id event-1 action demo
XREADGROUP GROUP interview:group consumer-A COUNT 1 STREAMS interview:stream >
XPENDING interview:stream interview:group
```

保存实际返回的消息 ID。等待超过 1000ms，使用 Redis 6.2+ 的认领命令：

```redis
XAUTOCLAIM interview:stream interview:group consumer-B 1000 0-0 COUNT 10
```

**预期：**符合条件的未确认消息可由 B 认领。A 此时只是没有 ACK，不一定真的退出。

使用实际 ID 执行以下命令；`<actual-id>` 是需替换的占位符：

```redis
XACK interview:stream interview:group <actual-id>
XPENDING interview:stream interview:group
XLEN interview:stream
```

**预期：**在此唯一消息状态下，待确认记录清零，但正文仍存在、XLEN 为 1。重复执行实验时使用新键或清理自己的实验键，避免既有消费组影响结果。

**你要解释：**业务提交后崩溃，为什么会再次交付？正文被裁剪后还能否重新处理？业务幂等记录必须与什么操作同事务？

### 实验 6：给性能结论附上条件

可在独立实例使用 redis-benchmark；它会产生实际负载：

```powershell
redis-benchmark -h 127.0.0.1 -p 16379 -n 20000 -t set,get -d 100 -c 20 -P 1
redis-benchmark -h 127.0.0.1 -p 16379 -n 20000 -t set,get -d 100 -c 20 -P 16
```

比较 Pipeline 深度，记录实例和客户端资源、部署距离、数据大小、持久化配置、吞吐与延迟分位数。随后改变响应大小或接入真实业务工作负载，观察结论是否仍成立。

**不要预设结果：**本机极低 RTT 时，Pipeline 与远程部署的收益可能不同；批次增大后的延迟展示也要结合工具计量方式理解。SET/GET 简单压测不能代替含 Lua、Hash、复制和真实 key 分布的容量验证。

**你要解释：**数据大小、并发数、Pipeline、客户端 CPU 中，哪一个因素改变了瓶颈？均匀压测为什么无法证明热点场景可承载？

## 十五、自测：能回答这些，才算进入中高级深度

每题按下列标准自评，而不是只判断“见过没见过”：

- 0 分：只能给名词或背结论。
- 1 分：能说明工作机制与正常流程。
- 2 分：能给出并发或故障反例，并指出方案边界。
- 3 分：能按明确业务要求选方案，说明代价，并给出验证证据。

### 六个核心问题与判分锚点

**1. 删除缓存与数据库提交都成功，为什么还是读到旧值？**

2 分答案必须包含读旧值发生在提交前、回填发生在删除后；3 分还要区分可靠失效与回填控制，解释版本屏障丢失后的恢复条件，或说明为什么业务选择接受这类陈旧。

**2. Redis 锁续约失败后，为什么业务还可能并发？**

2 分答案必须包含旧持有者仍可访问资源；3 分应能解释资源端原子 fencing 校验、幂等副作用及不能采用 fencing 的外部接口怎样处理。

**3. Redis 客户端超时，可不可以直接重试扣减？**

2 分答案必须包含结果未知及重复扣减时序；3 分应有稳定 request_id、结果记录生命周期、重试预算，并说明 Redis 去重记录丢失后的业务防线。

**4. WAIT 或 WAITAOF 达标，为什么不能直接承诺永不丢？**

2 分答案应区分确认数、刷盘与提升节点；3 分应给出项目的故障模型、RPO/RTO、连接作用域及未达标时的业务处理。

**5. Redis P99 上升而慢日志很少，怎么排查？**

2 分答案应区分命令执行、等待、网络和客户端；3 分应按事件窗口列出可以证伪的假设，并用负载与资源数据决定优化措施。

**6. 同槽 Lua 为什么仍不代表订单全流程原子？**

2 分答案应指出跨 MySQL/外部动作不在脚本内，迁移中还可能暂时失败；3 分应拆出预留、提交、取消与对账状态，说明幂等和补偿的约束。

### 三道综合题

**题 A：商品展示系统。** 10 万 QPS，命中率 99%，数据库可持续承担 3000 QPS；展示允许短暂陈旧，但结算价格必须按规则校验。设计缓存读写、Redis 故障降级和恢复流程。

判分重点：正常回源约 1000 QPS；全部回源不可承受；剩余数据库预算还应留给其他业务与波动；展示与结算走不同新鲜度规则；失效事件可恢复；恢复逐步放量。

**题 B：热门单商品限购。** 4 个应用实例、Cluster、请求可能超时重试。要求不重复创建订单、库存不为负。比较数据库事务方案与 Redis 预留方案。

判分重点：单商品相关键同槽；Redis 检查原子性与业务 request_id 分开；订单唯一约束；预留、确认、取消状态；重复补偿；故障丢失及库存对账；解释复杂度是否必要。

**题 C：异步任务。** 数据库业务已提交，消费者进程在 ACK 前崩溃；另一个消费者认领，老消费者又恢复。设计不重复副作用的处理，并说明消息裁剪策略。

判分重点：重复交付可发生；同事务业务幂等；外部调用需要额外幂等协议；认领不停止旧进程；正文保留与消费进度一起管理；Redis 持久化与复制单独分析。
