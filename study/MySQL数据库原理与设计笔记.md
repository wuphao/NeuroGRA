# MySQL 数据库原理与设计笔记

### 统一案例与表达约定

查询章节使用订单表作为案例，避免每个概念都更换数据模型。

```sql
CREATE TABLE orders (
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id    BIGINT UNSIGNED NOT NULL,
    status     TINYINT UNSIGNED NOT NULL,
    amount     DECIMAL(12,2) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    remark     VARCHAR(1000) NULL,
    PRIMARY KEY (id),
    KEY idx_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

订单列表的主要查询为：

```sql
SELECT id, amount, created_at
FROM orders
WHERE user_id = 42 AND status = 1
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

并发章节另外使用 `accounts(id,balance,version)`、`on_call(id,on_duty)` 和 `lock_demo(id,k,payload)` 等最小模型。这些表用于说明事务时序，没有暗含完整业务系统的约束。

SQL 中的 `:qty`、`:cursor_time` 等写法表示应用绑定参数，不是可直接粘贴到 mysql 客户端执行的字面量。不同索引方案属于候选方案，不表示应同时建立所有索引。事务时序中的 A、B 表示两个独立连接。

## 1. 系统边界与设计约束

### 1.1 数据库同时处理访问效率、并发和故障

关系数据库向应用提供表、约束和 SQL。实现层还需要处理三类相互关联的约束：数据规模通常超过内存，多个会话同时访问同一份状态，进程或机器可能在任意步骤发生故障。

如果所有记录都逐行从磁盘查找，访问代价会随数据量增长；如果全部操作都用一个全局互斥锁串行执行，并发能力会受到限制；如果每次提交都立即写完全部数据页，随机写入和同步等待又会放大事务延迟。InnoDB 因此分别采用页与索引、锁与多版本、缓存与日志来处理这些约束。

这些机制不能彼此孤立。索引决定访问哪些记录，同时影响加锁范围；缓存延后数据页写入，因此需要日志保护；历史版本让读取能够绕过写锁，但需要额外存储和清理。一个局部优化可能将成本转移到另一条路径。

### 1.2 Server 与存储引擎的职责

```text
应用 / 驱动 / 连接池
        │ SQL、参数、事务控制
        ▼
Server：连接与权限 → 解析与名称解析 → 优化 → 执行
        │ 存储引擎接口                    │ binlog
        ▼                               ▼
InnoDB：索引与记录、Buffer Pool、锁、undo、redo
        │
        ▼
表空间、数据页、日志文件及底层持久存储
```

Server 处理 SQL 层的通用语义，存储引擎提供数据访问与事务能力。可插拔的引擎接口使 SQL 层能够支持不同存储实现，但也意味着数据库能力存在引擎边界。例如，InnoDB 的行锁、MVCC 和崩溃恢复不能直接推广到所有 MySQL 存储引擎。

binlog 位于 Server 层，记录可供复制与恢复使用的变更事件；redo 位于 InnoDB 层，保护引擎内部的页修改。两者服务于不同抽象层，启用 binlog 时需要协调提交结果，相关机制见第 14 章。

### 1.3 逻辑对象与物理对象

表、行、主键是逻辑对象；页、表空间、索引树和日志记录是实现对象。默认启用独立表空间时，常见的 `.ibd` 文件承载表的数据与索引，但 InnoDB 还存在系统表空间、通用表空间和 undo 表空间等组织方式，不能将所有数据文件都概括成每张表一个 `.ibd`。

SQL 不带 `ORDER BY` 时，数据库没有承诺结果顺序。聚簇索引按键组织记录，只影响访问路径，不会将某次观察到的主键顺序自动提升为查询结果的语义保证。

## 2. 类型、记录与页

### 2.1 类型定义同时决定语义和存储成本

字段类型限定合法值、比较规则和表示方式。`DECIMAL` 适合需要精确十进制计算的金额；浮点类型采用近似表示，不能仅因为存储较小就直接替代金额字段。整数类型还需要考虑取值范围和有符号属性，避免业务增长后溢出。

`VARCHAR(n)` 中的 `n` 是字符数，实际存储字节数依赖内容与字符集。`utf8mb4` 的单字符最大长度为 4 字节，因此字段定义评估不能只看字符数。字符比较还受排序规则影响，同一组字符串在不同规则下可能被视为相等，进而影响查询和唯一性约束。

`NULL` 表示未知或不适用，与空字符串、零并不等价。SQL 中 `column = NULL` 不产生普通的相等判断，需要使用 `IS NULL`。字段是否 `NOT NULL` 应首先根据业务语义决定；仅为了节省少量位图空间而用零或空字符串替代未知值，会使聚合和条件判断失去原有含义。

### 2.2 记录需要保存可解析、可定位、可回滚的信息

对于 COMPACT / DYNAMIC 等行格式，记录除业务字段外，还需要记录头、可空字段位图和变长字段长度等信息。以下图只表达职责，不表示各字节的精确物理排列：

```text
字段长度与 NULL 标记 │ 记录头 │ 业务字段 │ 事务系统字段
       解析                 页内管理          MVCC / 回滚
```

变长字段不能通过固定偏移直接定位，因此需要长度信息；NULL 位图表示可空列是否有值；记录头保存删除标记和页内记录链接等控制信息。记录在页内的物理位置与键顺序不必相同，链接和目录负责在这些位置之间建立可搜索的逻辑顺序。

聚簇记录中的 `DB_TRX_ID` 标识相关修改事务，`DB_ROLL_PTR` 指向 undo 信息；没有显式主键或合适唯一非空索引时，InnoDB 才额外使用隐藏 `DB_ROW_ID` 构造聚簇键。二级索引记录没有与聚簇记录完全相同的系统字段布局。[官方多版本机制](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

### 2.3 行大小存在两层约束

MySQL Server 的最大行定义限制为 65535 字节，其中还涉及字段开销；`TEXT` / `BLOB` 的计算方式与普通内联列不同。InnoDB 另外约束记录在页内占用的空间：默认 16KB 页下，页内记录的最大本地尺寸略小于半页。两者分别是 SQL 层定义限制和存储引擎页布局限制。[官方 InnoDB 限制](https://dev.mysql.com/doc/refman/8.4/en/innodb-limits.html)

当变长字段较大时，InnoDB 可以将部分内容存到溢出页。DYNAMIC 行格式可将适合页外存储的长列内容移出本地记录，只保留页外指针；COMPACT 的相关策略不同。具体是否溢出取决于记录大小和行格式，不是所有长字符串都必然页外存储。[官方行格式说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-row-format.html)

页外存储缓解页内空间压力，但访问完整大字段可能需要更多页读取。订单列表仅返回金额和时间时，避免读取 `remark` 等宽列，能够减少数据搬运，也便于建立较窄的覆盖索引。

### 2.4 页作为缓存和索引管理单位

InnoDB 通常以页管理数据与索引，默认页大小为 16KB。页包含控制信息、记录、空闲区域和页目录。SQL 返回一行，并不意味着底层只从磁盘读取这一行；发生缓存未命中时，往往需要载入所在页。

页大小不是操作系统或存储设备保证的原子写入大小。一次页写可能在故障时只完成一部分，这是 doublewrite 需要处理的问题，见第 15 章。

页目录对页内记录分组建立定位信息，使查找先缩小到某一组，再沿记录链接定位具体记录。页内所有记录既不需要各占一项目录，也不需要按物理地址完全有序。

由此可以推导行宽的影响：同样数量的记录，行越宽，需要的叶子页越多，缓存覆盖的记录越少。即使索引树高度保持不变，实际页访问量仍可能明显增长。

## 3. B+ 树与聚簇存储

### 3.1 面向页的有序索引

数据库索引需要同时支持定位和有序遍历。Hash 能有效支持等值定位，但键之间没有可用于一般范围扫描的顺序。平衡二叉树具有有序性，但如果简单地将每个节点映射成单独的磁盘访问，多层访问开销会较高。B+ 树通过一个页保存多个索引项，提高分支数量，并将最终记录集中在叶子层。

```text
                   根页：分隔键与子页引用
                  /          |          \
            内部页         内部页         内部页
              │             │             │
            叶子页 ←→ 叶子页 ←→ 叶子页 ←→ 叶子页
                      键有序的扫描路径
```

实际内部页还需要子页定位信息和控制开销，不能将其解释成只包含几个纯键值。叶子页的链接支持跨页范围遍历；键上的逻辑相邻不表示文件中物理地址必然连续。

### 3.2 扇出、行宽和树高

假设内部页能容纳 500 个子页引用，叶子页平均容纳 100 行，三层结构的容量量级可写为：

```text
根页 → 500 个内部页 → 每个内部页 500 个叶子页
容量约为 500 × 500 × 100 = 2500 万行
```

这只是带有明确假设的数量级估算。键长度、记录宽度、页填充率和分裂情况会改变容量。它不能推导出“2500 万行就是容量上限”。

树高也不等于物理 I/O 次数。根页和常用内部页通常可以命中缓存；相反，扫描大量叶子页或随机回表，即使树只有三层，也可能产生很高的 I/O。判断性能时，页访问数量和局部性往往比单独的树高更有解释力。

### 3.3 聚簇索引使表数据成为一棵索引树

InnoDB 使用聚簇索引组织表数据。存在主键时，以主键作为聚簇键；没有主键时，选取第一个所有列均为 `NOT NULL` 的唯一索引；仍不存在时，创建隐藏聚簇索引。[官方聚簇与二级索引说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

聚簇索引叶子记录承载完整行的本地部分，宽字段可能继续指向页外数据。因此“叶子节点存完整行”是逻辑上的完整性，不代表所有字段字节都一定放在同一个叶子页。

显式主键使应用能够稳定引用记录，也方便更新、复制定位和故障排查。原稿将隐藏 row_id 计数器溢出直接描述为一般性的记录覆盖风险，缺少实现条件与证据，本文不将该说法作为主键设计依据。

### 3.4 二级索引以聚簇键定位完整记录

订单表的 `idx_user(user_id)` 可以概念化为：

```text
二级索引叶子记录：(user_id, id)
聚簇索引叶子记录：(id, user_id, status, amount, created_at, remark, ...)
```

按 `user_id` 查询金额时，二级索引能够找出候选 `id`，但不能直接提供 `amount`，需要继续访问聚簇索引。这个第二次访问称为回表。

聚簇键被多个二级索引携带，所以主键变宽会放大整张表的索引空间和维护开销。修改主键还可能改变聚簇记录位置和二级索引中的定位信息。因此，主键通常倾向于稳定、较短，而不只是业务上唯一。

### 3.5 主键顺序的收益和代价

递增主键使新记录通常插入索引末端，减少对分散页的随机访问，有利于局部性。随机键使插入位置遍布索引，在缓存不足时可能带来更多读取与分裂。

递增插入仍会发生页分裂，而且高度并发的末端写入可能产生热点。随机 ID 的成本也受表示方式影响：宽文本 UUID 与较紧凑的二进制表示并不等价。跨节点生成、业务可见性和存储成本需要共同评估，不能把所有系统的主键选择都化约为单一规则。

AUTO_INCREMENT 是身份分配机制，不是无间断编号机制。失败、回滚和并发分配都可能留下空洞；不同 `innodb_autoinc_lock_mode` 会改变分配期间的并发协调方式。连续业务编号需要另行定义语义与协调成本。[官方自增处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-auto-increment-handling.html)

## 4. 联合索引与访问路径

### 4.1 索引的四种作用

索引不只用于找到某个值，还可以用于减少候选范围、提前过滤、直接提供结果列，以及按目标顺序返回记录。

| 作用 | 减少的工作 | 订单案例 |
|---|---|---|
| 定位 | 需要进入扫描的候选记录 | 用 user_id、status 限定一个连续区间 |
| 过滤 | 无效候选的后续处理 | 在索引层排除不满足条件的条目 |
| 覆盖 | 为获取缺失列而进行的聚簇访问 | 索引中保存 amount |
| 排序 | 额外排序和排序前的候选收集 | 按 created_at、id 顺序读取 |

“使用了索引”只说明存在某种索引访问，不说明这四类收益全部成立。全索引扫描可能仍处理很多条目，而按索引顺序读取少量结果可能在过滤性一般的情况下也有价值。

### 4.2 联合索引是元组顺序

索引 `(a,b,c)` 先按 `a` 排序，在 `a` 相同的组内按 `b` 排序，再按 `c` 排序。

```text
(1,10,2)
(1,10,8)
(1,20,1)
(2,10,3)
(2,20,4)
```

条件 `a=1 AND b=10` 对应连续片段；条件仅为 `b=10` 时，符合记录分散在不同 `a` 组内。最左前缀原则来自这个排序结构，不来自 WHERE 条件的书写顺序。[官方多列索引说明](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)

未给首列不等于任何形式的索引访问都不存在。全索引扫描、覆盖访问或满足条件的 skip scan 等路径仍可能被选中。需要区分有效缩小扫描范围和仅仅扫描索引。

### 4.3 范围条件之后的列仍可能有用

对 `(a,b,c)` 使用 `a=1 AND b>10 AND c=7`，`b` 的范围会跨越多个组，每个组内 `c=7` 对应的位置并非简单的单个连续前缀。`c` 未必继续缩小初始扫描范围，但仍可用于索引内过滤或覆盖结果。

`>`、`>=`、`BETWEEN`、`IN` 的范围构造细节也不完全相同，不能将“遇到范围就停止”解释成所有边界条件都具有同一种实现。准确判断要结合范围优化和实际执行计划。[官方范围优化](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html)

### 4.4 从订单查询推导索引

最初的 `idx_user(user_id)` 只限定用户。数据库可能需要读取该用户大量订单，回表判断 `status`，再对符合条件的记录排序。

候选索引 A：

```sql
CREATE INDEX idx_feed
ON orders(user_id, status, created_at DESC, id DESC);
```

`user_id` 和 `status` 固定后，剩余键按目标顺序排列，访问路径具备按序扫描并在取得 20 条后停止的条件。索引是否最终被选中，还取决于优化器估算。

候选索引 B：

```sql
CREATE INDEX idx_feed_cover
ON orders(user_id, status, created_at DESC, id DESC, amount);
```

B 将金额也放入索引，进一步具备覆盖查询的条件。但每条索引记录更宽，更新金额需要维护该索引。如果 A 每次只需回表 20 行，B 的额外空间与写入成本未必值得。

列顺序还需要考虑其他查询。若大量查询只按用户读取，`user_id` 作为首列有利于复用；若只按状态跨用户处理订单，则该索引未必合适。因此，“区分度最高的列放最前”不能替代对整个查询集合的分析。

### 4.5 索引条件下推与覆盖的区别

索引条件下推（ICP）将可在索引条目上判断的部分条件交给存储引擎，在回表前排除无效条目。例如 `(user_id,created_at,status)` 在用户与时间范围定位之后，仍可能先根据索引中的 `status` 过滤，再读取缺失的金额。[官方 ICP 说明](https://dev.mysql.com/doc/refman/8.4/en/index-condition-pushdown-optimization.html)

ICP 主要减少后续回表，不必减少最初进入范围的索引条目数量。覆盖则表示查询所需列能够从索引获得，两者解决的成本不同。

覆盖也不是绝对的零聚簇访问承诺。二级索引的 MVCC 信息不等同于聚簇记录，某些删除标记或页修改条件下仍需要读取聚簇记录验证可见性。覆盖是列集合属性，实际访问还受事务版本影响。

### 4.6 可搜索条件与计划选择

条件能够转化成索引键范围，通常称为具有可搜索性。对原始时间列执行 `DATE(created_at)`，与直接限定原始时间范围不同：原索引按照完整时间排序，而不是按照函数结果建立索引。

```sql
WHERE created_at >= '2026-10-01 00:00:00'
  AND created_at <  '2026-10-02 00:00:00'
```

半开区间保留当天全部精度，不依赖人为构造最后一微秒。涉及 TIMESTAMP 或应用时区时，还需要先确定“当天”的时区含义。

| 条件形式 | 主要问题 | 分析边界 |
|---|---|---|
| `LIKE 'abc%'` | 前缀可形成范围 | 依赖字符集、排序规则与实际计划 |
| `LIKE '%abc%'` | 缺少确定的左侧前缀 | 仍可能全索引扫描，但通常不能据此前缀定位 |
| `DATE(created_at)=...` | 原始索引与表达式不对应 | 可改时间范围，或评估匹配表达式的索引 |
| 字符串列与数值比较 | 转换可能作用到索引列并改变语义 | 参数类型应与字段及业务含义一致 |
| `name=... OR age=...` | 多条候选路径需要合并 | 可能使用 Index Merge，也可能扫描，不能一概否定 |
| 命中绝大多数记录 | 索引回表成本可能高 | 全表扫描可能是合理选择 |

“索引失效”混合了无法构造范围、优化器选择其他路径、扫描过宽等不同情况。诊断时需要明确是哪一种，而不是仅凭 `key=NULL` 修改 SQL。

## 5. SQL 执行与优化器

### 5.1 声明式 SQL 需要转换成执行计划

SQL 描述需要什么结果，通常不规定从哪个表开始、使用哪棵索引、采用哪种连接算法。数据库需要先解析语法和解析对象名称，再根据统计信息和可用访问路径生成计划。

```text
连接与权限
  → 语法解析、表列名称与类型处理
  → 等价变换与成本估算
  → 访问路径、连接顺序、排序聚合方案
  → 执行器驱动存储引擎
  → 返回结果
```

这些阶段是职责划分，实际实现可能存在重写、下推及阶段交互。Prepared statement 可以复用部分处理工作，但不意味着所有执行成本和计划变化都被消除。MySQL 8.0 已移除旧查询缓存，Buffer Pool 缓存的是页，也不是任意 SQL 的最终结果。

### 5.2 成本估算与数据分布

优化器估算候选扫描量、回表、连接、排序等成本。统计信息反映的是数据分布的近似摘要，不是每次查询前完整读取真实数据。

订单中普通用户只有几十条记录，而某个大客户有几百万条时，相同 SQL 可能具有不同代价。`status=1` 在全表占比很低，也不保证在用户 42 的订单中占比同样低。列之间的相关性会造成独立估算失真。

统计信息过时、参数倾斜和成本假设偏差，都可能使优化器选择不理想的计划。更新统计信息、调整 SQL 或索引应围绕已定位的偏差开展；强制索引会限制选择，也可能使未来数据分布下的计划变差。

### 5.3 JOIN 的成本来自候选组合与重复访问

对嵌套循环连接，外层每返回一条记录，内层可能执行一次访问。外层输出从 100 行增长到 10 万行，即使内层每次都按索引快速查询，总工作量仍可能增大三个数量级。

有效过滤较早发生，可以减少后续连接工作；内层关联列索引有助于降低单次探测成本。但优化器可能重排内连接，SQL 书写顺序不必等同于执行顺序；外连接也需要保留未匹配行，不能为了下推条件而改变语义。

MySQL 8 支持 Hash Join 等路径。连接策略需根据等值条件、数据量和实际计划分析，不能将所有 JOIN 都解释成固定的两层循环。[官方 Hash Join 说明](https://dev.mysql.com/doc/refman/8.4/en/hash-joins.html)

### 5.4 排序与临时表是工作类型

`Using filesort` 表示额外排序，名称不意味着必然写磁盘。排序可能在内存完成，数据量或内存条件不足时才产生外部排序成本。`Using temporary` 表示需要临时结构，也不能直接等同于磁盘临时表。

能够沿索引返回目标顺序时，排序可能省去；如果过滤要求和排序要求无法同时由同一访问路径满足，就需要比较“先过滤后排序”和“按序扫描再过滤”的成本。LIMIT 能减少最终输出，不能保证每个方案都只处理 LIMIT 指定的行数。

## 6. 执行计划与性能判断

### 6.1 估算计划与实际执行

```sql
EXPLAIN
SELECT id, amount, created_at
FROM orders
WHERE user_id = 42 AND status = 1
ORDER BY created_at DESC, id DESC
LIMIT 20;

EXPLAIN ANALYZE
SELECT id, amount, created_at
FROM orders
WHERE user_id = 42 AND status = 1
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

普通 EXPLAIN 主要展示计划与估算；EXPLAIN ANALYZE 会实际执行受支持的语句，并报告迭代器时间、行数和循环次数。它从 MySQL 8.0.18 引入，不同版本支持的输出格式与语句范围需要核对。即使是 SELECT，也可能消耗大量资源或等待锁。[官方 EXPLAIN 说明](https://dev.mysql.com/doc/refman/8.4/en/explain.html)

### 6.2 常见字段的含义

| 字段 / 信息 | 可用于判断 | 不能直接推出 |
|---|---|---|
| `possible_keys` | 可能考虑的索引 | 实际一定使用某索引 |
| `key` | 选定索引 | 扫描量小、一定高效 |
| `type` | 访问类型，如 ref、range、ALL | 整条 SQL 的总成本排名 |
| `key_len` | 访问使用的键长度线索 | 查询所需列是否全部被覆盖 |
| `rows` | 估算候选行数 | 实际扫描量或结果行数 |
| `filtered` | 估算过滤比例 | 精确过滤效果 |
| `Using index` | 列覆盖访问线索 | 所有版本条件下绝无聚簇访问 |
| `Using index condition` | ICP 线索 | 已经成为覆盖索引 |
| `Using filesort` | 存在额外排序 | 排序一定落盘 |

访问类型只描述局部路径。一个 `ref` 节点如果重复执行 10 万次，可能比一次小表扫描更昂贵。

### 6.3 迭代器树的阅读顺序

树形计划需要沿数据产生方向分析：先看底部如何取候选，再看过滤保留多少行、连接重复多少次，最后看排序和 LIMIT。

假设内层节点显示每次平均返回 3 行、循环 10000 次，则累计输出量约为 30000 行。节点时间通常具有包含子节点、按循环平均等语义，不能简单将整棵树所有时间相加，或将所有节点的 `rows` 当作单次扫描量。

如果估算 100 行、实际 100000 行，首先需要查明数据倾斜、统计信息或表达式选择率的问题；如果工作量不大但耗时高，则需要继续观察等待、I/O 或 CPU。计划解释的是执行路径，不能单独解释连接池排队和网络传输。

### 6.4 优化验证的比较条件

索引变更的验证应保持参数、数据规模和并发条件可比，区分冷缓存与热缓存。单次耗时下降可能只反映缓存已被前一次查询预热。

有效证据包括候选扫描量减少、回表减少、排序消失或更小、估算接近实际，以及写入延迟和索引体积仍可接受。对于订单索引 A、B，读性能之外还需要观察金额更新带来的额外维护成本。

## 7. 结果语义与扫描代价

### 7.1 COUNT 的语义

`COUNT(*)` 统计当前查询可见的结果行数；`COUNT(column)` 只统计该表达式非 NULL 的行。`COUNT(1)` 中的常量 1 非 NULL，行数语义通常与 `COUNT(*)` 相同。`COUNT(主键)` 在主键非空的前提下也有相同计数语义。[官方聚合函数](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html)

InnoDB 不能只用一个全局精确计数器回答所有事务的 COUNT，因为不同快照可能看到不同数量的行。无条件统计通常仍需遍历可见索引记录，可能选择较小的二级索引，而非读取每行所有字段。

精确统计、近似统计和缓存统计是不同产品语义。若使用异步计数表或缓存，必须定义允许的误差与延迟；将精确查询替换为估算值属于接口行为变化。

### 7.2 OFFSET 消耗来自丢弃前缀

```sql
SELECT id, amount, created_at
FROM orders
WHERE user_id=42 AND status=1
ORDER BY created_at DESC, id DESC
LIMIT 100000, 20;
```

即使索引能够提供顺序，执行通常也需要取得足够多的符合记录，再丢弃前 100000 条。若每条候选都需回表，丢弃的记录仍然付出了聚簇访问成本。

延迟关联可以先用覆盖索引选出目标 ID，再只对最终一页回表。但它仍扫描 OFFSET 对应的前缀，并且外层还需要明确排序。原稿中“先查起始 ID，再用 ID 范围返回”的写法，只能在过滤和排序确实可由 ID 表达时保持语义，不能直接套用于按时间排序的订单列表。

### 7.3 游标分页从位置继续扫描

时间可能相同，因此游标必须包含完整的稳定顺序键：

```sql
SELECT id, amount, created_at
FROM orders
WHERE user_id=42 AND status=1
  AND (
       created_at < :cursor_time
       OR (created_at = :cursor_time AND id < :cursor_id)
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

只保存 `created_at` 会遗漏同时间但尚未返回的记录。增加 `id` 作为唯一的次序键，能够准确描述上一页末尾之后的位置。

游标分页减少重新扫描已返回前缀的需求，但通常不能直接跳到任意第 N 页。分页期间记录的状态、时间若发生改变，跨请求结果仍可能变化。若要求一次导出中的固定集合，还需要设计固定快照或固定数据边界，并评估长事务成本。

### 7.4 排序和 NULL 参与结果契约

分页所用列应尽量具有稳定含义。允许 NULL、可修改排序字段或跨时区转换，都需要明确比较规则。数据库优化只能保持已经定义的语义；如果结果顺序本身不稳定，增加索引无法修复分页契约。

## 8. Buffer Pool 与页生命周期

### 8.1 页缓存连接内存访问和持久存储

Buffer Pool 缓存表与索引页。查询首先查找所需页是否已在内存中，未命中时再读取；更新修改内存中的页，使其变成脏页。锁系统、连接内存和执行器工作区不应全部归入 Buffer Pool。[官方 Buffer Pool](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html)

```text
磁盘页 → 载入缓存 → 干净页 → 修改 → 脏页
                  │                  │
                  └→ 可直接淘汰       └→ 日志满足 WAL → 刷页 → 干净页
```

“干净”表示缓存页与相应持久页一致；“脏”表示有待写回修改。脏页可以包含多个事务、多次修改，不能把一个页与一个事务简单对应。

### 8.2 不同链表表达不同管理维度

Free List 跟踪可用缓存帧；LRU List 管理页的保留与淘汰优先级；Flush List 组织脏页刷写所需的信息。同一页可以同时处于 LRU 和 Flush 管理之中，它们不是互斥的三种页分类。

如果缓存没有可复用空间，淘汰干净页较直接；淘汰脏页需要先满足日志顺序并完成刷写。这使缓存压力能够转化为前台延迟。

### 8.3 分段 LRU 抵抗一次性扫描

普通 LRU 容易将刚读入的页放在最热位置。一次大范围扫描可能把不会再访问的页提升为热点，挤出真正的工作集。

InnoDB 在 LRU 中使用 old 和 young 区域，新载入的页先进入 old 一侧，并通过访问条件决定是否提升。`innodb_old_blocks_time` 用来限制新进入 old 区的页因短时间访问就立即晋升，从而降低扫描污染。[官方抗扫描策略](https://dev.mysql.com/doc/refman/8.4/en/innodb-performance-midpoint_insertion.html)

这种策略减少误判，但不保证热点永不被淘汰。工作集超过缓存容量时，仍需通过访问模式和容量分析处理根本压力。

### 8.4 命中率需要结合绝对访问量

假设某段时间每秒发起 100 万次逻辑页访问，命中率 99.9% 仍意味着约 1000 次未命中访问每秒。这个计算只是数量级说明，实际读取会受预读和 I/O 合并等因素影响，但足以说明高命中率不等于低 I/O。

增大 Buffer Pool 可以扩大缓存覆盖，但需要给连接、排序、临时表、其他服务和操作系统留出空间。若造成换页，可能抵消收益。缓存容量也无法解决锁等待、错误执行计划或重复查询过多等问题。

## 9. 事务与业务约束

### 9.1 事务将多步状态变化划为一个提交单位

转账包含源账户扣款、目标账户入账和流水写入。如果这些步骤分别提交，故障可能留下只扣未加等中间状态。事务把相关数据库修改纳入一个提交边界，使成功提交和回滚成为可区分的结果。

```sql
START TRANSACTION;
UPDATE accounts SET balance=balance-100 WHERE id=1 AND balance>=100;
-- 应用确认影响行数为 1 后，才继续执行后续操作。
UPDATE accounts SET balance=balance+100 WHERE id=2;
-- 应用还需要确认目标账户存在，并写入流水。
COMMIT;
```

上述注释代表必要的控制逻辑。如果条件扣款影响 0 行却仍然执行入账，事务仍可能正常提交。原子性只能保证已执行的一组修改共同提交或撤销，不能自动修正错误的业务分支。

### 9.2 ACID 的实现边界

| 属性 | 对外目标 | 主要机制与边界 |
|---|---|---|
| 原子性 | 事务修改作为一个整体生效或撤销 | undo、提交状态与恢复协作；涉及非事务引擎或外部系统时边界不同 |
| 一致性 | 提交状态满足声明约束和业务不变量 | 类型、唯一键、外键等约束，以及正确的事务程序 |
| 隔离性 | 并发影响受到所选隔离级别约束 | MVCC 与锁；不同隔离级别允许的行为不同 |
| 持久性 | 在规定故障模型下保留成功提交的结果 | 日志同步、恢复协议与存储设备保证 |

一致性不能直接等同于“数据库开启事务后，所有业务规则都成立”。数据库无法从两条普通 UPDATE 推导出系统期望的总金额守恒、至少一人值班等未声明规则。

### 9.3 autocommit、隐式提交与连接范围

autocommit 开启时，未显式开始事务的独立语句通常各自提交。一个 SELECT 和随后 UPDATE 若属于两个独立事务，中间仍可能被其他会话修改。

显式事务的边界绑定连接，连接池和事务框架必须保证相关操作使用正确连接。某些 DDL、管理语句会隐式提交，不能因为外层写了 BEGIN 就认为它们可以与普通 DML 一样整体回滚。[官方隐式提交说明](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)

事务不是越长越能保证一致性。持锁时间增加会放大等待，长期快照会推迟旧版本清理。外部接口调用、文件处理等耗时工作放在持锁事务内，通常会使故障与重试边界复杂化。

## 10. undo、MVCC 与 Read View

### 10.1 回滚与历史读取共享旧版本信息

更新当前状态后，数据库仍需要能够撤销未提交修改，也需要让早先建立快照的事务读取旧状态。如果每次更新都保留整张表快照，成本过高。InnoDB 因此保存操作相关的 undo 信息，并通过聚簇记录上的事务字段连接历史版本。

undo 不是固定格式的“整行复制”。它保存足以撤销相关操作或重建历史版本的信息，插入 undo 与更新 undo 的生命周期也不同。更新 undo 在提交后可能仍被一致性读需要，不能立刻全部丢弃。[官方 undo 说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-undo-logs.html)

```text
聚簇记录：balance=200，修改事务=120
            │ undo 信息
            ▼
可重建版本：balance=150，修改事务=110
            │ undo 信息
            ▼
可重建版本：balance=100，修改事务=更早的事务
```

这张图表示重建关系，不表示 undo 中实际存储了三条完整相同行格式的记录。

### 10.2 Read View 判断可见性

Read View 保存快照建立时的活跃事务集合和事务 ID 边界。读取聚簇记录时，如果当前版本不可见，就沿 undo 信息寻找可见版本。

以 `creator` 表示当前事务、`active` 表示快照建立时的活跃读写事务集合、`low` 表示其低位边界、`high` 表示当时下一个待分配的事务 ID，概念规则为：

```text
版本由当前事务自己产生                  → 可见
版本事务 ID 小于 low                  → 可见
版本事务 ID 大于或等于 high             → 不可见
版本事务 ID 位于 [low, high) 且在 active → 不可见
版本事务 ID 位于 [low, high) 且不在 active → 可见
```

活跃集合为空时，边界按实现规则处理。只读事务的事务 ID 分配也存在优化，因此这里的模型用于解释版本可见性，不替代具体版本的内部结构定义。

事务 ID 的顺序不能单独表示提交顺序：较小 ID 的事务可能仍未提交，而较大 ID 的事务已经提交。活跃集合正是用于区分这类情况。

### 10.3 快照建立时间

RR 下，普通一致性读通常在第一次这类读取时建立 Read View，并在事务内复用。仅执行 BEGIN 不必已经固定快照。RC 下，每次普通一致性读使用新的视图。[官方一致性非锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

| 时序 | A | B | 理论预期 |
|---|---|---|---|
| 1 | RR，BEGIN，尚未查询 | — | 此时不应仅凭 BEGIN 判断快照已建立 |
| 2 | — | 将余额改为 200 并提交 | 已提交版本成为最新状态 |
| 3 | 首次普通 SELECT | — | 可读取 200 |
| 4 | — | 将余额改为 300 并提交 | 当前状态变化 |
| 5 | 再次普通 SELECT | — | RR 仍读取已有快照中的 200 |

`START TRANSACTION WITH CONSISTENT SNAPSHOT` 可用于在适用隔离级别下主动建立一致性快照。普通读取也能看到当前事务此前产生的修改，因此“同一视图”不等于“事务中的所有输出永远完全不变”。

### 10.4 当前读的职责

UPDATE、DELETE 和锁定读取需要对可操作的当前状态进行协调。`SELECT ... FOR UPDATE` 获取排他保护；`SELECT ... FOR SHARE` 获取共享保护。它们不是普通一致性读，可能等待冲突事务结束，再读取可锁定的状态。[官方锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

当前读不表示可以读取其他事务未提交的任意修改，也不表示读取整库在同一时刻的全局最新快照。其语义与具体记录、锁等待和执行路径相关。

### 10.5 旧版本保留与 purge

记录逻辑删除后，如果仍有快照可能需要旧记录，物理清理就不能立即完成。purge 在旧版本不再需要时清理相关 undo 和删除标记记录。[官方 purge 说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-purge-configuration.html)

长期快照可能阻碍清理，使历史累积并增加版本访问成本。History list length 是观察线索，但不等于简单的字节数或业务行数；分析时还需要事务持续时间、写入量和清理进度。

增加 purge 线程不一定能解决长快照问题，因为真正障碍可能是旧版本仍合法地被需要。结束或缩短相关事务，才可能解除保留边界。

## 11. 隔离级别与并发异常

### 11.1 隔离级别规定允许的观察结果

脏读是观察到其他事务未提交的修改；不可重复读是同一事务重复读取既有行时观察到已提交变化；幻读是重复执行同一谓词查询时，符合条件的记录集合变化。丢失更新和写偏差则反映更复杂的读写依赖。

| 级别 | InnoDB 主要行为 | 关键边界 |
|---|---|---|
| RU | 普通读取允许更弱的可见性保证 | 可能脏读，通常不适合需要可靠状态判断的业务 |
| RC | 普通一致性读逐次建立视图 | 可能不可重复读及集合变化；一般搜索减少间隙保护 |
| RR | 普通一致性读复用视图；锁定搜索通常有范围保护 | 不自动保证所有业务程序可串行化 |
| Serializable | 在相关条件下将普通读取转换为共享锁定读取 | 不等于整个实例只能同时运行一个事务 |

InnoDB 默认隔离级别为 RR。Serializable 中普通 SELECT 的加锁行为需要结合 autocommit 和事务范围判断，不能仅凭级别名称推导全部锁。[官方隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)

### 11.2 RR 中读取和修改可能基于不同状态

初始余额为 100，A 使用 RR 显式事务；B 使用另一个连接并提交修改。

| 时序 | A | B | 解释 |
|---|---|---|---|
| 1 | BEGIN；普通 SELECT 得到 100 | — | 建立 A 的视图 |
| 2 | — | UPDATE 将余额改成 200；COMMIT | 最新提交状态为 200 |
| 3 | 普通 SELECT 仍得到 100 | — | 使用已有视图 |
| 4 | `UPDATE ... SET balance=balance+10` | — | 当前读基于可更新状态 200 计算 |
| 5 | 普通 SELECT 得到 210 | — | 当前事务自己的修改可见 |

如果 A 在第 4 步使用应用按旧余额算出的常量 `SET balance=110`，可能覆盖 B 的结果。这说明数据库内的原子增量与应用读出后写回是不同程序，RR 的普通读稳定性不能消除所有丢失更新。

### 11.3 幻读保护有两条路径

重复普通一致性读时，RR 使用相同视图，其他事务后来插入的记录不会因再次读取就进入该视图。锁定读取需要保护当前可操作的集合，通常通过索引记录和间隙锁阻止相关插入。

如果 A 先用普通 SELECT 观察不存在的记录，B 随后插入并提交，A 再用 UPDATE 修改该记录，则 A 后续普通读取可能看到自己的新版本。这个结果来自读取模式与自身修改的组合，不能用“RR 所有 SQL 必须使用同一历史状态”解释。

### 11.4 写偏差涉及跨记录约束

假设有两个值班人员，业务要求至少一人继续值班。A、B 在 RR 下都通过普通 SELECT 看到两人值班，随后各自将自己的记录改为不值班。

```text
A 读到：人员 1、2 都值班 → A 更新人员 1
B 读到：人员 1、2 都值班 → B 更新人员 2
更新的是不同记录 → 可能均提交 → 最终无人值班
```

每个事务都依据一个稳定快照做决定，但两个决定组合后违反约束。单独锁住各自最终修改的行不足以解决该问题。

一种方案是在同一事务中按固定顺序锁定涉及的全部值班记录，基于锁定后的状态判断；另一种是将共同约束汇总为同一条需更新的控制记录，或评估 Serializable 与重试。具体方案应明确所有写入入口是否遵守同一种协调协议。

### 11.5 RC 与 RR 的选择

RC 允许后续语句观察较新的提交状态，通常减轻普通搜索中的间隙锁冲突，但跨语句判断需要额外设计。RR 为一致性读提供稳定视图，也可能因范围保护增加冲突。

选择隔离级别需要围绕不变量、读写程序和实际竞争评估。提高级别不替代正确事务边界，降低级别也不意味着数据库没有锁。

## 12. 锁与索引扫描

### 12.1 数据锁保护状态，元数据锁保护结构

多个会话修改同一记录，需要决定谁先操作。另一方面，查询依赖的表定义不能在执行过程中任意被另一会话更改，因此结构还需要独立的元数据协调。

| 机制 | 保护对象 | 典型作用 |
|---|---|---|
| 记录 S / X 锁 | 索引记录 | 协调共享读取和排他修改 |
| Gap Lock | 索引键之间的间隙 | 阻止特定位置插入 |
| Next-Key Lock | 记录及前方间隙 | 保护扫描到的记录和范围 |
| 插入意向锁 | 间隙内准备插入的位置 | 协调插入与范围保护 |
| IS / IX | 表上的行锁意图 | 协调表级锁与行级锁 |
| MDL | 表等对象的定义 | 协调访问与 DDL |
| AUTO-INC 相关机制 | 自增值分配 | 由自增锁模式影响并发分配 |

事务锁不同于保护内存页和内部结构的短时 latch。一次 UPDATE 延迟既可能来自事务锁等待，也可能来自内部热点争用，两者观察方式和解决方向不同。

### 12.2 锁模式与意向锁

同一记录上的 S 锁可彼此兼容，X 锁与其他冲突记录锁不兼容。普通一致性读通常可以读取可见历史版本，并不因另一事务持有记录 X 锁就必然阻塞。

事务获得行级 X 锁前，在表上表达 IX 意图，帮助系统与整表级锁做兼容性判断。IX 与 IX 可以兼容；观察到表级 IX 不表示已经以排他方式封锁整张表。[官方 InnoDB 锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)

### 12.3 锁住缺失位置的设计理由

假设主键为 `10,20,30,40`，A 在 RR 显式事务中执行：

```sql
SELECT * FROM lock_demo WHERE id=15 FOR UPDATE;
```

不存在 id=15，因此没有这条记录可以加记录锁。如果事务需要保护“该位置不存在”，只锁现有记录无法阻止 B 插入 15。InnoDB 可以在相关索引间隙 `(10,20)` 设置间隙保护。

```text
10 ──────────────── 20
      缺失位置 15
      间隙 (10,20)
```

在没有其他冲突的前提下，B 插入 12 或 15 都可能受阻，而 B 更新 20 的非键字段不因这个纯间隙锁受阻。保护范围由物理索引间隙表达，可能大于业务条件中的一个值。

如果查询唯一键 id=20 且命中，通常可只用该记录锁完成保护，而不需要同样的间隙锁。该规则要求完整唯一条件，复合唯一索引仅指定部分列不能按唯一命中处理。[官方不同语句的锁范围](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)

### 12.4 Next-Key 的区间表达

Next-Key Lock 包含当前记录及其前方间隙，常写为 `(前一键,当前键]`。纯 Gap Lock 则不包含端点记录。

间隙锁主要抑制插入，因此两个事务的纯间隙锁可以共存，不能按照记录 X 锁的互斥规则理解。两个事务先共同锁住缺失位置，再各自尝试插入，还可能形成死锁。

在最大键之后，需要考虑 supremum 代表的尾部间隙。范围边界、LIMIT 和优化路径会影响实际锁集，不能从抽象区间画法推导出所有语句都锁定同样的边界。

### 12.5 非唯一二级索引需要带上主键

假设数据为：

```text
id： 10      20      30      40
k：   1       2       2       3

idx_k 的概念顺序：
(1,10) → (2,20) → (2,30) → (3,40)
```

对 `k=2 FOR UPDATE` 的分析不能只画一个抽象的 k=2 点。相同二级键通过聚簇键区分位置，还需要阻止该组内出现新的匹配记录，并锁定相关聚簇记录。

给定 RR、`idx_k(k)`、固定该索引的访问路径，典型分析包括匹配二级条目的 next-key 保护、匹配组之后的间隙保护，以及 id=20、30 的聚簇记录锁。不同版本的边界优化应以 `data_locks` 验证，本文不把这种示意写成已实测结果。

### 12.6 全扫描扩大锁范围

锁定搜索和更新通常围绕实际扫描的索引记录及范围设置锁。未使用有效索引时，可能扫描大量聚簇记录，因而保护大量记录和间隙，使不相关业务也等待。

InnoDB 不会因为扫描行数较多就自动将所有行锁升级为一个表级排他锁。大量行与范围被锁住造成的表面效果，和真正的表锁机制不同。

RC 的普通搜索通常减少间隙锁，并可能释放不匹配记录的锁，但重复键与外键检查仍有例外，二级索引维护也可能引入冲突。因此 RC 不等于永远只锁最终修改的那几行。

### 12.7 锁范围分析方法

分析应依次明确数据库版本、隔离级别、事务范围、实际索引、唯一性和完整索引键顺序，再分别讨论命中记录、间隙、聚簇记录与其他约束。

更换索引会改变扫描路径，也可能改变并发冲突范围。索引评审因此既是性能评审，也是事务行为评审。仅根据 WHERE 文本列出“锁住几行”通常缺少足够条件。

### 12.8 MDL、表锁与全局读锁

MDL 在访问对象时自动获取，事务中的相关 MDL 通常持续到事务结束。A 查询后不提交，即使已处于空闲状态，也可能让 B 的 ALTER TABLE 等待；等待中的 DDL 又可能影响后续访问。[官方元数据锁](https://dev.mysql.com/doc/refman/8.4/en/metadata-locking.html)

显式 `LOCK TABLES` 是另一种机制，读锁、写锁对并发访问有不同限制，不适合简单代替一般的 InnoDB 行级事务协调。

`FLUSH TABLES WITH READ LOCK` 获取全局读锁，常用于某些备份协调流程，但不能将其理解为把所有实例状态永久切换为统一只读。对于全部使用 InnoDB 的适用场景，一致性快照备份可以减少全局阻塞；DDL 和非事务表仍需要另行考虑。[官方 mysqldump 一致性选项](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html#option_mysqldump_single-transaction)

## 13. 死锁与业务并发设计

### 13.1 等待环使事务无法自行推进

```text
A 已持有 id=1 → 请求 id=2，等待 B
B 已持有 id=2 → 请求 id=1，等待 A
```

普通等待可以随着持锁方提交结束；等待环内的事务相互依赖，不能仅靠延长等待时间解决。开启检测时，InnoDB 选择受害事务回滚以打破环，通常倾向回滚修改量较小的事务，而非固定回滚后开始的事务。[官方死锁检测](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlock-detection.html)

固定访问顺序、短事务和较小扫描范围能降低概率，但唯一键检查、外键检查和二级索引维护也可能参与等待，不能保证只要排序访问就完全没有死锁。

### 13.2 失败后的回滚范围

| 失败 | 常见 InnoDB 行为 | 事务程序的处理要求 |
|---|---|---|
| 1213，死锁 | 回滚整个受害事务 | 新建事务并重新执行完整业务决策 |
| 1205，锁等待超时 | 默认回滚失败语句，相关配置可改变范围 | 明确剩余事务状态，必要时主动回滚整个事务 |
| 唯一键冲突 | 通常回滚失败语句 | 判断是重复请求还是不可接受的冲突 |
| 提交时连接中断 | 应用可能无法确认提交结果 | 查询已有业务结果，不能直接假定回滚 |

应用捕获异常后继续执行，不意味着此前修改全部已撤销。重试也不应复用已经失败的事务上下文。[官方错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)

可重试事务需要有限次数、退避、重新读取状态和可识别的最终失败。涉及外部付款、消息或其他不可重复副作用时，还需要单独的幂等与结果查询机制。

### 13.3 单行条件更新

```sql
UPDATE product
SET stock=stock-:qty
WHERE id=:product_id AND stock>=:qty;
```

前提为 `qty` 是合法正数，目标 id 唯一。语句将库存检查与修改放在同一次锁保护的当前状态操作中；影响 1 行表示条件更新成功，0 行可能表示记录不存在或库存不足。

它解决的是单行条件扣减，不自动覆盖订单写入、优惠额度和重复请求。若需要同时写订单，应由同一事务提交；若请求可能重发，还需要请求身份约束。

### 13.4 乐观并发控制

```sql
UPDATE accounts
SET balance=:new_balance, version=version+1
WHERE id=:id AND version=:old_version;
```

版本条件检测读取后是否发生冲突。影响 0 行时需要重新读取并重新计算，不能只替换版本号后继续沿用旧结果。

“乐观”指应用先读取计算，再在写入时检查，不表示 UPDATE 内部没有数据库锁。所有相关写入都需要正确推进版本，否则检测机制失去完整性。

### 13.5 唯一键与幂等

先查询 request_id 不存在再插入，存在两个会话同时通过查询的窗口。非空唯一键将并发裁决交给数据库，事务再将请求记录与业务效果绑定。

完整设计还包括同一 request_id 的参数一致性、处理中状态、成功结果回查和失败后能否再次处理。唯一列允许 NULL 时可出现多条 NULL，排序规则也会影响哪些请求身份被视为相同，因此约束需要与业务身份定义一致。

如果提交成功但响应丢失，客户端重试应找到已有结果；无条件重新扣减会产生重复效果。幂等的目标是请求效果稳定，而不是仅仅让 INSERT 不报错。

### 13.6 数据库与消息的协作

先提交数据库再发送消息，进程可能在两步之间崩溃；先发送消息再提交数据库，又可能让消费者处理最后被回滚的业务。

事务内同时写业务表与 outbox，使“业务变更”和“待发送事件”具有共同提交边界。独立投递程序再将 outbox 发送到消息系统，发送成功后的标记也可能失败，因此消费者仍需去重，系统仍需重试和对账。

这个边界不同于 InnoDB 与 binlog 的内部两阶段提交。内部提交协调不自动将外部消息系统纳入同一个原子事务。

### 13.7 SKIP LOCKED 与任务领取

```sql
START TRANSACTION;
SELECT id
FROM job_queue
WHERE state=0
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- 在同一短事务中将返回任务标记为已领取，并记录领取者和租约。
COMMIT;
```

SKIP LOCKED 让消费者绕过其他消费者已锁定的任务，降低等待。它返回的是跳过锁定行后的集合，不能用于要求完整状态判断的余额或额度统计。

实际任务应在领取事务提交后执行，配合租约、超时重新领取与幂等处理。否则持锁执行长任务会持续占用事务资源；没有失败恢复机制则可能使任务永久停留在已领取状态。

## 14. 日志与提交协议

### 14.1 缓存写入需要额外的持久性证明

修改 Buffer Pool 后，数据页可能暂未写回。如果每个事务都等待所有相关数据页落盘，随机页写入会直接进入提交延迟。数据库可以先持久化较紧凑的变更日志，再由后台安排数据页写入。

但故障后的重做、运行中的回滚和副本的变更传输属于不同任务。因此 InnoDB 和 Server 保留不同日志，而不是简单复制三份相同内容。

| 日志 | 所在层 | 记录的抽象与主要用途 | 不能单独替代 |
|---|---|---|---|
| undo | InnoDB | 撤销操作、重建历史版本所需信息 | 已提交页修改的可靠重做 |
| redo | InnoDB | 页相关修改的重做信息，服务于崩溃恢复 | 长期业务历史与任意时间点恢复 |
| binlog | Server | 变更事件，服务于复制和结合备份恢复 | InnoDB 页恢复、运行中回滚 |

redo 既保护业务数据页，也保护 undo 等引擎内部页的相关修改；undo 本身不是无需恢复保护的独立信息。

### 14.2 WAL 约束数据页写入顺序

Write-Ahead Logging 的核心约束是：在将某个修改后的数据页写到持久存储前，能够恢复该页修改所需的日志必须先达到必要的持久化位置。[官方 redo 说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-redo-log.html)

```text
内存：生成 undo / 修改页 / 生成 redo
                   │
日志：写出并同步保护该页修改的 redo
                   │ WAL 顺序约束
数据：允许将相关脏页写出到持久存储
```

“先写日志”不表示在 CPU 修改缓存页之前，必须先完成一次磁盘同步；约束针对日志持久化与数据页持久化的先后。写入 redo buffer、调用文件写入、同步到持久存储也不是同一个动作。

WAL 允许尚未提交事务的部分脏页被写出。故障恢复因此不能只重做已提交业务：需要先恢复页结构和相关修改，再根据事务状态通过 undo 撤销应回滚的事务。

### 14.3 binlog 的事件格式

ROW 格式主要记录行变更事件，STATEMENT 格式记录语句，MIXED 根据适用规则选择。ROW 便于避免一些语句重放不确定性，但行事件体积受修改规模和 row image 等配置影响，不能将每个事件都描述为固定的完整前后行副本。[官方二进制日志](https://dev.mysql.com/doc/refman/8.4/en/binary-log.html)

binlog 文件按策略保留和清理，不会无条件永久保存全部变更。它能用于时间点恢复的前提是存在可用基线备份，并保留从备份位置到目标位置的完整日志链。

### 14.4 两种持久记录需要一个提交决策

启用 binlog 后，若引擎状态已经提交而对应 binlog 没有可靠保存，副本和恢复流程可能缺失该变更；如果 binlog 已保留事务，而引擎恢复后将其回滚，则本地和复制历史可能不一致。

内部两阶段提交使 InnoDB 先进入可恢复的 prepared 状态，再由 binlog 中的有效事务信息支撑提交决策，最后完成引擎提交。

```text
InnoDB prepare
    → binlog 写入并按持久性要求同步
    → InnoDB commit
```

这个图是逻辑状态顺序，不代表每个事务都固定进行三次独立 fsync。prepared 状态的可靠性、binlog 同步和恢复协调需要共同成立。

| 故障边界 | 恢复时的主要判断 |
|---|---|
| 尚无可靠 prepare 或提交依据 | 对未完成事务进行恢复并撤销应回滚修改 |
| 有可靠 prepare，但没有对应有效 binlog 提交依据 | prepared 事务不能仅凭已准备就自动认定成功 |
| 有可靠 prepare 和对应有效 binlog 事务依据，尚未完成引擎 commit | 恢复协调可完成该 prepared 事务的提交 |
| 提交完成，但客户端未收到响应 | 数据库结果可能已成功，应用需要查询确认 |

这里讨论普通 InnoDB 事务与 binlog 的内部协调，不是用户执行 XA PREPARE 后由外部协调器决定结果的完整外部 XA 流程。[官方 binary log 的恢复协调说明](https://dev.mysql.com/doc/refman/8.4/en/binary-log.html)

### 14.5 组提交共享同步成本

多个事务并发提交时，可以汇集成一组完成相关日志写入与同步，降低每个事务独占同步等待的成本。组提交将逻辑事务顺序与物理同步次数分开：`sync_binlog=1` 对提交组进行同步，不等于每个事务独占一次磁盘同步。

MySQL 8.0 的 ordered commit 实现包含 flush、sync、commit 等阶段，并由阶段队列组织多个事务；具体调用与持久化安排应以对应版本实现为准。[官方 8.0.46 源码文档](https://dev.mysql.com/doc/dev/mysql-server/8.0.46/group__Binary__Log.html)

汇集等待存在延迟与吞吐取舍。增加组提交等待可能扩大批量，也会让轻负载事务承担额外等待，不能仅因磁盘同步昂贵就无限延长等待窗口。

### 14.6 持久性配置定义故障窗口

| `innodb_flush_log_at_trx_commit` | 典型行为 | 主要风险边界 |
|---|---|---|
| 1 | 每次提交按要求写出并同步 redo | 仍依赖底层真正兑现持久化 |
| 2 | 提交写出 redo，周期性同步 | 操作系统或机器故障可能丢失尚未同步部分 |
| 0 | 写出和同步主要周期性进行 | mysqld 进程故障也可能丢失内存中的部分日志 |

周期性调度不构成严格的“最多丢一秒”承诺，系统负载和调度可扩大间隔。使用 binlog 时还需要同时评估 `sync_binlog`，否则引擎日志和复制历史的可靠性不一致。[官方 redo 同步参数](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_flush_log_at_trx_commit)、[官方 binlog 同步参数](https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html#sysvar_sync_binlog)

持久性配置需要与可接受数据损失窗口对应。应用收到“提交成功”、机器掉电后仍能恢复、任意副本已可读，是三个不同保证。

## 15. 刷页、checkpoint 与恢复边界

### 15.1 刷页与提交是不同进度

事务提交可以先由可靠日志保护，数据页后续再写回。一次数据页刷写可能包含多次修改，将它们合并成一次写入，有助于减少写放大。

后台会根据脏页、日志推进和存储能力进行刷写；缓存淘汰、redo 空间压力和关闭流程也会影响刷写。正常关闭是否进行完整清理还受 `innodb_fast_shutdown` 等配置影响，不能统一解释成关机前所有内部工作都完成。

如果日志产生速度长期超过数据页写回速度，后台工作会积压，最终迫使前台等待。偶发延迟因此可能是后台压力传导到前台，而不是当前 SQL 突然需要更多逻辑记录。

### 15.2 LSN 与 checkpoint

LSN（Log Sequence Number）标识日志中的推进位置。页也记录相关修改进度，使恢复能够判断日志与页之间的关系。

checkpoint 表示较早的恢复起点已经向前推进：相关旧修改被充分写回后，恢复无需再从所有历史日志的开头重做，旧日志空间也可按规则复用。[官方 checkpoint](https://dev.mysql.com/doc/refman/8.4/en/innodb-checkpoints.html)

```text
较旧日志                          新生成日志
────── checkpoint ───────────────── current LSN
       │<──── 尚需保留的恢复范围 ────>│
```

checkpoint age 可概念化为当前日志位置与 checkpoint 的差距。它越大，说明更多日志仍处于恢复保留范围；接近可用容量时，系统需要加快相关刷写或限制前台推进。

这不是固定周期冻结全部写入、一次性写出所有脏页的模型。InnoDB 使用持续推进的机制，使多数刷写能够在后台进行。

### 15.3 redo 容量是缓冲，不是存储吞吐

扩大 redo 容量可以吸收更长写入峰值，为刷页合并和调度提供余地。它不能使慢磁盘无限追上持续更高的写入量，并会改变空间和恢复工作量的评估。

MySQL 8.0.30 起使用 `innodb_redo_log_capacity` 管理 redo 容量；较早 8.0 版本主要使用 `innodb_log_file_size` 与 `innodb_log_files_in_group`。配置建议应明确版本，避免把旧日志文件模型直接套用于 8.4。

### 15.4 doublewrite 处理页写不完整

页为 16KB 并不保证存储一次原子写完整个页。如果故障发生在页写中间，原位置可能只有部分新内容。redo 通常描述页修改，不能保证仅靠这些记录就能把任意损坏的页恢复为合法基础页。

doublewrite 先将待刷页写入额外区域，再写到正式位置。恢复时若发现目标页损坏，可使用保留的完整副本建立正确页基础，再继续相关恢复。[官方 doublewrite](https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html)

WAL 解决“日志先于数据”的顺序，doublewrite 解决“页可能写了一部分”的完整性，两者保护的缺口不同。是否可关闭 doublewrite 取决于具体存储保证和配置，不能仅凭设备较新作出判断。

### 15.5 崩溃恢复与误操作恢复

崩溃恢复利用数据页、redo、undo 和提交协调结果恢复有效状态；已成功提交的错误 DELETE 对数据库而言同样是合法提交，redo 不会主动撤销它。

误操作恢复通常需要在隔离环境中恢复基线备份，再重放到错误操作前的明确事务边界。日志链完整性、备份坐标、恢复目标与结果校验缺一不可。[官方时间点恢复](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery.html)

副本可能快速重放误删除，因此复制不能替代独立备份。备份成功也不等于可按目标时间恢复，实际恢复演练需要验证恢复时间、数据完整性和业务一致性。

## 16. 复制与写后读

### 16.1 复制链路中的不同进度

```text
源库提交并生成 binlog
    → 副本接收事件
    → 写入 relay log
    → 应用线程执行事务
    → 副本上的查询能够观察该结果
```

日志已经到达不表示事务已经执行，事务已经执行也不表示某个早先建立的查询快照必然能看到它。复制延迟因此至少要区分接收阶段和应用阶段。[官方 relay log](https://dev.mysql.com/doc/refman/8.4/en/replica-logs-relaylog.html)

大事务、热点锁、I/O 压力和 DDL 都可能降低应用速度。只看一个“延迟秒数”，通常不足以判断瓶颈和日志丢失风险。

### 16.2 异步与半同步

异步复制允许源库在副本尚未收到相关日志时返回提交结果，故障切换可能缺失副本尚未获得的事务。

半同步在启用且没有降级的情况下，源库等待配置要求数量的副本确认。副本确认的是事件已写入 relay log 并同步，不是保证已经应用。等待点、超时降级和确认数量共同影响保证范围。[官方半同步复制](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)

因此半同步不能直接保证将请求路由到任意副本后立即读到刚写的结果，也不能替代完整故障切换协议。

### 16.3 写后读策略

| 策略 | 主要收益 | 必须处理的边界 |
|---|---|---|
| 相关读回源库 | 容易获得源库当前提交结果 | 源库负载和读事务快照 |
| 一段时间粘滞源库 | 减少短窗口复制延迟影响 | 固定时间不构成严格追平证明 |
| 使用目标 GTID 等待副本应用 | 对目标事务建立明确等待 | GTID 获取、超时、路由和新快照 |

`WAIT_FOR_EXECUTED_GTID_SET` 等机制可用于等待目标事务集合已执行。等待成功后，业务查询仍要避免复用早于目标事务建立的 RR 快照。[官方 GTID 函数](https://dev.mysql.com/doc/refman/8.4/en/gtid-functions.html#function_wait-for-executed-gtid-set)

### 16.4 故障切换需要避免多个写入源

提升副本为新源库前，需要判断日志完整性、待应用事务和旧源库状态。旧源库在网络分区后恢复并继续接收写入，可能形成双写分歧，必须通过隔离、路由和故障判定机制防止。

高可用系统的目标应明确为允许损失多少数据、多久恢复服务以及如何证明新源库状态。仅部署一个副本，并不自动形成满足这些目标的高可用方案。

## 17. DDL、容量与数据生命周期

### 17.1 在线 DDL 仍有协调与资源成本

DDL 修改表定义或物理布局，需要与正在访问表的事务协调。INSTANT、INPLACE、COPY 表示不同算法路径；`LOCK=NONE` 等选项描述并发要求，它们不是同一个维度。

INPLACE 不意味着一定不重建数据；INSTANT 只适用于相应版本和满足条件的操作。在线建索引通常仍需扫描和构造索引，产生 I/O、临时空间和并发修改日志成本。[官方在线 DDL 操作支持表](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)

即使允许并发 DML，操作开始和结束等阶段仍可能需要更严格的 MDL。长事务、空间不足、并发变更过多和复制积压都会影响上线行为。[官方在线 DDL 限制](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-limitations.html)

明确要求支持的算法和并发条件，有助于避免操作默默选择超出预期的路径。发布前还应验证预计时长、空间、锁等待与失败后的处理，不能只在小表上证明语法能够执行。

### 17.2 行数不是容量阈值

容量至少包含数据体积、索引体积、热工作集、访问量、写入速率、存储延迟、备份窗口和恢复目标。同样 2000 万行，窄记录与宽记录、点查与全表聚合、均匀访问与热点访问的需求差别很大。

树高可能尚未增长，缓存命中和随机回表已经恶化；总表体积很大，但热记录很少且访问路径稳定，也可能继续良好运行。因此固定行数不能代替瓶颈测量。

### 17.3 删除、复用与归档

DELETE 需要事务日志、索引维护和版本清理，大批删除可能产生长事务及复制积压。分批处理可以控制单次资源消耗，但仍需要定义批次一致性与进度恢复。

purge 清理记录后，空间可以供内部复用，不表示文件立刻缩小。需要返还文件空间时，可能涉及重建等操作，又会增加 I/O 和维护成本。

按数据生命周期设计冷热归档，可以减少在线工作集。但历史查询、审计保留和回查路径也需要同步设计，不能将“删除旧数据”只作为性能操作。

### 17.4 分区的收益与约束

分区在一个逻辑表下拆分物理数据，适合按时间裁剪访问和管理数据生命周期。分区通常仍在同一实例内，不自动提供跨机器写入容量。

MySQL 要求分区表达式涉及的列满足各唯一键的相关规则。若原业务要求 id 全局唯一，而时间分区迫使主键改为 `(id,created_at)`，该复合唯一约束只禁止两列组合重复，并不单独保证 id 不重复。[官方分区键与唯一键限制](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations-partitioning-keys-unique-keys.html)

分区裁剪还需要查询条件能够定位相关分区。缺少时间条件的查询可能继续扫描大量分区，分区数量增加也会带来维护成本。

### 17.5 分片将单实例问题转化为分布式问题

分片可以将数据和负载分布到多个实例，但会引入跨片唯一性、事务、连接、聚合、分页和迁移问题。

设计至少要明确分片键是否包含在主要查询中、热点是否均匀、跨片事务是否必要、扩容期间如何校验和切换。按 user_id 分片也可能因大租户而严重倾斜。

扩展方案应针对已确认瓶颈：先比较 SQL 和索引、数据生命周期、缓存、读写隔离等措施，必要时再承担分片复杂度。分片不是对某个固定行数阈值的自动响应。

## 18. 查询、更新与排障全链路

### 18.1 一次订单列表查询

```text
SQL 与参数进入 Server
  → 优化器估算候选访问路径
  → 执行器按选定索引读取
  → Buffer Pool 命中或载入相应页
  → 根据读取类型判断版本或申请锁
  → 定位、过滤，必要时回表
  → 排序 / 连接 / 聚合
  → LIMIT 输出与网络传输
```

选择 `idx_user` 时，瓶颈可能是大量候选回表与排序；选择 `idx_feed` 时，可能按序读取很少记录；使用覆盖候选时，可能进一步减少取金额所需访问。若发生 MDL 或其他等待，局部访问路径很好也不保证总延迟很低。

### 18.2 一次订单金额更新

```sql
START TRANSACTION;
UPDATE orders SET amount=amount+10 WHERE id=100;
COMMIT;
```

引擎沿聚簇索引定位记录，申请必要锁，保存撤销信息，修改缓存页并生成恢复信息。如果 amount 进入覆盖索引，还需要维护该二级索引。Server 收集对应 binlog 事件，提交时协调日志与引擎状态，后台随后刷写脏页。

这个流程是职责顺序，不能理解为每一行图示都恰好对应一个底层函数或一次磁盘操作。页可能已缓存，日志可能由组提交同步，后台刷页也可能与其他事务交错。

同一索引既改善读取又增加写入、日志和缓存占用，正是数据库设计需要比较工作负载的原因。

### 18.3 延迟按工作量与等待拆分

```text
请求延迟 ≈ 应用排队 + 数据库等待
         + 定位 / 扫描 / 回表
         + 连接 / 排序 / 聚合
         + 提交同步 + 结果传输
```

这是排障用的分类模型，不是优化器公式。

| 现象 | 优先收集的证据 | 可能方向 |
|---|---|---|
| 返回很少，扫描很多 | 实际计划、参数分布、扫描统计 | 范围过宽、残余过滤、深分页 |
| 工作量不大，等待明显 | 锁等待关系、MDL、等待事件 | 长事务、热点、DDL |
| 扫描增加且缓存变差 | 页读增量、工作集、I/O | 数据增长、宽记录、批量扫描污染 |
| UPDATE 快但 COMMIT 慢 | 日志同步、磁盘延迟、复制确认 | 同步成本、组提交或半同步等待 |
| 相同 SQL 部分参数特别慢 | 参数分布与估算 / 实际偏差 | 数据倾斜、计划不适配 |
| 数据库完成快但请求慢 | 连接池、网络、返回体、应用耗时 | 数据库之外的排队或传输 |

这些方向是待验证假设。没有等待事件和 I/O 证据时，不能直接把偶发变慢归因于刷脏页。

### 18.4 常用观察语句

以下为观察入口，执行权限和结果可见范围依账号而异。

```sql
SELECT VERSION(), @@transaction_isolation, @@autocommit;
SHOW FULL PROCESSLIST;
SHOW ENGINE INNODB STATUS;

SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;

SELECT object_schema, object_name, index_name,
       lock_type, lock_mode, lock_status, lock_data,
       engine_transaction_id, thread_id
FROM performance_schema.data_locks
WHERE object_schema=:schema_name;

SELECT requesting_engine_transaction_id,
       blocking_engine_transaction_id,
       requesting_engine_lock_id, blocking_engine_lock_id
FROM performance_schema.data_lock_waits;

SELECT object_type, object_schema, object_name,
       lock_type, lock_duration, lock_status, owner_thread_id
FROM performance_schema.metadata_locks
WHERE object_schema=:schema_name;

SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_pages_dirty';
SHOW GLOBAL STATUS LIKE 'Innodb_log_waits';
```

`data_locks` 展示引擎数据锁，`data_lock_waits` 建立请求与阻塞关系，MDL 则需要查看 `metadata_locks`，不能用单一数据锁表覆盖全部等待。[官方 data_locks](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-locks-table.html)、[官方 data_lock_waits](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-lock-waits-table.html)

状态计数通常需比较同一时间窗口内的增量，实例启动以来的累计值不能直接当作当前每秒负载。`lock_data` 可能包含用于表示间隙的后继键，不能仅凭键值就认定该端点记录被排他锁定。

### 18.5 从证据推进到改动

排障首先明确慢发生在连接、执行还是提交，再根据计划和等待证据建立解释。确认索引扫描量过大后才调整访问路径；确认长事务阻碍清理或 DDL 后才处理事务边界；确认刷写跟不上后才评估日志容量与存储吞吐。

改动后既要确认目标指标改善，也要评估副作用，包括写入延迟、索引空间、锁范围、复制积压和结果语义。机制解释只有能预测行为变化时，才形成可用于设计与排障的知识。
